# 03 · 故障排查

按"症状 → 原因 → 对策"组织。**遇到新的失败模式，加到这里，别只在对话里说一遍。**

> 本文提到的脚本都在本项目内：旧的操作/同步/校验脚本在 `ingest\legacy\` 下，
> 入库与计算链在 `ingest\jobs\`（`python -m ingest.jobs.<名>`）。相对路径均相对项目根 `D:\finance\YuanShan`。

## 窗口枚举全是空 / 看起来通达信没开

**症状**：`list_all_windows.py` 返回空列表，或 `Get-Process TdxW` 有进程但 `MainWindowTitle` 是空字符串。

**原因**：**会话隔离**。当前进程在 Session 0（以服务身份、或计划任务勾了"不管用户是否登录都运行"）。
Session 0 是隔离的非交互会话，看不到任何用户桌面的窗口。

**对策**：

```powershell
(Get-Process -Id $PID).SessionId   # 必须和 query session 里 Active 那行一致
```

UI 自动化只能在登录用户的会话里跑。计划任务必须勾 **"只在用户登录时运行"**。
`diag_login.ps1` 就是为比对 SessionId 写的。

## 登录框定位错位

**症状**：账号填到了密码框里、或者两个框都是空的、或者内容变成 `1896996969618969969696`。

**原因**：三种

1. `open_tdx.ps1` 按 **Y 坐标排序**区分账号/密码框（收集 `class=SafeEdit` 的子控件后排序）。窗口尺寸或系统 DPI 缩放变化就会错位
2. `type_creds.ps1` 用**硬编码屏幕坐标** `Click 874 563` / `Click 874 607`，分辨率一变就点空
3. 输入框里**残留上次的内容**，直接输入变成拼接

**对策**：

- 输入前必须 `Ctrl+A` + `Delete` 清空（`type_creds2.ps1` 是这个做法，`type_creds.ps1` 不是）
- 输入后**读回验证**：`edit_read_uia.ps1`（UIA，能读 `ValuePattern`）或 `edit_read.ps1`（Win32 `WM_GETTEXT`）
- 长期解法：改用 UIA 按控件 Name/AutomationId 定位，不靠坐标排序

## 点菜单后通达信直接退出

**原因**：`trigger_download.py` / `trigger_download.ps1` 用 `Alt+S` → `Enter` **盲触系统菜单第一项**，
或发键盘精灵命令 `.933`。菜单顺序变化 / 焦点不在主窗口时会点到别的功能，包括"退出"。

**对策**：

- **不要用盲触**。先 `uia_dump.ps1` dump 控件树，拿到 `TQ策略` / `TQ数据设置` 的真实控件，按控件点
- 点击前先确认前台窗口是主窗口（`win_info.py`），焦点不对就先 `force_focus_tdx.py`
- 万一退出了：回 [01 步 2](01-通达信启动与登录.md#步-2--关闭并重启通达信) 重启重来

## 复选框点了但没勾上

**原因**：复选框是**切换**语义。如果它本来就是勾选态，点一下变成取消勾选。

**对策**：点之前先读状态，只在状态不对时才点。

- UIA：`uia_dump2.ps1` 能读 Toggle 状态
- Win32：对控件发 `BM_GETCHECK`（`0x00F0`），返回 1 = 已勾选

点完再读一次确认。**"点了"和"勾上了"是两件事。**

## 窗口被其他程序弹窗盖住

**症状**：点击落到了别的程序上，或 `SetForegroundWindow` 返回失败。

**原因**：Windows 拒绝非前台进程抢焦点；或者别的程序（微信、更新提示）弹到了最前。

**对策**：

- 用 `force_focus_tdx.py`（`AttachThreadInput` + `BringWindowToTop` + `SetForegroundWindow` 三连），
  比单独 `SetForegroundWindow` 可靠
- **优先用不需要焦点的方式**：对目标控件 hwnd 直接发 `BM_CLICK`（`btn_click.ps1`）或
  `PostMessage WM_KEYDOWN`（`sendkey.ps1`）。这类消息不要求窗口在前台，从根子上绕开抢焦点问题
- 整个流程期间**反复关弹窗**，而不是只在登录后关一次

## 弹窗关不掉

**对策**：`close_tdx_popup.py` 已内置 4 级降级，逐级尝试并验证：

1. `SendMessage WM_CLOSE`
2. `WM_SYSCOMMAND SC_CLOSE`
3. `SetForegroundWindow` + ESC / ENTER
4. `AppActivate` + `Alt+F4`

四级都失败 → 该窗口可能是模态且需要点具体按钮（"确定"/"我知道了"）。
用 `child_enum.ps1` 找出它的按钮，`btn_click.ps1` 点。

**不要盲关所有窗口** —— 会把"盘后数据下载中"这种正在干活的窗口关掉。

## 下载窗口消失了但数据还是旧的

**原因**：下载失败但没有任何报错，或者只完成了一部分。

**对策**：不看窗口，**看数据**。用 [02 步 3 判据 B](02-盘后数据下载与入库.md#判据-b多只票的-day-最后一条日期--目标交易日) 的抽样脚本，
沪深京各 3 只，全部日期到位才算完成。部分 OK 部分 OLD 就重跑下载（通达信增量续传，不会重复下）。

## 「下载到一半没成功」是三种病，不是一种（2026-10-06 定）

这一条之所以单列：三种"没成"该做的事**互相冲突**，混成一种处理就必然出错 ——
把"晚到"当"死了"去重启客户端，正好打断一次本来会成功的下载；
把"要人来"当"普通的坏"去自动重来，就是连着几遍把同一个失败再演一次，
而每一轮开头都会 `reset.kill_all()` 把**你正开着的通达信也杀掉**。

| | 怎么判（全是可观测的，不靠感觉） | 动作 | 上限 | 退化 |
|---|---|---|---|---|
| **A 卡死** | ① 子进程 `STALL_LIMIT=600s` 一句话都不说（分钟线那遍状态栏每几秒就变，5 分钟不出声必是死了）；② 下载窗口消失了而 `.day` 尾部日期没前进 | 守护线程按**进程树**收掉这一步（`proc.kill_tree`，绝不按映像名杀）→ 本轮判失败 → 先 `kill_all` 再从第 1 步整条重来 | `--attempts`（默认 2 轮）**且**总预算 `--budget-sec`（默认 1800s），先到算哪个 | 预算内没能推到目标日，但**前沿还在涨** → 降级成 B（出口码 4），不报"死了" |
| **B 慢，还在推进** | 每轮之后取一次**日线前沿**：抽样文件 max(`last_date`) 变新了，或 `TPyth*` 下载子进程还在（`locator.sync_running()`） | **什么都不动**：不重开对话框、不重启客户端。交回链子按重试节奏等（`DAILY_CLOSE_RETRY_MIN = 0/25/60/100/150` 分钟） | 本脚本不再自己另等 —— 等待是链子的事 | 等到下一档仍然不动、且下载子进程也不在了 → 升级成 A 或 C |
| **C 要人来** | 子进程交回出口码 2：GUI 定位失败 / 登录框弹出来 / 广告吃掉焦点 / 会话不是交互会话、输入桌面不可用。现场包在 `var\stuck\<时间>_<步骤>\`（`screen.png` + `tree_*.txt`） | **不再自动重来**（`run_agent` 与 p0 都判到 2 就立刻停手），直接出声 | 1 次 | 没有退化 —— 这类失败重试修不好，桌面不会自己亮起来 |

判据只认数据：`.day`/`.lc1`/`.lc5` 尾部的日期（`app/tdx_client/readiness.py`），**出口码不算数**。
"通达信说下载完毕"也不算数 —— 实测出现过窗口消失而文件日期还是上一个交易日的情况。

### 收窗的两条死规矩（10-06 18:3x 实测掉数据之后写死）

用户 18:30 的发问是「到这个弹窗，后续没动静了你就结束了吗？」。顺着查下去，**那个截图里的确认框是我们自己点出来的**：

- `close_dialog()` 原来找按钮是 `for label in ('关闭','取消','退出')` + **子串**匹配，
  而「盘后数据下载」窗口上有个按钮就叫 **「取消下载」**（id=1）—— 它回过
  `["点了 '取消' 按钮", '对话框仍在']`，按下去是**放弃这一轮正在下的数据**，
  通达信于是弹「您确定取消下载吗？」。
- 现场形状（18:33 / 18:5x 两次实测）：`盘后数据下载 #32770 562x417`，
  状态栏 id=1224 在 `正在下载5分钟线数据..[20260924-20260930] 9560/9604`，
  按钮 **id=1「取消下载」**、id=2「最小化」（不是"关闭"！）。
  **同一个 ctrl_id 的文字会变**：没在下时 id=1 才叫「开始下载」——
  所以 `dl_dialog.start()` 现在也先读文字，写着「取消下载」就拒绝点。
- 那个决定框 **标题是 `'TdxW'`（零信息）**，正文 Static id=65535 才是内容，
  按钮 id=1「确定」/ id=2「取消」。**任何按标题写的判据/规则都认不出它。**

两条死规矩：

1. **只在"没在下"时关窗**（`download_running()` 两条证据任一成立就算在下：
   id=1 写着「取消下载」，或状态栏有 `正在下载/正在转档` 且还没 `下载完毕`）。
   还在下 → **故意不关窗**，只最小化主窗口，`tdx_close_verify` 不记失败（那是正确的保守）。
   按钮标签改成**精确匹配**，另加硬黑名单 `NEVER_CLICK`（`取消下载/停止下载/终止下载/放弃下载/删除/清空`）**永不点**。
   ⚠️ "日线文件已到位"**不能**当成关窗许可 —— 现场就是日线早到了而分钟线还在下，
   那时关窗掉的是分钟线那一整轮。
2. **决定框要会答，但绝不盲关**：`answer_confirm(allow_cancel=…)` ——
   判完成/判卡死才点「确定」（放弃这一轮已经死了的下载），还在下就点「取消」
   （意思是**不取消、继续等**）。找不到确切那个按钮就**原样留着交人**，
   绝不 WM_CLOSE：模态框按 X 走哪个分支没人知道，而这里两个分支的后果相反。
   看门狗侧两道闸：`config.popup_rule` 的 `cancel_download_confirm`（title `TdxW` → **alert 不 close**）
   + `watchdog._close` 里**看正文**的硬闸（标题不是稳定信息）。
   顺带修掉同族的一处：`modal_ok` 那种 `button_text='确定'` 的规则原来不看类名，
   会命中正文 Static「您确**定**取消下载吗？」并 BM_CLICK 一段静态文字 —— 现在只认按钮类且文字精确相等。

### 卡住 vs 慢：两条同时成立才算死

「没动静就结了」原来的形状是：`s6 wait_done(DOWNLOAD_TIMEOUT)` 到点 → fail → `retry=2`
→ p0 `--attempts 2` → handoff rc 2 → 链 rc3/4 结束，**而下载窗口一直开着、`TPyth*` 一直挂着**，
下一轮 s5 再点就是两层窗口。现在 `wait_done` 多一条判据，**两条同时成立才判卡住**：

| 判据 | 观测 | 只它一条成立时 |
|---|---|---|
| ① 状态栏文字连续 `STATUS_STALL_SEC=300s` 一个字没变 | `dl_dialog.status_text`（id=1224） | 可能只是慢 → 再核 ② |
| ② 抽样覆盖不涨 | `readiness.write_stamp()`：抽样 `.day/.lc1/.lc5` 的 `(名字,字节数,mtime_ns)` 指纹，隔 `COVERAGE_GAP_SEC=20` 取两次对比 | 文件还在写 = 还在推进（三分类 B），重新计时继续等 |

两条都成立 → 返回 `卡住：…` → `s8_finish.reap_stalled()` **主动收窗**（唯一一条 `force=True` 的路）
+ 记一条 `tdx_close_verify` not-ok。用**字节数+mtime**而不是"尾部日期"当推进信号：
分钟线正在下时日期要到那只票写完才变，而大小和 mtime 一直在涨（18:33 实测 12 秒涨 2900 只）——
判"死/慢"要的是秒级信号。

> `TPyth*` 赖着不走由常驻 `tdx-watch` 的 `_reap_stale_sync` 收（三道闸：没链在跑 + 活了超过
> `tdx_watch.sync_reap_after_min` + vipdoc 不再往前写；只收 `TPyth*`，**绝不动 `TdxW.exe`**）。
> 这一层不要再起一份定时杀进程 —— 两个收手抢同一个 pid。

### 为什么 p0 必须自己带预算（`BUDGET_SEC` / `--budget-sec`）

三个上级的超时是 `daily_close_sync` 2100s（最紧）、`e1_fill_all` 的 tdxdl 4200s、`c10` 5400s，
而 p0 三步超时相加是 6600s/轮、两轮 13200s。**不自限的后果不是"失败"，是"没人知道发生了什么"**：
上级到点用 `kill_tree` 把我们收掉，对话框停在哪个状态、vipdoc 有没有写一半、
这一轮算不算数，全都没有任何出口码。现在的形状是：

- 每一步的超时 = `min(该步上限, 剩余预算)`；
- 剩余不足 `MIN_PHASE_SEC=120s` → 不再开新步；不足 `MIN_ROUND_SEC=600s` → 不起新一轮（也就不去 kill_all）；
- 第 2 轮之前至少隔 `ROUND_SPACING_SEC=60s` —— **不许在几十秒内把自己重试完**，
  否则链的下一档（+25 分钟）永远等不到我们；
- 预算小到放不下轮时会**明说**再抬到 600s，不会静悄悄换成默认值（那种"看起来能配"的旋钮是坑）。

要一次跑更久就显式传 `--budget-sec`，前提是调用方也给得更宽。
回归钉在 `tests/test_tdx_autoexec_selfcheck.py`（含"默认预算必须小于最紧上级超时"这条常数锁）。

### 自愈（`heal()`）开不开 —— 一句可决定的话

**开了会怎样**：看护（`app/tdx_client/watchman.py`，只读探测默认开、每 10 分钟一次）发现客户端没在跑时，
会**自己启动通达信并登录**（凭据走 `.env`），把 TQ 那条通道拉回可用；
代价是它会在你桌面的时间上占鼠标、起一个你没要求过的窗口，而且判据是 GUI 的，误判就是白折腾一趟。

**不开会缺什么**：客户端关着的时候 **TQ 直接不可用**（2026-10-06 17:30 实测：客户端关着，
`available()` 探不到 127.0.0.1:17709，c12/c13/c15/c20 这些走 TQ 的一次全空，报的是"取不到"而不是"0 条"），
于是所有 T 类补数只能等下一次盘后下载链把它起来；vipdoc 那一圈（日线主源）**不受影响**，
因为它读的是文件。

> 默认值现在仍然是 `enabled=False`（探测照跑、动手要人点头）。**要改就改库里的
> `config.setting['tdx_watch.enabled']`，不要改代码默认值** —— 改默认值等于替所有
> 以后的会话做这个决定，而这个决定应该由人在知道上面这段话之后做。

### 下载阶梯住在常驻侧，这一层不再做一份（10-06 19:1x 用户原话固化）

用户原话：「大概下载了 10 分钟之后你就应该去检测对应的数据是否全了，全了就关闭进程。
如果不全，就再等 10 分钟，再检测如果数据全了就关闭，如果不全，就关闭重新试一次（我指的是通达信相关的全重启一下）」。
这一条已经装在常驻监控里（`server.py::_download_ladder_round` / `_vipdoc_download_complete` /
`_restart_tdx_for_retry`；三道闸 = 链在跑整段不接管、只收 `TPyth*` 不动 `TdxW.exe`、
`tdx_watch.auto_restart=false` 就不碰键盘）。**`app/tdx_client/**` 这一层不许再写一份定时阶梯** ——
两份会抢同一个 pid、同一个客户端。三者这么切，别混：

| 谁 | 判据 | 动作 |
|---|---|---|
| 常驻阶梯（总协调） | **只看 vipdoc**：日期（日线/指数/1分/5分）+ **整目录条数 ≥ 前一天登记的条数 − 偏离值**（`duanxian/completeness.py`，2026-10-06 换掉了原先的"放大抽样 ≥90%"；2026-10-07 又把百分比容差换成**条数偏离值**，默认 30、分钟类 200，系统配置里改得动），不看窗口文字/mtime/退出码 | 收 `TPyth*` 进程；两档不全就全重启客户端 |
| 这一层的等待（`dl_dialog.wait_done`） | 状态栏 300s 没变 **且** 抽样文件 `(名字,字节数,mtime_ns)` 不动 | 判 `卡住` → 关**窗口**（不杀进程）+ 记 `tdx_close_verify` |
| 这一层的收尾（`s8_finish`） | 状态栏「下载完毕」或没有任何在下的证据 | 关对话框 + 最小化；**还在下就故意不关** |

### 客户端关着的那天 TQ 是零 —— 三档分开，一句可决定的话（19:23 新增）

19:23 实测 `TdxW.exe` 不在跑，而 `tq_bridge.available()` 的判据就是它在不在：
**客户端没开 = TQ 直接不可用**，收盘链的 ③b（TQ 直取）拿不到任何数，只能等 vipdoc 或走网络兜底。
阶梯里的"全重启"只在**看到 `TPyth*` 在跑**时才触发，客户端根本没开的情境它不主动拉。

- **A 阶梯（在跑，`auto_restart` 默认开）**：管"看到在下载但两档都不全" → 全重启客户端。
- **B `heal()`（默认关，`tdx_watch.enabled=False`）**：管"根本没开" → 探测到没在跑就自己启动并登录。
- **C 什么都不开（现状）**：客户端关着的那天 TQ 那一圈就是空。

> **一句话决定**：开 B 会在**你没要求的时刻**自己把通达信启动、抢前台、发真实键鼠登录（凭据走 `.env`），
> 换来的是"客户端关着的日子 TQ 也有数、`c12/c13/c15/c20` 不再整批空"；
> 不开 B 缺的**只有那一圈**（估值/画像/逐票交叉核对那天是 NULL 而不是值），
> 日线主源读文件、不受影响。**开了不会让日线更准，不开也不会让日线变坏 —— 它只决定 TQ 那一圈。**

## 一条通用原则

**每一步都要有"怎么验证已完成"的判据，而且判据要看结果而不是看过程。**

- 看窗口消失 → 不可靠（可能失败退出）
- 看进程结束 → 不可靠（可能异常退出）
- **看数据里的日期变成目标交易日 → 可靠**

固定 `sleep` 从来不是判据。

## 10-07 · 自选同步现在有两种"没删"的读法

问"库里为什么还有同花顺已经删掉的票"，先分清是哪一种，两种处置完全不同：

| 现象 | 因 | 怎么确认 |
|---|---|---|
| 组/成员在库里、同花顺 ini 里没有，且**一直删不掉** | `watchlist.sync_mode=append`（增量添加：只加不删） | `python -X utf8 scripts/jobs.py status` 看 `watchlist` 那一行的 `sync_mode`；同步报告里 `applied.groups_kept_absent` / `members_kept_absent` 会给"这一轮留下没删的条数" |
| 组/成员在库里、ini 里没有，但**下一次 20:40 就没了** | 默认档 `full`（以同花顺为准）本来就是全量镜像 | 同上；`applied.groups_dropped` 是删掉的条数 |

默认值只住 `duanxian/jobs.py::WATCHLIST_DEFAULTS`（现在是 `full`），改它有三条路：
`/system` 的「常驻循环与定时任务」卡（`watchlist` 那一行的「同步模式」下拉）、
`POST /api/jobs/loops`、`python -X utf8 scripts/jobs.py set watchlist sync_mode=append`。
三条写的是同一份 `jobs/config.json`，下一个心跳生效、不用重启。

⚠️ 全量档有一个必须说出来的连带后果：**自选 ⊃ 重点关注（持仓）不是系统保证**。
持仓是从交易日志的未平仓成交聚合出来的，而同花的 ini 里没有的票，20:40 同步后就从自选中消失。
系统不改那份 ini、也不在库里造"本机补充"（用户 10-07 选的就是"严格全量，只点名不兜底"），
只在持仓页点名"这几只有持仓但不在自选清单里"，要它们常驻得在同花顺客户端里加一次。
