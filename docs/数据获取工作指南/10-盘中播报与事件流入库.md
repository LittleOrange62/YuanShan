## 二、口径边界（搬迁时改了三处，其余一字未动）

1. **缺数不再拿默认值顶**：外部 `normalize()` 是 `lbc or 1`、`zbc or 0`、`(_num(p) or 0)/1000`。
   后果：连板数缺格会把一只 3 板票在第一针记成**首板**且事后无从发现；
   开板次数缺格填 0 与真实读数"从头封到尾＝0"同值；价格缺格算出 0.0 元。
   现在一律 `NULL` + `missing` 点名，`digest()` 的首板数/最高板**排除 None 并点名"板数缺数 N 只"**。
   已导入的历史行**原样保留**（不事后猜哪几行是填的），只在播报行的 `source_detail` 标 `legacy_default_filled`。
2. ~~板块涨幅单位：库里是小数要 ×100~~ —— **这条是我 10-26 的误判，已撤销，且撤销本身留字为证**。
   我先看到 `TDX_880347 = -0.0619` 就断定"库里存小数、外部按百分数渲染会错 100 倍"，加了 ×100；
   同一晚渲染出「专精特新 −232.3%」才发现不对，复测同场分布：`avg(abs)=1.79`、`max=9.30`，
   与 `market_data.stock_daily.pct_change`（−29..+20）同量纲 ⇒ **`sector_daily.pct_change` 本来就是百分数**，
   那句 −0.0619 只是一个 −0.0619% 的小幅波动，外部原来的渲染是对的。
   教训写进 `sources.sector_pcts` 的 docstring：**别拿单行样本定单位**，定量纲要看同场分布。
   （同场确有近 10 行 `|pct_change|>12`、min −99.5，那是数据本身的异常值，另案登记，不靠截断掩盖。）
3. **`or None` 不许吞掉真实的 0**：外部 `market_stats()` 把涨/跌家数写成 `x or None`，
   全场只数 0 会被当成缺数。0 是读数，null 才是判不了。

其它换算（现查 10-26）：池行 `p`＝元×1000、`zdp` 已是百分数、`fbt` 是 hhmmss 整数、
`fund`＝元；**跌停池没有 `fbt` 字段**，`sort` 必须 `fund:asc`（见下一条）。

⚠️ **顺手修掉的一个活缺陷（不在迁移清单里，是搬的时候撞出来的）**：
`duanxian/live_emotion.py` 原来对三个池一律传 `fbt:asc`，而跌停池按 `fbt` 排会**整池静默返回空**
（不是报错，是 `[]`）→ 首页跌停家数念成 0。10-26 盘中现查：`fbt:asc` → **0 行**，`fund:asc` → **14 行**。
现在排序键收在 `live_emotion.POOL_SORT` 一处，`tests/test_full_audit_fixes.py::test_live_pool_uses_per_endpoint_sort` 钉住。
外部 README 10-23(一) 那次"47 家跌停读了个 0"是同一个坑。

## 三、执行形态：单次短跑，不做常驻线程

外部 10-23(二) 事故登记：watcher 常驻 loop 在 09:29 建完基线后**静默死亡**
（无 traceback、无日志、任务计划程序还显示"运行中"），盘中 8 轮全瞎。
修法是弃常驻，改**每日触发器 + 每 5 分钟重复的单次 `--once`**——调度器本身就是看门狗。

所以迁进来的时候**不把这四条做成 uvicorn 里的常驻循环**（那是把人家踩过的坑再踩一遍）。
每个入口都是一次性短进程：

```
python -m ingest.jobs.zt_watch --once                  # 取一针、判事件、落库（默认不发送）
python -m ingest.jobs.zt_watch --once --dry-run        # 不写库不发送
python -m ingest.jobs.zt_watch --once --send           # 落库 + 按系统配置的渠道发
python -m ingest.jobs.zt_import_history                # 外部历史 jsonl → 库（幂等，重跑 0 新增）
```

**默认不发送**：发到群里是别人看得见的动作，不该被一次调试顺带做掉；渠道与开关在系统配置里配
（走 `duanxian/notify.py:send_to`，送达判据是**渠道业务码**，不是 HTTP 200——10-16 实测无效 token 也回 200）。

与总协调那条**下载阶梯**的分工（`server.py::_download_ladder_round`，只看 vipdoc 完不完整）：
它收 `TPyth*` 进程，这一层只管播报与落库，**两边都不许再写第二份收进程的代码**。

## 四、验收复现（下一个人照这个跑一遍）

```
# 判据（纯函数，不连库不联网）
PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -m pytest -q tests/test_intraday_pool_events.py
# 真跑一针并回读库里（不是"我写了"，是"库里有"）
PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -m ingest.jobs.zt_watch --once
PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -c "from app.intraday.store import state_summary;\
import datetime as dt;print(state_summary(dt.date.today()))"
# 建表与授权（DDL 54/55 可重复执行；权限按项目惯例四权齐全给 ft_etl/ft_app）
```

⚠️ 建表时只授 `insert, update, delete` 会留个骗人的坑：**纯 INSERT 过得去，
带 WHERE 的 UPDATE/DELETE 和 `ON CONFLICT DO UPDATE` 全报 `permission denied for table`**
（谓词与冲突键要读行）。所以 DDL 末尾一律
`grant select, insert, update, delete on <t> to ft_etl, ft_app;`。
