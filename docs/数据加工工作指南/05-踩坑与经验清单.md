# 05 · 踩坑与经验清单

这一路实证出来的结论，避免重复踩。

## 同步 / GUI

1. **判据只认数据日期，不认状态栏**。通达信状态栏"下载完毕"不代表文件真更新了——每步之后都回去读 vipdoc 尾部日期复核（`readiness` 锚定代码判据）。
2. **prepare 阶段 s3/s4 常触发 600s 卡死判定被杀——无害**。它们在静默轮询，链路照常进 day 阶段，别手动干预。
3. **s5 打开下载对话框，第 1 轮常失败**：主窗口没真正最大化 → 菜单坐标点空。**等第 2 轮 `kill_all` 重启通达信后基本能过**（两次实测如此）。
4. **下载期间别抢前台焦点**（Qoder 会话窗口会挡住坐标点击）。GUI 自动化靠屏幕坐标，最大化是前提。
5. **切分钟线 tab 只能点标签**，用 `TCM_SETCURSEL` 会把通达信搞崩。
6. **`.933` 命令即使返回 `ErrorId=0` 也可能不真弹界面**——所以它只是 s5 的 B 级备选，主用 D 级菜单坐标。

## TQ 接口

7. **必须客户端已启动+登录**；**单连接**（固定脚本名，别并发跑两个 `run_snippet`）。
8. **除权 `get_divid_factors` 是"每10股"口径，库里是"每股"**——实证映射：
   `cash_per_share = Bonus/10`、``bonus_ratio = ShareBonus/10`、`rights_ratio = Allotment/10`、`rights_price = AllotPrice`。
   对齐验证：600519 2021-06-25 TQ Bonus=192.93 ÷10 = 东财 19.293 ✓。**别直接塞原值，会放大 10 倍**。
9. **东财 dividend 只回溯到 2021，TQ 有 1990 起的完整历史**——TQ 补历史的价值点。
10. `get_relation` 里风格类板块 `BlockCode` 可能是 `"0"`（无指数代码），入库/匹配时要容错。
11. `get_more_info` 只给**当前快照**（HqDate=当日），不是历史序列——stock_profile 是快照表。

## 文件解析

12. **分钟线 `date_idx` 年份基准是 2004 不是 1900**（按 1900 解会把 2026 写成 1922）。
13. `tdxzsbase.cfg`/`tdxzsbase2.cfg` 名字像板块配置，其实是**逐代码行情快照**（9/26 列），别当板块表读。板块定义只有 `tdxzs.cfg`/`tdxzs3.cfg`（6 列）。
14. 板块类型码（col3）→ 分类，按码段+真实名反推：`2=行业(880) 3=地区 4=概念 5=风格 12=行业(881新一级)`。

## 数据库

15. **全库已改名 `md/ref/fct/ops → market_data/reference_data/analytics/operations`**。standalone 用 `ref.` 会 `UndefinedTable`；SQL 一律用全称。
16. `security/dividend/sector_member/stock_snapshot` 的标的列是 **`security_code`** 不是 `ts_code`。
17. **b6 对账的"板块日线行数与基线不符"是误报，已修**：`check_rowcount` 里 `sector_daily_matched` 从 `new==old` 改成 `new>=old`（old 是迁移快照、只增不减，相等判据迁移后必假）。现在每日同步后 `--check-only` 正常返回 0。
18. 含中文 SQL 必须 UTF-8 文件 + `PGCLIENTENCODING=UTF8 -f` 执行；含中文的 `.ps1` 会被 PowerShell 5.1 按 GBK 误读破坏引号，**脚本正文用纯英文**。
19. **全库改名进程会漏改脚本里 SQL 字符串的列名**：`08` 迁移和 c17~c19 被自动规范成 `security_code`/`source_batch_id`，但 c20 的 UPSERT 字符串没改到，跑时 `column "ts_code" does not exist`。新表/新脚本落地后要**拿真列名核对脚本里的 SQL 字面量**（c20 已于 09-24 修）。

20. **SQL 里数"连续几天"，必须先把不满足的行筛掉、再开窗**（10-15 两条新判据同时踩到）。想当然的写法是"掉线那一天让组号 +1，然后在同一列上 `row_number() over (partition by 代码, 组号)`" —— 但**掉线那一行自己也被算进了下一组**（它的累计计数与紧随其后的那一段相同），于是段内位置整体 **偏 1**：连着天数多一天、第几板多一板。症状很阴：2026-10-15 上证跌 1.586%，涨停 36 只里"首板行数 = 0"（全被数成 2 板），于是新加的节点 1 一只都不命中 —— 看着像判据写错，其实是分组写错。正确写法：段键用 `行号 − 满足条件的累计数`，并且 `where` 先只留满足条件的行，再在那个 CTE 里开窗。钉在 `tests/test_board_node_trend.py`（合成序列 T,F,T,T,F,T ⇒ 连着天数必须是 1,1,2,1）。
21. **往 `coverage.TARGETS` 里加表，第 4 个字段是拼成 `where true {它}` 的，必须写成 `and …`**（10-15 踩到）。写成 `spec_version = 'trend-1'` 会拼出 `where true spec_version = …`，语法错被 `_probe` 的 except 吞成 `status: "error"` + 那句写死的"多为 statement_timeout 60s 撞车"—— **归因是错的**，看的人会去查超时，而实际是没写 `and`。加完必须单发一次 `coverage.report(table='新键')` 看它回 `ok`（本次两张新表：`trend_stock_daily` 1,257,321 行／243 场、`board_node_daily` 18,508 行／243 场，`missing_sessions` 都是 0）。

22. **集合查询里「取最近 N 场」的写法：`limit` 前面必须有 `order by … desc`**（10-27 首板分析那四列第一版踩到）。
   `select distinct trade_date from t where trade_date <= :d limit 20` 是**没有顺序保证**的：Postgres 走索引顺序，
   给的是**最早**那 20 场。实测窗口取成了 2021-08-02~08-27，而界面那一列的名字写着「近 20 场」。
   症状最阴的地方：**老票看不出来**（老票两种窗口都正好 20 根，数只是"另一段日子的对数"，看着完全正常），
   10-26 那批 44 只里只有 7 只 2022 年后上市的票整格 `—` 才露馅。
   三条一起做的修法：① 补 `order by trade_date desc limit 20`；② **随行交「这个窗口里最近的一根在哪天」**
   （`dbl_last_day`），它不等于本场日期就是取错了年代；③ 配一条**不打桩的独立重算**用例
   （`tests/test_first_board_daily_view.py::_对账近20场倍量`：自己现取最近 20 场再数一遍，逐字段比）。
   同一族的 `days` CTE 在 `board_span._sealed_series`、象限那发与本次修后的倍量那发里都显式排序了 ——
   **改动任何一发时三处一起看**（《04-schema与命名》里那条"先筛后开窗"是同族问题：窗口的边界永远要自己写清楚）。

## 工程原则

20. **私有二进制一律走 TQ，不逆向**——通达信插件自己也是走 TQ 取板块成分/复权/档案的；硬啃 `.dat`/`gbbq` 无文档易错。符合项目"宁可不猜"原则（c7 docstring 里就写着"猜错的行业名比六位数字更害人"）。
21. **龙虎榜、资金流本地真没有**——别找文件了，走网络源。现役三条：`c6` 龙虎榜、**`c21` 新浪个股资金流榜（主源，加工链第 23 步 `fundflow_rank`，库 89,020 行到 10-16）**、`c22` 同花顺行业榜（第 24 步 `sectorflow`，630 行）；`c11` 东财 push2 只剩大盘那一路（`market_fund_flow` 135 行），而 akshare 那两路东财接口实测已 down。⚠️ 新浪/同花顺**只给当天** ⇒ 采集停一天就永久缺一天（这是数据现实，不是待修 bug）。
22. 入库脚本一律**幂等**（`ON CONFLICT DO NOTHING` 只补，或 `DO UPDATE` 刷新）+ **只补不覆盖**人工/已有数据 + **报出被口径筛掉的行数**（不静默丢）。
23. 复用而非新造：调度/队列/下载重试项目里都有（`p0_tdx_predownload --attempts`、`e1_fill_all`、`tq_bridge`），别再写第三套。
24. **"一天应该有 N 只"的表，`max(date)` 单独不能证明它有数** —— 覆盖体检要再比"最近一场的数量 vs 上一场"。
    实测教训（2026-09-26）：分钟线 09-23 只进了北交所 **351 只 / 83,523 行**（全市场应 9,527 只 / 约 227 万行），
    而日期区间一天不缺、行数也不算空 → 体检报"已到 09-23"，页面读起来就是覆盖全了。
    **半截数据冒充全量比缺数更坏**：缺数会让人去查，半截数据会被直接拿去算。
    已落进 `duanxian/coverage.py`：`ENTITY_DAY_TABLES`（分钟线数 `count(distinct security_code)`，
    日线/快照/指数/板块数当日行数）。**2026-10-06 判据换血**：原先是"最近一场 ≥ 上一场的 60%"
    （`ENTITY_MIN_RATIO=0.6`，一个写死的比例），用户把它否了 —— 新股只会让条数往上走，
    所以要的是**动态条数规则：本场条数 ≥ 前第 2 个交易日的条数**。
    **2026-10-07 再改一次（同一条规则，两处收紧）**：用户原话"我之前说的方法没考虑退市、停牌的，
    所以那个计算方法可能是不行的。你就按照前一天的数量 偏离值在 30 以内就算全了
    （这个偏离值可以在系统配置中手动设置和修改）"。于是
    ① 基线由"前第 2 个"改回 **T-1（池子里最新一场）**，隔了几场照实交出 `sessions_back`；
    ② 百分比容差换成**条数偏离值**：默认 30 条，**分钟类单开一档 200** ——
      10-07 逐日实测：`.day` 相邻两场最大回退 −11 条，`.lc1/.lc5` 最大 −107 条，
      PG 分钟线只数最大 −143 条（停牌那天就是没有那些文件）。把分钟类也压成 30，
      正常日子会天天判不全、收盘链天天去重启通达信重下；
    ③ 两个数**默认值只住 `duanxian/jobs.py::COMPLETENESS_DEFAULTS`**，判据（`deviation_for`）、
      页面（`/api/jobs/completeness`）、CLI（`scripts/jobs.py set completeness deviation=…`）
      都读这一份；取 0 合法（= 少一条都算不全），上限 100000 只防数量级手滑 ——
      **偏离值一旦不小于基线，这道门等于没有**，`judge()` 会在结论里当场说破，不靠上限兜。
    实现只在 `duanxian/completeness.py` 一处（每判一次把条数登记进
    `<ASTOCK_DATA_HOME>\completeness\session_counts.json`，只登记判为全的那些场，
    半截那天绝不进基线池；没有历史时按各口径的绝对下线判）。不达标照旧打
    `entity_partial` 与 `coverage_note`，并点亮页面原有的 `thin_coverage` ⚠，
    覆盖页现在还直接显示「本场 / 基线（哪天，隔几场）/ 偏离值（含出处：默认还是系统配置里填的）」。
    代价实测：日线/快照单日 `count(*)` 0.03~0.16 秒，分钟线单日 distinct 0.65~3.7 秒；
    换规则后每张表少一条"上一场是哪天"的查询。全表体检 58→60 秒（10 分钟缓存兜着）。
25. **冒烟测试限了范围，跑完就要收尾** —— `c16_minute --market bj --period 1` 一次**成功**的实跑
    （batch 311：`status=ok`、5 秒、83,523 行）就能造出"09-23 只有北交所"的半截状态。
    要么随后补全，要么别让它进正式表：`--dry-run` 才是安全的验证姿势。
26. **「板块名没显示出来」要先问那是不是板块**（2026-10-06，用户问「份额抬升端为什么全是六位代码」）。
    两层答案，少一层都会改错：
    ① **名字有权威来源**：`T0002\hq_cache\shs.tnf`（通达信证券名称表，GBK 定长记录：代码列在记录首、
       名字列固定第 31 字节起，那一段 1,120 条 88xxxx 记录相邻偏移差**恒为 360**）。
       `tdxzs*.cfg` 四份里这批码**一条都没有**（实测 grep 零命中），所以 c7 原来只能补到 80 个。
       交叉验证：两份都有的 1,072 个码里 604 个完全一致，剩下 468 个是 cfg 那一列写的就是 '1'，
       没有一条真矛盾 —— 结构判据（间距恒定 + 代码列后全 0 + GBK 可解）任何一条不过就整段放弃。
    ② **这 48 个根本不是板块**：880001 总市值 / 880002 流通市值 / 880005 涨跌家数 /
       880011~880019 主板… / 880031~880039 创业… / 880041~880049 科创… / 880071~880079 北证… /
       880096 ETF等权 / 880097 REITs / 880098 可转债 / 880099 通用回购。
       它们在 `sector_info` 里挂的是 `sector_type='行业'`，而实测 `sector_daily` 的 `amount_yuan`
       **逐日等于全 A 成交额**（09-30：全 A 段 14,501 亿、主板 8,552、创业 3,690、科创 2,136、北证 123）——
       份额口径下必然霸榜。所以"补名字"只是让它从 `880001` 变成"总市值"，榜还是错的。
    **做法**：c7 回填名字 + 按**名字**（不是代码段）把它们改判成 `sector_type='统计'`；
    凡按 `('行业','概念')` 正列表取母体的读取方自动排除（份额轮动的读层另加了同口径过滤，
    因为库里历史行还在）。判据用正向列表的意义：**下一个混进来的市场级指数也进不了榜**，
    而不是只修这一次看见的 48 个。
    ⚠️ 只补名字不改类型会**反向制造 bug**：`allocator` 那层的旧过滤条件是 `name <> 代码`，
    名字一填上，"总市值"就会以板块身份进入分配者榜。
27. **重启 8910 别从 Git Bash 传 `powershell -Command "…$env:X…"`**（2026-10-06 踩）：双引号里的
    `$env:ASTOCK_LAUNCH_ID` 会被 **bash 先展开成空串**，PowerShell 根本收不到那条赋值 —— 于是
    uvicorn 起来了但 `/api/astock/health` 回 `launch_id:""`，"这次是谁起的"接不上。
    正确姿势是落成 `scripts/restart_8910.ps1` 用 `-File` 跑（文件里没有这层展开），
    起完判活仍按老规矩：先看 `Get-NetTCPConnection -LocalPort 8910 -State Listen`，再看 `launch_id` +
    `ready:true`，最后看 `/api/jobs` 的 `scheduler.host_loops` 有没有装配齐。

28. **`sys.path` 把 `vr/` 插到 0，会让 `import app` 拿到 `vr/app.py` 而不是仓库根的 `app/` 包**（2026-10-26 踩）：
    单跑 `tests/test_first_board_sentiment.py` 出 6 条红，报的是
    `ModuleNotFoundError: No module named 'app.compute'; 'app' is not a package`，
    链上追到 `duanxian/quant.py:38` —— 那条 import 是 10-14 就有的，**与断言无关**。
    成因：这些测试文件头部写的是 `sys.path.insert(0, vr)`，而 `python -m pytest` 已经把仓库根放在 index 0，
    再插一次就把根顶到第 1 位；`vr` 在前 ⇒ `app` 认成 `vr/app.py`（一个模块，不是包）。
    全量跑时看不出来，因为别的测试先把真 `app` 包导进了 `sys.modules`（**顺序依赖**）。
    **做法**：要 `vr` 里的模块（`market`/`firstboard`/`gstock`）就 `sys.path.append(vr)`，别插 0。
    已按这条改掉的五个文件：`test_first_board_sentiment.py`、`test_board_span.py`、`test_seal_strength.py`、
    `test_session_date_honesty.py`、`test_ttlcache.py`。判据：**单跑该文件必须绿**，
    全量绿不代表这条路径没问题（`tests/test_jobsboard.py:425`、`tests/test_notify_config.py:260` 早就写过同一句警告）。
29. **批量取数的那句 SQL 要按"要的那几天"限制，别对整表去重**（2026-10-26 首页提速实测）：
    `duanxian/pg_sources.py::sentiment_on_dates` 里的
    `mood as (select distinct trade_date, value from analytics.score where capability_key='market_mood')`
    不带日期条件 —— 而 `market_mood` 在 `score` 里是**每场每票一行**（全史 distinct 出来才 272 行，
    扫的是百万行级）。下游 `left join` 只按传入的那几天取，等于**全扫一遍再丢掉**：
    首页那一块单这一句 4.46 秒（占整个 `/api/market/emotion` 冷发 9.78 秒的一半）。
    加 `and trade_date in (select td from d)` 后 0.27 秒，交出的行**逐字段一致**（对账写在
    `tests/test_first_board_sentiment.py::test_那一句mood只扫要的那几天而不是全史`，
    那里是"一天一天单独查"的独立算法比对，不是拿自己比自己）。
    这类写法**去掉条件不会报错、结果也照旧**，只会每天慢四秒 —— 所以判据要配一条测 SQL 文本的。

28. **"按实体全历史算"的判据必须先物化，别在分区表上写相关子查询**（2026-10-07 实测，两遍都踩了）。
    `app/compute/limit_prices.py` 里"这一天是不是这只票的头 5 场"（`no_limit_first5` 那一层）
    第一版写成 `row_number() over (partition by security_code …)` 嵌在 640 万行的单条 UPDATE 里 ——
    **40 分钟不提交、外部完全看不见进度**（`wait_event` 为空 = 吃 CPU 不是卡锁，只能靠
    `pg_current_wal_lsn()` 两次采样确认它在写）。第二版以为"单日不用窗口就行了"，
    改成两条相关子查询（往前数 5 场、取最早一场），结果**单日 4.6 秒、一个月 566 秒**：
    `market_data.stock_daily` 按 `trade_date` RANGE 分了 22 个分区，而子查询里的比较值是
    **外层那一行**，规划器拿它做不了分区裁剪 ⇒ 每行展开成 22 次索引探测。
    → 正解是把这件事物化成 `reference_data.security_session_span`（一码一行，
    `first_session` / `fifth_session`，`app/db/sql/27_security_session_span.sql`），
    判据只留**一份** SQL（范围只体现在 WHERE 上）。实测：整表重算 27.4 秒、单日预览 1.0 秒、
    整年 79.5 秒，`--since/--until --months` 切片后一片一提交一行进度。

44. **"一次单击 461 毫秒"不是渲染慢，是整表重新协调一遍**（2026-10-26 实测，交叉高亮那一块共用实现）。
    选中态原先是一份 `useState`，而每一格的 className 都跟着它变 ⇒ 点一下，React 要把那张 800 格的表
    每个元素重新协调一遍。三条都是现量出来的，不是猜的：
    ① `cn()` 里那层 tailwind-merge 单发 1.6 微秒、React 把第一格改动提交出去 6~10 毫秒 ⇒ 钱不在拼字符串也不在提交；
    ② **行级 `React.memo` 治不了这一族**：列高亮会动到"每一行的那一格"，所以每一行的 props 都变了，memo 每次都判"变了"；
    ③ 改法是把选中态从 React 里拿出去（className 交静态串，点击时在 DOM 上标行／列／交叉那一格三个类，
      颜色只在样式表一份），同一张表上的单击实测 1.1~4.3 毫秒（最大一张 13,380 格）、`PerformanceObserver('longtask')`
      只圈那一下 ⇒ **记不到长任务**。
    两个跟着来的坑，都比改本身容易漏：
    ① 参数从 `(行号, 列键)` 改成 `(被点那一格, 行号, 列键)` —— 一屏多张表（倍量页三张、首页四张）时
      行号与列键在两张表里都对得上号，只有那一格知道自己属于哪张 `<table>`；靠行列号拼选择器就是第二处实现。
    ② 有**两屏要在渲染里读"选中哪一只"**（点完顺手展开量化档案、发一发按代码取数的请求）。
      这类订阅必须圈在依赖它的那一小块子组件里；提到页面组件本体，那张大表就又回到每次点击重渲染 ——
      改动等于白做。所以这两屏各多了一个子组件，并由测试**反向**钉住"订阅不许出现在页面那半截文件里"。
    → 判"这一族值不值得改 React 之外的路"，先量出那个数（长任务毫秒数、格子数、提交耗时），
      别拿"感觉卡"当依据；上面三条里任何一条单独看都能得出相反的结论。

45. **两把尺不换版本号就会互相冒充；换了版本号才发现"缺口"和"涨幅"是两个数**（2026-10-27 异动提醒 `abn-1`→`abn-2`）。
    用户拿行情软件那张「明日涨幅至涨停，能触发严重异动」对账，点名几只"我们没报"。三步定性：
    ① 先排掉"没减大盘"这个猜测 —— 偏离值一直是个股减**对应分类指数**，那几只票的数早就减了；
    ② 真差在累计那把尺：`abn-1` 是**逐日相加**（交易所那句公开算法），行情软件用的是**区间涨幅**。
       本机可复算的两个反例：688137.SH @09-30 相加 78.7 / 复利 108.5，300313.SZ @08-25 78.3 / 101.8 ——
       两把尺在连板段差 20~30 个点，**旧那把是漏报**（把已触发的判成没到线），比多报更坏；
    ③ 换尺 ⇒ 必须升 `spec_version` 并重算全史，旧行留着对账（同一张表两批并存，读侧与 `coverage.py`
       一律带版本条件；`coverage.py` 里那句 `where` 原先写死 `'abn-1'`，已改成读写入侧的常量）。
    换完之后冒出三条只有实测才会撞上的：
    ① **前瞻的"缺口"不再等于"明日要涨多少"**。复利下每涨 1 个点会把已经涨过的那段放大 `(100+S)/100` 倍，
       所以 `trigger_pct = 缺口 × 100/(100+S)`，S 只能从对数和回来（`dev` 是个股减指数，拆不回个股那半边）
       ⇒ 新增 `window_gains()` 一个出口，`forward()` 里三档各乘各的系数。
       漏掉这一步，屏幕上「距 100 还差 1 点」与「明日要涨 1 个点」就自相矛盾（真值是 0.5 个点）。
    ② **缺读数那天在复利里比在加法里危险得多**：加法少一天只是偏小，复利把那天当 0% 会把整段乘歪。
       `sum()` 静默跳过 NULL ⇒ 一律交 `NaN` 毒化整档，出口 `_f()` 折成 None（界面念"判不了"），
       且下游每次比较先 `x = x` 挡 NaN（float8 里 NaN 比一切数都大，直接 `>=` 会假阳性）。
    ③ **`SET` 不收绑定参数**（`set local work_mem = $1` 直接语法错），而这一发全场窗口 SQL 在 7 层
       `WindowAgg` 下默认 `work_mem` 会 spill 到盘：一场从 17 秒变 70 秒、顶穿 reader 的 60 秒超时。
       `set local work_mem='256MB'` 之后 37.9 秒 —— 常量拼进 SQL 可以（它只能改代码），
       用户输入一个字都不许进这条路。
    ④ 顺手的一条：`hit_if_limit_up` 的"三档全判得动"判据原先拿"进了候选名单的档"当分母 ——
       次数档"算得出来但明日凑不满第 N 次"于是被数成"判不动"，整只票错报成判不了。
       **判得动 ≠ 进了候选**，两件事要各存一份（`judged` 与 `need_for`）。
    → 对不上的那两只（688071／688836）如实留着：把 8/9/10/11/12/13/14 场窗口 × 相加/复利 × 减不减指数
      全算了一遍，没有任何一种组合给出截图上那五个数（我们最大只能到 89.8，他们要的是 91.7/88.5/84.5/76.0/68.6）。
      差异不在"要不要叠加大盘"，在他们那一边窗口起点/归零口径与本机不同（最可能是"指标自公告日重新计算"，
      本机没有公告日这份数据）。**拿不到一份能看逐日明细的样本之前不改判据、不猜公式** ——
      这一条写进《异动提醒.md》四之二，不当已解决。
