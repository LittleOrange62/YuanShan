# 06 · 数据清洗与加工任务总览

> 本项目"采集→清洗→加工→质检"任务的一张全景图（这套流程的经验源自旧项目 FinanceTool，
> 说明书在本目录 `../参考/FinanceTool/`）。
> 事实来源：`config.job` 注册表 + `app/orchestrator/runner.py` 的 `RUNNERS` + `config.quality_rule` + `ingest/jobs/` 实目录。
> 更新：2026-09-25。

## 分层

```
盘后下载(P0) → 采集入库(c1~c20) → 质量审计(e2, 24 规则) → 因子/评分计算(d1~d7) → 报表/摘要
                     ↑ 清洗在入库时靠 CHECK 约束 + 单位触发器 + 口径筛除完成
一次性迁移(b1~b7)：从旧系统 D:\finance / D:\financeWeb 把历史搬进 financetool 库
```

- 权威作业目录：本项目 `ingest\jobs\`（下表所有 `c*/d*/p0/e1/e2/b6` 都是这里的模块，跑法 `python -m ingest.jobs.c1_day`）。
  通达信 GUI 拟人操作在 `app\tdx_client\`，二进制解析在 `app\ingest\tdx_binary.py`，编排/执行器在 `app\orchestrator\`。
- 触发方式：`/jobs` 页面点"立即触发"，或命令行跑脚本；cron 列出的作业**当前不自动跑**（调度器总开关默认关，见 01）。
  ✅（历史坑，已修）页面按钮曾经一按就失败：`RUNNERS` 那时把作业写成 `scripts/{ingest,ops,compute}/*.py` 路径
  ——这类路径在本项目里根本不存在（现役模块在 `ingest\jobs\`），于是 `/jobs` 上每个「立即触发」都是 FileNotFoundError；命令行 `-m` 跑法不受影响。**10-18 现状**：`RUNNERS` 每行是 `{'module': 'ingest.jobs.c1_day', …}` 这种模块名（`app/orchestrator/runner.py:76` 起，`:60-61` 还留着这段教训的注释）。

## 二、清洗与质量层（这是"数据清洗"的核心）

清洗**主要发生在入库那一刻**，不靠事后脚本：

1. **CHECK 约束**（`04_constraints.sql`）：`ohlc_order`（low≤open,close≤high）、`code_format`、`period IN (1,5)`、`price_positive` 等，坏行根本进不来。
2. **单位一致性触发器** `md.trg_daily_sanity`：`amount_yuan/vol_shares` 必须落在 `[low*0.5, high*2]`，专抓"股/手 ×100""元/千元 ×1000"这类单位错。c1 入库前先按同判据筛掉越界行并**报出条数**（不静默丢）。
3. **质量审计 e2_quality_audit.py**（作业 `quality_audit`，on_ready）：跑 `config.quality_rule` 的规则，逐交易日审计（**10-18 现查 30 条 = 23 error + 7 warning，全部 enabled**；本文其他处出现的「24 条」都是 09-25 的快照）。
   - **error 级 17 条**：ohlc_order、price_positive、vol_amount_consistent、amount_sane、amount_magnitude_drift、no_gap（缺口）、date_is_trading_day、daily_row_count、null_rate、code_format、not_sector_code、index_present、pre_close_chain（除权链）、board_coverage、sector_key_aligned、score_range、score_not_constant、weight_sum。
   - **warning 级 7 条**：daily_source_is_tdx（源应为通达信 vipdoc）、minute_daily_consistent、row_count_drift、score_coverage、score_stale_check、sector_member_valid。
   - ⚠️ 现状：`has_blocking_error` 只是承诺，`mark_ready()` 零调用 → 审计**拦不住下游**，是"报问题"不是"卡闸门"（见 project 记忆）。

## 逐步台账、单步补跑与夜间重试阶梯（2026-10-08）

链 42 步跑完只报一个 `DONE/PARTIAL` 是不够的 —— 10-08 之前的真实形状是"17:21 收工说 PARTIAL，
但没人知道差哪一步、为什么差、有没有人再试过"。现在有三件事：

**1. 逐步台账**：`~/.duanxian-agents/jobs/last_chain_steps.json`，每次链跑完写一格，
一步一行，`status` 是**三态**：

| 态 | 含义 | 会不会进重试名单 |
|---|---|---|
| `ok` | 这一步真跑成 | 不 |
| `fail` | 真失败（网络、异常、退出码非 0） | **会** |
| `refused` | 按口径**主动拒写**（未开市、上游没数、软失败）——带 `soft` 文字说明 | 不（重试也不会变成成功） |

另有 `cycle`：**整条链跑一次才算一个新周期**，`--only` 补跑继承原 `cycle`。
没有 `cycle` 的话，阶梯会拿被每次补刷新的 `written_at` 当"这批重试到第几档了"的锚，
结果**同一档每 60 秒重跑一次**（10-08 实测踩过）。

**2. `--only NAME[,NAME]` 的台账是合并的**：只跑点名的那几步，其余步骤保留旧读数，
并写一句 `merged`（"本次只跑了 X；合并台账里仍有 N 步没成：…"）、按合并后的名单**重算 verdict**。
`--only` 直接覆盖整份台账的做法 19:30 就露过一次馅：别的步的失败被抹掉，页面上一片绿。

**3. 夜间重试阶梯**（常驻循环第 10 条 `step-retry`，判据在 `ingest/jobs/step_retry.py`）：
默认 `21:00 / 22:00 / 23:00 / 01:00 / 02:30 / 04:20`，档期**在系统配置里可增删**（`step_retry.times`，
逗号分隔 HH:MM，早于 12:00 的算次日）。每一档先重读台账、**只补还挂着 `fail` 的步**，
补成就把那格摘掉；档期用完仍有失败就记放弃，等下一次收盘链顺手补。
三条硬约束：与 15:59 那条链**抢同一把 `fill_all` 锁**（抢不到就顺延，不算失败）；
档期按**绝对日期排序**（按钟点排会把 01:00 排在 21:00 前面，10-08 实测 21:00 那一档因此整晚没跑）；
真起进程那一步 `step_retry._run_only` 在测试进程里硬挡。

```bat
:: 阶梯自己那一格（档期、最近跑过、连败）；逐步台账它**不**打印
python -X utf8 scripts\jobs.py status
:: 逐格读数（一步一行、三态与原因）：直接看那份台账文件，或打接口

:: 手拨一档（判据仍走 step_retry：只跑还挂着 fail 的步）

```

`/system` 上三处可见：「收盘链」那一格的**失败步骤**列表（一步一行、含用时与原因）、
每格的**补救一次**按钮（走 `--only`）、**重试档期**那一格（时点可增删、每档跑没跑都列出来）。
接口是 `GET /api/jobs/chain-steps` 与 `POST /api/jobs/chain-steps/{name}/run`
（202 只说"已排队"，约一分钟后再刷新 —— 补跑是在后台线程里起的）。
