## 一、先认清这条链（任何一个数都走这五步）

```
① 原始来源        通达信本地文件 / TQ 接口 / 东财·新浪 HTTP / 同花顺 ini / 本地快照库
       ↓          （谁在跑、多久跑一次：数据获取工作指南；每晚 15:59 收盘链 + 夜间重试阶梯）
② 入库（清洗层）   market_data.* / reference_data.* / operations.*

④ 读侧组装        duanxian/*_view.py、duanxian/quant.py、duanxian/stock_dossier.py
       ↓          参数默认与上下限在 vr/app.py 的函数签名里；缺数经 _num/_rows 洗成 null
⑤ 屏幕            frontend/src/pages/*.tsx ＋ components/quant/*.tsx
                  点列头排序、悬停、`—` 的显示规则见页面展示 01
```

## 三、表达式里的函数词表（`app/compute/expr.py`，决定"为什么这格是 `—`"）

| 函数 | 实现 | 缺数据时 |
|---|---|---|
| `MA` `SUM` `STD` `HHV` `LLV` | `:80 :92 :96 :105 :109`（都走 `_roll:65`） | 时序族用 `min_periods=n` ⇒ **一只票凑不满 n 根就给 NULL**；`HHV/LLV` 例外（`min_periods=1`，永不为空） |
| `EMA` | `:84`（`adjust=False`，从第一根起算） | 没有暖机期规则 ⇒ 前几根值本身不可与老票横比 |
| `REF(x,n)` | `:101`（`shift(n)`） | 该票自己前 n 根没有 ⇒ NULL。**⚠️ 按行不按日历**：停牌三天，`REF(close,1)` 就是停牌前那一根，中间那三天不占位 |
| `SLOPE(x,n)` | `:113-130`（向量 OLS，分母 `n(n²−1)/12`） | 窗口不满 ⇒ NULL（继承） |
| `RANK` `PCTRANK` | `:134`（`method='min'`）`:139`（0~100） | **当日截面**函数，按 `trade_date` 分组；缺原值的行不进排名 |
| `MEAN` `MEDIAN` `BY 字段` | `:144 :151`，分组 `_group_by_field:158` | `BY` 那列不存在直接抛 `ExprError`（不静默按全市场算） |
| `MAX(a,b)` `MIN(a,b)` | `:185 :194`（`np.fmax/fmin`） | **⚠️ 静默吞 NaN**：有一边缺就用另一边（`35_ma_hfq_screen.sql:32-37` 记着这个坑），与"缺数给 NULL"相反 |
| `ABS` `IF` `COUNT` | `:167 :202 :206` | `COUNT` 用 `min_periods=1` |
| 除法 | `_safe_div:342` | 分母 0 或缺 ⇒ NaN → 出口变 `null`，屏幕上显示 `—` |

三条读法（这是本项目最容易被误读的地方）：

1. **`—` 不是 0，也不是"没有形态"**。`MIN_BARS`/`BARS_MIN`/`n<5 样本` 那几道闸会故意留空，
   因为填 0 会让"没数据"被排成"很差"（见 §九）。
2. **窗口不满是 NULL，不是"少算几天凑合看"**。所以次新票、长期停牌的票在指标列上是空的。
3. **`MAX/MIN` 是唯一的例外**（吞 NaN）。用到它的表达式只有 `atr14`，
   所以 `atr14` 在"昨天缺收盘"的那一天仍会出一个数 —— 读它时别当完美值。

## 四、怎么算出来的：各榜判据（阈值与常量都在文件里，改判据要换 `spec_version`）

### 4.1 倍量形态（`app/compute/vol_double.py`；表 `analytics.volume_double`）

- **倍量**＝`volume_shares ≥ 2.0 × vma5`（`MULT=2.0`，`:50`）；基准 `vma5` 是
  **前 5 场均量、不含当日**（`:126-127,156-157`）。同一个数另算一份 `dbl_prev_count`
  （对比前一场，`≥2×vprev`）。
- 窗口 `LOOKBACK=40`、`MA_WIN=60` ⇒ `BARS_NEEDED=100`、`FETCH_DAYS=150`（`:43-66`）：
  **不满 100 根就不出这一行的分布读数**。
- `dev_med` = 那 40 场里 `|close/ma60 − 1| × 100` 的**中位数**（`percentile_cont(0.5)`，`:163`）；
  `above_ratio` = 收盘在 MA60 上方的场次 ÷ 有 MA60 的场次 ×100（`:166`）；
  `cross_count` = 上下穿翻转次数（`:160`）；`ma60_chg` = 窗口末根对首根的 MA60 变化（`:225`）。
- MA60 要满 60 根才算，否则 `NULL`（`CASE WHEN ma60_n >= 60`，`:141`）；榜筛掉一根 MA60 都没有的行（`HAVING count(ma60)>0`，`:175`）。
- 默认筛条件（`FILTER_DEFAULTS:272-282`，可被 `config.setting['vol_double.filter']` 覆盖）：
  `min_dbl 2`、`dev_med_max 8.0`、`above 20~80`、`cross_min 2`、`ma60_chg_max 20.0`、
  `min_ma60_days 35`、`min_amt_yi 0.5`、`limit 50`；排序 `dbl_count DESC, dev_med ASC`（`:340`）。
  ⚠️ 这八条**只被 `d7_vol_double --verify` 用来打印"当前阈值下入选几只"**，`/volume-double` 那一屏一条都不应用
  （那一屏的门槛是接口参数 `min_count`，默认 0）。别把它当页面筛子读。

- **算例（回答"倍量次是不是量翻倍的次数"）**：是，且判据是 **`≥`（等号算）**、比的是**前 5 场的均量、不含当日**。
  设某票近 6 场成交量（万股）为 100、120、80、90、110、**430**：
  `vma5 = (100+120+80+90+110)/5 = 100` ⇒ 第 6 场 430 ≥ 2×100 = 200 ⇒ 这一场记一次倍量。
  把 430 换成 199 就不算；换成 200 **算**（`>=`，`vol_double.py:50` 的 `MULT=2.0` 配 SQL 里的 `>=`）。
  同一行另一列 `dbl_prev_count` 是**对昨日量**比（`≥2×vprev`），两把尺子不同：昨天缩量会把它顶高，
  所以榜只按 `dbl_count` 排、那一列只作对照（档案里那格 10-14 改名「对昨日倍量次」并写了这句）。

- ### 4.1 之二　**加权分**（2026-10-19 换尺，本节往下为准；上面那段 `dbl_count` 只作历史口径）

  用户当天裁定：「倍量次不能限定死是翻倍及以上，应该是一个加权的数字」，并且
  **「以后每次更新之后都需要回算覆盖，要有这样的一个回算机制」**。界面上不再有「倍量次数」那一列，
  主列与排名都用 `dbl_energy`。

  ⚠️ **当天有过两稿，第二稿作废了第一稿** —— 记住这件事是因为它是判据类缺陷里最难自己发现的一种：
  第一稿写成「占比＝分值 ÷ Σ分值」（还带一个 `normalize` 开关可切 `sum`/`top`）。用户当晚否掉：
  **「其实不存在系数这个参数，系数这个说法是错的」**，正确算法是
  **每个段出现的次数 × 赋予的分值，逐项累加成得分，再按得分排名**。
  现在 `validate()` 反过来**拒绝**载荷里出现 `normalize`（`已经取消「量纲／占比」这一层`），
  `points()` 里没有任何除法。留这一段是为了下一个人别再把它加回来。

  **算式（只住 `app/compute/volume_energy.py`，界面逐字读 `scale.formula`）**：

  ```
  得分 = Σ 每档 ( 这一档在窗口里出现的次数 × 这一档的分值 )
  窗口 = 这只票最近的 LOOKBACK=40 场（与旧口径同一个窗口）
  档   = 当日量 ÷ 前 5 场均量（基准不含当日，与 `vma5` 同一把尺）落在哪一档
  ```

  **档表**（`BANDS` / `DEFAULT_SCORES`）：日量比从 **1.0 起每 0.1 一档到 2.5**（15 档），
  再加尾三档 **2.5–3.5 / 3.5–5.0 / ≥5.0**，共 18 档；**1.0 以下一分不给**（缩量不是放量信号）。
  默认分值依次为
  `0.05 0.08 0.12 0.18 0.25 0.35 0.45 0.55 0.68 0.80 0.88 0.93 0.96 0.98 0.99`（1.0→2.5 那 15 档）、
  然后 **`1.00`（2.5–3.5，顶档）、`0.90`（3.5–5.0）、`0.70`（≥5.0）**：

### 4.2 趋势评分与四维象限（`app/compute/scoring.py`，权重在库 `config.capability`）

**权重不在代码里**，在注册表（seed `05_seed.sql:420-433`）：

```
oper（操作评分） = 0.40 × X(个股质量 stock_quality) + 0.60 × Y(环境共振 env_resonance)
X = 0.25 形态 + 0.25 趋势 + 0.20 位置 + 0.20 筹码 + 0.10 量能
Y = 0.65 板块热度 + 0.35 大盘情绪
板块热度 = 0.30 涨幅 + 0.30 广度 + 0.25 动量 + 0.15 成交额
```

- 合成方式 `score = Σ(分量×权重) ÷ Σ(在场分量的权重)`（`scoring.py:352`）；
  **缺的那一项从分母里剔掉，不按 0 计**（`:338-342`）—— 这一条决定了"缺数不会把票排到最后"。

  x 或 y 是 NaN ⇒ 象限为 `None`（`quadrant_of:284-306`；标签的**口径以 `config.setting.quadrant_labels` 为准**）。
- `rank_in_market` = 降序 `rank(method='min')`、`percent_rank` = `rank(pct=True)×100`（`:391-392`）：
  **分位是"这一场里排在前面的百分比"，与名次不是一回事**，跨场比较只能用分位。
- `is_stale=true` = 这一行的输入已经不是该场最新数据（脚本校验和/权重变过会自动置真，重算写回 false）。

#### 4.2.1 名次稳定榜：近 N 场**名次之和**（读侧派生，10-15 新增，不建新表）

写侧没有新东西：`analytics.score.rank_in_market`（§4.2 那条 `rank(method='min')`）每天每票一行早就落库。
「和」是**读侧现算的派生量**（`duanxian/quant.py::rank_stability()` `:624`，端点 `vr/app.py:618`），
理由与 `score_trend` 同一类：**再造一份"和"进库＝多一份会和源表各说各话的副本**。
（要的是"当天屏幕快照可回放"才需要建表，那时必须先定 `spec_version` 与回算范围 ——
`analytics.score` 与 `analytics.volume_double` 都还没有版本列，这是已登记的欠账。）

```
名次之和   = 最近 N 个「有 oper_score 名次」的交易日里，每天的全市场名次相加（N 只收 3 / 7 / 11）
进榜条件   = 这 N 场每场都有名次（SQL 里的 where，不是页面筛的）
排序       = 和 ↑ → 最好名次 ↑ → 代码 ↑，取前 limit（默认 50，夹在 1~200）
平均名次   = 和 ÷ 场次         ← 跨窗口长度只能比这一列，不能比和
极差       = 最差名次 − 最好名次
```

- **N 是交易日不是日历日**：`window.first_day ~ last_day` 逐场交出（长假里"近 7 天"可能是 12 个日历日）；
- **缺场次不进榜**而不是按 0 补：少加一项的票去和加满的票比大小＝缺席反倒占便宜（与 §4.2 那条"缺项不按 0"同源）；
  被排除多少只随 `universe.excluded_partial` 上屏；
- 各场母体只数略有出入（10-15 实测每场 5,550~5,562 只）⇒ 这个和只回答"这几天谁一直靠前"，不是可换算的分数；
- `rank_path`（逐日名次，`string_agg(... order by trade_date)`）与 `latest_rank` 是用来分辨"一直稳"还是
  "某天冲进来看坏了均值"的：10-15 实测 11 场榜顶中信银行和=194，路径 `13→151→1→1→1→4→4→7→4→5→3`。
- 窗口只收三档（`RANK_WINDOWS` `:621`），别的值走 `_reject`（"参数不对"）而不是 `_fail`（"库里没这场"）。

### 4.7 交易体系榜（`app/compute/system_entry.py`，`sys-1`）

三条**同时**成立才算（常量 `:55-62`）：
① 最近 `LIMIT_LOOKBACK=20` 场内有涨停（`|收盘−涨停价| ≤ SEAL_TOL=0.005`）；
② 向前 `GAP_AGO_MIN=4~GAP_AGO_MAX=7` 场处有一个向上跳空缺口（`bars[i].low > 前日 high` 且
`缺口幅度 ≥ GAP_MIN_PCT=1.0%`），之后连续 `GAP_UNFILLED_DAYS=3` 场最低价都不破缺口下沿；
③ 回调段（`PULLBACK_WINDOW=3`）最大量 ≤ 缺口日量（≤1.0 倍）且至少一根阴线。
`entry_ok` = ③ 且当日确认阳线（`confirm_yang`，收盘 > 开盘 且 > 前收）；
`stop_ref` = 缺口下沿、`stop_dist_pct` = 现价离它的百分比。
统计那一块 `WINDOW_DAYS=250`，分桶 `baseline / c12 / entry`，规则期望用 −7.0% 止损 / +20% 止盈算。

`analytics.system_entry_stats` 里每一列的算法（前瞻一律 `lead` 语义、按 `bar_no` 自连接取未来根，
**不是**窗口帧内自比 —— 帧里的 `close` 不是锚点那天的收盘，10-14 就踩过这一刀）：

| 列 | 怎么算 |
|---|---|
| `win_next` / `avg_next` | 未来第 1 根：收盘上涨占比 %（分母＝那一根有数的行）／`pct_change` 算术平均值 % |
| `avg_2d`…`avg_5d`（10-22 加，用户点名） | 未来连续 N 根**复利累计**的平均值 %：`100 × (exp(Σ ln(1+pct_i/100)) − 1)`，i = 1..N。⚠️ **不是"第 N 天那一天"**的单日涨幅；"日"是**场次**（`bar_no` 是这只票自己的日线序号，停牌不占根）。要求这 N 根一根不缺（`nbN = N`）才算进这一档 |
| `n_2d`…`n_5d` | 上面那一列**自己的分母**（这一档里凑齐 N 根的锚点票·日数）。窗口越长它越小，所以必须与均值一起落库：只交均值就会把不同批样本摆成一排比大小。落库前 `check_stats()` 自验单调不增且 ≤ `n`，不过就 `⚠️` 出声、`--stats-only` 退 3 |
| `up10_med` / `up10_p90` | 未来 10 根**盘中最高** ÷ 当日收盘 −1 的中位 / 90 分位 %（后复权） |
| `p20_up20` | 未来 20 根内盘中最高冲出 +20% 的占比 % |
| `d20_med` | 未来 20 根复利累计收益的中位 % |
| `hit_take` / `hit_stop` | 未来 20 根内**先**碰 +20% / **先**碰 −7% 的占比 %（同批样本互斥判定，都碰到算先碰到的那个） |

列头中文名与逐列说明是**同一份常量的另一半**：`STATS_COLUMNS_SPEC`（key/label/note/signed/
versus_base/bold/denom_key），由 `history()` 随读数交出，前端按它渲染 —— 页面里不许抄中文列名。

**下面那一叠（10-22 新增，`duanxian/system_entry_cohort.py`，只读、不建表）**：母体＝近 6 个自然月的
`entry_ok`（实测 672 行 / 403 只），每行两件事：

| 读数 | 怎么算 |
|---|---|
| `c1/c2/c3/c5/c10/c15` | 从符合日收盘起第 N 个**市场场次**的**累计**涨幅 %（后复权 `close×adjustment_factor`，与 `day_returns.py` 同一条尺）。停牌那天没有行 ⇒ `null`（界面 `—`），不拿更早/更晚的一天冒充；`fwd_at`/`fwd_sessions`/`fwd_bars` 交出「哪几档它有行情」 |

### 4.11 趋势股形状榜（`app/compute/trend_stock.py`，`trend-1`；10-15 新增）

入选四条**同时**成立：① 所选周期（`SHAPE_WINDOWS=(5,10)`）内**每一个**交易日收盘都**严格**高于「截止这一天的 5 日收盘均线」（`MA_N=5`，简单算术平均、不复权，谈得上形状至少要有 `MIN_BARS=9` 根收盘价）；② 当天收盘没涨停（`close >= limit_up - 0.005` 记封住）；③ 当日涨幅算得出来；④ 归得进主板／创业板／科创板（**北交所不纳入**）。

同一行另交两把尺子：`nh_10`／`nh_20` = 收盘 > **前 10／前 20 根的 `max(high)`**（`NH_WINDOWS`，**不含当日**）；`vol_gt_prev`／`vol_gt_vma5` = 当日量 > 前一交易日量、> **前 `VMA_N=5` 根量的平均**（不含当日）。`limit_ups_5`／`limit_ups_10` 是周期内收盘涨停的天数，就是页面上「近 N 日 X 板」那一枚。

参数（默认与上下限都在读侧与端点上，界面能改）：`lookback` 只认 5 或 10（给了别的回 `_reject`，不借用"这一场没有数据"那句）、`limit` 默认 300 上限 1000、`date` 空=库里这一版最新一场。**每日加工段不跟窗口补**（`--recent 1`）：它的窗口帧按"目标日 + 前 60 根"整段扫，跟 span 跑等于把同一段日线按天重扫；补历史用 `--since … --skip-done`，模块自己按 20 场分段。

三条纪律：① 帧**带根数检查**，帧不满置 NULL（不拿两三根算个偏高的均线，那正是"次新看着像走强"的来源）；② 连续段**先筛掉不满足的行、再开窗**，段键 `rn − cum_above`（旧写法把掉线那天和下一段并成一组 ⇒ 连着天数整体偏 1，症状见 §4.12）；③ 没入选的行留着并交 `reject` 短码，`selected` 与 `reject` 互斥由 `--verify` 钉。

实测（2026-10-15）：单日 18.1 秒／5,214 行；5 日档入选 212 只（主板 168／创业板 39／科创板 5），10 日档 19 只（主板 18／创业板 1／科创板 0）；一年回算 243 场／1,257,321 行、覆盖体检 `missing_sessions=0`。

**跨条件组合判据**（不是单指标），两条各自判断、同时命中写 `1, 2`：

- **节点 1** = 当日**首板** × 上证指数当日跌幅 ≥ 1 个点（`NODE1_SH_DROP=-1.0`，读 `market_data.index_daily` 的 `000001.SH`）× 当日成交量 > 前一交易日成交量；
- **节点 2** = 当日**首板或二板** × 前一交易日全场最高连板 ≥ `NODE2_MIN_HEIGHT=6` × 站在那个最高高度的那批票**今天全部没涨停**（**断板与停牌同向**：停牌要有证据 —— 上证已有当天这根日线、而这只票没有当天那行）。
- 三板及以上**不看当天**：取本轮连板的**首板日与二板日**两天命中的并集；窗口把更早的连板截断时对不上就不猜（`hits=NULL` + `hit_reason=run_window_broken`）。

连板**全部由本地日线数**：`close >= limit_up - 0.005` 记封住；除权形态那根（最低价涨破涨停价／最高价跌破跌停价）判为不可信并**截断连板**。梯队样本先剔三类：当日 ST（`security_st_period` 的**当日档期**，一条记录都没有才退回当前快照，退回只数记 `st_fallback_count`）、新股（名字 N/C + 汉字开头，**或**截止这天不足 `MIN_BARS_FOR_LADDER=6` 根 —— 按每只票**第 6 根日线的日期**判真条数，不拿场次跨度猜）、名称表里没名字的票。

**为什么不能用今天的名称判 ST**：那会把"现在是 ST、那年还不是"的主板票按 ±5% 档算涨停价。这条本机实测过后果：全史越界 **16,074 行／1,698 只**（见 `limit_prices.py` 头部），所以档位一律走 `limit_up` 那一列（唯一写入口 `app/compute/limit_prices.py`）。

缺项一律 NULL + `hit_reason` 短码：`hits` 只有 `1`／`2`／`1, 2`／NULL 四种，NULL 在界面是「—」，而「—」有**三种来历**（库里没这一行／这一场判不了／真没命中），由读侧 `node_warn` 那一句点名是哪一种 —— 这也是本机与"打开时现算"那份口径最大的不同：我们能说"没算到"，不会把它念成"没有"。

实测（2026-10-15）：单日 8.2 秒；近一年 243 场／18,508 行，命中 `2` 3,752 只次、`1` 291、`1, 2` 154。机制当面验过一条：10-12 全场最高板 10 板只有 `600825.SH` 一只，10-13 它没有日线行（上证有 10-13 这根）⇒ 按口径算"当天没涨停"，10-13 的首板与二板全部记节点 2。**开发过程中抓到的真缺陷**：连续段初版写成"掉线那天组号 +1、却在含掉线行的分区里数 `row_number`" ⇒ 板数整体偏 1，症状是上证跌 1.586% 那天 36 只涨停里"首板行数 = 0"、节点 1 一只不命中；改成"先筛后开窗"后同日命中节点 1 的有 23 只次。

### 4.13 财务多期加权外推（`app/compute/financial_forecast.py`，`finfc-1`；10-16 新增，纯函数不碰库）

三条格子各自的答案，**判不了就不给数**（给的是 `reason`，不是 0、不是"预计持平"）：

- **下一季** ＝ 上一年的同一季 × (1 + 近 `GROWTH_WINDOW=4` 季单季同比的**半衰加权**，半衰期 `HALFLIFE=2` 季)，增速夹在 `GROWTH_CLAMP=(-60%, +150%)`；另一条腿 B ＝ 上一年的同一季 × 近 `SEASON_YEARS=3` 年**同季季节环比**（Q4 单独一档，分母是同年前三季均值，比例 `4/3`）。**两法相对差 > `DIVERGENCE_MAX=25` 个百分点 ⇒ 不给单一数**，并排念 A/B（分歧本身就是结论）。
- **当年** ＝ 已披露的累计原样保留（那不是预测），未披露的几季按上面逐季补；补不下去的那一季留 `fail_reason` 且值为 null。
- **明年** ＝ 0.4×近 5 年年报 CAGR + 0.6×近 3 年年报 CAGR（`cagr_basis` 说这一只是几条腿算的），情景带取**近 `SCENARIO_YEARS=5` 份**年报同比的 25/75 分位与点估计取并，样本 < `BAND_MIN_SAMPLES=6` 不给带。⚠️ 带子曾经用满全部 28 份年报 ⇒ 描述的是二十年前的样子，与屏上那句「近 5 年」打架，已改。
- 同比一律**自己按同季重算**一份（`yoy`，基期为 0 或 None ⇒ null，负基数取绝对值所以方向仍可读）；源给的那一列只并排留着对账，**从没进过任何外推**。
- 源的比率族封顶在**读侧**：率 >±`RATIO_ABS_MAX_PERCENT=1000`%、源同比 >±`YOY_SRC_ABS_MAX_PERCENT=10000`% ⇒ 交 null 并在 caveat `source_ratio_absurd` 里报这一只被挡掉几格。库里照源存（源镜像不删数，10-16 实测 `002670.SZ` 近 20 期有 16 期净利率超 1000%、最大 3.89e7%）。

### 4.14 近 30 根量价的相似样本检索（`duanxian/volume_similarity.py`；10-16 新增，权重只住这一处）

六维可解释加权：`shape 0.35`（12 格占比向量余弦）· `intensity 0.20`（p60/p80/p90/中位/最大各÷自身均值后欧氏，距离 2＝完全不像）· `rhythm 0.15` · `price_volume 0.15`（方向不同乘 0.35）· `mood 0.10` · `comparability 0.05`。
**缺的那一维从权重里剔掉再归一**，`weights_used` 交实际用的权重（缺维给 0）——否则屏上会念"情绪占 11%"而那一维根本没算。
硬过滤：`MIN_BARS=20`、`long_gap_days=0`、同板块档（任一侧认不出档就不比）、排除目标票 ±90 天的自身窗口；情绪一维是筛完批量补 ⇒ **补完必须重算合分并重排**（先取 `k×MOOD_WIDEN=3` 再截断），否则榜序与分数两头对不上。
母体与尺子与「启动前逐日量能比对」那张表**同一处实现**（`startup_volume.classify()/range_counts()`），唯一区别是窗口方向（那张表启动日往前、这里截止今天往前 ⇒ 列名是「窗口末」）。

### 4.15 量价走势三块（`duanxian/price_volume_trend.py`，`pvt-1`；10-16 新增，**不建新表**）

日线／周线／月线同一时刻都只读 `market_data.stock_daily` 一份：周线按 **ISO 周**分组、月线按 `YYYY-MM`，`_rollup` 是开=本期首根开、高=各根最高的最大者、低=最低的最小者、收=末根收、量额相加、换手率逐根相加（近似，分母随股本变）。
四件容易读错的事都在这一处定：① 价格＝`价 × adjustment_factor`，因子最新一场为 1、越老越小 ⇒ 图上那是**以今天为基准的前复权形状**，每根同时交 `close_raw`（本机 600519 是 1,259 根／63 个月）；② 逐根折算后再取极值，所以跨除权日的高低不会互相拉成假影；③ 区间涨跌＝本期复权收 ÷ **上一期**复权收 − 1（对本期开盘比会把整根实体读反），第一期 null 不给 0%；④ 最后一根永远标 `partial`（日线那块显式改回 false，因为它的收就是最新一场的真收）。
均线 MA5/MA20（日）、MA5/MA10（周）、MA3/MA6（月）用**整段算完再截断**，所以窗口最左边那根也有值；序列开头凑不满一整根窗口的几根给 null（`i+1 >= n` 才给，不拿三根均值冒充 MA6）。少于 `MIN_BUCKETS=6` 根的那一块不画线，只列读数。

### 4.16 首板形状预示（`app/compute/first_board_shape.py`，`fb-2`；10-17 新增，表 `analytics.first_board_shape`）

**这一屏回答「启动前什么形状预示能走到几板」，与 §4.5 那块 `sv-2` 的分工只有一条：母体。**
`sv-2` 的母体是 `len>=4`（回头看才成立 ⇒ 它那一列「启动后收益」带未来函数，同一批样本两套口径 +32% 对 −6.3%）；
这里的母体是**每一个连板段的第一天**（那天收盘就知道它是首板、当天就能决定明早买不买），
于是 `seg_len`（走到几板）与 `r*`/`ex*`（次日开盘进场的收益）都是**结果变量**，母体 SQL 里不许拿段长筛
（钉 `tests/test_first_board_shape.py::test_母体是每一个连板段的第一天_段长不当筛子`）。

六条口径：① 涨停判定 `close >= limit_up - 0.01`，连板岛号用**未过滤日线序列**的 `bar_no` 去减（§4.5 同一课）；
② 启动前 30 根倍数只读 `analytics.volume_ratio_daily`（vr-1），缺的格子**不参与、不补 0**，实际根数存 `bars`
（读侧默认 `min_bars=20` ⇒ 不满窗的不进分档）；③ 价格一律后复权 `价 × coalesce(adjustment_factor,1)`；
④ **两套结果分开交**：`r1/r3/r5/r10` ＝进场（首板次日**开盘**）后第 k 场收盘相对进场价，
`ex1/ex3/ex5/ex10` ＝同一场相对对应分类指数的超额，基准起点＝**进场当日该指数的开盘**
（fb-1→fb-2 就是为这一条换的号：fb-1 拿当日收盘当起点 ⇒ `ex1` 恒等于 `r1`，那一列写着「超额」却一个基准都没含；
`verify()` 现在逐批数「ex1 与 r1 相等」的行数，非 0 把整批判成不通过 —— 这类缺陷不报错，只给一句听着合理的读数）；
⑤ 号段→指数那张表与异动提醒共用（`BENCH_PREFIX`：68→000680、6→000002、30→399102、00→399107，同
`abnormal_move.py:86`），**前缀顺序就是判据**（`6` 排前面会把科创板喂给上证综指）；北交所 8x/4x/920 没有对应指数 ⇒
`bench_code`/`ex*` 一律 NULL，只报绝对收益，不拿上证指数冒充；⑥ 财务取启动日往前 60 天**已披露**的那一期
（同花顺只有报告期、没有披露日 ⇒ 60 天是保守补偿，宁可取到旧一期也不许用未来的数）。

三条「不是缺数」的形状：`seg_complete=false`（末板日之后还没出现过非涨停日）的行段长是**下界**，读侧默认剔掉并在
caveat 里点名条数；`entry_locked`＝次日一字板（high==low），五年实测 1,864 条（3.1%）开盘买不进，默认剔掉，
取消那个勾选后每一档的「买不进」才不是 0；`bars<30` 只出现在上市／停牌早期（全史 376 条）。
取数**按 12 个月分片**（`CHUNK_DAYS=366`，每片走 etl 角色）：同一条母体 SQL 在 5 年窗口上实测 61 秒，
而 `ft_reader` 60 秒就被服务端掐掉。每日链走 `--recent-sessions 40`（步 `fbshape`，加工段第 29 步，超时 900 秒）
只重算最近 40 场的首板事件；回填 2021-11-01→2026-10-16 实测 60,173 条／5,131 只、约 15 分钟、体检通过。

### 4.17 启动前 30 场四维象限轨迹（`app/compute/startup_quadrant_track.py`，`sqt-1`；10-17 新增，表 `analytics.startup_quadrant_track`）

用户 2026-10-17 的原话：**「你把这几类票前 30 个交易日的四维象限分数、名次、象限位置变化情况分析一下」**。
母体沿用 §4.5 那四类启动事件（`analytics.startup_volume_profile`，sv-2，四档全要），
读数一律来自 `analytics.score`（长表：每票每场每键一行）。
**10-18 新增母体档 `anyfirst`＝全部首板（不筛结果）**：从 `analytics.first_board_shape`（fb-2）取全部首板事件、
`seg_len` 一律不筛 —— sv-2 的 board4/`board4_45` 两档的筛子本身就是「回头看 ≥4 板」，4 板率恒 100% 是同义反复，
只有不筛结果的母体答得了「名次往上爬的是不是更容易走到 4 板」这一问；这一档里 `outcome_len` 就是该行自己的
`seg_len`（恒有值），读侧白名单把它排在第一档（cohort 默认与退回仍是 board4，坏值出声退回）。
**一行 = (票, 启动日, cohort, capability_key)** ⇒ 这一行说的是一条轨迹（首末读数 + 中间极值 + 象限翻转），不是一个读数。

六条口径（与 DDL 表注释/列注释同一份，改一处要同批另一处）：

- 窗口＝启动日**之前** `window_days` 个该票自己的有效交易日（**不含启动日当天**：当天已经涨停，分数被启动本身污染）。
  `win_to`＝启动日前一场（T-1），`win_from`＝窗口最早一场；`first`/`last` 就是这两场的读数。
- `rank_delta = rank_first − rank_last`，**正数＝名次上升**（rank 越小越靠前）。这一列是 `buckets` 的分组依据，
  符号写反就是整句结论写反（钉 `tests/test_startup_quadrant_track.py`，并在 DDL 列注释里写死）。
- 象限那一族（`quad_first/quad_last/quad_switches/quad_last_switch_gap/q1_days..q4_days`）**只在 `oper_score` 行有值**，
  其余六个键**必须 NULL 不是 0**（库里那些键根本没有象限；出口只住 `quad_columns()` 一处）。
  `quad_switches` 用 `lag(quadrant)` 数相邻两场不同（两边都取到象限才比，NULL 参与不算一次翻转）；
  `quad_last_switch_gap = bars − 最后一次翻转那场的正序序号`（0＝翻转就发生在 T-1；一次都没翻＝NULL）。
- **`market_mood` 一族不进这张表**：实测同一天全市场同一个数（`rank_in_market` 恒 1、`percent_rank` 恒 50.0090）
  ⇒ 它的「名次/分位」没有横截面意义。这是显式排除，DDL 头部、`TRACK_KEYS`、读侧 caveat 三处都点名，不静默。
- **`vol_stage` 的 value 是档位（1 冷却 / 2 酝酿 / 3 高潮 / 4 背离 / 5 退潮）** ⇒ 那一行读「档位差」，读成百分比就是错。
- **只取 `analytics.score` 里 `is_stale=false` 的那一批**：库里那 227,985 行是旧算法迁入批
  （列注释原话「算法已改，不能与新结果混着比」，实测横跨 2026-01-27..2026-07-27 共 119 场且 `quadrant` 全为 NULL），
  混进同一个窗口 `value_delta`/`rank_delta` 就成了「旧算法减新算法」。
  代价如实交出：可用批次只从 **2026-07-29 起 47 场** ⇒ **窗口凑不满 30 场是覆盖事实，不是缺陷**（读侧必说话）。
- `pct_first/pct_last` 照 `score.percent_rank` 原样存：**库里列注释写「0~1」，实测刻度是 0~100**
  （min 0.0180 / max 100.0000，`scoring.py` 那条 `rank(pct=True)*100`）⇒ 按百分数读。
- 结果两列：`outcome_len`＝`analytics.first_board_shape`（fb-2，同 (票,启动日)）的 `seg_len`（走到几板，结果变量）；
  `outcome_gain4`＝sv-2 的 `trigger_gain`（**fb-2 没有 `trigger_gain` 这一列**，它是母体 sv-2 的列）——
  小数比例（0.4641＝+46.41%），与 fb-2 那按百分数存的 `r*`/`ex*` 不是一把尺子。

**取数按 12 个月分片**（`CHUNK_DAYS=366`，同 fb-2 那一课：逐票 lateral 在宽窗口上会撞 `ft_reader` 60 秒 `statement_timeout`），
取数与写库都走 `role='etl'`。聚合尽量下推 SQL：`row_number() over (partition by 代码,启动日,键 order by trade_date desc)`
取窗口那 N 场、`lag(quadrant)` 数翻转、`percentile_cont(0.5)` 出中位、`min/max(rank_in_market)` 出最好/最差名次，
一条 SQL 把 score 窗口 + 名次变化 + 象限翻转一起算出来。CLI：`--months/--start/--end/--date/--window(10|20|30)/--cohort/--dry-run/--verify`；
退出码 0 写了／1 一条没写成／2 按设计不写（没有母体事件或窗口凑不满）／3 写了但体检不过。
每日链 `quadtrack`（加工段**第 30 步**，排在 `startupvol`、`fbshape` 之后 —— 它读那两张表，超时 900 秒）跑 `--months 12`。

实测（2026-10-17 回填 `--months 12`，约 25 秒）：**2,263 行 / 167 只 / 324 个母体事件**，
按 cohort 分：`board4` 420 行（60 事件）、`board4_45` 420 行（60 事件）、`board4_or_gain45` 642 行（92 事件）、
`jump40` 781 行（112 事件）；其中 **`bars<30` 的 1,612 行**（全部是启动日早于 2026-07-30 的那批事件），
`outcome_len` 有值 1,628 行（`jump40` 的触发日多半不是连板段首日 ⇒ 那 112 个事件里只有 21 个有 fb-2 那一行）。

**这一屏的答案（`buckets` 按 oper_score 的 `rank_delta` 现算三分位，逐档看后来走到几板与进场收益）**：
「启动前名次往上爬 ⇒ 更容易走成 4 板、买进去更划算」这一句**数据不支持**，方向甚至是反的——

| cohort | 档（rank_delta） | n | 4 板率 | 段长中位 | r5 中位 | ex5 中位 | r5 胜率 |
|---|---|---|---|---|---|---|---|
| `board4_or_gain45` | Q1 ≤ −772（名次下滑） | 31 | **74.2%** | 4.0 | +29.76% | +25.96% | 93.5% |
| `board4_or_gain45` | Q2 −772～+622（没怎么动） | 30 | 53.3% | 4.0 | +26.25% | +22.99% | 96.6% |

| `jump40` | 三档 | 38/37/37 | 0%（分母只有 7 条） | 1.0 | +0.84%／−3.35%／+1.60% | — | 57／14／50% |
| `board4` / `board4_45` | 三档 | 各 20 | **恒 100%** | 4.0～4.5 | 32.40／22.30／26.27% | 32.73／22.43／31.20% | 95／95／84% |

三句话：① `board4`/`board4_45` 的母体筛子本身就是「回头看 ≥4 板」⇒ 那一问在这两档**没有分辨力**（4 板率恒 100%，
读侧自动出 `no_power` caveat），只能看 `board4_or_gain45` 与 `jump40`；② `board4_or_gain45` 里名次上升那一档

### 4.18 启动前爆量／突然拉高 × 量增／量缩（`app/compute/startup_spike_days.py`，`ssd-1`；10-18 新增，表 `analytics.startup_spike_days`）

## 七、算例：屏幕上「趋势评分 14.94」这一格是怎么来的（2026-10-14 现查现算）

对象 `601998.SH 中信银行`，交易日 `2026-10-14`（选股汇总那一屏点它，档案第一行也是这个数）。

```bash
# 1) 分量与权重（这一场这一只票实际用的那一份）
PYTHONPATH=. .venv/Scripts/python.exe -X utf8 -c "from app.db import engine as e; \
 print(e.query('select capability_key,component_key,component_value,weight,contribution \
 from analytics.score_detail where security_code=%s and trade_date=%s order by 1,4 desc', \
 ('601998.SH','2026-10-14')))"
```

| 层 | 算式 | 结果 |
|---|---|---|
| **X 个股质量** | `0.25×形态89.4112 + 0.25×趋势83.5358 + 0.20×位置88.3622 + 0.20×筹码18.7673 + 0.10×量能(−28.3145)` | **61.8311**（库里 `stock_quality=61.8312`，全场第 7、分位 99.9） |
| **板块热度**（Y 的第一项） | `0.30×涨幅70.2747 + 0.30×广度(−70.7170) + 0.25×动量65.4683 + 0.15×成交额35.8323` | **21.6092**（全场第 86、分位 94.1） |
| **Y 环境共振** | `0.65×21.6092 + 0.35×大盘情绪(−86.7451)` | **−16.3148**（全场第 86） |
| **操作评分 oper** | `0.40×61.8312 + 0.60×(−16.3148)` = `24.7325 − 9.7889` | **14.9436** → 屏幕显示 `14.94`，Q2（X 正 Y 负）＝持有 |

三句话读法：

1. **为什么"板块还行"而 Y 是负的**：它的板块热度 +21.61 被当日大盘情绪 −86.75 用 0.35 权重拖下去
   （`0.35×(−86.75) = −30.36`，比板块那一项的 +14.05 大两倍）。Y 是**板块/市场级的数**，
   同一天同一行业共享一个 Y（2026-10-14 实测 5,562 只票只有 32 个不同的 Y），
   所以 Y 的差别只落在"你在哪个板块、当天大盘如何"，与这只票自己好坏无关。
2. **缺数不会把票拖到最后**：某分量缺 ⇒ 它的权重从分母里去掉（`Σ贡献 ÷ Σ在场权重`），
   不是按 0 计。所以"缺一项的票"与"该项 0 分的票"在屏上是两个数。
3. **分位 100.0 不是"满分成"**：`percent_rank` 是"排在前面的百分比"，第 1 名就是 100.0，
   与分数本身的 0~100 无关。想跨场比较只能用分位，不能用名次（榜长会变）。
4. **上面那句"全场只有 32 个不同的 Y"就是名次失真的形状**：这 32 档摊到 5,562 只票上 ⇒ 名次是
   **档位里的名次**（最大一档并列几百只，10-21 实测 755 只），"第 86 名"不等于"比第 87 名好一点点"。
   更极端的是 `market_mood`：同一场全市场**同一个值**，写侧那两列在这种档上恒给「第 1」与「50.0」——
   两个数互相打脸。2026-10-22 起读侧先判这一项能不能排名次，判不了就念 `—`（判据见 §4.2.2），
   这一格不再是"全市场第 1"。

## 十一、八分量那一屏怎么读成一句话 ＋ 窗口趋势的「高点在第几天」（2026-10-15，000601.SZ 实算）

用户 2026-10-15 对着 `/grouped` 的「该支票的趋势量化计算」说：**「这块内容完全看不懂」**。
把那一屏读出来的东西记在这里，下次不必重新推。

### 11.1 三层塔：`-26.91` 就是这么拼出来的（基准日 2026-10-14，全部现查 `/api/quant/scores`）

```
操作评分 oper_score = −26.9089
  = 0.40 × 个股质量 X (5.7283)  =  +2.2913
  + 0.60 × 环境共振 Y (−48.667) = −29.2002

X 个股质量 5.7283 = 形态 43.446×0.25 (+10.8615) + 趋势 7.3455×0.25 (+1.8364)
                  + 量能 57.1653×0.10 (+5.7165) + 筹码 −12.8556×0.20 (−2.5711)
                  + 位置 −50.5747×0.20 (−10.1149)

Y 环境共振 −48.667 = 板块热度 −28.1634×0.65 (−18.3062) + 大盘情绪 −86.7451×0.35 (−30.3608)

板块热度 −28.1634 = 广度 −87.0224×0.30 + 涨幅 4.527×0.30 + 动量 −18.8664×0.25 + 成交额 8.6786×0.15
```

- **八项里只有三项进合分**：`oper_score`（塔尖）、`stock_quality`（X）、`env_resonance`（Y）。
  其余五项（`temp_score`/`sector_heat`/`market_mood`/`vol_stage`/`vol_temp`）是旁证：
  `sector_heat` 与 `market_mood` 已经通过 Y 进来了，单列是为了核对 Y 被谁拖累。
- **`vol_stage` 是档位不是分数**（这一场交 `3.0`，分位 67.5）。把它当"3 分"读就是错。
- **负分不等于要跌**：`oper_score` 是"同一场里比强弱"的尺子。这一票 −26.91 却排 **第 910 / 5,562**
  （比 83.7% 的票强），屏上那格「前 16.3%」就是这么来的。值不能跨日比，名次可以。
- 权重住在 `config.view_effective_binding`（`weights_registry_table` 那一格交的就是表名），
  代码里没有第二份；`weight_sum_ok=false` 时那一项**不可跨票比**，屏上会标出来。

### 11.2 「哪天最高」旁边新加的一列：高点在窗口第几天（用户的第二个疑问）

用户问：「为什么会有哪天最高这个值？有啥意义？不应该都显示那一天的情况吗？」
答案：**斜率只说平均每天动几分，同一个平均数可以由完全相反的形状拼出来** ——
库注释原话就是"出现在第 2 天还是今天，含义完全相反"。所以 10-15 补了一列，把"离今天几天"这个心算省掉。

- 判据：`x_plus_y_max_day_no` ＝ 峰值日是窗口内**第几个有评分日**（1＝窗口第一天，`window_days`＝基准日自己）。
  与斜率**同一把尺子**（都按 `analytics.score` 的 `capability_key='oper_score'` 有评分日数），**不数日历日**
  —— 长假里 10 个日历日可能只剩 5 个交易日。
- 词（阈值只住 `duanxian/quant.py::_peak_position`，页面只转述 `peak_rule` 那一句）：
  序号＝`window` 记「就在这一场（刚创新高）」、`window-1` 记「最近两天」、
  ≤前三分之一记「起点附近（高点早已过去）」、其余记「中途见顶」。
- 定位不了就交 `None`（屏上 `—`）并出一条 `peak_day_no_unlocated` caveat，**不猜一档**。
- 实测踩到的一条（当天 08:2x）：取"有评分日序列"时把上界锚成了**最早**那个基准日，
  结果比它晚的日子全不在序列里，12 行有 11 行定位不了 —— 整列 `—` 看起来像"这列没做"。
  锚点必须是**最晚**基准日，并多取 `window_days + 5` 场。
