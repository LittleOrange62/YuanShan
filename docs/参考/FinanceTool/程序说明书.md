**关键修正**（相对旧系统）：

- `.day` / `.lc1` / `.lc5` 解析**只有一份实现**，带固定字节样本单元测试。旧系统有 5 份重复实现
- 字段名自带单位：`amount_yuan`（元）、`volume_shares`（股）。彻底消灭"文档写千元代码写元"的 1000× 偏差和"文档写手代码写股"的 100× 偏差
- 分钟线日期锚点用 1899-12-30 起算 + 测试标定，不用 `LO_BASE=45881` 这种只能撑到 2027 年的魔法常量
- 涨跌停按 `reference_data.security.board` 分板块算（主板 10% / 创业板 20% / 科创板 20% / 北交所 30% / ST 主板 5%），不是一刀切 ×1.1
- `adjustment_factor` 由分红记录真实累乘，不硬编码 1.0
- `880*`/`881*` 板块伪代码在解析阶段就分流到 `market_data.sector_daily`，且个股表有 CHECK 约束挡住。旧系统靠事后 `clean_880.py` 删
- 市场归属单一判据（以文件所在市场目录为准），不再三套并存

**功能点↔脚本自定义**的实现（用户的明确要求）：

```
config.capability  功能点＝插槽    'stock_quality' / 'sector_heat' / 'oper_score'
config.script      脚本＝积木      登记路径、版本、checksum、参数 schema、能实现哪些功能点
config.binding     绑定＝插法      capability_key × script_id + weight + display_order + params + enabled
```

一个功能点可以绑 1 个脚本、绑 N 个加权合成、绑 N 个按序串联、或同一脚本绑两次不同参数。换实现、调权重、A/B 对比、临时停用子因子，全在页面上完成。

旧系统权重写死在代码里：

```python
X    = 0.25*形态 + 0.25*趋势 + 0.20*位置 + 0.20*筹码 + 0.10*量能   # factor_engine.py:148
Y    = 0.65*板块热度 + 0.35*大盘情绪                              # :281
oper = 0.40*X + 0.60*Y                                          # :300
```

新系统这些数字全在 `config.binding.weight`，且按 `enabled` 归一化——停用一个子因子，剩下的权重自动补齐。

**策略脚本契约**：

```python
def run(ctx: StrategyContext) -> StrategyResult: ...
```

四条硬规则：

1. 一切时间以 `ctx.trade_date` 为准，禁止 `date.today()`。旧系统四个 `score_*d_*` 脚本用 `get_recent_dates()` 取当前窗口、无视传入日期，导致所有回溯计算都是错的
2. 取数只能经 `ctx.repo`，沙箱不暴露 DSN
3. 必须周期性检查 `ctx.cancel.is_set()`。旧系统取消是假的：只改内存状态，Event 永不 set，`_finish_task` 又覆盖回 done
4. 输出必须匹配 `capability.output_spec`，不匹配则任务失败且不写库

内置策略与外部脚本走同一契约、同一注册表，**没有特权路径**。旧系统外部脚本模式下 `x/y/oper` 被硬编码为 0.0，等于外部脚本无法产出主评分。

**核心页 `/review` 三层下钻**：

```
交易日选择器 ── 上一交易日 / 下一交易日 / 导出
─────────────────────────────────────────────
第一层 大盘：温度 上涨家数 涨停数 成交额 情绪评分
             涨跌幅分布直方图 │ 指数走势 │ 情绪 20 日时序
─────────────────────────────────────────────
第二层 板块：热度榜 TOP20（名称 热度 涨幅 广度 动量 成交额 领涨股）
             轮动热力图（近 10 交易日 × 板块）      ← 点行下钻
─────────────────────────────────────────────
第三层 个股：四象限散点（X=个股质量 Y=环境共振）
             Q1买入 Q2持有 Q3试探 Q4回避           ← 点象限筛选
             个股表 → 行点击 → 抽屉：K线 + 评分拆解
```

**评分拆解**是关键设计，让评分不再是黑盒：

```
Oper 62.4 = 0.40 × X(48.2) + 0.60 × Y(71.9)
  X 48.2 = 形态 0.25×60 + 趋势 0.25×45 + 位置 0.20×38 + 筹码 0.20×55 + 量能 0.10×20
  Y 71.9 = 板块热度 0.65×78.5 + 大盘情绪 0.35×59.6
```

每项显示子分值、权重、贡献、产生它的脚本名与版本。旧系统 Y 轴板块热度恒为 0（`factor_engine.py:478` 漏传 `block_stocks` 参数，导致 65% 权重完全失效，影响已存的 75,995 条记录），有这个面板肉眼就能发现。

**图表统一约定**（固化在代码里，不开放配置，保证跨日可比）：涨红跌绿、金额带单位后缀、直方图固定分箱边界、热力图固定色阶、空数据明确提示而非空白图。

**必须避开的旧 UI 坑**：Interval 自动刷新只更新展示型 Output 永不写回输入组件；表格行内按钮用 pattern-matching callback 取真实行索引（旧 `/software` 点任意行都作用于第一行）；所有回调引用的组件在初始 layout 中存在；每个 Output 唯一 callback；前端不拼 SQL。

### 4.5 块 4 · 数据质量与口径契约（app/quality + app/db CHECK/触发器）

这是用户需求里空着的第 4 块。**它存在的理由是：前两套系统的故障不是功能缺失，而是数据错了但没人知道。**

| 功能点 | 说明 |
|---|---|
| 字段口径注册表 | 每个字段的单位、值域、合理区间、计算口径、来源、展示格式 |
| 落库前行级校验 | error 阻断、warning 放行并记录 |
| 落库后表级/跨日/跨表审计 | 独立作业 |
| 质量结果与违规样本 | 存 `operations.quality_result`，含最多 10 条样本 |
| **阻断下游** | 有 blocking error 则不写 `operations.data_ready`，加工作业不触发 |
| 血缘追踪 | 任何一行数据可回溯源文件、mtime、批次；任何评分可回溯脚本与 checksum |
| stale 标记与重算 | 脚本或权重变更后受影响的历史结果自动标记 |
| 库层强制 | CHECK 约束 + 触发器，绕不过去 |

**两条最有价值的规则**（有它们，旧系统的四个静默错误都活不过第一天）：

- `vol_amount_consistent` — 成交额 ÷ 成交量应落在当日价格区间内。单位错 100 或 1000 倍必然撞穿。做成 PG 触发器，写入即拒绝
- `score_not_constant` — 子分项在全市场的标准差必须 > 0。恒为 0 说明该分项失效，正是 Y 轴板块热度那个 bug 的探测器

**迁移期存量数据处理原则**：`limit_up/limit_down` 一刀切的错误值置 NULL 后按 board 重算——**宁可 NULL 也不留已知错误值**；`adjustment_factor` 全量重算；75,995 条评分全标 stale 待重算；两套 ETL 的 1.8% 行数差异（9,531,333 vs 9,359,339）逐条归因后再定主源。

#### 4.7.1 复盘闭环与效果验证

**这是原说明书漏掉的一整块，也是最要紧的一块。**

前四块能把数据取进来、算出分、画成图，但整条链到"给你一个 78 分和一个 Q1 象限"就断了。
你看了什么、判断了什么、最后做了没有、做了之后对不对 —— 系统一概不知道。
结果是：`/blocks` 页面上那 17 个因子权重你可以随便调，但**调完没有任何东西告诉你调好了还是调坏了**。
一个能改权重却看不到效果的系统，改权重这件事本身就是在盲调。

| 功能点 | 存哪 | 说明 |
|---|---|---|
| 每日复盘结论 | `analytics.review_note` | 一天一条：今天的市场判断、明天的计划、附带当日 market_mood 快照 |
| 个股标注 | `analytics.stock_note` | 对某只票某一天的标注：看多/看空/观察/放弃 + 理由 + 标签 |
| 交易流水 | `analytics.trade_log` | 买卖记录（时间、代码、方向、价、量、费用、原因），手工录入或从券商导出文件导入 |
| 持仓 | `analytics.position` | 由 trade_log 推导，不独立维护 —— 两处维护必然对不上 |
| 前瞻收益 | `analytics.forward_return` | 每个 (代码, 日期) 的 T+1/3/5/10/20 收益率，按交易日历对齐 |
| 因子效果评估 | `analytics.factor_eval` | 每个功能点/分项按分数十分位分档，统计各档的平均前瞻收益、胜率、IC（信息系数） |

**为什么前瞻收益要单独存表而不是查询时算**：它是所有效果评估的公共分母，
`/scores` 页面的分档胜率、`/blocks` 的权重调参、质检的 `score_not_constant`
升级版（分项与未来收益完全无关也是失效）都要用。每次现算等于把同一段
窗口函数跑十遍，而且 T+20 收益要等 20 个交易日才定稿，天然适合落库 + 增量补。

**闭环的形态**：
```
评分 → 象限 → 你的标注(stock_note) → 交易(trade_log) → 持仓(position)
                                                          ↓
        因子权重 ← 效果评估(factor_eval) ← 前瞻收益(forward_return)
```
右边那条回路是本块的全部意义：**让"页面上调权重"从手感变成有据可依**。

#### 4.7.3 情绪周期与涨停复盘

调研专业每日复盘工具（复盘网 / VIP 复盘网）与打板体系后补的一块。
**这一块几乎全部能用现有数据算出来**，不需要新数据源 —— 涨停判定用的是
按板块分档回算的 `limit_up`，比"涨幅超过 9.8%"准确（创业板 20%、
北交所 30% 的票用 9.8% 判会全部漏掉）。

| 功能点 | 存哪 | 数据依赖 |
|---|---|---|
| 涨停 / 跌停池 | `analytics.limit_pool` | 现有日线 + 回算的涨跌停价 |
| 连板数与连板梯队 | 同上，`streak` 列 | 连续涨停日计数，按交易日历对齐 |
| 封板率 / 炸板率 | 同上 | 分钟线才精确；日线可用"最高价触及涨停但收盘未涨停"近似 |
| 首板 / N 连板成功率 | `analytics.limit_stats` | 涨停池 + 次日收益 |
| 涨停次日溢价（赚钱效应） | 同上 | 情绪最直接的度量 |
| 亏钱效应 | 同上 | 跌停家数、炸板股次日跌幅 |
| 情绪周期四阶段 | `analytics.mood_cycle` | 冰点 → 回暖 → 高潮 → 退潮 |
| 全市场情绪温度 0~100 | 同上 | 已有 `temp_score` 是个股温度，这里是市场温度 |

**情绪周期的四维判据**是调研里最有价值的一条：涨停家数、**最高连板高度**、
**连板梯队深度**、跌停家数。现在的 `market_mood` 只用了涨跌家数比 / 涨停家数 /
中位涨幅 / 成交额环比 —— 缺了连板高度和梯队深度，而这两个恰恰是区分
"高潮"与"退潮"的关键：涨停家数还在、但最高板从 7 板掉到 3 板，
就是退潮的第一信号，光看家数看不出来。

四阶段对应的仓位区间（冰点 ≤2 成 / 回暖 4~6 成 / 高潮 2~3 成 / 退潮 ≤1 成）
写进 `config.setting`，页面可调 —— 这是判断，不是事实，必须可配。

**分级推荐替代纯评分排序**：调研里有一条实测结论值得警惕 —— 某套打板体系
回测发现"评分与次日收益相关性 r = -0.002"，于是放弃纯评分排序，
改成 A+/A/B+/B/C/D 六级分类 + 同类内排序。对本系统的启示是：
`analytics.score` 的连续分值必须由块 8 的分层胜率来背书，
**不能假设"分数高 20 分就更值得买"**。所以 `/scores` 页面的主视图应是
分档胜率柱状图，连续分值只作排序键。

#### 4.7.4 因子工程与效果验证

量化投研的标准链路是 **因子构建 → 预处理 → 检验 → 合成 → 归因**。
现在只有"构建"（`config.indicator` + 求值器）和粗糙的"合成"（`config.binding` 固定权重），
中间三步全缺。缺的后果很具体：

| 功能点 | 现状与缺口 |
|---|---|
| 去极值 winsorize | **缺**。现在用截面百分位规避了极值，但物理量映射 `clip_score` 仍受影响 |
| 标准化 | 部分有（百分位 / 线性截断），但没有统一入口，17 个脚本各写一遍 |
| **行业与市值中性化** | **缺，且最要紧**。某行业整体强势时该行业所有票分数一起虚高，评分退化成"猜哪个行业涨"。中性化后才是个股 Alpha |
| 因子有效性 IC / ICIR | **缺**。IC = 因子值与未来收益的截面秩相关，ICIR = IC 均值 / IC 标准差。判断"这因子到底有没有用"的唯一硬指标 |
| 分层回测 | **缺**。按因子值分 10 档看各档前瞻收益是否单调，不单调说明逻辑错了 |
| 因子相关性与拥挤度 | **缺**。五个质量分项若互相相关 0.9，等于同一因子算了五遍，0.25/0.25/0.20/0.20/0.10 的权重就是假的 |
| 权重合成方法 | 只有固定权重。应支持等权 / ICIR 加权 / 相关性惩罚三种，页面可选 |
| 归因分析 | **缺**。一天的组合收益里多少来自行业暴露、多少来自真正选股 |
| 参数敏感性（参数平原） | **缺**。权重扰动 ±10% 后 Top50 名单变化率；变化率极高说明结果是拟合出来的 |
| 过拟合防范 | **缺**。样本内 / 样本外切分、滚动窗口验证 |

落表：`analytics.factor_ic`（每日每因子 IC）、`analytics.factor_eval`（分档收益 / 胜率 / ICIR /
相关性矩阵）、`analytics.forward_return`（块 5 已规划，是这一切的公共分母）。

**新增求值器函数**（页面写公式时可用）：`WINSOR(x, 0.01)`、`NEUTRAL(x BY sector)`、
`ZSCORE(x)`、`CORR(x, y, n)`。中性化做成显式函数而不是隐式行为 ——
隐式中性化会让人看不懂自己写的公式算的到底是什么。

#### 4.7.5 组合、风控与执行

| 功能点 | 说明 |
|---|---|
| 组合层面指标 | 累计收益、最大回撤、夏普、卡玛、月度胜率，基于 `analytics.position` 推算 |
| 仓位建议 | 按情绪周期阶段（块 7）给区间，不给具体数字 |
| 集中度检查 | 单票上限、单行业上限、相关性过高的持仓预警 |
| 止损线 | 按 `config.setting` 的规则（固定比例 / ATR 倍数 / 跌破均线）生成提示 |
| 滑点与费用 | `analytics.trade_log` 记实际成交价与信号价之差，累计出真实滑点 |
| 回测 vs 实盘偏差 | 同一策略的回测收益与 `trade_log` 实际收益并列对照 |

调研里反复出现"回测封神、实盘翻车"。本系统的防线是：
**滑点和费用用你自己 `trade_log` 里的实测值，不用行业默认的 0.1%**；
以及所有分层胜率都必须能追溯到具体的 (代码, 日期) 明细，随时抽查。

## 第 5 章 可配置化体系（十三张注册表）

原则：**凡是"以后可能要改"的，都存表、页面能点。代码只提供积木块。**

### 5.1 十三张注册表一览

| # | 表 | 管什么 | 典型改动 |
|---|---|---|---|
| ① | `config.data_source` | 数据源 | 通达信换目录、启停某源、多源优先级 |
| ② | `config.field_spec` | 字段口径与展示格式 | 成交额显示"亿"还是"元"、小数位 |
| ③ | `config.dataset` | 数据集与就绪标准 | 行数下限从 4800 改 4500 |
| ④ | `config.quality_rule` | 校验规则 | 新增一条 SQL 布尔规则、调阈值、是否阻断 |
| ⑤ | `config.indicator` | 指标（页面写公式） | 加"20日振幅标准差" |
| ⑥ | `config.capability` | 功能点（插槽） | 新增一个评分维度 |
| ⑦ | `config.script` | 脚本（积木） | 扫描目录登记新脚本 |
| ⑧ | `config.binding` | **功能点↔脚本** | 调权重、换实现、A/B、停用子因子 |
| ⑨ | `config.job` | 作业与触发 | 同步时间、标的范围、重试、并发键 |
| ⑩ | `config.screen_rule` | 筛选条件类型 | 加"N日内出现过涨停" |
| ⑪ | `config.chart` | 图表 | 换配色、折线改柱状、换 X/Y 字段 |
| ⑫ | `config.notify_channel/rule` | 推送 | 换飞书群、改消息模板、加触发条件 |
| ⑬ | `config.page_layout` + `config.menu` | 页面布局与菜单 | 拖卡片、建自定义看板、隐藏页面 |

### 5.2 指标公式写法（window/expr/rank/crosssec 四类）

`config.indicator` 支持四种 kind，覆盖绝大多数需求：

| kind | 含义 | 示例 |
|---|---|---|
| `window` | 时序窗口 | `MA(close, 20)` `STD(pct_change, 60)` `HHV(high, 250)` |
| `expr` | 同行运算 | `(high - low) / pre_close * 100` |
| `rank` | 截面排名 | `PCTRANK(amount_yuan)` |
| `crosssec` | 截面聚合 | `close / MEAN(close BY sector)` |

用受限求值器（白名单函数 + AST 校验，禁属性访问与任意调用），**不是 `eval`**。可用函数约 30 个：`MA SMA EMA WMA STD SUM MAX MIN HHV LLV REF DIFF SHIFT ABS LOG SQRT POW SIGN CLAMP IF AND OR NOT RANK PCTRANK ZSCORE MEAN MEDIAN QUANTILE COUNT CROSS SLOPE POLYFIT CORR`。

保存后下一次加工作业就会算出这一列，立刻可用于筛选、图表、评分。

### 5.3 /blocks 页面四个通用能力（校验 / 试跑 / 被谁引用 / 变更历史回滚）

每张注册表都有：

- **校验** — 保存前检查引用完整性、表达式可解析、SQL 可 EXPLAIN、依赖无环、权重和合理。不通过不让存
- **试跑** — 指定日期 + 小范围标的立刻算给你看，只回显不落库
- **被谁引用** — 反查依赖，避免删出空引用
- **变更历史 + 回滚** — 所有 `config.*` 写操作由触发器记 `operations.config_history`（存变更前后完整行），一键回滚到任意版本

外加**导入/导出 JSON**：整套配置可导出成文件，用于备份、换机复现、分享调好的因子配置。

### 5.4 权限分层（锁定 / 受保护 / 开放 / 个人）

| 层级 | 内容 | 谁能改 |
|---|---|---|
| **锁定** | 二进制解析器、DB schema、单位换算、涨红跌绿、执行引擎 | 只能改代码 + 迁移 + 测试 |
| **受保护** | 字段口径、校验规则、筛选 SQL 模板、DDL 操作 | admin 角色，二次确认 |
| **开放** | 权重、参数、cron、标的范围、指标公式、图表、布局、推送 | 普通登录用户 |
| **个人** | 自选分组、筛选预设、自定义看板 | 各自管理 |

划线理由：锁定层错了整库数据不可信；开放层错了只影响当次结果，且有试跑与回滚兜底。

### 5.5 现有配置能力的边界与后续方向

#### 5.5.1 现状天花板

先说清楚现在这套"可配置"到底卡在哪，不然后面加的东西没有靶子。

| 表面上可配 | 实际的硬编码在哪 |
|---|---|
| 指标公式页面可写 | 但**面板取哪些列写死在 `indicators.load_panel()` 里**（固定 13 列 + board/is_st/float_share）。写一个用到 `total_share` 的公式，求值器直接报未知字段 |
| 权重页面可调 | 但**归一化方法和阈值写死在 17 个脚本里** —— `clip_score(dd, -22, 0)`、`_lin(breadth, 30, 70)` 这些数字页面上看不见也改不了。`config.binding.params` 字段建了，脚本几乎不读 |
| 新增功能点是插一行 capability | 但**新增分项必须写一个 `.py` 文件**放进 `builtin/`，还要 `load_entry` 能导入。这是"改代码 + 重启"，按 §5 的判断标准就是设计错了 |
| 图表页面可配 | 但**取数是 `app/web/queries.py` 里的 14 个 Python 常量**，`config.chart.data_query` 只能引用已有的名字，加一个新图表要先改 Python |
| 18 张注册表都能存配置 | 但**每张表都要单独写一个编辑界面**。现在只写了 `config.binding` 一个。加第 19 张表 = 再写一个界面 |
| 权重改了就是改了 | **没有"方案"概念**。想对比新旧两套权重只能改一次看一次，改坏了靠 `operations.config_history` 回滚 —— 能回滚不等于能对比 |

结论：现在是**"参数可配"**，不是**"结构可配"**。要到"点一下就行"，缺的是下面三层。

#### 5.5.2 自配置三层架构（远期设计）

```
L3 组装层   方案 / 看板 / 分档 / 钩子      —— 把积木拼成成品，不碰算法
              config.scheme  config.dashboard  config.bucket  config.hook
                            ↑
L2 表达层   表达式即算法，SQL 即取数        —— 不写 Python 就能加算法与数据
              config.script(kind=expr)  config.query  config.derived_field
              config.panel_spec  config.normalizer
                            ↑
L1 元层     注册表的注册表                  —— 一个界面渲染全部注册表
              config.registry_meta  config.registry_column
```

**每一层的意义**：L1 让"加一张配置表"不再需要写界面；L2 让"加一个算法/一列数据/一个图表"不再需要写 Python；L3 让"组合出一个成品"不再需要理解底层。三层解决的是三类不同的人：L1 给我（开发），L2 给你（调参与研究），L3 给未来的你（日常使用）。

#### 5.5.3 L1 元层 · 注册表的注册表

两张新表描述所有注册表自身：

```
config.registry_meta    reg_key, schema_name, table_name, label, pk_cols,
                     editable, protect_level, order_by, row_limit, note
config.registry_column  reg_key, col_name, label, widget, dtype, required,
                     enum_values, fk_ref, validator_key, visible, editable, display_order
```

`widget` 取值 `text | number | switch | select | json | expr | sql | color | date`，
决定页面上渲染成什么控件；`fk_ref` 写 `config.script.script_key` 这类引用，
页面自动变成下拉选择并做引用完整性校验；`validator_key` 指向已注册的校验器
（表达式可解析 / SQL 可 EXPLAIN / cron 合法 / 权重和为 1 / 依赖无环）。

于是 `/blocks` 页面只需要**一个**通用组件：读 `registry_meta` 列出所有注册表，
读 `registry_column` 渲染表格与表单，保存前跑 `validator_key`，
写入由已有触发器记进 `operations.config_history`。
**加第 19 张注册表 = 插一行 meta + 若干行 column，界面代码零改动。**

顺带把 §5.3 承诺的四个通用能力也做在这一层，而不是每张表各做一遍：
校验、试跑、被谁引用（从 `fk_ref` 反查，不用手写）、变更历史与回滚。

#### 5.5.4 L2 表达层 · 不写 Python 加算法

| 新表 / 新列 | 作用 | 安全边界 |
|---|---|---|
| `config.script.kind = 'expr'` + `expr` 列 | **分项直接用表达式定义**，不用写 `.py`。例：`PCT(MA(close,5)/MA(close,20)-1)` | 走已有 AST 白名单求值器，与 `config.indicator` 同一条通路 |
| `config.panel_spec` | 面板取哪些列、回溯多少天、过滤条件、要不要 join 股本/板块 | 列名必须在 `config.field_spec` 里注册过；回溯天数有上限 |
| `config.derived_field` | 派生列定义一次全系统可用（总市值 = `close * total_share`、量比、连板数） | 落成视图或 GENERATED 列；只允许引用已注册字段 |
| `config.normalizer` | 归一化方法与参数从脚本里搬到表里：`pct` / `clip` / `zscore` / `bucket` / `rank_within` + 参数 | 每个 `binding` 选一个 normalizer，参数走 `params` JSON |
| `config.query` | **命名查询存表**，替代 `queries.py` 的 Python 常量。图表和看板引用查询名 | 只允许单条 `SELECT`；仅用 `reader` 角色执行；保存前 `EXPLAIN` 校验；强制 `LIMIT`；禁分号多语句；参数只走占位符不做字符串拼接 |
| `config.bucket` | 连续值 → 标签的分档映射，阈值可调 | 用于 A+/A/B/C 分级、情绪四阶段（冰点/回暖/高潮/退潮） |

**这一层的关键是 `kind='expr'` 的脚本。** 它让"新增一个评分分项"从
"写 Python 文件 + 重启" 变成 "页面上写一行公式 + 点试跑"。
17 个内置 `.py` 脚本继续保留 —— 复杂逻辑（如筹码分布代理、板块广度）
用表达式写不出来也不该硬写，两种 kind 并存，`load_entry` 按 kind 分派。

判据：**能用一个表达式说清的分项，就不要写成文件。**

#### 5.5.5 L3 组装层 · 积木拼成成品

| 新表 | 作用 |
|---|---|
| `config.scheme` / `config.scheme_binding` | **方案**：一整套 binding 权重 + 参数 + normalizer 的命名快照。可并行计算多个方案，`analytics.score.scheme_key` 区分，页面并列对比。调权重从"改一次看一次"变成"另存为新方案再对比" |
| `config.dashboard` / `config.dashboard_card` | **自定义看板**：选命名查询 + 图表类型 + 筛选条件，保存成自己的页面，菜单自动出现。个人级，不影响别人 |
| `config.hook` | **事件钩子**：在 `数据就绪 / 评分完成 / 质检失败 / 任务失败` 等事件点挂动作（跑某个 job、发通知、写标注、置 stale）。现在只有 job 的 `chain` 一种衔接方式，钩子把它一般化 |
| `config.alert_rule` | 价格 / 指标 / 评分 / 组合层面的触发条件，命中走块 6 的通知渠道 |
| `config.review_checklist` | 每日复盘固定要看的项，勾选式 |
| `config.role_perm` | §5.4 那张分层表**落成数据**：哪个角色能改哪张注册表的哪些列。现在只是文档里的约定，没有代码执行 |
| `config.cache_rule` | 哪些结果缓存多久、什么事件失效 |

**方案（scheme）是这一层里最该先做的。** 没有它，块 8 的因子效果验证就没有对照组 ——
你只能知道"当前这套权重的分档胜率是多少"，不能回答"换成 ICIR 加权会不会更好"。

#### 5.5.6 配置化的代价与划线

配置化不是免费的，说清楚代价才好判断：

- **调试变难** —— 出错时"是配置错了还是代码错了"多了一层。对策：所有配置读取集中在 `registry.py`，每次计算把生效配置的快照写进 `operations.task.params`，事后能复现当时的配置
- **性能** —— 表达式求值比手写 pandas 慢。实测 D1 指标计算优化后是 147s/日，`kind='expr'` 的分项会落在同一量级；真正的热路径（如面板加载）保持代码实现
- **安全面变大** —— `config.query` 存 SQL 是最危险的一处。边界是：单条 SELECT + reader 角色 + EXPLAIN 预检 + 强制 LIMIT + statement_timeout 60s + 禁多语句。**库层的只读角色是最后一道防线，不依赖应用层自觉**
- **配置本身会腐烂** —— 停用的脚本、没人引用的图表、失效的查询会堆积。对策：L1 的"被谁引用"反查 + 一个定期作业报出零引用配置

**我不打算配置化的东西**：二进制解析器、单位换算、DB schema、涨跌停分档规则、
角色与权限的执行逻辑、评分驱动本身的算法（权重归一、缺失分项不计权）。
理由一致：**这些错了会让整库数据不可信，而配置化的收益是"改起来快"——
对一年改不了一次的东西，快没有价值，风险却是永久的。**

## 第 6 章 数据库设计（schema / 角色 / 备份）

### 6.1 schema 分域

| schema | 内容 |
|---|---|
| `md` | market data — 行情（日线、分钟线、指数、板块） |
| `ref` | reference — 证券基础信息、板块成分、交易日历、股本、分红 |
| `fct` | factor — 指标、因子、评分及拆解 |
| `config` | config — 十三张注册表、自选股、筛选预设、用户 |
| `ops` | operations — 任务、审计、血缘、质量结果、配置历史 |

### 6.2 核心表要点

`market_data.stock_daily` — 按年 RANGE 分区，主键 `(security_code, trade_date)`，`trade_date` 用 `date` 类型（不是 `'20260825'` 字符串），字段名自带单位，带 `source_batch_id NOT NULL` 强制血缘，带 6 条 CHECK 约束 + 单位一致性触发器。

分区取代了年份分库。代码里不再有 `_get_year_db_path` / `trade_date[:4]` 路由 / `ATTACH prev_db`，跨年查询是一句普通 SQL。

`market_data.stock_minute` — 按月分区，`dt timestamptz`。当前 37 GB 单 SQLite 文件的痛点在这里解决。

`reference_data.security` — 必含 `board`（主板/创业板/科创板/北交所），涨跌停靠它算对。含 `pinyin` / `pinyin_abbr` 支持拼音首字母检索。

`reference_data.trade_calendar` — 表驱动日历，`is_open` / `prev_open_date` / `next_open_date`。

`operations.ingest_batch` — 血缘：source、source_path、source_mtime、target、row_count、状态。

### 6.3 角色

| 角色 | 权限 | 给谁 |
|---|---|---|
| `postgres` | 超级用户 | 仅运维 |
| `ft_admin` | 库 owner，可 DDL | 迁移建表 |
| `ft_app` | 业务 schema 读写，无 DDL | FinanceTool 主程序 |
| `ft_etl` | `md`/`ref` 写，其余只读 | 同步与批量导入 |
| `ft_reader` | 全库只读 | 智能体默认、分析脚本、查询台 |

角色级 `statement_timeout`：reader 60s、etl 30min。`idle_in_transaction_session_timeout` 防长事务拖死 autovacuum。

### 6.4 备份

备份的前提是先分清什么可再生、什么不可再生：

- `md`（行情）**可再生** —— 源头是通达信 vipdoc 的 `.day` / `.lc1`，重新解析即可重建。占了库里 99% 的体积，却是最不值得每天全量备份的部分。
- `config` / `fct` / `ops` / `ref` **不可再生** —— 指标公式、页面布局、权重绑定、自选分组、历史评分、审计流水，丢了没有第二份。体积不到几十 MB。

据此分三档，全部由 `app/ops/backup.py` 承担，入口 `python -m app.operations.backup <kind>`（或安装后的 `ft-backup`）：

- **每日 22:30** — `pg_dump -Fc` 只导 `config,fct,ops,ref` 四个 schema，保留 30 份
- **每周日 23:00** — `pg_dump -Fc` 全库（含 `md`），保留 8 份
- **每 4 周六 23:30** — 全库 dump + `pg_dumpall --globals-only` + 一次 `pg_basebackup`，保留 180 天

三条容易踩的坑，说明书里写死：

1. **单库 dump 不含角色和密码。** `pg_dump financetool` 导不出 `ft_reader` / `ft_app` / `ft_etl` / `ft_admin` 这四个角色，换机器恢复后所有 DSN 全部认证失败。所以月度必须带 `pg_dumpall --globals-only`。
2. **直接复制 `D:\finance\TataPG` 目录不是通用备份。** 物理拷贝要求：服务已停、目标机 PG 大版本一致（17.x）、同平台。而且它会把已经损坏的页面一起复制过去 —— 旧库 `tq_minline_2026.db` 就是这么烂掉且无人察觉的。要跨机器搬，用 `pg_dump` 的逻辑备份。
3. **没验证过的备份不算备份。** 每次 dump 完自动恢复到临时库 `financetool_verify`，比对 11 张关键表的行数，比对通过才删临时库并把结果写进 `operations.quality_result`；不通过退出码 2。

不需要任何图形客户端。pgAdmin 只是可选的查看工具，备份是 `pg_dump.exe` 的事。计划任务用 `scripts\setup_backup_task.ps1` 注册（管理员 PowerShell），日志落 `logs\backup_*.log`，当前状态看 `python -m app.operations.backup status`。

SQLite 时代"复制文件即备份"的便利没有了，这是换 PG 必须接受的账；换来的是这套备份本身可被验证。

不做 MCP/HTTP 网关。智能体与库同机，MVCC 已解决锁问题，多一层是纯开销。

### 9.5 板块主键命名空间分裂（阻断级）

实测：

- `market_data.sector_daily` 的 653 个板块码**全部**是 `TDX_` 前缀
- `reference_data.sector_member` 的 748 个板块码分布在 `GN_`(268) / `TDX_`(217) / `FG_`(154) / `ZS_`(109)
- 两边的交集是 **0** —— 有日线的 653 个 `TDX_` 行业板块，一条成员记录都没有；
  有成员的 217 个 `TDX_` 板块（类型是"自定义"），一根日线都没有
- 653 个有日线的板块里，422 个的 6 位块号在成员表里以**另一个前缀**存在

成因：旧库对同一个通达信板块用两套命名登记，B2/B3 各自忠实迁移，
于是两侧的键从来就对不上。表现是 `sector_heat` 一只票都算不出来，
而它在 `env_resonance` 里占 65%、`env_resonance` 在 `oper_score` 里占 60%，
**四象限的 Y 轴实际上只剩大盘情绪**，且不报错。

修法：以 6 位块号为准归一到单一命名空间，`sector_type` 取更具体的那一份
（`概念`/`风格`/`地区` 优先于 B2 给 `TDX_` 一律打的 `行业`），
合并重复的 `reference_data.sector_info` 行并重映射 `reference_data.sector_member`。
这同时修掉另一个错误：`TDX_880501/行业/含H股` 这类把概念板块标成行业的行 ——
`indicators.sector_map()` 正是按 `sector_type = '行业'` 取个股主行业的。
