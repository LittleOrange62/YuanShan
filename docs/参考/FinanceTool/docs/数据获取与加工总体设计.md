# 数据获取与数据加工：总体设计（v3 · 2026-08-31 夜）

> **v3 相对 v2 改了什么**（v2 的判断有几条已经过时或被推翻）：
>
> 1. **P0 通达信 GUI 盘后下载已经跑通并固化**（v2 §附注还写着"走不通、分钟线保持手动"）。
>    入口 `scripts/ops/p0_tdx_predownload.py`，日线 10s、1 分钟线 4.5min、5 分钟线 3.2min。
>    所以"一键获取最新数据"这件事**现在真的可以从关软件那一步开始算**。
> 2. **补上「每交易日 × 数据类型」的采集进度矩阵设计**（用户新要求）：日期不用手选，
>    缺口自己标出来，补录按钮跟着数据类型走、可横跨多个日期，标签页顶部一个「一键补录」。
> 3. **顶部条落到具体实现**：`app/web/app.py` 的抬头行加"数据最新到 X"+ 一键按钮。
> 4. **运维两页功能点全梳理**（谁管取数、谁管加工、哪些是半成品），并把「当前有效权重」
>    那张卡从 `/scores` 搬到 `/data`。
> 5. **现状数字全部按 08-31 收盘后实测重写**：v2 说"库里最新 08-28"已经不成立，
>    但**新暴露出三个真缺口**（板块热度停 08-28、资金流是空表、两融/ETF 份额落后），
>    见 §0.2。这三个正好是"降级 + 补算"要治的对象，不是假想场景。

这份文档回答五个问题：

1. `/datasource`（数据获取）和 `/data`（数据加工）现在**到底有哪些功能点、哪些是半成品**；
2. 每个交易日的采集进度**怎么展示**才不用手选日期，补录按钮怎么摆；
3. 收盘后要**自动**跑完「P0 下载 → 入库 → 二次加工」，缺的是哪几块；
4. 源不稳定时的**重试 / 手动取值 / 降级 / 补算**四件事怎么定义、存哪张表、页面在哪看；
5. 全站顶部那行"数据最新到哪天 + 一键获取最新数据并跑分"怎么做。

写作原则不变：**先如实记录现状（带实测证据），再写目标设计，最后拆成可验收的批次**。
每条设计都要能落到一张表、一个脚本、一个卡片上。

### 0.2 三个真缺口（这就是降级/补算要治的对象）

- **`analytics.sector_heat_daily` 停在 08-28**：`d3_sector_trend` 没跑。它是 `d4_ignition` 的输入，
  所以启动点也停着。这属于"骨干加工漏跑"，不是源不稳 —— **调度器要治的第一类问题**。
- **`market_data.market_fund_flow` 是空表**：`ak_fundflow_em` 实测 `RemoteDisconnected`（`down`）。
  这就是每天 `fill_all` 退出码 3 的主要来源。**这类是"三轮全源失败"的真实样本**，
  而且现在只登记了一个源，连"换源"都无从谈起（见 §6.2 要给它加 `em_datacenter` 直连）。
- **`market_data.etf_share` / `market_data.margin_detail` 落后一天**：两融和 ETF 份额是 T+1 发布，
  盘后当天本来就没有。**这不是缺口，是"这一天本就不该有"** —— 矩阵上必须能区分
  「缺」和「不适用」，否则每天都有两格红的，人会开始无视红色。

### 0.3 `operations.data_ready` 是空表 → 两条链是断的

`config.job` 里 `trigger_kind='on_ready'` 的有 4 个（`calc_base`、`calc_breadth`、
`calc_vol_double`、`quality_audit`），它们的判据全是 `operations.data_ready`。
表是空的、也没有任何代码在写它 —— `app/db/repo/operations.py` 里 `mark_ready()` / `is_ready()`
**函数在、调用点缺**。所以"日线到了就自动算因子"这条链**从来没有成立过**，
现在能有数据全靠人点 `fill_all`。

### 0.4 没有任何调度进程

`config.job.cron_expr` 有值（`sync_daily` 是 `10 15,16,17 * * 1-5`），但**没有任何进程在读它**，
也没有注册 Windows 计划任务。`operations.task` 最近几行说明了现在的真实工作方式：

```
11 quality_audit    08-31 22:19  failed     退出码 3（有规则没通过，其实算跑完了）
10 sync_etf_share   08-31 21:19  succeeded  2026-08-24 1615 只 净申赎 +98.77 亿份
 9 fill_all         08-31 21:19  failed     退出码 3221225786 = 0xC000013A（被 Ctrl+C／终止）
```

三件事一眼可见：**全是人点出来的**；`max_retry` 存了 2 但没人读（`attempt` 一直是 0）；

## 2. 页面设计

### 2.1 采集进度矩阵（用户第 1 点）

**目标**：打开 `/datasource` ① 就能看出"最近这些交易日，每类数据到齐了没有"，
不用先选日期；缺的地方自带补录按钮，补录**按数据类型横跨多个日期**。

**布局**（替换现在的「手动采集」表，作为标签 ① 的第一张卡）：

```
[近 10 交易日 ▾]  [只看有缺口的 ☐]           [⚡ 一键补录全部缺口 (7)]
                08-19 08-20 08-21 08-24 08-25 08-26 08-27 08-28 08-31   ⟳
P0 vipdoc 日线    ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
P0 vipdoc 分钟线  ○     ○     ○     ○     ○     ○     ○     ○     ●    [补这一行]
个股日线          ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
指数日线          ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
板块日线          ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
ETF 份额          ●     ●     ●     ●     ●     ●     ●     ●     –    [补这一行]
两融明细          ●     ●     ●     ●     ●     ●     ●     ●     –    [补这一行]
龙虎榜            ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
大盘资金流        ×     ×     ×     ×     ×     ×     ×     ×     ×    [补这一行]
──────────────── 加工 ────────────────
基础因子          ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
评分              ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
板块热度/趋势     ●     ●     ●     ●     ●     ●     ●     ●     ○    [补这一行]
启动点            ●     ●     ●     ●     ●     ●     ●     ●     ○    [补这一行]
情绪读数          ●     ●     ●     ●     ●     ●     ●     ●     ●    [补这一行]
质量审计          ●     ●     ●     ●     ●     ●     ●     ●     ⚠    [补这一行]
```

**五种格子状态，含义不许混**：

- `●` 齐：行数达到该数据集的 `expect_min_rows`
- `◐` 部分：有行但不足阈值（例：个股日线只有 800 行 → 大概率抓了一半）
- `○` 缺：一行都没有，而这一天**应该有**
- `–` 不适用：这一天本就没有（T+1 未发布、非交易日、当天无龙虎榜）→ **灰色，不计入缺口数**
- `×` 阻断：`operations.data_gap.state='blocked'`（三轮全源失败）；`⚠` 降级：有 `operations.compute_degrade` 未 resolved

**交互**：

- 点**单格** → 只补 `(dataset, date)` 这一格
- 点**行尾「补这一行」** → 该 dataset 在**当前视图全部日期**上的缺口一起补（横跨多日，用户明确要求）
- 点**顶部「一键补录全部缺口 (N)」** → 所有 `○`/`×`/`◐` 格按依赖顺序补一遍；
  **N 是实数**（`–` 不算），N=0 时按钮禁用并显示"无缺口"
- 悬停格子 → 行数、来源（`operations.ingest_batch.source`）、写入时间、上次失败原因
- 所有可补的格子/按钮都带同一个标识（`bi-arrow-repeat` 图标 + 黄框），**一眼能扫出"哪里要点"**

**数据来源（性能是硬约束）**：**一次查询**出整张矩阵，不许每格一条 SQL。

- 事实来源 = `operations.view_coverage`（**已存在，但现在只 UNION 了 3 张表**）扩成按
  `config.dataset` 登记的全部数据集；叠加 `operations.data_gap`（状态）与 `operations.compute_degrade`（降级）
- 日期轴 = `reference_data.trade_calendar` 里 `is_open` 的最近 N 天，**不是** `generate_series`
- 阈值与"这天该不该有" = `config.dataset` 的 `expect_min_rows` / `lag_days`（T+1 的填 1）
- ⚠️ 不用"打开页面就扫 6 张大表 count(*)"的实现：`market_data.stock_daily` 628 万行，
  9 个数据集 × 每次刷新一遍 = 页面点一下卡好几秒。矩阵读的是**聚合视图**，
  真正的重活在入库时写 `operations.data_ready`（§5 的 P1）

**执行入口**：新增 `scripts/ops/e4_backfill.py --dataset X --from d1 --to d2`。
它只做一件事：把 `(dataset, 日期区间)` 翻译成对应 runner 的调用并串起来（含依赖：
补板块热度会自动先确认评分在）。页面按钮 = 提交一个 `operations.task`，复用现有 3s 轮询。

## 3. 自动化与容错（用户第 5 点）

### 3.1 一句话架构

> **调度器只做一件事：把"数据日期上的缺口"翻译成任务。**
> 取数按「数据集 × 源优先级」竞速，三轮全源失败就把该数据集标 `blocked`；
> 加工读 `operations.data_ready`，缺非骨干分量时**降级计算并登记**，缺口补上后由
> `operations.recompute_queue` 触发重算。**所有状态都在库里，页面只是它的视图。**

```
15:30 收盘线
   │
   ├─ e3_scheduler（常驻，60s 一 tick，PG advisory lock 防双开）
   │     ① 算目标交易日            tradeday.target_date()
   │     ② 列缺口 dataset × date   config.dataset ⨯ operations.view_coverage
   │     ③ 到点/就绪 → 建 operations.task（cron / on_ready / chain 三种触发都在这里解释）
   │     ④ 失败任务按 max_retry + 退避表重排（轮次 round）
   │
   ├─ P0（15:32）  p0_tdx_predownload.py：关进程 → 开 → 登录 → 盘后下载日线+分钟线
   │                失败 → 杀干净通达信相关进程从头再来，最多 N 轮
   │
   ├─ 取数：fetch(dataset, date)
   │     一轮 = 按 config.dataset_source.display_order 依次试完所有启用的源
   │     本地源（tdx_vipdoc / ths_local_*）永远 display_order 最小
   │     每次尝试写一行 operations.fetch_attempt（round, datasource_key, ok, ms, err）
   │     成功 → 写 md.* → 阻断级质量规则通过 → 写 operations.data_ready
   │     三轮全败 → operations.data_gap.state='blocked'
   │
   └─ 加工：compute(target, date)
         骨干缺（日线）→ 不算，停在这里（等价现在的退出码 1/2）
         非骨干缺（两融/龙虎榜/资金流/分红）→ 降级算 + 写 operations.compute_degrade
         缺口后来补上 → scheduler 发现 → operations.recompute_queue → 重算并清降级标记
```

### 3.2 三层重试，别混在一起

| 层 | 谁负责 | 次数 / 间隔 | 失败后 |
| --- | --- | --- | --- |
| **L1 单次调用** | `registry.call()`（已有） | 同一个源 3 次，退避 `1.5^n` | 记 `degraded`，抛 `DataSourceError` |
| **L2 一轮 = 全源竞速** | 新增 `app/datasource/fetch.py` | 按 `config.dataset_source.display_order` 把该 dataset 的**所有启用源**试完 | 每次尝试写 `operations.fetch_attempt`；本轮无源成功 → `data_gap.state='retry_wait'` |
| **L3 轮次** | `e3_scheduler` | **3 轮**，间隔 `5min / 30min / 60min`（存 `config.setting`） | 三轮全败 → `blocked` → 进降级路径 |

规则细节：

- **本地源永远排最前，且失败不算"源不稳"**：`tdx_vipdoc`、`ths_local_*` 的 `is_local=true`。
  它们失败通常意味着"文件还没生成"（P0 那一步还没跑），不是"源坏了"，不该把 health 标红
- **sticky 状态轮内直接跳过**：`no_permission` / `broken` 的源不占重试次数（`registry.STICKY` 已有此语义）
- **口径优先**：网络兜底源写进来的行 `need_overwrite=true`；主源补下来后用 `--overwrite`
  覆盖回通达信口径，并**重算派生列**（`pre_close` / 涨跌停 / 换手率）。
  只换 OHLC 不重算前收 = 一天前收来自旧源、涨跌幅算不对的混合状态
- **手动取值**（用户明确要求）：`/datasource` ① 的矩阵格子点开支持"指定源"
  （默认自动按优先级）+ "覆盖已有"。手动一次也写 `operations.fetch_attempt`（`round=-1` 表示人工），
  所以"人工补过"在历史里看得见

### 3.3 稳定源与不稳定源（用户强调的那条）

**稳定（P0，本地文件，不受网络影响）**：通达信 `vipdoc`（97,468 个 `.day`）、
同花顺本地 ini（板块 1,015 / 行业 90 / 自选 43 组）。这两类是**唯一可以当"必然拿到"的源**，
所以它们进 `p0` 层、`display_order=0`、`is_local=true`。

**不稳定（网络）**：akshare 系、东财、新浪、Tushare（配额按接口 1 次/分钟，只能当手工兜底）。
它们的定位是**补充**：三轮全源失败就降级，不阻塞主链。

### 3.4 降级与补算（用户第 5 点的后半段）

**先分清骨干与辅助** —— `e1_fill_all.STAGES` 已经有这个划分，沿用：

- **骨干**：日线（个股/指数/板块）、基础因子、评分、板块热度趋势。
  缺日线 = **不算**，停在这里（现在的退出码 1/2）。**不允许降级**：
  降级一个没有价格的评分毫无意义
- **辅助**：ETF 份额、两融、龙虎榜、资金流、分红、股本、启动点、个股趋势分。
  三轮全败 → 按 `level='partial'` 降级：**把缺失分量的权重按剩余分量重新归一化**，
  并在 `operations.compute_degrade.weight_note` 写清"哪个分量缺、权重怎么摊的"

**三档降级**（`operations.compute_degrade.level`）：

- `full`：完整
- `partial`：分量缺，权重重归一化（例：资金流缺 → `market_mood` 里那 0.2 摊到其余分量）
- `stale`：沿用上一交易日值，**仅限截面类**（股本、行业归属这种一天不变的），
  时序类（涨跌幅、资金流）**禁止 stale**

**降级必须看得见，不允许静默**：

- `/scores`、`/review` 等用到评分的卡片，当天有降级记录时脚注挂一行
  「⚠️ 本日为降级计算：缺 两融、资金流；这两项权重已摊到其余分量」
  —— 静默降级比空表危险，用户会拿一个看起来正常的数字做决策
- `/data` ③ 的「降级与缺口」卡：`operations.data_gap` 非 ready 行 + `operations.compute_degrade`
  未 resolved 行，各带「立即重试」按钮
- 矩阵上对应格子显示 `⚠`

**补算**：某个 `(dataset, date)` 从 `blocked` 转 `ready` 时，scheduler 把所有引用它的
未 resolved `compute_degrade` 转成 `recompute_queue` 行 → 重跑对应 compute 脚本
（脚本本来就是按日期幂等的 UPSERT）→ 成功后写 `resolved_at` / `recomputed_at`。
**每日摘要报告"今天补算了哪几天"**，否则补算成功与失败都没人知道。

### 3.5 调度器 `scripts/ops/e3_scheduler.py`

- **一个常驻进程**，不是给每个作业注册一条 Windows 计划任务。理由：依赖链（`after_job`）、
  就绪触发（`ready_on`）、退避重试都需要一个知道全局状态的东西
- **Windows 侧只注册两条**：开机自启（`schtasks /sc onstart`）+ 每日 15:35 的"催一下"兜底
  （进程死了也能补跑当天）
- **防双开**：`pg_try_advisory_lock`，拿不到就退出并打印谁在跑
- **心跳必须显示**（`config.setting['scheduler_heartbeat']`）：否则调度器死了，
  页面看起来和"今天没数据"一模一样
- **幂等**：判据是"库里有没有这一天的数据/ready 行"，不是"现在几点"。
  机器 16:00 才开机也会把 15:35 该做的补上
- **`only_trade_day` / `concurrency_key`** 表里已有，scheduler 必须读：
  非交易日不排 ingest；同 key 串行，避免两个脚本同时写 `market_data.stock_daily`
- **输出实时回显不落盘**（项目已踩过两次的坑）：长任务把输出吞进文件会被当成卡死

**默认时刻表**（写进 `config.job.cron_expr`，可在 `/jobs` 改）：

- `15:32` **P0 通达信盘后下载**（`tdx_predownload`）—— 要交互式桌面
- `15:45` 本地源优先的当日追平（`sync_catchup`）
- `16:10 / 17:10 / 18:10` 三轮重试窗口（只处理 `operations.data_gap` 里非 ready 的行）
- 就绪触发：日线 ready → `calc_base` → `calc_scores` → `{calc_sector_trend → calc_ignition,
  calc_score_trend, build_review}`；`calc_breadth` / `calc_vol_double` 挂日线 ready
- `19:30` 兜底 `calc_scores_fallback`（已在表里）
- `20:00` `daily_digest` 摘要 + **降级清单**推送
- `20:30` 质量审计追平（`quality_audit`，缺几天补几天）
- `21:00` 备份：`pg_dump` 只导 `config`/`fct`/`ops`/`ref`（§8.1）

## 7. 明确不做

- **不引入 Airflow / Celery / Redis**：单机单人，PG + 一个常驻进程足够
- **不做无限重试**：三轮之后转人工/降级。无限重试会把跑批拖死，还会把源打到限流
- **不让网络源静默覆盖通达信口径**：`need_overwrite` + `market_data.view_daily_source` 保留可追溯性
- **不静默降级**：降级一定有台账、有页面提示、有摘要报告
- **不把 P0 当成"无人值守也一定成"**：它要交互式桌面（抢前台 + 真实鼠标点击）。
  锁屏/无人登录时它会在会话自检那一步照实退出，**由 TQ 接口那一级接手**，
  不假装成功（`p0_tdx_predownload.py` 的出口码 2 就是这个语义）
- **不引外部 skill 的数据口径**：金融虾那 11 个 skill、`yuanshan` 这些只借职责切分
  （`config.job.kind` 预留 `monitor` / `research` 两类），实现走自己的库 ——
  外部的复权口径、板块口径和我们不可比，混进来就是同一条曲线两种口径
