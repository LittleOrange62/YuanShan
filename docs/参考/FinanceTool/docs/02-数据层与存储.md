# 数据层与存储

本文档回答两个问题：**用 PostgreSQL 对现状改动影响大吗？智能体怎么访问？**

## 一、结论先说

用 PostgreSQL。改动面比直觉小，收益直接命中已实测到的病根。

**改动面（基于实测扫描）**

```
D:\finance\脚本 : 199 个碰库脚本 / 147 只读 / 52 有写
                  32 用 INSERT OR REPLACE / 34 用 PRAGMA / 6 用 ATTACH
D:\financeWeb   :  14 个碰库脚本 /   3 只读 / 11 有写
```

199 个碰库脚本听起来很多，但 **147 个是只读**。只读脚本的迁移成本近乎为零：

```python
# 之前
conn = sqlite3.connect(r'D:\finance\data\tq_daily_2026.db')

# 之后
conn = psycopg.connect(os.environ['FT_DSN'])
```

SQL 本身大多不用改——`SELECT ... WHERE trade_date=%s ORDER BY ...` 在两边都成立。

真正需要改语法的只有三类，且高度集中：

| 改动项 | 涉及文件数 | 改法 |
|---|---|---|
| `INSERT OR REPLACE` | 32 | → `INSERT ... ON CONFLICT (security_code, trade_date) DO UPDATE SET ...` |
| `PRAGMA journal_mode/synchronous/mmap_size` | 34 | 直接删掉，PG 无此概念 |
| `ATTACH DATABASE` 跨库 JOIN | 6 | 删掉，PG 单库多 schema，跨"库"JOIN 天然可用 |
| 年份分库路径拼接 | ~10 | 删掉，改为分区表，代码不再关心年份 |
| 占位符 `?` → `%s` | 全部有参数化的 | 机械替换，可脚本化 |
| `LOCKED` 重试逻辑 | 数个 | 删掉，MVCC 不需要 |

按文件计，需要人工判断的大约 **50–60 个文件**，其余是机械替换。而且这里面有相当比例是 `ceo/temp` 下的一次性探测脚本（160 个），本来就不该迁移，直接弃用。

**收益（不是理论，是当场观测到的）**

- 会话中 `tq_minline_2026.db` 的 `stock_minline` 表**连只读计数都返回 LOCKED**，因为同时有进程在写。PG 的 MVCC 下读永不被写阻塞，这个问题从根上消失。
- `04_数据清洗` 里存在 `temp_del.py` / `temp_del2.py` 两个锁重试变体 —— 说明锁冲突已经真实发生过并迫使写补丁。
- 37 GB 单文件的 SQLite 已经接近实用上限；PG 分区表 + BRIN 索引处理这个量级是常规操作。
- 4 个智能体并发写，SQLite 只有"整库写锁"一档粒度；PG 是行级锁。

**成本（诚实列出）**

- Windows 上装一次 PostgreSQL 服务，配置 `postgresql.conf`（shared_buffers、work_mem、max_connections）
- 备份需要自己做（`pg_dump` / `pg_basebackup` + 计划任务），SQLite 时代"复制文件即备份"的便利没有了
- 一次性迁移窗口：9,531,333 行日线 + 分钟线，用 `COPY` 导入
- 多一个需要监控的服务进程

**不推荐的替代路径与原因**

- 继续 SQLite：并发写是本项目的核心矛盾，SQLite 结构上解决不了
- DuckDB：分析性能极好，但**单写入者**模型，多智能体并发写场景不适用（可作为只读分析副本，见下）
- Parquet 湖 + DuckDB：适合追加式历史数据，但配置类小表和频繁 upsert 场景不合适，且失去事务

## 二、最重要的一点：顺序

**先把口径约束立起来，再换存储。** 顺序反了的话，PG 只是把今天的混乱换个地方重演——199 个脚本从裸连 199 个 SQLite 文件，变成裸连一个 PG，照样没人管谁写了什么、单位对不对、有没有并发冲突。

所以正确顺序是：

1. 建库时就把约束写进 schema：CHECK、单位一致性触发器、写审计触发器、四个角色
2. 建 `app/db/repo/*` 与 `ftdb` 作为顺手的统一入口（省事用，不承担兜底责任）
3. 迁移存储到 PG
4. 逐批把存量脚本切到新入口，切完即弃用旧路径

第 3 步和第 1、2 步的先后可以调整，但**第 4 步必须发生**，否则前三步都是白做。

关键判断：**兜底责任放在库层，不放在应用层。** 应用层的校验函数，下一个写脚本的人可以不调用；库层的约束和触发器，任何连接、任何语言、任何工具都绕不过去。这也是能安全去掉 MCP 网关的前提，详见 `07-多智能体直连规范.md`。

## 三、智能体怎么访问

智能体与库同机，直连 PG，不再经 MCP/HTTP 封装。四种方式，按推荐度排序。

### 方式 A（推荐）· `ftdb` 共享库

`pip install -e D:\FinanceTool` 之后 `import ftdb` 即用，默认走 `ft_reader` 只读角色。

```python
import ftdb
df = ftdb.daily('600367', '2026-01-01', '2026-08-25')
d  = ftdb.latest_trade_date()
rows = ftdb.query('SELECT security_code, close FROM market_data.stock_daily WHERE trade_date = %s', (d,))
```

写入用 `ftdb.batch()`，它会开 `operations.ingest_batch` 记血缘，异常时自动标记失败：

```python
with ftdb.batch('my_agent_import') as b:
    ftdb.upsert_daily(rows, batch_id=b.id)
```

好处：连接池、角色、超时、血缘、单位字段名都是现成的，不用每个脚本自己攒一遍。

### 方式 B · 直接 psycopg

不想装库、或者用别的语言时。DSN 从 `.env` / 环境变量读，**不硬编码**（现状把通达信明文口令写在 3 个 `.ps1` 里）。写入照样受库层触发器约束。

### 方式 C · psql 命令行

一次性排查、导出用。`psql -U ft_reader -d financetool -c "..."`。

### 方式 D · pgAdmin 4

人肉看数据、看执行计划用。

四种方式的共同前提：**权限由 PG 角色决定，不由调用方自觉**。`ft_reader` 只有 `SELECT`，它连不上写路径；`ft_etl` 能写 `md`/`ref` 但 `statement_timeout` 30 分钟封顶。

现状的反面教材：`/api/sql/execute` 只黑名单 `select`/`with` 开头，`ATTACH DATABASE '任意路径' AS x` 就能绕过库白名单和只读限制；`sql_api_auth_enabled` 默认 `False` 且监听 `0.0.0.0`。新系统里这类风险由"只读角色 + `default_transaction_read_only`"从根上消掉，而不是靠字符串匹配。

### 页面上的 SQL 控制台

Web 侧确实需要一个查询框（旧 `/sqlite` 页面的正经替代）。它用 `ft_reader` 连接，并且用 sqlglot 解析语法树确认是单条 `SELECT`（不是字符串前缀判断），自动补 `LIMIT`。即使这层判断被绕过，角色权限也写不了数据。

### 只读分析副本（可选加速）

如果后续因子回溯的扫描量成为瓶颈，加一层：PG 逻辑复制或定时导出 Parquet → DuckDB 只读查询。这是纯加法，不影响上面几种方式。

## 四、Schema 设计

单库 `financetool`，按 schema 分域：

| schema | 内容 |
|---|---|
| `md` | market data — 行情 |
| `ref` | reference — 证券基础信息、板块、日历、股本、分红 |
| `fct` | factor — 因子与打分结果 |
| `config` | config — 配置、策略注册表、自选股 |
| `ops` | operations — 任务、审计、血缘、日志摘要 |

### market_data.stock_daily（分区表）

```sql
CREATE TABLE market_data.stock_daily (
    security_code       text        NOT NULL,   -- '600367.SH'
    trade_date    date        NOT NULL,
    open          numeric(12,4),
    high          numeric(12,4),
    low           numeric(12,4),
    close         numeric(12,4),
    pre_close     numeric(12,4),
    change        numeric(12,4),
    pct_change       numeric(10,4),
    volume_shares    bigint,                 -- 单位：股（名字自带单位）
    amount_yuan   numeric(20,2),          -- 单位：元
    turnover_rate numeric(10,4),
    limit_up      numeric(12,4),          -- 按板块规则计算，非一刀切 1.1
    limit_down    numeric(12,4),
    adjustment_factor    numeric(16,8),          -- 真实复权因子，非硬编码 1.0
    source_batch_id  bigint,                 -- → operations.ingest_batch
    updated_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (security_code, trade_date)
) PARTITION BY RANGE (trade_date);

CREATE TABLE market_data.stock_daily_2026 PARTITION OF market_data.stock_daily
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
-- 2021..2025 同理

CREATE INDEX ON market_data.stock_daily (trade_date);
CREATE INDEX ON market_data.stock_daily USING brin (trade_date);
```

分区替代了年份分库。代码里不再有 `_get_year_db_path` / `trade_date[:4]` 路由 / `ATTACH prev_db` 这类逻辑，跨年查询是一句普通 SQL。

### market_data.stock_minute（分区表）

```sql
CREATE TABLE market_data.stock_minute (
    security_code    text NOT NULL,
    dt         timestamptz NOT NULL,      -- 完整时间戳，不再有 LO_BASE 魔法常量
    period     smallint NOT NULL,         -- 1 | 5
    open       numeric(12,4),
    high       numeric(12,4),
    low        numeric(12,4),
    close      numeric(12,4),
    volume_shares bigint,                    -- 股
    amount_yuan numeric(20,2),            -- 元
    source_batch_id bigint,
    PRIMARY KEY (security_code, dt, period)
) PARTITION BY RANGE (dt);
```

按月分区。当前 37 GB 单文件的痛点在这里解决。

`.lc1` 里那个 `LO_BASE=45881` / `DATE_BASE=2026-08-25` 的魔法锚点在新解析器里被彻底移除——用交易日历表反查日序，见 [03-数据获取与同步.md](03-数据获取与同步.md)。

### reference_data.security

```sql
CREATE TABLE reference_data.security (
    security_code    text PRIMARY KEY,
    symbol     text NOT NULL,             -- '600367'
    market     text NOT NULL,             -- SH | SZ | BJ
    name       text,
    pinyin     text,                      -- 全拼（来自 .tnf）
    pinyin_abbr text,                     -- 首字母
    board      text,                      -- 主板|创业板|科创板|北交所  ← 决定涨跌停幅度
    asset_type text NOT NULL,             -- stock|index|etf|sector
    list_date  date,
    delist_date date,
    is_active  boolean NOT NULL DEFAULT true
);
```

`board` 字段是必需的：现状 `limit_up = pre_close * 1.1` 对创业板/科创板（20%）和北交所（30%）全错。

### reference_data.trade_calendar

```sql
CREATE TABLE reference_data.trade_calendar (
    calendar_date   date PRIMARY KEY,
    is_open    boolean NOT NULL,
    prev_open_date  date,
    next_open_date  date
);
```

表驱动，节假日真实存在。现状 `scheduler.py:229-242` 三个 return 全是 `weekday() < 5`，节假日照样触发任务。

### config.strategy / config.strategy_binding

策略注册表，块 2 的核心，详见 [04-调度与策略注册表.md](04-调度与策略注册表.md)。

### operations.ingest_batch（血缘）

```sql
CREATE TABLE operations.ingest_batch (
    batch_id     bigserial PRIMARY KEY,
    source       text NOT NULL,           -- 'vipdoc/sh/lday' | 'tqcenter/snapshot'
    source_path  text,
    source_mtime timestamptz,
    target       text NOT NULL,           -- 'market_data.stock_daily'
    row_count    bigint,
    started_at   timestamptz NOT NULL,
    finished_at  timestamptz,
    status       text NOT NULL,           -- running|ok|failed
    message      text
);
```

任何一行数据都能回答"从哪个文件、哪个时刻、哪一批进来的"。

### operations.audit

```sql
CREATE TABLE operations.audit (
    id         bigserial PRIMARY KEY,
    occurred_at         timestamptz NOT NULL DEFAULT now(),
    actor      text NOT NULL,             -- 智能体/用户标识
    channel    text NOT NULL,             -- mcp|rest|web|worker
    action     text NOT NULL,             -- 工具名或路由
    params     jsonb,
    rows_affected bigint,
    ok         boolean,
    error      text
);
```

多智能体环境下没有审计等于没有可追溯性。

## 五、迁移路径

| 阶段 | 动作 | 验收 |
|---|---|---|
| M1 | 装 PG，建 schema 与分区 | `python scripts\init_db.py` 反复跑结果一致，`operations.schema_migration` 记下四个文件的 sha256 |
| M2 | 写新解析器 + 新 ETL，**双写**：既写旧 SQLite 也写 PG | 同一交易日两边行数与抽样值一致 |
| M3 | 历史回填：SQLite → `COPY` 进 PG | 日线 9,531,333 行全量对账，逐年比对行数与 checksum |
| M4 | 只读侧切换：Web 与智能体读 PG | 页面数据与旧系统一致 |
| M5 | 停旧 ETL，PG 成为唯一写入目标 | 旧 SQLite 转为归档只读 |
| M6 | 存量脚本按目录批次切到 `ftdb` / repo | `脚本/` 下无裸 `sqlite3.connect` |

M3 的对账不能省。两套现存系统行数差 1.8%（9,531,333 vs 9,359,339），迁移时必须查清每一条差异归因（A 股前缀白名单 / `880*` 伪代码 / `asset_type` 分类），而不是选一个数字了事。

## 六、连接与并发配置

```ini
# postgresql.conf 起点（按机器内存调整）
max_connections = 100
shared_buffers = 4GB
work_mem = 64MB
maintenance_work_mem = 1GB
effective_cache_size = 12GB
wal_compression = on
checkpoint_timeout = 15min
```

应用侧连接池：`web` 10 连接、`api` 20、`worker` 10、留给智能体直连 30。

角色划分：

```sql
CREATE ROLE ft_reader LOGIN PASSWORD '...';   -- 仅 SELECT
CREATE ROLE ft_etl    LOGIN PASSWORD '...';   -- md/ref 的 INSERT/UPDATE
CREATE ROLE ft_app    LOGIN PASSWORD '...';   -- 全部业务表读写，无 DDL
CREATE ROLE ft_admin  LOGIN PASSWORD '...';   -- DDL、迁移
```

智能体默认发 `ft_reader`；需要写的按需给 `ft_app` 或 `ft_etl`。

## 七、备份

| 频率 | 方式 | 保留 |
|---|---|---|
| 每日 22:00 | `pg_dump -Fc` 全库 | 7 天 |
| 每周日 | `pg_basebackup` | 4 周 |
| 持续 | WAL 归档到另一磁盘 | 7 天 |

备份脚本纳入计划任务并有失败告警。SQLite 时代"复制文件"的省事没有了，这是换 PG 必须接受的账。
