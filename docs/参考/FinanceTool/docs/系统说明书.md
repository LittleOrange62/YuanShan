# FinanceTool 股票复盘系统 · 程序说明书

版本 1.0 ｜ 基线日期 2026-08-27 ｜ 代码根目录 `D:\FinanceTool`

---

## 一、这个系统是什么

一套自用的 A 股盘后复盘系统。每天收盘后把行情、板块、资金、龙虎榜落进本地
PostgreSQL，算出个股与板块的评分，在网页上按"大盘 → 板块 → 个股"的顺序
复盘，并把选出来的票放进自选池跟踪。

它替代的是 `D:\financeWeb`（旧系统，Dash + 8 个按年分库的 SQLite + MCP 服务层）。
沿用旧系统已经验证好用的部分：Dash + dash-bootstrap-components 的侧栏单页形态、
筛选器的 5 种条件语义、X/Y/操作分的评分口径、自选分组的组织方式。
换掉的部分：SQLite 分库 → 单库 PostgreSQL；MCP 服务层 → 直连（智能体在本机，
不需要中间一层 HTTP）；写死在代码里的公式和页面 → 存进注册表。

### 设计目标：积木城堡

一句话：**能配置的都不要写进代码**。

具体到这个系统里，"配置"指的是 `config` 这一组表。加一个指标、换一个评分公式、
调一个权重、加一张图、加一个页面、加一个定时任务，都是往表里插一行，
在网页上点几下完成，不需要改 Python、不需要重启。

代码里保留的是**能力边界**：哪些计算脚本可以被绑定、哪些命名查询可以被引用、
哪些执行器可以被调度。这条边界是刻意留的 —— 如果配置里能塞任意 SQL 或任意
命令行，`/blocks` 页就变成了远程代码执行入口，那是旧系统 `/api/sql/execute`
的老问题，不重复。

## 二、技术选型（定稿）

| 层 | 选择 | 为什么 |
|---|---|---|
| 数据库 | PostgreSQL 17，数据目录 `D:\finance\TataPG` | 单库替代 8 个 SQLite 分库；需要分区表、窗口函数、jsonb、并发写 |
| 驱动 | psycopg 3 + psycopg_pool，**手写 SQL** | 不引 SQLAlchemy：装 2.x 会顶掉同机旧系统的 1.4；且本项目 SQL 复杂度高，ORM 反而是负担 |
| schema 版本化 | 编号 SQL 文件 + `operations.schema_migration` 存 sha256 | 不引 Alembic，避免"迁移脚本"和"schema 文件"两套真相 |
| 计算 | pandas + 受限表达式 DSL（ast 白名单） | 指标公式要能存进表里、由页面编辑，所以需要一个安全的求值器而不是 `eval` |
| Web | Dash 3.x + dash-bootstrap-components 2.x | 与旧系统同栈，形态熟悉；纯 Python 出交互页，不引前端构建链 |
| 图表 | Plotly（Dash 原生） | 同上，避免 echarts 那一套 JS 打包 |
| 生产 server | waitress | Windows 上比 gunicorn 可用，比 Dash 自带 devserver 稳 |
| 口令哈希 | argon2-cffi | 现代默认，不用自己调 PBKDF2 参数 |
| SQL 校验 | sqlglot | `/sql` 查询台用语法树判断是不是只读，比正则可靠 |
| 通达信自动化 | 纯 `ctypes` Win32 | 不引 pywinauto/pywin32；`SafeEdit` 这类自绘控件必须走底层消息与真实输入 |
| 代码检查 | ruff（E/F/W/I/UP/B/SIM） | 重点是 F821：旧系统 `web/helpers.py` 用了 `dbc.Alert` 却没 import，四处 NameError |
| 测试 | pytest | — |

**明确不引入**：SQLAlchemy、Alembic、Vue/React、任何前端构建工具、MCP 服务层。

八个模块的边界：

- **db** — 只管连接、事务、SQL 与 schema 版本。不含业务判断。
- **ingest** — 只把外部数据解析成 DataFrame/行列表，**不写库**。写库由 `scripts/ingest` 的 C 系列脚本用"暂存表 + 单条 INSERT…SELECT"完成。
- **compute** — 因子与评分。脚本只暴露 `run(ctx, params) -> pd.Series`，不自己连库、不自己决定权重。
- **datasource** — 外部源的层级、健康与配额。回答两件事："该先用谁"（`layer`：
  P0 本地 / 主力 / 基座 / 辅助）和"现在哪个源不能用、是坏了还是没权限"（`health`）。
- **orchestrator** — 读 `config.job` 派发 `operations.task`，跑子进程，记状态。
- **web** — 展示与配置维护。取数一律走命名查询，不在页面里写 SQL。
- **tdx_client** — 通达信客户端的 GUI 自动化，独立成包，别的模块不依赖它。
- **scripts** — 一次性与周期性作业的入口，命名 `<阶段字母><序号>_<对象>.py`（B=迁移 C=采集 D=计算）。

### 三条硬规矩

1. **血缘强制**：`md.*` 每张表都有 `source_batch_id NOT NULL`，指向 `operations.ingest_batch`。任何写入必须先 `begin_batch` 再 `end_batch`，用 try/except/finally 包住。

## 五、注册表机制：积木怎么拼

### 5.1 计算的三级结构

```
config.capability   功能点 —— 插槽。"个股质量"是一个插槽
      ↓
config.script       脚本 —— 积木。builtin/quality_xingtai.py 是一块积木
      ↓
config.binding      绑定 —— 插法。哪个插槽用哪几块积木、各占多少权重
      ↓
config.view_effective_binding  视图对 enabled 的行自动归一化
```

关掉一个子因子，剩下的权重自动按比例补上，不用手工把和凑成 1。
页面同时显示 `raw_weight` 和 `eff_weight`，让归一化这件事看得见。

内置脚本共 19 个：

- 个股质量 X：`quality_xingtai` 形态 .25 ｜ `quality_qushi` 趋势 .25 ｜ `quality_weizhi` 位置 .20 ｜ `quality_chouma` 筹码 .20 ｜ `quality_liangneng` 量能 .10
- 板块热度：`sector_zhangfu` .30 ｜ `sector_guangdu` .30 ｜ `sector_dongliang` .25 ｜ `sector_chengjiao` .15
- 环境共振 Y：`env_sector` .65 ｜ `env_mood` .35
- 操作分：`oper_x` .40 ｜ `oper_y` .60
- 其他：`base_factors`、`market_mood`、`temp_score`、`vol_phase` 量能温度、`vol_stage` 量能阶段、`review_report`

**`config.indicator` 的 34 个基础因子**由 `scripts/compute/d1_indicators.py` 用
`app/compute/expr.py` 的受限表达式算出来，加一个因子＝往表里插一行表达式、不改代码。
2026-08-29 新增 7 个（旧系统自选股列表那几列的口径）：

- `chg10_avg` = `MA(pct_change, 10)` —— **近 10 个交易日每日涨跌幅的算术平均**。
  数学上 `Σ(近10日每日涨跌幅)/10 ≡ MA(pct_change,10)`。旧系统这一列是"和 ÷ 9"，
  比正确值小约 1/10；而且它和同表里的 `chg10`（**区间**涨幅）长得一样、含义不同，
  表头中文名分别是「10日日均涨跌」和「10日涨幅」，口径钉在 `tests/test_screener.py`。
- `amp10_avg` / `amp20_avg` = `MA((high - low) / pre_close * 100, n)` 日均振幅。
  振幅**内联写成表达式**而不是引用一个 `amp` 字段：`ALLOWED_FIELDS` 里有 `amp`，
  但 `indicators.py` 的面板 `PANEL_COLS` 里没有这一列，写 `MA(amp,10)` 会静默算不出来。
- `chg20_avg` = `MA(pct_change, 20)`
- `amp_pred` = `MA(amp,20) + SLOPE(amp,20) * 10.5` —— **明日振幅预测**。
  最小二乘直线外推一步：`ŷ(21) = ȳ + b·(21 − x̄)`，20 点时 `x̄ = 10.5`。
  它只说波动大小、**不说方向**，页面上的卡片说明里写明了这一点。
- `avg_price` = `amount_yuan / volume_shares` 成交均价 ｜ `mid_price` = `(high + low) / 2`

**不足窗口长度的票没有值，不是 0**：`expr._roll` 用 `min_periods=n`，所以上市不满
20 天的票不会得到一个用 3 天凑出来的"20 日均值"（这是旧系统"除有效天数"那个 bug 的
反面）。实测 08-28：`amp20_avg` 覆盖 5,525 只、`chg10_avg` 5,534 只、全市场
`amp_pred` 区间 0.47~21.7（单日理论上限 40%）。

**"10 日"数的是有行情的交易日，会跨过停牌段。** 停牌那几天在 `market_data.stock_daily` 里
根本没有行，面板是按"每只票自己的行"排的，所以窗口自动往前多伸几天。实测
（08-28 基准）920138.BJ 杰理科技近 30 个交易日只有 13 天有行情，它的 10 日窗口是
**08-17~08-28**（跨了 12 个自然交易日），手算 `chg10 -1.9952 / amp10 5.4061` 与库里
逐位一致。这是选择而不是 bug：停牌日补 0 会把均值往 0 拽、补前值会造出假的横盘。

**除权不会污染均值。** 除权日的 `pct_change` 已由 `quote_repo.recompute_pct_chg_ex()`
按"上日收盘 × 上日因子 ÷ 当日因子"重算过（见十、已知缺口第 1 条）。实测三只近 20 日
除权的票：603093.SH 南华期货除权日 +0.80%、688501.SH 青达环保 +0.19%、
301172.SZ 君逸数码 +3.63%，窗口内最小涨跌分别 −4.92 / −4.45 / −6.26%，没有任何
"除权当天 −30% 以上"的假跌幅，`chg10_avg` 手算与库里也逐位一致。

**`amp_pred` 用两条互不相干的实现对过答案**：表达式引擎（`MA + SLOPE × 10.5`）
和一条独立的 SQL 最小二乘（`avg(amp) + regr_slope(amp, 21 − rn) × 10.5`）。
取 08-28 amp_pred 最高的 5 只（秋乐种业 21.7221、肯特股份 16.5249、天山生物
16.1855、花溪科技 15.4057、西点药业 15.3464），两边**差值全部为 0.0000**。
旧系统的同名数字**无法对照** —— 旧库 `fin_*.db` 是空壳（见项目基线），
所以只能用"两条独立实现互相验证"代替"和旧值比对"。



### 5.2 页面的两级结构

```
config.menu          导航栏：菜单名、路由、分组、排序、need_role
      ↓
config.page_layout   卡片：第几格、多宽多高、什么类型、引用谁
      ↓
app/web/pages/generic.py  按上面两张表把页面渲染出来
```

`page_key` 等于 `config.menu.menu_key`。**只要菜单里有一行、布局里有几张卡片，
页面就存在** —— 不需要为它写 Python 模块。写模块只有一个理由：这一页需要
按钮和回调（`/sql`、`/blocks`、`/datasource`、`/stock`、`/jobs`、`/admin` 属于这类）。

左侧导航栏本身（`app/web/app.py`）：

- **定宽 150px，不占栅格**（2026-08-29 改）。原来是 `lg=2`，也就是 12 格里的 2 格
  ——1920 屏上约 320px，可菜单名最长才 7 个字（"全市场个股分析"），宽度纯浪费，而
  表格多的页面正文被挤窄。现在侧栏 `width='auto'` + `style={'width': NAV_WIDTH}`

`RUNNERS` 每一项除了脚本路径还写了 **`date` 口径**：`iso` = `--date YYYY-MM-DD`、
`compact` = `--date YYYYMMDD`、`None` = 这个脚本没有 `--date` 参数（c1/c3/c7/c8/

永远等于"库里已经有的那天"，追平直接变成空操作。

### 5.4.1 一键追平（`scripts/ops/e1_fill_all.py`）

一个按钮把十一步按顺序跑完，入口在 `/jobs` 顶部那张卡：

```
日历 → 日线/指数/板块 → ETF份额 → 两融 → 龙虎榜 → 资金流
     → 分红+复权因子 → 股本 → 基础因子 → 评分 → 板块热度趋势
     → 质量审计（operations.quality_result）
```

最后那一步是 2026-08-30 加的：**数据补完不体检，页面上的「最近一次」就还停在
上一次** —— 看板一片绿而实际没人查过这几天。它是非骨干步骤，退出码 2/3
（有规则未通过）被识别成"审完了、有问题去看质量看板"，不算追平失败。


**目标交易日按点下去那一刻算**，判据在 `app/orchestrator/tradeday.py`（页面和
脚本共用一份，抄两份就会出现"页面写 08-28、脚本按 08-27 跑"）：

1. 先同步 `reference_data.trade_calendar`。日历是从历史行情反推的，**它不知道明天开不开
   市**；不先接上，第 2 步永远算出"日历里最后那天"，判定永远是"已经最新"
   （2026-08-27 实测：日历停在 08-25，目标就算成 08-25，该拿的是 08-26）。
2. 收盘线 **15:30**。14:00 点这个按钮，最新已收盘交易日是上一个交易日。
3. 目标 = 日历里 `is_open` 且 ≤ 上限的最大那天。日历比上限还旧时退回按星期几
   估算，并在页面上标明"偏激进"。

**"往前"补到哪**：`market_data.stock_daily` 里缺的最早那天；一天都不缺时按 `--back`
（默认 5 个交易日）开窗口 —— 两融是 T+1 发布、龙虎榜和 ETF 份额都会补发，
只打目标日那一天会永久漏掉迟到的数据。缺口只看"库里最新那天往后"，不数远古
空洞：否则窗口起点被拉回几年前，评分那一步要跑几小时，看起来就是卡死。
因子/评分单次最多回算 30 个交易日（`MAX_SPAN`，实测 45 天≈18 分钟）。

退出码是有分工的，页面上看到 failed 要照这个读：

- `0` 全部成功（或按 `--skip` 跳过）
- `1` 骨干失败（日线 / 因子 / 评分）
- `2` vipdoc 还没覆盖目标日、又没开 `--allow-web` —— **按设计停在这里**，不是坏了
- `3` 只有辅助源失败（两融/龙虎榜/资金流这些经常抖），骨干是好的

最后一行是给 `operations.task.message` 看的一句话摘要（`DONE`/`PARTIAL` + 每步结果 +
哪些表没追上目标日），验收部分逐表对照目标日的 `max(trade_date)` 和行数 ——
**只看日期不看行数会漏掉"日期在、行数 0"这种空表**。



### 5.5 有执行，但**没有调度**

`config.job.cron_expr` / `ready_on` / `after_job` 目前**没有任何进程在读**：没有常驻
scheduler，也没有注册 Windows 计划任务（2026-08-29 用 `Get-ScheduledTask` 核过，
一条都没有）。所以：

- 数据更新的唯一路径是**手动触发** —— `/datasource` 的「手动采集」或 `/jobs` 的
  「运行」，也可以直接在命令行跑 `RUNNERS` 里那些脚本。
- 页面上把 cron 显示成「计划(未接调度)」。写成 `0 8 * * 1-5` 摆在「触发」列里，
  任何人都会以为它每天早上八点自己跑了 —— 这是最贵的那种误解。
- 触发一律异步（`run_job(wait=False)`）：子进程在后台线程里跑，页面立刻返回，
  `dcc.Interval` 每 3 秒刷新状态，没有在跑的任务就自动停表。
- `operations.task.result_meta.owner_pid` 记发起进程的 pid，`runner.reap_orphans()`
  在每次刷新前把"发起进程已经不在"的 running 行收成 failed。不做这件事的后果
  实测过：网站一重启，那一行永远停在 running，页面显示「正在跑」且轮询不停。
- 子进程 env 里加 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`：默认按 cp936 输出，
  父进程按 utf-8 读，`operations.task.message` 里会全是 `\ufffd`。

**想接真定时的话，只有一条命令值得挂**（挂 Windows 计划任务，每个交易日盘后）：

```powershell
cd D:\FinanceTool; python scripts\ops\e1_fill_all.py
```

它是 5.4.1 那十步的完整链路，自己判断缺几天、缺哪层。**不要**去挂单个
`config.job` —— `after_job` 那个链在没有调度器的前提下不会被任何人执行。

### 表格十字高亮（点一格 → 整行 + 整列 + 该列表头一起亮）

2026-08-30 加的，**全站所有表格自动都有**，一行 Python 都没改：实现是
`app/web/assets/ft-table.css`（Dash 会自动把 `assets/` 下的 CSS 注进每一页）。

为什么不用回调：表格是按 `config.page_layout` 动态生成的，回调要按 id 一张张挂，
加一张卡就漏一张；而且回调改 `style_data_conditional` 在表格重渲染（排序/翻页）
时会掉。CSS 挂在 Dash 自己给单元格加的 class 上，重渲染后照样有效。

三处不能改坏的细节：

- **靠 class 不靠 nth-child**。Dash 3.3.0 给单元格的 class 是
  `dash-cell column-{序号}`，选中格额外带 `cell--selected`，表头是
  `dash-header column-{序号}`（出处 `dash/dash_table/async-table.js`）。
  隐藏列（`hidden_columns`，比如排名列）会让 nth-child 和列序号错位。
- **用 `box-shadow: inset` 铺半透明色，不用 `background-color`**。涨跌红绿是 Dash
  以**行内 style** 写上去的，行内样式赢过外部 CSS，改背景得 `!important`，
  那就把红绿盖掉了 —— 高亮的代价不该是看不见涨跌。
- **列上限写死 60**（`column-0` ~ `column-59`）。最宽的表约 20 列，留了三倍余量；
  超出上限的列点了不亮，而且不报错，所以 `tests/test_table_crosshair.py` 里有一条
  拿最宽表的列数去卡这个上限，还有一条去 dash 的 bundle 里核那三个 class 名还在
  （dash 升级改名的话，页面不报错、只是"点了没反应"，是最难发现的一种失效）。

`:has()` 需要 Chrome/Edge 105+（2022-08 起）。老浏览器里的表现是点了没反应，
不影响其它功能。


同一个模块里还有**站内深链** `detail_link('600519.SH')` → `[看详情](/stock?code=…)`。
和 `em_markdown` 的分工：那个去东财看行情，这个留在本站看评分归因，名单页两个都要。
放在 `app/quote_link.py` 而不是 `ui.py` 是因为 `queries.py` 也要造这个链接，
而 `ui.py` 反过来 import `queries` —— 写在 ui 里就成了循环 import。
`ui.table()` 认它的方式是**看值**（首行里以 `[` 开头且含 `](` 的列自动按 markdown
渲染），不是看列名写死一个「详情」—— 那样下次换个列名就漏。

### 5.7 筛选引擎（`app/compute/screener.py`）

`config.screen_rule` 里存的是 **WHERE 片段模板**，不是整条 SQL。引擎负责把勾选的条件
按 and / or 拼成一条参数化 SQL 跑出来。占位符分两类，这条分界线是这个模块存在的
全部理由：

- **值类**（数字、日期、天数）→ 一律换成 `%(名字)s` 走 psycopg 绑定，不进 SQL 文本
- **字面类**（列名 `close`、比较符 `>`）→ 列名和运算符不能当绑定参数用，所以这类参数
  在 `param_schema` 里必须带 `"literal": true` 并给出 `enum`，引擎只在枚举白名单命中
  时才做文本替换，没命中直接 `ScreenError`

没有这条分界线，"条件类型可配置"就等于"数据库里能写任意 SQL" —— 而 `config.screen_rule`
是 `/blocks` 页面上能改的表。

其余约定：
- 参数名加前缀 `c{槽号}_`：同一次筛选里两条「N 日内涨停过」用不同的 days，
  不加前缀第二条会覆盖第一条的绑定值。
- 替换用**一次 `re.sub`** 走完，不按名字逐个 `str.replace`：模板里同时有 `:d` 和
  `:days` 时，替换 `:d` 会把 `:days` 咬掉半截（回归测试
  `test_placeholder_prefix_collision`）。
- **窗口起始日由引擎算**：模板写 `:start`，引擎按参数 `days` 从 `reference_data.trade_calendar`
  倒数第 N 个交易日取。用日历而不是 `:d - days` —— 自然日往前推 5 天遇上长假只剩
  两个交易日，"近 5 天涨停过"就漏了。
- **候选集默认自选池**（旧系统 `/watchlist_filter` 的语义），可切全市场；
  全市场两条条件实测 1.3s。**一条条件都不勾＝候选集本身**，不报错。
- `price_compare` 额外带「条件N价」「条件N到今涨跌幅」两列，其它四种不带 ——
  它们对应的是一段窗口，没有单一价格，通用化的代价是编出一个似是而非的数。
  列名**不带 `%`**：psycopg 会把 SQL 文本里的 `%` 当占位符起手（`"…涨跌%"` 直接
  报 `only '%s','%b','%t' are allowed as placeholders`）。
- 方案（`config.screen_preset.conditions`）存的是 `{'logic','universe','conditions'}`
  三件套，不是只存条件 —— 同一组条件 and 还是 or 是两个完全不同的方案。

当前 5 种条件类型（2026-08-29 重写）：`price_compare` 指定日价格比较 /
`limit_up` N 日内涨停过 / `intraday_limit_up` N 日内盘中冲板 /
`amp10_over` 10 日日均振幅大于 / `rising_closes` N 日内收阳天数不少于。

**删掉了 6 条旧模板**（`between`/`topn`/`cmp`/`consecutive`/`belongs`/`had_limit_up`）：
它们从来没有任何引擎读过，而且写不对 —— `consecutive` 的模板里根本没用到
field/op/value，`belongs` 依赖一张不存在的 `config.v_universe`。注册表里留着"点了不动"
的条目比明写"还没实现"更贵。口径钉在 `tests/test_screener.py`（18 条，其中
`test_every_enabled_rule_has_a_case` 强制"注册表加一种就得补一条测试"）。


### 5.8 形态扫描（`app/compute/pattern.py`，2026-09-01 加）

筛选器页面第二个 Tab「② 形态扫描」，两个独立的扫描卡，各自一套参数、各自一个
「开始扫描」按钮。**没有做成 `config.screen_rule` 的条件模板**：那个引擎存的是
WHERE 片段，而这两个形态都要窗口函数（gaps-and-islands 数连板）和"窗口内最后一个
涨停日"这种游标逻辑，塞不进片段 —— 历史上那条 `consecutive` 模板就是因为写不对被
删掉的。所以写成两个取数函数，页面照旧只认命名查询
（`q_pattern_streak` / `q_pattern_box`）。

**① 窗口连板计数** `limit_streak_scan(n_back, m_back, times, op)`

- 「前 N 到前 M 个交易日」翻成真实日期对，**两端都含**，N 可以填 0（含基准日本身）。
  `back_days()[0]` 就是基准日，这个 0 起点的约定要记住。N/M 填反了自己正过来。
- 窗口按 **`market_data.stock_daily` 里真有行情的日子**数，不按自然日、也不按 `reference_data.trade_calendar`：
  日历有 is_open 但库里还没摄入的那天（今天就是这种情况）会让窗口整体飘一格。
- ⚠️ **「涨停次数」是窗口内涨停的天数，不是连板段数、也不是板高**（用户 2026-09-01
  确认的口径）。窗口里 D1D2D3 连板、隔一天 D5D6 又连板，这一列给 **5**。口语里的
  "连板 3 次"是另一回事，所以另给一列「连板高度」＝最长那一段的板数（上例是 3），
  两个数摆在同一行，想按哪个口径看都不用回头重算。
- `op` 只有 `>=` / `=` / `<=`（白名单）。默认 `>=`。

**② 断板走箱体 + 跌破均线** `box_break_scan(lookback, box_days, box_pct, ma, price)`

- 断板日 ＝ 近 `lookback` 个交易日里**最后一个涨停日的次一个交易日**。窗口内没涨停过
  的票不参与 —— 这个形态的前提是"曾经有过板"。
- 箱体 ＝ 断板日到基准日 `(最高−最低)/最低×100 <= box_pct`（默认 15）、天数 ≥
  `box_days`（默认 3）、**期间不再涨停**（再涨停是二波，形态含义完全不同）。
  上下沿取的是**断板日之后**的最高最低，不含断板前那根板 —— 含进去箱体振幅永远等于
  那根板的涨幅，判据就废了。
- 破线 ＝ 基准日 `close`（收在线下）或 `low`（盘中破过）低于 `ma5/ma10/ma20`。
  `low` 的结果必然是 `close` 的超集。
- **均线是现算的，不读 `analytics.indicator_value`**：2026-09-01 实测两者逐票完全相等
  （5,544 只，最大差 0），而现算不依赖因子链有没有跑到基准日 —— 读表的写法在因子只
  算到昨天时会**安静地返回 0 行**，而 0 行在页面上跟"今天真没有这种票"长得一模一样。
  多取 `ma_n` 个交易日暖机，否则窗口最早几天是残缺平均。

**两个坑**

- **相关子查询不许打 CTE**。第一版箱体查询写了 `WHERE r.security_code = a.security_code` 这种
  回扫，CTE 上没有索引，5,545 只 × 25 天 = 14 万行每票再全扫一遍，直接撞
  statement timeout。改成 `last`（`row_number() OVER … ORDER BY run_end DESC`）
  ＋ `box`（一次 GROUP BY 把断板日/上下沿/期间涨停数全聚出来）。全市场实测
  连板 1.1s、箱体 1.6s，测试里留了 6s 的哨兵。
- ⚠️ **`market_data.stock_daily.limit_up` 是推导值，ST 那一档是错的** —— 见下面「涨跌停价」。

页面上另写了一段用户给的**后续观察规则**（不参与筛选，只是提示）：后一天对 10 日线
一次反包、这次反包必须打板，然后看后面两天的箱体突破，必须是一字板或加速秒板。

口径钉在 `tests/test_pattern_scan.py`（41 条）。

#### 涨跌停价：推导值，ST 已知不可信（2026-09-01 下午推翻上午的结论）

`market_data.stock_daily.limit_up/limit_down` 不是交易所公布值，是
`app/db/repo/quote.py::recompute_limits()` 用
`pre_close × reference_data.board_limit_ratio(board, is_st)` **现算**的，ST 一律给 ±5%。

实测（近 20 个交易日）：每天有 **6~21 行收盘价直接越过了算出来的涨跌停价，全是 ST**。
`*ST西旅 000610` 09-01 从 6.75 涨到 7.43（+10.07%，最高价＝收盘价，明显封死），
推导涨停价只给到 7.09；`*ST萃华` 连续三天 −9.5% 左右；`ST金鸿顺`+7.17%、
`*ST联翔`+7.90%。成交价站在通达信 `ZTPrice` 那一边。

所以 08-30 那条结论「库里 ST ±5% 是对的、通达信快照的 ZTPrice 不对」**对 ST 这一半
是反的**（北交所那一半仍然站得住：库里四舍五入正确、通达信是截断）。后果是 **ST 票
会在涨 5% 上下被判成涨停**，形态扫描对 ST 的结果不可信。

**没有顺手改**：改涨停口径要先定哪个源当权威（通达信 `ZTPrice` 是现成的，但那就等于
把 08-30 的判断整个翻过来），这个得先定。现在只做了三件事：`pattern.py` 模块注释里
写明、`tests/test_pattern_scan.py::test_limit_price_is_derived_and_its_error_stays_bounded`
把越界行占比 < 0.5% 钉成哨兵（修好后归零也照样通过，但 `board_limit_ratio` 或
`is_st` 大面积走样会先炸）、记进「已知缺口」。

**大盘温度（＝`market_mood`）怎么算的**，以及为什么要三个窗口（2026-08-29 加）：

指标块上那个数（例如 08-28 的 23.6）是四项加权，每项先线性截断映射到 -100~100：

- 涨跌家数比 × 0.35 —— `上涨 / (上涨 + 下跌) × 100`，区间 30~70
- 涨停家数 × 0.25 —— `count(close >= limit_up - 0.01)`，区间 20~120。
  用回算的 `limit_up` 而不是"涨幅 > 9.8%"，后者会漏掉创业板 20%、北交所 30%
- 中位涨幅 × 0.25 —— `median(pct_change)`，区间 ±1.5%。用中位数，几只妖股拉不动它
- 成交额环比 × 0.15 —— `sum(amount) / sum(MA(amount, 5))`，区间 0.8~1.3

08-28 实测复核：家数比 55.69% → +28.43、涨停 88 家 → +36.00、中位 +0.22% → +14.69、
成交额环比 ≈1.066 → +5.7，加权得 23.5 左右，库里存的是 23.5575。**统计口径是全市场
个股，不是指数** —— 指数被权重股主导，反映不了赚钱效应。这个数摊给每只票同一个值
（`analytics.score` 一只票一天一个功能点一行，结构不为它开特例）。

#### 自选组的分数、趋势与振幅（2026-08-29 学 `D:\financeWeb` 做的）

旧系统本身**没有**"分组趋势分数"和"组内加权平均分"这两个数 —— 它的
`web/pages/watchlist.py` 只有个股行，分组那一侧只有
`scripts/sector_y_score.py:calc_group_heat`（组内涨幅均值×10 + 平均换手×3 +
平均成交额/1e3，截断到 ±100）。这里学的是它的**两个做法**，不是照抄它的输出：

- 加权聚合的思路来自 `calc_group_heat`（组内先聚合再打分，而不是逐票看）
- 最小二乘趋势外推来自 `scripts/score_amp_trend.py`（对 20 日振幅做
  `np.polyfit(x, y, 1)` 再取第 21 点）

**「自选组热度」表**（`q_group_heat`，一行一个组）。**列序按复盘的提问顺序排**，
不是按算的顺序：

`分组` → **`预测操作分`（默认排序键）** → `加权操作分` / `平均操作分` /
`趋势分数` → `平均涨跌幅` / `组内10日均涨跌bp` / `组内20日均涨跌bp` /
`上涨占比` → `组内明日振幅` / `组内10日振幅` / `组内20日振幅` → `上榜次数` →
`趋势天数` / `成员数` / `有分只数` / `重点关注`

最后四列是**元信息**，用来判断前面那些数可不可信（只有 3 只票的组、一半票
没评分的组），不是主角，所以压到最后。**默认按预测操作分从高到低**：这一列
已经把"今天多少分"和"在往哪走"合成了一个数，比单看当日分更接近"明天先看谁"；
算不出来的组（历史不足）`NULLS LAST` 排最后，不用 0 顶到中间。

三块内容：

- **分数**：预测操作分 / 加权操作分 / 平均操作分 / 趋势分数
- **振幅**：组内明日、10 日、20 日日均振幅（组内个股同名指标取均值）
- **广度**：平均涨跌幅 / 组内10日均涨跌bp / 组内20日均涨跌bp / 上涨占比 / 上榜次数

**组内 10 / 20 日均涨跌为什么用 bp（2026-09-01 用户指定 ×100 显示）**：
组内每票的 `chg10_avg`（近 10 个交易日**日均**涨跌幅）取组平均后只剩 ±1% 以内
（实测 −1.11 ~ +1.08），两位小数的百分数在表里满屏是"−0.25"，看不出组间差别。
×100 之后单位正好是**基点**（1bp = 0.01%），所以抬头写 `bp` 而不是 `%` ——
标成 % 会把 −25bp 读成 −25%，量级差 100 倍。20 日那一列 2026-09-01 新加
（`chg20_avg` 本来就在 `analytics.indicator_value` 里，只是没取）。


**加权操作分 = `Σ(操作分 × 当日成交额) ÷ Σ当日成交额`**，权重用成交额。
本想用流通市值，但 `market_data.stock_snapshot` 还是空的（已知缺口），拿一个查不到的
字段当权重＝整列变空，不如用真有数的成交额。
**分母只统计"有分的行"**（`sum(amount_yuan) FILTER (WHERE value IS NOT NULL)`）——
写成裸的 `sum(amount_yuan)` 会把没评分的票的成交额也算进权重和，
结果是"组里越多票没评分、加权分越被压低"。`tests/test_group_agg.py::
test_weighted_score_matches_hand_calc` 就是这一条的回归测试（24 个组逐组复算）。

**加权分和等权分必须两列都给**：两者差得多，说明这个组的分是被成交额最大的
一两只票拉出来的，"整组都强"就不成立。实测 `抗日` 组加权 17.6 / 等权 13.5，
`算力金属` 两者都是 14.8 —— 一个是被带的，一个是真齐。

**趋势分数 = 最小二乘斜率 × 10**，读作"这组的加权分每 10 个交易日变化多少分"。
直接给斜率（分/天）要看小数点后三位，量纲不好用眼睛比。用 PG 自带的
`regr_slope` / `regr_intercept`，不把序列拉回 Python 手搓。
**正负号才是主信息：分数高但趋势为负 = 在退潮的强组。**

**预测操作分 = 把这条回归线外推一天**（第 `n+1` 点，`a + b×(n+1)`）。它同时含了
"今天多少分"和"在往哪走"，所以拿它当默认排序键。
⚠️ **不是预测涨跌方向，也不含明天的任何新信息** —— 一根大阳线或一条突发消息，
这个数完全不知道。实测值域约 −18 ~ +10。

窗口是**最近 20 个有数的交易日**，不是 20 个自然日：按自然日圈的话长假一压
只剩十来个点，斜率的量纲跟着行情日历漂移，跨月不可比。
不足 10 个交易日的组，趋势三列**留空不补 0** —— 两三个点也能拟合出一条斜率，
但那个数没意义，而 0 会被读成"横着走"。

**「自选组趋势」折线图**（`config.chart.group_score_trend` → `q_group_trend`）：
表给的是今天这一个点和一条斜率，图给的是这 20 天怎么走过来的 —— 斜率一样的
两个组，一个稳步爬升、一个暴涨后回落，只看数字分不出来。两处**共用同一段
CTE**（`queries.py` 里的 `_GROUP_WSCORE_CTE`），各写一份迟早对不上。

**所有够长度的组都在图里**（当前 24 条），但只有**趋势最好的 3 个**默认画出来，
其余 21 条收在图例里，点组名展开、再点收回。实现是 Plotly 的
`visible='legendonly'`：查询多返回一个布尔列 `show`，`config.chart.options.visible_col`
指向它，`ui._line()` 据此设 `visible`。
以前是"只查前 6 个"，等于把第 7 名从图里删掉，想看得改 config 或改代码。

"趋势最好"按**斜率**排，不是按当日分：这张图问的是"谁在起来"。所以默认那 3 条
**很可能分还是负的** —— 实测 `存储 看HBM` 从 −15.2 抬到 −3.6，是跌得最狠之后
反弹最快的那个，不是最强的那个。"谁最强"看上面那张表的第一行。
不足 10 个交易日的组不进图：两三个点连不成趋势。

**数值自证**：加权分与 Python 逐组手算完全一致（`抗日` 17.6、`固态_钠` 10.5）；
趋势斜率与 `numpy.polyfit` 独立复算相差 ≤0.01（差值来自图上序列已 round 到
1 位，SQL 内部用的是全精度）；组内日均振幅全部落在个位数量级（最大 6.4），
超过 20 就说明把"区间涨幅"当振幅取了，这条也写成了断言。


**表头上方一行「组内小结」**（`_group_summary`）：
`4 只　·　涨 2 / 跌 2 / 平 0　·　平均涨跌 +0.30%　·　平均操作分 7.8　·　1 只有成本，平均盈亏 -13.51%　·　收盘列 08-24 ~ 08-28`。
均值只对**有值的行**求（没算出指标的票不拉低平均），并把收盘价列覆盖的日期区间
写出来 —— 表头只有 `08-28` 这样的月-日，隔一天再看得知道这五天是哪五天。

三套配色规则（`ui.rules_pct` / `ui.rules_amp` / `ui.rules_rank`）：涨跌有正负
（红 / 绿 / 灰），振幅只有大小（>3% 红、>1.5% 橙），近 5 日收盘按**行内高低**排名
五档着色。行内排名要靠一个隐藏的排名列（`_rk_08-28`…，`hidden_columns`）——
DataTable 的 `filter_query` 只能比较**同一行内的列**，没法写"本行最大值"。
没数据的列**留空不填 0**：0 和"没算出来"在涨跌幅上是两个意思。

  原来那个 `wl-members` 多选下拉删了 —— 票已经列在表里，再去下拉里找一遍是多余的。

**就地编辑怎么实现的（三个坑）**

1. **不能造成循环依赖。** 同时 `Output('wl-gdt','data')` 和
   `Input('wl-gdt','data')`，Dash 3 直接报 Circular Dependencies、整个应用起不来。
   正确写法是 **Input 用 `data_previous`、State 用 `data`**：`data_previous` 是
   前端在 `data` 变化时自动写入的旧值，只读。`_diff_cell(prev, cur)` 从两份
   `data` 里认出"哪一行哪一列被改了"，只 UPDATE 那一个字段。
   **行数不一样直接当没差异** —— 那是整表重画（建组 / 删组 / 换组），
   不是有人改了一格；不挡的话重画会被误判成一次编辑去写库。
2. **列名是唯一拼进 SQL 文本的东西**（PG 不允许列名当参数），所以只能从
   `GROUP_EDITABLE` / `STOCK_EDITABLE` 两张写死的白名单里取，值照旧走参数。
   白名单外的列（`成员数`、`操作分`）抛 `ValueError`，测试里连
   `'name; DROP TABLE …'` 一起试过。
3. **写不进去要把表格拉回库里的样子**：组名重名、成本填了字母，都要在
   `wl-msg` 报出库层原话并重建那张表，否则页面上留着一个库里并不存在的值，
   下次刷新才发现。实测重名报的是
   `duplicate key … Key (owner, name)=(fin, 昇腾) already exists`，
   成本填 `abc` 报 `could not convert string to float`，两者都回滚了。

⚠️ **修掉一个连带缺陷：新建的组 owner 不对，重名约束形同失效。**
`config.watchlist_group.owner` 的库默认值是 `current_user`，网站连库用的是
**ft_app** 角色，而迁移进来的 24 个组都是 **fin**。唯一约束是 `(owner, name)` ——
两个 owner 就是两套命名空间。实测（不写 owner 时）把新组改成和老组同名
**不报错**，列表里会出现两行同名的组，而 `q_group_trend` 里那句
`SELECT DISTINCT group_name` 还会给同一个名字画出两条曲线。
现在 `app/db/repo/watchlist.py` 里定了 `DEFAULT_OWNER = 'fin'`，页面建组显式写它
（那个 repo 函数原来的默认值是 `'ft_app'`，也一起改了）。

**按需刷新：库没动就不重画**（原来的 `heavy` 开关升级成四个按需开关）

`_refresh()` 默认**一个 Output 都不刷**，各分支自己打开需要的：

- `groups=True` 重建左栏组表、`members=True` 重建右栏成员表、
  `opts=True` 只刷「移动到哪个组」下拉、`head=` 给右栏抬头。
- 真写了库的分支（建组 / 删组 / 加票 / 批量加 / 移出 / 移动）才全开。
- ★**就地编辑成功时绝不能开 `groups`** —— 重建表格会把正在编辑的单元格连光标
  一起换掉，连着改两行就没法做了。改组名只刷抬头和「移动到」下拉，改排序 / 备注
  只刷一行消息，改成本只刷成员表（盈亏要重算）。

实测（直接打 `/_dash-update-component` 重放整条链路）响应里变了哪些 Output：

- 换组 → `wl-cur` / `wl-gid` / `wl-mwrap` / `wl-msg`，**组表没重建**
- 就地改组名 → `wl-cur` / `wl-tgroup` / `wl-msg`，**组表没重建**
- 就地改排序 → 只有 `wl-msg`
- 改组名撞重名 → `wl-gwrap`（回滚）+ 报库层原话
- 改成本 → `wl-mwrap` / `wl-msg`；成本填 `abc` → `wl-mwrap` 回滚

`tests/test_watchlist_refresh.py` 与 `tests/test_watchlist_edit.py` 锁住这些 ——

### 加票的键盘流

```
①关键词框：连续打字，页面不动、焦点不跑（中文可以正常拼完再上屏）
   回车#1 → 才去搜，候选列出来并默认选中第一条
            ★只搜到一只时不再要求确认，直接跳到 ③成本
   回车#2 → 确认这条候选，焦点跳到 ③成本（可留空）
   回车#3 → 焦点跳到 ④备注（可留空）
   回车#4 → 加入本组，三个框清空、候选清空，焦点自动回到①
批量：在①里贴一串代码（空格 / 逗号 / 换行分隔）→ 回车#1 直接全部加入
成本 / 备注也可以先不填，加进来之后在成员表里双击就地改
```
"只命中一只就不用再确认"是学旧系统 financeWeb 的做法（它命中唯一时连候选下拉
都不展开）：多一次回车没有信息量。实测 `gzmt` → 唯一命中贵州茅台，直接进③。

⚠️ 四段阶梯本身是因为**上一版每敲一个字符就搜一次，实测不可用**：中文输入法
拼不完一个字就被打断，敲个 `h` 页面像刷新了一下、焦点从输入框里掉出来，
得用鼠标点回去才能接着打。两处修的：
- 输入框加 `debounce=True`，`value` 不再每键回传服务端；只有回车 / 失焦才提交。
- **删掉原来那个专门监听 `wl-q.value` 的 `_search` 回调**，搜索改成合并进主回调
  `_act`。Dash 3 里一个 Output 只允许一个回调写，候选框既要被"搜索"写又要被
  "加完票清空"写，只能合并 —— 拆成两个回调 Dash 直接拒绝启动。这也是为什么
  就地编辑、换组、删组确认全都塞在同一个 `_act` 里，靠 `triggered_id` 分支。
  同一个组件的两个 prop（`wl-gdt` 的 `selected_rows` 和 `data_previous`）
  还要再按 `triggered[0]['prop_id']` 区分，不然改一格会被当成换了一次组。
- 阶梯走到第几级不靠猜，用 `dcc.Store('wl-step')` 记住「上一次搜的是什么词」：
  词变了＝这次回车是搜索，词没变且已有候选＝这次回车是确认。
- 焦点跳转只能用 **clientside 回调**拿 DOM 节点 `.focus()`（服务端回调没有焦点这个
  概念），并且要延时 80ms —— Dash 重绘组件后立刻 focus 会被重绘覆盖掉。

- **表格高度按行数算**，不写死：`_fit_height(行数)`＝`76 + 27×行数 + 12`，

  表格身上（表头冻结才有参照物）。★重点关注只有 2 只票时高度就是 142px，不留空白；
  43 个组要 1249px，1240 基本一屏铺完。组表 `page_size=60`、成员表 `page_size=200`，
  少翻页。
- **自选池明细**（下半截配置卡）2026-08-30 一起放大：`config.page_layout` 里
  height 560→1040、`options.page_size` 30→100，并且 `q_watchlist` 的排序从
  "先按组再按分"改成**全表排**。2026-09-01 排序键改为**10 日振幅从高到低**
  （同振幅按操作分、再按代码兜底），和右栏组内成员表用同一个键 —— 同一批票在两张
  表里给两种默认顺序，对着看只会互相干扰。想按组看点「组名」表头排一下。

- 写操作都是**模块级函数**（`create_group` / `update_group_field` /
  `update_stock_field` / `delete_group` / `add_stock` / `add_stocks` /
  `remove_stocks` / `move_stocks`），不埋在回调闭包里 —— 埋进去就只能靠点页面
  验证，拎出来可以脚本里跑一遍增删改再删掉测试数据。
- `create_group` **返回 group_id 而不是影响行数**（`INSERT … RETURNING`）：
  建完要立刻切到新组，返回行数的话页面还得再查一次"最后建的是谁"，重名时就猜错。
- **勾选行取代码要从隐藏的 `_code` 列取**，不能从显示的「代码」列取 ——
  那一列已经被 `ui.table` 换成 `[600519.SH](https://…)` 这样的 Markdown 链接。
- **加票不用 `dcc.Dropdown`，用"输入框 + `RadioItems` 候选"。** 原来的 Dropdown
  服务端搜得到、页面上出不来：Dropdown 会拿浏览器里的输入**再过滤一遍**服务端
  返回的 options，默认按 `label` 匹配，而 label 里没有拼音首字母 —— 打 `gzmt`
  永远是"无结果"，这就是用户报的"加不了票"（2026-08-29 查实）。顺带给所有下拉的
  options 补了 `search` 字段（`stock.search_options` / `group_stock_options`），
  `/stock` 的搜索框同一个坑一起修掉。
- **换组是"先插后删"而不是 `UPDATE group_id`**：目标组已有同一只票时 UPDATE 会撞
  主键 `(group_id, security_code)`；插入用 `ON CONFLICT DO NOTHING` 吞掉重复再删源组那份。
- **写库前每个 token 都要解析成 `security_code`**（`resolve_code`）：手打少个 `.SH` 会写进
  一条永远 join 不上 `reference_data.security` 的孤行，页面上表现为"有票但没名字没行情"。
  6 位码可能同时命中股票和指数（`000001` = 平安银行 / 上证指数，库里 45 个重码），
  按 `stock → etf → 其它` 分档，同档还有多个就报"请写完整代码"，不静悄悄挑一个。
  自选池只收 `asset_type ∈ (stock, etf)`：指数和板块加进来在 `market_data.stock_daily` 里
  join 不到行，就成了"有票没价没分"。
- `ui.table()` 为这一页加了四个透传参数：`editable_cols`（按列开编辑，整表开等于
  让人去改盈亏、操作分这些算出来的列，改了没地方存）、`row_selectable`、
  `selected_rows`、`dropdowns`（只有两三个合法值的列做成下拉，比让人手打 ★ 靠得住）。
  可编辑列给了淡黄底 —— 不然人不知道哪一格能改。

#### 表格高度＝一页行数，不再手填（2026-09-01）

用户两条反馈其实是同一件事：「个股扫描……显示的多一点，直接在界面上能看到 30 行
或者以上」、「四象限趋势分……整个标签页面范围增大了，但是下面部分是空的，数据部分
还是跟以前一样大，想看更多得用滚轮往下翻或者翻页」。

病根是**高度和行数是两个手填的数**：卡片高度来自 `config.page_layout.height`、
表格高度是它 −60，而"一页几行"来自 `options.page_size`。两个数一漂就出两种症状 ——

- 高度**小于**一页内容 → 想看更多得**在表格里**滚（页面上看不出是高度算错了）；
- 高度**大于**一页内容 → 表格下面一片空白（看着像"表格坏了/还在加载"）。

实测当时库里 18 张表格卡有 **13 张**的高度比一页内容矮 11~1,386px
（`watchlist#3` 一页 100 行只给了 980px，差 1,386px）。

改法：**表格卡不再有固定高度**。`ui.render_card` 对 `card_kind='table'` 既不给
卡片高度也不给 `style_table.height`，一页有几行就画多高；`ui.table` 的默认
`maxHeight: 420px` 也去掉了（那是同一个病的另一半：没给高度的表在 420px 处偷偷
开始内滚）。要多看几行就把 `options.page_size` 调大，高度自己跟上；真要限高
（让表格内部滚）在 `options` 里写 `max_height`。

- `page_layout.height` 对表格卡从此**不生效**，列注释与「积木管理」里的「高」输入框
  都写明了这一点 —— 不写清楚就是"填了没反应"的坑。
- 手写页面的表格同批清掉了写死高度：`quality`（4 处）、`data`（4 处）、
  `datasource`（3 处）、`admin`（2 处）、`stock`（2 处）、`screen`、`sql_console`、
  `builder`、`blocks`、`helpedit`。`watchlist` / `scores` 本来就是
  `_fit_height(实际行数)`，等价，保留。
- 护栏：`tests/test_stock_scan.py::test_table_cards_do_not_pin_a_height`
  遍历 home/scores/sector/screen/watchlist 的表格卡，断言渲染出来的 DataTable
  没有 `height`、`maxHeight` 只在配了 `max_height` 时才有，CardBody 也没有高度。

用户点名的两张卡因此变成：个股扫描一页 **30 行全部直接可见**（原来 780px 的框
只装得下约 30 行的一部分），四象限趋势分一页 **40 行全部直接可见**、下面不再留白。
想再多看就调 `page_size`，不用再动高度。

#### 四象限趋势分（2026-08-31 新增 · `q_quadrant_trend` · scores#7）

这一页别的卡都是**今天的切片**，这张回答"近 10 个交易日在往哪走"。同样 60 分的
票，一个是从 20 分爬上来的、一个是从 90 分掉下来的，在切片里长得一模一样。

**三列一起看，任何一列单看都会骗人**：

- `趋势分数` = 最小二乘斜率 × 窗口长度，即**整个窗口的累计变化分**。口径与
  `q_group_heat` 的「趋势分数」一致（`regr_slope`，序列不拉回 Python）。
- `拟合度R²` = `corr(oper, rn)²`。`+8 分 / R²=0.9` 是一条斜线，`+8 分 / R²=0.1`
  是一团噪声恰好收在高位 —— 排行榜上挨着，能不能跟完全不是一回事。
- `形态`：**判定有先后，顺序就是语义** —— `横盘`（|趋势分| < 1）→ `冲高回落`
  （距最高 ≤ −15）→ `稳步/震荡上行` → `稳步/震荡下行`。
  ⚠️ **冲高回落必须排在上行前面**：前 8 天一路上、最后两天塌回去，斜率仍然是
  正的、R² 还很高，先判上行会把这种票标成「稳步上行」。这与量能阶段里"背离必须
  最先判"是同一类错误，所以同样写成了断言
  （`test_shape_fade_is_judged_before_up`）。

配套列：`窗口最高X+Y` / `最高那天` / `距最高` 三列一起回答"是不是已经回落了"——
用户原话是"近 10 日 xy 总分和最大"，但光给最大值会误导：最大值出现在第 2 天还是
今天，含义相反。`象限迁移`（`Q4→Q1`）的升格按**好坏次序 Q1 > Q3 > Q2 > Q4**
判，不是 Q 编号大小。`趋势图`是 ▁▂▃▅▇ 块字符（DataTable 画不了图），
**只表示形状不表示绝对高低** —— 每只票在自己的 min~max 之间归一化。

**性能是这张卡的主要工程量**（全市场 10 天评分 ≈ 5.5 万行，逐票拟合）：

- 三表自连接取 X / Y / 操作分：**2.0s**
- 换成一遍扫 + `FILTER` 条件聚合摊平三个 capability_key：仍 2.0s（瓶颈是排序，
  166,308 行宽行 GROUP BY 要外部归并，临时文件 9.6MB）
- 日期上下界从 `d − window_days×3` 收紧到**取自窗口本身**（`min(display_order)`/`max(display_order)`）：**1.34s**
- 序列只留 `oper_score` 一个 capability_key，X+Y 的最高值单独聚合、且用
  `sum(value) … HAVING count(*) = 2` 代替 `x JOIN y`：**≈1.0s**
- **落库预算**（2026-08-31，见下）：**0.45s**（其中 SQL 执行 0.22s）

`HAVING count(*) = 2` 那一条不能省：只有 X 没有 Y 的那天 `sum` 出来是"半个
X+Y"，会凭空拉低（或拉高）窗口最高值。测试红线现在按落库那条路定在 1.2s ——
`/scores` 是服务端一次性渲染的，这张卡慢多少页面就慢多少。

##### 落库预算：`analytics.score_trend`（2026-08-31）

趋势是**当天收盘后就定死的历史值**，每次进页面重算一遍是纯浪费。所以照
`analytics.sector_trend` 的先例落库：

- 表 `analytics.score_trend`（主键 `security_code, trade_date, window_days`）存斜率、截距、`r`、
  窗口最高 X+Y 及其日期、连升天数、窗口第一天的象限、迷你走势、`point_count`。
- **存斜率（分/天）不存"累计变化分"**：与 `analytics.sector_trend` 一个量纲，页面上的
  `趋势分数` = 斜率 × 窗口是展示层换算，换窗口长度不用重刷历史。
- **存 `r` 不存 `r²`**：`r` 的符号是信息（和斜率同号才自洽），开方就丢了。
- `min_n` 在**查询时**过滤而不在落库时过滤：表里如实记 `point_count`，"要不要看
  只有 3 天数据的票"是展示层的事。
- 算它的是 `scripts/compute/d5_score_trend.py` / 作业 `calc_score_trend`
  （`after_job = calc_scores`，执行器 `compute_score_trend`），「一键追平」那条链
  也带上了它（`scoretrend` 步，非骨干）。`--verify` 拿 `numpy.polyfit` 复核斜率
  （斜率最容易把 x 轴取反，正负号一翻整列就废了）。已回填最近 60 个交易日。

两条关键取舍：

- **库里没有那天时自动回退现算**，不给空表。判据是"**这一天**有没有行"而不是
  "表里有没有行" —— 后者会在日常链路没跑时拿昨天的趋势配今天的切片，页面上看不
  出来，比慢一秒危险得多。
- **落库与现算共用同一份 SQL**（`app/compute/score_trend.py` 的 `CORE_SQL`：落库时
  `INSERT … SELECT` 它，回退时把它当子查询）。各写一份的话两边会慢慢漂开，而页面
  上两条路长得一模一样。`tests/test_quadrant_trend.py::
  test_stored_and_live_paths_agree_row_for_row` 逐行逐列比对两条路。

⚠️ 改 `options.params.window_days`（比如 10 → 20）之后结果仍然正确，但**会离开落库那条
路**、每次现算慢约 0.7s —— 想要快就跑一次 `d5_score_trend.py --window_days 20 --recent N`。

⚠️ 窗口内至少 `min_n`=8 天有分才出行，**新股和长停票整片缺席**（3 天数据拟合
出来的斜率没有意义）。基准日走 `_scored_day()`：`latest_date()` 读的是
`reference_data.view_latest_trade_date`，即**日历上最新的已收盘交易日**（15:00 之后就算当天），
和"库里有没有这天的数据"无关 —— 实测 2026-08-31 15:50 它给 08-31，而
`market_data.stock_daily` / `analytics.score` 都只到 08-28（当日链路还没跑）。拿 08-31 去 JOIN
`analytics.score` 一行都对不上，卡片会静默变空，所以请求日要**向下取整到有评分的那天**。


**表格卡的配色现在也走注册表**：`config.page_layout.options.color` →
`ui._table_color()`，支持四类规则 —— `pct`（涨红跌绿）、`amp`（振幅三档）、
`flag`（等于某个符号就红字加粗，用在 `quad_up` 的 `↑`）、`dim`（低于阈值压灰，
用在 `r2` < 0.5）。以前 `rules_pct` 只有专属页能用，同一张表搬进注册表就掉色，
"涨红跌绿"要靠改代码才能给，与"布局是数据"的前提冲突。列名用**字段 id**
（`trend_score`），不是中文抬头。

两个和"静默失效"有关的取舍：

- `升格` 那一列给的是符号 `↑` / 空，**不是布尔**。DataTable 的 `filter_query`
  对布尔列的写法在版本之间不稳，匹配不上时页面不报错、只是不亮；文本等值
  （`{quad_up} = "↑"`）是文档里明确支持的。
- ⚠️ 一开始把 `quad_path` 也写进 `flag.cols`，它的值是 `Q2→Q1`，永远等不到 `↑`。
  所以加了 `test_flag_rule_matches_a_value_that_actually_occurs`：flag 的每一列
  都必须真的出现过那个符号，否则规则是死的。
- `dim.below` 必须等于代码里的 `R2_TIGHT`（测试断言），否则"页面上压灰的行"和
  "形态说震荡的行"不是同一批。

**整套方案也写进了卡片说明**（`config.help_note` 的 `card.q_quadrant_trend`，
2,800 余字）：点卡片右上角「说明」就能看到六节完整方案 —— 一句话结论、三个主角、
形态判定顺序、回落三列、其余列、数据基础与性能优化四步。说明是数据不是代码，
改它走 `scripts/ops/seed_help_notes.py --force --only card.q_quadrant_trend`。

## 七、评分口径

值域统一 **-100 ~ 100**，0 是中性。缺数据给 NULL 而不是 0 —— 0 表示"一般"，
NULL 表示"不知道"，混用会把数据缺口伪装成中性评价。

```
X 个股质量 = 0.25·形态 + 0.25·趋势 + 0.20·位置 + 0.20·筹码 + 0.10·量能
Y 环境共振 = 0.65·板块热度 + 0.35·大盘情绪
操作分     = 0.40·X + 0.60·Y
象限        Q1 双高 ｜ Q2 高X低Y ｜ Q3 双低 ｜ Q4 低X高Y

板块热度 = 0.30·涨幅 + 0.30·广度 + 0.25·动量 + 0.15·成交
量能温度 = 0.30·量比 + 0.25·放量节奏 + 0.25·持续性 + 0.20·位置
量能阶段  1 冷却 ｜ 2 酝酿 ｜ 3 高潮 ｜ 4 背离 ｜ 5 退潮
```

### 量能阶段的判定顺序：4 → 3 → 2 → 5 → 1

**背离必须最先判。** 背离的形态特征是"天量之后缩量上涨、价格创新高但成交量
接不上"，这在数值上同时满足"高潮"的部分条件（位置高）。如果先判高潮，
最危险的那一档会被吞掉，页面上永远看不到背离。

2026-08-25 的分布：冷却 2,047 ｜ 酝酿 1,171 ｜ 高潮 1,241 ｜ 背离 112 ｜ 退潮 958。
值得注意的是背离档的平均温度（26.14）低于冷却档（26.34）—— 这正说明温度和
阶段必须分成两个指标，单看温度会漏掉背离。

### 板块成交分项的踩坑记录

原写法 `clip_raw(amount / MA20, 0.8, 2.5)`。实测 2026-08-25 的 649 个板块，
`amount/MA20` 的中位数只有 **0.796**、p95 只有 **1.195** —— 整个分布压在下界
0.8 以下，于是 5,413 只票的成交分项全是负的（区间 -93.71 ~ -0.91，最大值都还是
负数）。

原因不是板块的问题，是"全市场今天缩量"被算进了每一个板块头上：MA20 里含着
前面的高量日，市场量能一收缩，所有板块的倍数一起掉到 1 以下。固定区间衡量的
是市场量能周期，不是"这个板块相对别人放量"。

修法：先除掉当日全部板块倍数的中位数，再比固定区间。1.0 就是"跟大盘一样"，
>1 才是真的相对放量。校准也对得上：p05/中位数 = 0.70、p95/中位数 = 1.50，
正好是新的默认上下界。

### 板块热度的多窗口趋势（2026-08-30 加）

板块热度榜上原来只有一个"趋势"列（今日热度 − 昨日热度）。现在拆成
**日趋势 + 3/5/7/9/11/15/21 日趋势**，全部落库，不在页面上现算。

**分两张表，都在 `fct`：**

- `analytics.sector_heat_daily`（板块, 日期）—— 预聚合的板块日热度。
  ⚠️ **2026-08-30 换过口径**：现在是 `app/compute/sector_heat_hist.py` 直接从
  `market_data.sector_daily` 算板块级（`source='sector'`），不再是
  `avg(analytics.score[sector_heat])` 按 `reference_data.sector_member` 聚回来（`source='member_agg'`，
  那批旧行还在库里但页面一律过滤 —— 旧口径把"成员股各自**主**板块的热度均值"
  记到了每个板块头上，是错的）。板块榜查询 0.19s、卡片渲染 0.05s。
- `analytics.sector_trend`（板块, 日期, **window_days**）—— **长表，一板块一天一窗口一行**。

**为什么是长表而不是 7 个列**：窗口集合是配置
（`config.setting['sector_trend.windows']`，默认 `[1,3,5,7,9,11,15,21]`），
以后想加个 13 日趋势只改这一行配置、重跑脚本，**不需要改表结构、不需要改查询**
（`q_sector_heat` 是按窗口列表动态生成 pivot 列的）。宽表方案每加一个窗口
都要 `ALTER TABLE` + 改 SQL + 改前端列名，这正是积木城堡要避免的。

**趋势值的定义：最小二乘斜率，单位是"分/天"。**

$$\text{slope}_N = \text{regr\_slope}(heat,\ rn)\ \text{over 最近 } N \text{ 个交易日}$$

- 向上为正、向下为负、**以 0 为界**，直接就是"趋势分值"。
- **没用 (今日 − N日前) ÷ N**：那个只看首尾两点，中间怎么走完全不管，
  一根插针就能把 21 日趋势翻正。最小二乘用上窗口内每一天，抗单日噪声。
- `window_days = 1` 存的是**日变化**（`heat − lag(heat)`），数学上就是两点斜率，
  跟原来那列 `日变化` 在 8 个板块上逐个核对过，完全一致。
- 用 `rn`（交易日序号）当自变量，不是日历天，所以长假不会把斜率摊平。

#### 「可用板块」判据与清理（2026-09-01）

热度里三个分项是**截面百分位**，所以"当天参与排名的板块有哪些"本身就是口径的
一部分：板块宇宙一天变一次，热度的时间序列就不可比。判据只有一份，在
`app/compute/sector_heat_hist.usable_clause()`，被 `sector_heat_hist.load`、
`scoring.sector_panel`、`ignition.load_sector` 三处共用：

- **数据可信**：历史上 `|pct_change|` 不超过 `MAX_ABS_PCT = 21%`（成分股全涨跌停也
  到不了 21%）。653 个有日线的板块里 **46 个**不合格，最离谱的 `TDX_880046`
  有 +429,900%；这 46 个分两类 —— 连板块名都没采到的无名板块，和「昨日涨停」
  这类每天重筛成分、本来就没有连续指数的风格板块。
- **历史够长**：在 `market_data.sector_daily` 里至少有 `MIN_HISTORY = 25` 天
  （= `WARMUP`，MA20 要 20 天）。起因是同花顺板块 2026-08-31 首次入库，
  一次多出 **86 个 `THS_*`、各只有 1 天历史**：它们照样算出了 heat
  （`min_periods=1` 点数不足也给值），当天的截面从 652 个板块变成 738 个。
  写成天数下限而不是排除 `THS_` 前缀 —— 攒够 25 天它们自己就进来了。

**同时补上"清理"这个动作**（`sector_heat_hist.prune()`，`d3_sector_trend.py`
每次运行前自动跑，`--no-prune` 跳过，`--prune-only` 只清不算）：热度是
`ON CONFLICT DO UPDATE` 写的，只覆盖不删，所以判据一收紧，之前那次口径写进去的
行会永久留在库里。实测清掉：

- `analytics.sector_heat_daily` 46,969 行、`analytics.sector_trend` 396,352 行
  —— 46 个不可信板块的行是 `MAX_ABS_PCT` 判据**加上之前**的那次全历史回补写的
  （同一天，先回补后加判据），此后没人回头清过。页面读 `source='sector'` 不带判据，
  于是 08-28 有 652 个板块、08-31 只有 604 个，同一列在不同日子含义不同；
- `analytics.ignition` 86 行（THS_ 的 08-31）—— 启动点读热度，热度里没了的板块它自己
  不会消失，而"启动点"和"板块热度"是同一屏的两张卡。

⚠️ **只清不算是错的**：留下来的历史行，分位当初是按"当时那个板块宇宙"排的名。
口径一变必须全量重算 —— 实测 `d3_sector_trend.py --recent 1232` 324s
（673,548 行热度 / 8 个窗口各 672,941 行趋势）+ `d4_ignition.py --full` 99s，
然后 `d2_scores.py --date <当日>`（Y 环境共振里 0.65 是板块热度）193s
+ `d5_score_trend.py --date <当日>` 1.2s。清完重算之后板块数逐日恒定在 604~606。

护栏在 `tests/test_sector_heat_hist.py`：`test_prune_has_nothing_left_to_delete`
（库里不该留着口径外的行）、`test_short_history_sectors_never_get_heat`、
`test_sector_universe_does_not_jump_between_days`（最近 20 个交易日板块数极差
≤ 20）、`test_warmup_and_min_history_are_the_same_number`。


**点数不足时不补零**：每行存 `point_count`（窗口内实际有热度的天数），
查询侧要求 `point_count >= window_days`（window_days=1 要求 2）才显示，否则该格为空。
**空 ≠ 0** —— 0 是"横着走"，空是"还没算够"。这一条在卡片说明里也写了，
因为它直接决定用户能不能相信那一格。

**上哪跑**：`scripts/compute/d3_sector_trend.py`，只处理当天真有
`sector_heat` 分数的日子。`--verify` 会拿 `numpy.polyfit` 逐窗口对账
（实测 5 个板块 × 7 个窗口，不一致 0 处）。日常执行挂在
**「一键追平」第 10 步**（`e1_fill_all.py` STAGES 里排在 `scores` 之后），
`config.job.calc_sector_trend` + `RUNNERS['compute_sector_trend']` 让它也能从
`/jobs` 单点触发。注意第 5.5 节那条：**系统没有调度器进程**，
`config.job` 里的 `after_job` 只是声明，真定时要靠 Windows 计划任务调
`e1_fill_all.py`。

**数据限制**：`analytics.score[sector_heat]` 目前只有 23 个交易日
（2026-07-29 ~ 08-28），而 `market_data.sector_daily` 有 1,231 天。所以 15/21 日趋势
只在最近几天有值，想往前看必须先回补评分：
`python scripts\compute\d2_scores.py --date 2026-08-28 --recent 120 --cap sector_heat`，
再跑 `d3_sector_trend.py --date 2026-08-28 --recent 120`。

### 板块轮动热力图的口径（2026-08-30 核）

**格子里不是分，是原始涨跌幅**，`market_data.sector_daily.pct_change =
(close − pre_close) ÷ pre_close × 100`，没有归一化也没有权重。
全库 719,170 行逐行验过这个恒等式，**0 例外**。

`close` 是通达信板块指数（880xxx/881xxx）的收盘，不是我们现场加权算的。
**它是等权口径**：2026-08-28 的 268 个概念板块里 240 个，板块涨跌幅与
「成分股涨跌幅的简单平均」差在 0.02 个百分点内，平均绝对差 0.012。
所以小票和大票对板块的贡献一样大，成分十几只的板块一两只票就能拉红一整行。
行业板块没有成员名单（`reference_data.sector_member` 覆盖 418/652），那几行无法用成分股自查。

其余三条都是为了"图能看"：

- **行选取按窗口内 `sum(pct_change)` 前 15**，不是当日涨幅 —— 按当日会选进一日异动的
  板块，图上是一行孤立红格。代价是它天生偏向"过去两周的赢家"。
- **只取行业和概念**。不过滤的话最近 15 日累计前 15 里有 6 个是风格板块，
  「昨日连板」+41.8% 排第一。风格板块成分股每天全换，等权口径也不成立
  （平均绝对差 0.72 vs 概念 0.012），跟行业放同一张色阶上比本身就不对。
- **色阶固定 ±5%**（`config.chart.options.zmin/zmax`），超界只是颜色饱和、
  数字照写不截断：08-28 那 225 格里 10 格 > +5%（最高 +13.54%）、5 格 < −5%。
  **深红不等于同一个涨幅**，要看格子里的数。空格留空不写 0。

### 倍量震荡榜（2026-08-31 加）

用户要的形态：**近 40 个交易日反复倍量、但价格一直沿 60 日线上下震荡**的票，
按倍量次数从高到低前 50。找的是"主力在 60 线附近反复进出" —— 有资金但没走出趋势，
**用法是等突破，不是当天买**。

链路：`app/compute/vol_double.py` → `analytics.volume_double` →
`scripts/compute/d7_vol_double.py` → `runner.RUNNERS['compute_vol_double']` →
`config.job.calc_vol_double` → `e1_fill_all` 的 `voldbl` 步 →
卡片 `q_vol_double`（`/scores` slot 8）。

四条定下来的口径：

- **倍量 = 当日量 ≥ 前 5 个交易日均量 × 2**，基准**不含当日**。含当日的话当日巨量
  把基准自己抬上去，次数被系统性低估；用"昨日量"当基准的话，昨天缩量就凭空多一次。
  对昨日的口径也算了一份放在 `倍量次数(对昨日)` 列作对照。
- **MA60 在 SQL 里自算，不读 `analytics.indicator_value`**：那张表的 ma60 只有 23 个
  交易日（评分历史起于 2026-07-29），40 天窗口过半取不到，筛出来是空表。
  不满 60 根 K 线的那天记 NULL，**次新股不凑数**。
- **"震荡"是四条同时成立**：`偏离60线中位% ≤ 8`、`线上天数占比%` 在 20~80、
  `穿越60线次数 ≥ 2`、`|60线变化%| ≤ 20`。只看偏离度会把"股价一直压着上行均线"
  的趋势票选进来，那和要找的形态正好相反。
- **必须落库**：现算实测 14 秒（5,516 只票 × 150 个市场交易日的窗口函数）。
  库里存**全市场每票的原始读数**，不是"入选名单" —— 阈值走
  `config.setting['vol_double.filter']`（默认值在 `FILTER_DEFAULTS`），
  改了立刻生效、不用重算。页面读表 0.18s。

一个踩过的坑：取数按"市场交易日"切，而 MA60 要的是**这只票自己的 K 线根数**。
停牌过的票在 100 个市场交易日里只有 90 几根，窗口最早几天凑不满 60 根 →
`ma60_days` 偏低（603221.SH 落库 33 天、逐日复核 40 天，`--verify` 当场抓到）。
现在取 150 个交易日、给停牌留 50 天余量；停牌超过 50 天的票 `ma60_days` 会如实偏低，
那种票也确实不该进"重点关注"。

### 通达信收盘快照库（2026-09-01 接入）

来源是通达信客户端里的 Python 插件 `PYPlugins\user\Get_DayEnd.py`（`py_strategy.cfg`
里 AutoRun=1），每天调 `tq.get_market_snapshot` + `get_more_info` 落到
`D:\new_tdx64\daily_close_data.db`：**一天一张 `day_end_YYYYMMDD` 表、一行一只票、
115 个字段**。`c15_snapshot.py` 把它搬进 `market_data.stock_snapshot`，六个定型列
（pe_ttm / pb / 总市值 / 流通市值 / eps / bps·roe）之外全进 `extra` jsonb ——
那些字段的口径没验过（`Zjl` 资金流实测全是 0），提前开列等于把没验证的当结论。

**这是市值与估值的唯一本地来源**：`reference_data.share_capital` 只有股本变动日，
算不出每天的流通市值。实测 2026-08-31 一天 5,541 只，总市值合计 116.4 万亿，
反算股本对得上（茅台 12.5 亿股、工行 2,696 亿股、平安银行 194 亿股）。

两个坑，都是接的时候真踩过的：

1. **表名里的日期是采集日期，不是交易日期。** 插件是 AutoRun，客户端什么时候
   被拉起来就什么时候采。26 张非空表里：17 张收盘后采的（表名=交易日）、
   2 张周末/凌晨采的（`day_end_20260801` 17:45 周六、`day_end_20260802` 09:16
   周日，装的都是 07-31 的数据；`day_end_20260821` 00:58，装的是 08-20 的）、
   7 张盘中或盘前采的（`Now` 是当时现价，整张表报废）。
   所以脚本**不认表名**：拿 `(Open,Max,Min,Now)` 回 `market_data.stock_daily` 投票定交易日，
   命中率 < 80% 的表直接跳过。收盘后采的命中 99.6%，盘中采的只有 1%~6%，
   中间没有样本，阈值不敏感。第一版按表名写，07-31 的市值被挂到 08-01
   这个不存在的交易日上，而表面上只看得出"那天匹配率低"。
2. **通达信的 `ZTPrice` 不是权威 —— 结论跟直觉相反。** 08-31 有 324 只与库里
   不一致，逐只查完是三类：175 只北交所差一分钱（`11.23 × 1.30 = 14.599`，
   库四舍五入 14.60、通达信截断 14.59，**库对**）；142 只主板 ST（库 ±5% 对，
   通达信给的是不区分 ST 的 ±10%，`reference_data.security.is_st` 交叉核过，212 只
   is_st 的名字里全带 ST、0 处冲突）；2 只库里 `pre_close=0` 涨跌停为空
   （**只有这类该补**）。所以默认**只填空不覆盖**，`--overwrite-limits`
   得显式开且不建议用。

代码是怎么对上的：快照接口**不返回股票代码**。2026-09-01 已经给插件补了
`Code` 列（`row = {'Code': code, **row}`），以后新表直接走代码；历史 26 张表
没有代码列，只能拿 OHLC 四元组反查，5,541/5,563 是唯一命中，撞价的
（同一天四个价一模一样的两只票）**丢掉不猜** —— 市值挂到错的票上是无声的错。



**硬规矩：日线一律先用通达信，网络源只能兜底，而且必须显式开。**
顺序是固定的三级，`c10_catchup.py` 就是按这个顺序挑源的：

1. **通达信 vipdoc 本地文件**（`c1_day.py` / `c3_sector.py`）—— 精度最高的主源。
   判据是 `.day` 文件尾部 32 字节里的日期，见 `app/tdx_client/readiness.py`；
   9 个市场锚定代码里至少 60%（`MIN_FRESH_RATIO`）到达目标日才算就绪。
   文件是客户端跑完「盘后数据下载」才写盘的，那一步由
   `scripts/ops/p0_tdx_predownload.py` 自动点（见下），**需要交互式桌面**。
2. **通达信 TQ 接口**（`c12_tq_day.py`）—— 同一个客户端、同一份行情，无 GUI。
   不需要桌面，也不用等盘后下载，所以无人值守时走这一级。
3. **网络源**（新浪 / akshare，`c10_catchup.py --allow-web`）—— **默认关**。
   不加这个开关时脚本宁可返回 2 让人接手，也不悄悄用网络数据把库填上。

**每一天的来源都能查**：`market_data.view_daily_source` 按 `operations.ingest_batch.source`
把每个交易日归成 `通达信vipdoc` / `通达信TQ接口` / `旧库迁移` / `网络兜底` / `未知`。
质量规则 `daily_source_is_tdx` 会在某天来源不是前三种时报 warning。

**覆盖规则**：同一天允许被更高优先级的源覆盖，覆盖走 `--overwrite`，
并且**派生列必须一起重算**（`recompute_pre_close(force=True)`、
`recompute_limits(only_missing=False)`、`recompute_turnover(only_missing=False)`）——
只换 OHLC 不重算前收，会留下一天前收来自旧源、涨跌幅算不对的混合状态。

**这三天的实际来源（2026-08-29 记）**：

- 08-26 / 08-27 一开始是**网络兜底**写进来的，后来用 vipdoc `--overwrite` 覆盖掉了，
  现在是 `通达信vipdoc` 各 5,547 行。

### 安全现状

访问控制是**两段串联**的，两段都在 `/admin → 访问白名单` 那张卡上：

- **监听地址**（`config.setting.web_bind_host`，默认 `127.0.0.1`）决定"谁能连到这个端口"。
  `app/web/run.py` 读这一项；`--host` 优先级最高。`.env` 里的 `FT_WEB_HOST` 已经不参与
  这个决定了 —— 原来那套"强行把 `0.0.0.0` 改写回 `127.0.0.1`"只有"全关"和"全开"两档，
  没有中间档。
- **IP 白名单**（`config.setting.web_allowlist`，默认 `["192.168.176.67"]`）决定"连上之后
  放不放进来"。`app/web/access.py` 在 Flask 上挂 `before_request`，非白名单一律 403 并在
  `logs/web.log` 留一行。挂 Flask 而不是 Dash 回调：回调只覆盖 `/_dash-update`，
  页面本体和静态资源不经过它。
- 因此**只绑 127.0.0.1 时，白名单里写什么都连不上**，这不是白名单失效。要开局域网：
  监听地址改 `0.0.0.0` → `python scripts\web_ctl.py restart`。白名单本身改完即时生效
  （3 秒 TTL 缓存，保存时主动失效），不用重启。

三条不能动的判据：

- **loopback 永久放行**，不受白名单影响。否则填错一个字就把自己锁在门外，而唯一的修复
  入口就是这个网页。
- **只认 TCP 来源地址（`request.remote_addr`），不看 `X-Forwarded-For`**。本机没有反向
  代理，信那个头等于白名单可以由请求方自己伪造。
- **失败方向选安全那一边**：白名单读不出来（库连不上、值写坏）时只放行 loopback。

实测（2026-08-30，本机 LAN 地址是 `192.168.176.68`）：绑 `0.0.0.0` 后
`http://192.168.176.68:18420/` 返回 **403**（响应体里写明来源地址和加白的办法），
把 `.68` 加进白名单 4 秒后同一地址 **200**，移除后又回到 **403**；`127.0.0.1` 全程 200。

- `config.setting` 里这两项在 `05_seed.sql` 用 `ON CONFLICT DO NOTHING`（其余设置是
  `DO UPDATE`）—— 重跑 seed 不能把用户在页面上改的白名单拍回默认值。
- 一旦 `config.app_user` 里有启用的账号，登录门自动生效，不需要改配置
- `/sql` 只读、只用 `ft_reader`、语法树校验、强制 LIMIT

## 十一、怎么加东西（快速索引）

| 想做什么 | 在哪里做 | 要不要改代码 |
|---|---|---|
| 加/挪一个菜单项 | `/blocks` → 页面搭建 → 建菜单 | 不用 |
| 给页面加一张卡片 | `/blocks` → 页面搭建 → 加卡片 | 不用 |
| 换一个图的类型或字段映射 | `/blocks` → chart 表 | 不用 |
| 调评分权重 | `/blocks` → binding 表 | 不用 |
| 调某个脚本的参数（如成交分项的上下界） | `/blocks` → binding 表的 `params` | 不用 |
| 加一条质检规则 | `/blocks` → quality_rule 表（一行 SQL） | 不用 |
| 加一个筛选条件类型 | `/blocks` → screen_rule 表（一行 WHERE 片段模板；列名/运算符这类参数必须带 `literal+enum`，见 5.7） | 不用 |
| 加一个定时作业 | `/blocks` → job 表 + `params.runner` 选执行器 | 不用（执行器已有的话） |
| 改一句窗口说明 / 加整页说明 | `/blocks` → ② 说明维护（`config.help_note`，刷新即生效） | 不用 |
| 改一句到处都在引用的口径（如操作分公式） | `/blocks` → ② 说明维护 → 改 `snip.*` 片段，所有 `includes` 它的说明跟着变 | 不用 |
| 加一个新的取数查询 | `app/web/queries.py` 里 `@register` | 要 |
| 加一块计算积木 | `app/compute/builtin/*.py` + `config.script`/`binding` | 要 |
| 加一种卡片类型 | `app/web/ui.py` 的 `render_card` | 要 |
| 加一个可被调度的脚本 | `app/orchestrator/runner.py` 的 `RUNNERS` | 要 |
| 改「一键追平」的步骤或顺序 | `scripts/ops/e1_fill_all.py` 的 `STAGES` + `plan` | 要 |
| 改"最新已收盘交易日"的判据 | `app/orchestrator/tradeday.py`（页面和脚本共用） | 要 |
| 给表格加/去行情外链 | `app/quote_link.py`（规则）+ `ui.table(link_codes=…)` | 要 |
| 给某个页面支持 URL 深链 | 页面 `render(params=None)` + `app/quote_link.detail_link()` | 要 |
