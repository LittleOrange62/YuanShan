# 块 4 · 数据质量与口径契约

这是用户需求里空着的第 "4."。

## 为什么它必须是独立一块

前两套系统的故障不是功能缺失，而是**数据是错的但没人知道**。清单：

| 缺陷 | 后果 | 沉默程度 |
|---|---|---|
| `amount` 写元、文档写千元 | 1000× 偏差 | 完全无告警 |
| 分钟线 `vol` 写股、文档写手 | 100× 偏差 | 完全无告警 |
| `limit_up = pre_close × 1.1` 一刀切 | 创业板/科创板/北交所涨跌停全错 | 完全无告警 |
| `adjustment_factor` 硬编码 1.0 | 全部数据未复权，跨除权日指标全错 | 完全无告警 |
| `calc_y_at_date` 漏传 `block_stocks` | Y 轴 65% 权重失效，75,995 条打分受影响 | 完全无告警 |
| `score_*d_*` 用当前窗口而非传入日期 | 回溯计算全错 | 完全无告警 |
| `_is_trading_day` 返回 `weekday()<5` | 节假日跑任务、产出垃圾数据 | 日志显示"成功" |
| 两套 ETL 行数差 1.8% | 不知道哪个对 | 无人比对 |
| `880*` 板块伪代码混入 `stock_daily` | 统计口径污染 | 靠事后写脚本删 |

共同点：**都是安静地错**。功能都在跑，日志都是绿的，页面都有数字。

一个复盘系统的输出是决策依据。错的数字比没有数字危险得多。所以质量与口径不能是"块 1 里顺手做的校验"，必须是有独立表、独立页面、独立作业、能阻断流程的一块。

## 三个组成部分

```
┌──────────────────┐
│ 1. 口径注册表     │  每个字段的单位、量纲、值域、计算口径 —— 机器可读
│    units.py      │
├──────────────────┤
│ 2. 校验规则       │  落库前拦截 + 落库后审计，规则存表可配
│    rules.py      │
├──────────────────┤
│ 3. 血缘           │  任何一行数据可回溯到源文件与批次
│    lineage.py    │
└──────────────────┘
```

## 一、口径注册表

### 字段名自带单位

第一道防线是命名，最便宜也最有效：

| 不要 | 要 |
|---|---|
| `amount` | `amount_yuan` |
| `vol` | `volume_shares` |
| `mktcap` | `mktcap_yuan` |
| `turnover` | `turnover_rate_percent` |
| `chg` | `pct_change` / `change_yuan` |

单位歧义在字段名层面就不存在了。1000× 偏差这种事无法再发生 —— 你不会把千元数字写进叫 `amount_yuan` 的列。

### 机器可读的注册表

```python
# app/quality/units.py
from dataclasses import dataclass

@dataclass(frozen=True)
class FieldSpec:
    table: str
    column: str
    label_cn: str
    unit: str                  # 'yuan' | 'shares' | 'pct' | 'ratio' | 'count' | 'none'
    dtype: str
    nullable: bool
    value_range: tuple | None  # 硬性值域，越界即错误
    sane_range: tuple | None   # 合理量级，越界告警但不阻断
    formula: str | None        # 计算口径，人类可读
    source: str                # 'vipdoc.day' | 'tqcenter.snapshot' | 'derived'

REGISTRY: list[FieldSpec] = [
    FieldSpec('market_data.stock_daily', 'amount_yuan', '成交额', 'yuan', 'numeric',
              True, (0, None), (1e4, 1e12),
              '来自 .day 第6字段 float32，原始单位即元，不做换算',
              'vipdoc.day'),
    FieldSpec('market_data.stock_daily', 'volume_shares', '成交量', 'shares', 'bigint',
              True, (0, None), (0, 1e12),
              '来自 .day 第7字段 uint32，原始单位股；显示为手时 ÷100',
              'vipdoc.day'),
    FieldSpec('market_data.stock_daily', 'pct_change', '涨跌幅', 'pct', 'numeric',
              True, (-100, 1000), (-31, 31),
              '(close - pre_close) / pre_close * 100',
              'derived'),
    FieldSpec('market_data.stock_daily', 'limit_up', '涨停价', 'yuan', 'numeric',
              True, (0, None), None,
              'pre_close * (1 + board_limit)，board_limit 取自 reference_data.security.board：'
              '主板 0.10 / 创业板 0.20 / 科创板 0.20 / 北交所 0.30；ST 主板 0.05',
              'derived'),
    FieldSpec('market_data.stock_daily', 'adjustment_factor', '复权因子', 'ratio', 'numeric',
              True, (0, None), (0.01, 1000),
              '由 reference_data.dividend 分红送配记录从最新交易日往前累乘',
              'derived'),
    # ... 全字段登记
]
```

`formula` 字段是文档与代码的唯一交汇点。不再出现"文档说千元、代码写元"——文档就是从这里生成的。

### 三处同步产出

同一份注册表驱动三件事，天然不会漂移：

1. **PG 注释** — 迁移时生成 `COMMENT ON COLUMN market_data.stock_daily.amount_yuan IS '成交额（元）| ...'`
2. **`ftdb.field_dict()` 与 `operations.view_field_dict` 视图** — 智能体查表结构时直接看到单位与口径，写 SQL 不会算错
3. **`docs/字段字典.md`** — 自动生成，不手写

旧系统 `core/field_comments.py` 是个纯字典且**比实际 schema 宽**（含 `kline_factors`/`etf_info`/`sector_heat` 等 `db.py` 根本不创建的表）。新注册表在启动时与 PG 实际列做双向比对：注册表有而库里没有、库里有而注册表没登记，都报错。

## 二、校验规则

### 两个执行点

**落库前（拦截式，在 `repo` 层）**

```python
def upsert_daily(rows: list[dict], batch_id: int):
    report = validate(rows, table='market_data.stock_daily', mode='block')
    if report.has_errors:
        raise DataContractError(report)      # 不写库，任务失败
    if report.has_warnings:
        logger.warning(report.summary())     # 写库，但登记告警
    _copy_and_upsert(rows, batch_id)
```

`value_range` 越界 = error，阻断。`sane_range` 越界 = warning，放行但记录。这个区分很重要：真实市场会出现极端值，硬拦会导致正常数据进不来；但量级错了（元/千元混淆是 1000 倍）一定会撞穿 `sane_range`。

**落库后（审计式，`quality_audit` 作业）**

跨行、跨表、跨日的检查，只能在数据落地后做。

### 规则清单

规则存 `config.quality_rule` 表，可增删改，不改代码：

```sql
CREATE TABLE config.quality_rule (
    rule_key   text PRIMARY KEY,
    name       text NOT NULL,
    scope      text NOT NULL,          -- row|table|cross_table|cross_day
    severity   text NOT NULL,          -- error|warning|info
    target     text NOT NULL,          -- 'market_data.stock_daily'
    expr       text NOT NULL,          -- SQL 布尔表达式，或内置规则标识
    threshold  jsonb,
    enabled    boolean NOT NULL DEFAULT true,
    description text
);
```

**行级（落库前）**

| rule_key | 检查 | severity |
|---|---|---|
| `ohlc_order` | `low <= open,close <= high` | error |
| `price_positive` | 价格 > 0 或 NULL | error |
| `amount_sane` | `amount_yuan` ∈ [1e4, 1e12] | warning |
| `vol_amount_consistent` | `amount_yuan / volume_shares` ∈ [0.5×low, 2×high] | warning |
| `pct_chg_bound` | `pct_change` ∈ [-31, 31] | warning |
| `pct_chg_recompute` | 与 `(close-pre_close)/pre_close*100` 差值 < 0.01 | error |
| `date_valid` | `trade_date` 在 `reference_data.trade_calendar` 且 `is_open` | error |
| `code_format` | `security_code` 匹配 `^\d{6}\.(SH|SZ|BJ)$` | error |
| `not_sector_code` | `security_code` 前缀不是 `880`/`881`（板块不该进 stock 表） | error |

`vol_amount_consistent` 是单位错误的专门探测器：成交额除以成交量应该落在当日价格区间内。如果 `amount` 单位错了 1000 倍，这个比值会离价格区间差三个数量级，立刻暴露。**如果旧系统有这一条，1000× 偏差不会存在三个月。**

**表级（落库后）**

| rule_key | 检查 | severity |
|---|---|---|
| `daily_row_count` | 当日 A 股行数 ≥ 4,800 | error |
| `index_present` | `000001.SH` 与 `399001.SZ` 当日均有行 | error |
| `null_rate` | `close IS NULL` 比例 < 0.1% | error |
| `dup_check` | `(security_code, trade_date)` 无重复（PK 保证，兜底） | error |
| `board_coverage` | 所有 `security_code` 在 `reference_data.security` 中有 `board` | error |
| `limit_price_by_board` | 涨停价/前收比值与 `board` 匹配 | error |

**跨日**

| rule_key | 检查 | severity |
|---|---|---|
| `pre_close_chain` | 本日 `pre_close` = 上一交易日 `close`（除权日按 `adjustment_factor` 容忍） | error |
| `no_gap` | 相邻交易日之间无缺口 | error |
| `row_count_drift` | 当日行数与近 20 日均值偏离 < 5% | warning |
| `amount_magnitude_drift` | 当日 `amount_yuan` 中位数与近 20 日均值偏离 < 10× | error |

`amount_magnitude_drift` 专门抓"某天起单位变了"这类回归。

**跨表**

| rule_key | 检查 | severity |
|---|---|---|
| `minute_daily_consistent` | 分钟线当日聚合 = 日线（抽样 100 只，容差 0.5%） | warning |
| `sector_member_valid` | `sector_member` 里的成分股都在 `reference_data.security` | warning |
| `score_coverage` | 有日线的标的应有评分（覆盖率 > 95%） | warning |

`minute_daily_consistent` 是最强的交叉验证：两个独立数据源（`.day` 与 `.lc1`）聚合后应该吻合。旧系统从未做过这个比对，所以两套 ETL 行数差 1.8% 三个月没人发现。

**因子/评分级**

| rule_key | 检查 | severity |
|---|---|---|
| `score_range` | 各评分在 `output_spec` 声明值域内 | error |
| `score_not_constant` | 子分项在全市场的标准差 > 0（**恒为 0 说明该分项失效**） | error |
| `weight_sum` | `config.binding` 归一化后权重和 = 1 | error |
| `score_dist_drift` | 评分分布与近 20 日 KS 检验 | warning |

`score_not_constant` 就是能抓住"Y 轴板块热度恒为 0"那个 bug 的规则。旧系统跑了 75,995 条记录，板块热度全是 0，标准差为 0，一条规则就能在第一天报出来。

### 结果存储

```sql
CREATE TABLE operations.quality_result (
    id         bigserial PRIMARY KEY,
    run_at     timestamptz NOT NULL DEFAULT now(),
    trade_date date,
    rule_key   text NOT NULL,
    target     text NOT NULL,
    severity   text NOT NULL,
    passed     boolean NOT NULL,
    actual     jsonb,           -- 实测值
    expected   jsonb,           -- 期望
    sample     jsonb,           -- 违规样本，最多 10 条
    batch_id   bigint
);
CREATE INDEX ON operations.quality_result (trade_date, passed);
```

`sample` 让排查不需要重新写 SQL 找问题行。

### 阻断逻辑

```
同步完成
   │
   ├─ 行级校验（已在落库前执行）
   │
   ├─ quality_audit 作业：表级 + 跨日 + 跨表
   │
   ├─ 有 error？
   │    ├─ 是 → 不写 operations.data_ready
   │    │        → 下游加工作业不触发
   │    │        → /quality 页面红色告警 + 推送
   │    └─ 否 → 写 operations.data_ready → 触发块2
   │
   └─ warning 只记录不阻断
```

**这是块 4 存在的意义**：它有权力阻止错误数据流向下游。校验不能只是"写个报告放着"——那和旧系统的日志没区别。

## 三、血缘

### 采集

`operations.ingest_batch` 记录每一批（表结构见 [02-数据层与存储.md](02-数据层与存储.md)），`md.*` 各表带 `source_batch_id` 外键。

派生数据同理：`analytics.score` 带 `task_id` → `operations.task` → `capability_key` + `script_id` + `params`。

### 能回答的问题

| 问题 | 查询路径 |
|---|---|
| 这行日线从哪来的？ | `market_data.stock_daily.source_batch_id` → `operations.ingest_batch.source_path` + `source_mtime` |
| 这个评分是哪个脚本哪个版本算的？ | `analytics.score.task_id` → `operations.task.script_id` → `config.script.checksum` + `version` |
| 权重改过之后哪些结果需要重算？ | `config.binding.updated_at` > `analytics.score.calculated_at` |
| 某个源文件解析有 bug，影响了哪些数据？ | `operations.ingest_batch WHERE source_path=...` → 反查 `source_batch_id` |
| 这个脚本改了，历史结果还有效吗？ | 比对 `config.script.checksum` 与任务记录里的 checksum |

最后一条解决旧系统 `05_辅助工具` 里"19 个脚本同日多次迭代、文件名即版本号"的困境：不需要靠文件名记版本，checksum 自动追踪。

### 重算标记

脚本或权重变更后，受影响的历史结果标记 `stale`：

```sql
UPDATE analytics.score SET is_stale = true
WHERE capability_key = 'oper_score'
  AND calculated_at < (SELECT max(updated_at) FROM config.binding WHERE capability_key='oper_score');
```

页面展示 stale 数据时明确标注，并提供"重算"按钮。旧系统权重一改，历史 75,995 条记录就与新配置不一致，但页面上完全看不出来。

## 迁移期的存量数据处理

历史数据（9,531,333 行日线）迁入时必然带着已知错误。处理原则：

| 问题 | 处理 |
|---|---|
| `amount` 单位 | 迁移时不换算（本来就是元），只改字段名，并跑 `vol_amount_consistent` 全量验证 |
| `adjustment_factor` 全 1.0 | 迁移后用分红记录全量重算 |
| `limit_up/down` 一刀切 | 迁移时置 NULL，按 `board` 全量重算。**宁可 NULL 也不留已知错误值** |
| `880*` 混入 `stock_daily` | 迁移时按前缀分流到 `market_data.sector_daily` |
| 两套 ETL 1.8% 差异 | 逐条比对归因后再选主源，不能"选一个数字了事" |
| 75,995 条评分（Y 轴失效） | 全部标 `is_stale`，修好依赖后重算，不直接信任 |

## 一句话总结

块 1、2、3 决定系统**能做什么**；块 4 决定系统**说的话能不能信**。一个每天输出决策依据的复盘系统，后者的价值不低于前者。
