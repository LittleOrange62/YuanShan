# 块 2 · 定时任务与策略注册表

这一块是需求里说得最具体的一条："**确认数据有了就定时进行加工——有很多策略去执行，功能点和脚本的匹配关系要能够自定义**"。

## 核心思路

功能点与脚本的绑定关系是**数据**，存在 PG 表里，页面上可编辑，不是代码里的 if/else。

```
┌──────────────┐      ┌───────────────┐      ┌──────────────┐
│  功能点       │ 多对多│  绑定关系      │      │  脚本         │
│  capability  │◄─────┤  binding      ├─────►│  script      │
│ "个股质量评分"│      │ 权重/顺序/参数 │      │ x_score.py   │
└──────────────┘      └───────────────┘      └──────────────┘
       ▲                                             ▲
       │ 被作业引用                                   │ 被沙箱加载
┌──────────────┐                            ┌──────────────┐
│  作业 job     │ 触发条件 + 依赖 → DAG      │  执行器 runner│
└──────────────┘                            └──────────────┘
```

四张核心表：`config.capability`、`config.script`、`config.binding`、`config.job`。

## 表设计

### config.capability — 功能点

功能点是"业务上要算出什么"，与实现无关。

```sql
CREATE TABLE config.capability (
    capability_key     text PRIMARY KEY,        -- 'stock_quality' / 'sector_heat' / 'oper_score'
    name        text NOT NULL,           -- '个股质量(X轴)'
    category    text NOT NULL,           -- factor|screen|report|derive
    output_kind text NOT NULL,           -- score|series|table|file
    output_spec jsonb NOT NULL,          -- 输出字段与类型契约
    depends_on  text[] DEFAULT '{}',     -- 依赖的其他 capability_key
    requires    jsonb NOT NULL,          -- 需要哪些数据集就绪：{"datasets":["market_data.stock_daily"],"lookback_days":250}
    is_active   boolean NOT NULL DEFAULT true,
    description text
);
```

`requires.lookback_days` 很关键：`stock_quality` 需要 250 天历史（250 日高低点），调度器据此判定"数据够不够"，而不是跑到一半才发现数据不足。

### config.script — 脚本登记

```sql
CREATE TABLE config.script (
    script_id    bigserial PRIMARY KEY,
    script_key   text UNIQUE NOT NULL,   -- 'x_score_v2'
    name         text NOT NULL,
    path         text NOT NULL,          -- 相对 app/strategies/ 的路径
    entry        text NOT NULL DEFAULT 'run',
    version      text,
    param_schema jsonb,                  -- JSON Schema，用于校验 params 并生成配置表单
    provides     text[] NOT NULL,        -- 这个脚本能实现哪些 capability_key
    checksum     text,                   -- 文件内容 hash，改动可感知
    is_active    boolean NOT NULL DEFAULT true,
    registered_at timestamptz NOT NULL DEFAULT now(),
    last_ok_at   timestamptz,
    last_error   text
);
```

`param_schema` 让页面能自动渲染参数表单——加一个新策略不需要改前端。

`checksum` 解决一个现实问题：`05_辅助工具` 里 19 个脚本"同日多次迭代，文件名即版本号"。有 checksum 后，脚本改了系统知道，可以标记历史结果需要重算。

### config.binding — 功能点 ↔ 脚本 映射（可自定义的核心）

```sql
CREATE TABLE config.binding (
    binding_id bigserial PRIMARY KEY,
    capability_key    text NOT NULL REFERENCES config.capability(capability_key),
    script_id  bigint NOT NULL REFERENCES config.script(script_id),
    weight     numeric(8,4) NOT NULL DEFAULT 1.0,   -- 多脚本合成时的权重
    display_order        int NOT NULL DEFAULT 0,              -- 执行顺序
    params     jsonb NOT NULL DEFAULT '{}',         -- 覆盖脚本默认参数
    enabled    boolean NOT NULL DEFAULT true,
    note       text,
    updated_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (capability_key, script_id)
);
```

这张表让以下场景全部变成"改配置"而非"改代码"：

- 一个功能点由多个脚本加权合成 → 插多行，设 `weight`
- 换实现 → 旧行 `enabled=false`，新行 `enabled=true`
- A/B 对比 → 两个 `capability_key`（`oper_score` / `oper_score_exp`）各绑不同脚本，结果并排看
- 同一脚本不同参数复用 → 两条 binding，`params` 不同
- 临时停用某个子因子 → 单行 `enabled=false`

**与旧系统的对比**：`financeWeb` 的 `factor_engine.py` 把权重写死在代码里：

```python
X    = 0.25*形态 + 0.25*趋势 + 0.20*位置 + 0.20*筹码 + 0.10*量能   # :148
Y    = 0.65*板块热度 + 0.35*大盘情绪                              # :281
oper = 0.40*X + 0.60*Y                                          # :300
```

改权重要动代码、重启服务。新系统这些数字全在 `config.binding.weight` 里。

**权重归一化**：读取时按 `enabled=true` 的行归一化（`w_i / Σw`），这样停用一个子因子后剩下的权重自动补齐，不会出现总和不为 1 的静默错误。

### config.job — 作业与触发

```sql
CREATE TABLE config.job (
    job_id      bigserial PRIMARY KEY,
    job_key     text UNIQUE NOT NULL,
    name        text NOT NULL,
    caps        text[] NOT NULL,           -- 本作业要产出的功能点
    trigger_kind text NOT NULL,            -- cron | on_ready | manual | chain
    cron_expr   text,                      -- trigger_kind='cron'
    ready_on    text[],                    -- trigger_kind='on_ready'：等哪些数据集就绪
    after_job   text,                      -- trigger_kind='chain'
    scope       jsonb NOT NULL DEFAULT '{"universe":"all"}',  -- all|watchlist|focus|sector|自定义列表
    only_trade_day boolean NOT NULL DEFAULT true,
    max_retry   int NOT NULL DEFAULT 2,
    timeout_sec int NOT NULL DEFAULT 1800,
    concurrency_key text,                  -- 同 key 的作业串行，防并发写同一批数据
    enabled     boolean NOT NULL DEFAULT true
);
```

`trigger_kind='on_ready'` 是需求里"确认数据有了就加工"的直接实现：不是猜一个时间点，而是等 `operations.data_ready` 落表后事件触发。

`concurrency_key` 是并发防护：所有写 `analytics.score` 的作业共用一个 key，同时只有一个在跑。

## 就绪判定与触发

```
块1 同步完成
     │
     ├─→ 校验通过（见 06-数据质量文档）
     │
     └─→ INSERT operations.data_ready(trade_date, dataset, row_count, ready_at)
                │
                ▼
     scheduler 监听（PG LISTEN/NOTIFY 或 15s 轮询）
                │
                ├─ 匹配 config.job WHERE trigger_kind='on_ready'
                │     AND ready_on <@ 已就绪数据集
                │
                ├─ 检查 only_trade_day → reference_data.trade_calendar.is_open
                │
                ├─ 检查 capability.requires.lookback_days 是否满足
                │
                └─→ planner 生成 DAG → 入 operations.task 队列
```

同时保留 cron 触发作为兜底与非数据依赖型作业（例如 20:00 生成日报）。

**双保险**：`on_ready` 事件触发 + cron 兜底（如 `run_scores` 既订阅就绪事件，也配 19:30 cron；执行器用 `(job_key, trade_date)` 唯一约束保证同一天只跑一次成功）。这样既做到"数据到了立刻算"，又不会因为事件丢失而当天不算。

## DAG 与依赖解析

`planner.py` 根据 `capability.depends_on` 拓扑排序。

举例，`oper_score` 依赖 `stock_quality` 和 `env_resonance`：

```
                 ┌─ stock_quality (X)  ─┐
data_ready ──────┤                       ├──> oper_score ──> quadrant_report
                 └─ env_resonance  (Y)  ─┘
                        ▲
                        └─ sector_heat, market_mood
```

- 同层节点并行执行（`ThreadPoolExecutor`，并发度可配）
- 上游失败则下游标记 `skipped`，不是静默跑出错误结果
- 检测到环立即报错，不允许保存这样的配置

**这里修一个旧系统的实质 bug**：`factor_engine.py:478` 调用 `calc_y_at_date(sub, all_data, date_str)` 漏传第 4 个参数 `block_stocks`，而 `calc_y_at_date:260` 是 `if block_stocks:` —— 结果板块热度恒为 0，Y 轴 65% 的权重完全失效，已存的 75,995 条打分记录全部受影响。

新系统的防护是双层的：

1. `capability.requires` 显式声明依赖，planner 保证 `sector_heat` 先算完并把结果注入下游
2. 策略入参用 pydantic 模型校验，缺必填字段直接抛错而不是走进 `if` 的 false 分支

## 策略脚本契约

`app/strategies/__contract__.py`：

```python
from dataclasses import dataclass
from datetime import date
import threading
import pandas as pd

@dataclass(frozen=True)
class StrategyContext:
    trade_date: date                  # 目标交易日（不是"今天"）
    universe: list[str]               # 标的列表，由 job.scope 解析而来
    params: dict                      # binding.params 合并 script 默认值
    repo: "Repo"                      # 数据访问层，唯一取数入口
    logger: "Logger"
    cancel: threading.Event           # 协作式取消，必须定期检查
    progress: "Callable[[int, str], None]"   # progress(pct, message)

@dataclass
class StrategyResult:
    frame: pd.DataFrame               # 必须含 security_code + output_spec 声明的列
    meta: dict                        # 任意补充信息，落 operations.task.result_meta
    warnings: list[str]

def run(ctx: StrategyContext) -> StrategyResult:
    ...
```

**契约里的四条硬规则**

1. **一切时间以 `ctx.trade_date` 为基准**，脚本内禁止调用 `date.today()` / `datetime.now()`。
   这修的是旧系统一个隐蔽的严重问题：`scripts/score_10d_chg.py` 等四个脚本用 `get_recent_dates()` 取**当前**窗口，无视传入的历史 `date_str`，导致任何回溯计算都是错的。新系统在沙箱里把 `datetime.date.today` 替换为返回 `ctx.trade_date` 的桩，并在代码审查规则里静态禁止。

2. **取数只能经 `ctx.repo`**，禁止 `psycopg.connect` / `sqlite3.connect` / 读文件。沙箱不向脚本暴露 DSN。

3. **必须周期性检查 `ctx.cancel.is_set()`** 并及时返回。
   旧系统的取消是假的：`/api/task/cancel:636` 只改内存状态，handler 拿到的是新建的 Event 永不 set，`_finish_task:76` 又把状态覆盖回 done/error。新系统 `cancel_event` 存在 runner 里、由 `operations.task.cancel_requested` 字段驱动，终态一旦是 `cancelled` 不再被覆盖。

4. **输出必须匹配 `capability.output_spec`**，runner 在写库前用 pydantic 校验列名、类型、值域。不匹配则任务失败，不写库。

### 内置策略与外部脚本一视同仁

旧系统区别对待：走外部脚本时 `x/y/oper` 被硬编码为 `0.0`（`factor_engine.py:438`），等于外部脚本无法产出主评分。

新系统内置策略也放在 `app/strategies/builtin/`，用同一个 `run(ctx)` 契约，走同一个注册表。没有特权路径。

### 沙箱加载

```python
spec = importlib.util.spec_from_file_location(f"strategy_{key}", abs_path)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)
```

沿用 financeWeb 验证过的 `importlib` 方式，但增加：

- 加载前校验 `checksum`，变了就重新登记并记录
- 加载失败 → 任务 `failed` + 写 `config.script.last_error`，**不静默回退到内置实现**（旧系统 `:457` 会静默 fallback，导致你以为在跑新脚本其实在跑老逻辑）
- 每个任务独立子进程执行（`multiprocessing`），脚本崩溃不拖垮 worker，`timeout_sec` 到点真能 kill

**旧系统的超时为什么无效**：`task_http_api.py:434` 用 `for line in proc.stdout:` 阻塞读取，永远走不到 `proc.wait(timeout=...)`，泄漏两次整个任务 API 就死锁。新实现用 `subprocess` + 独立读线程 + `proc.kill()` 兜底，或直接用 `multiprocessing.Process.terminate()`。

## 任务队列

```sql
CREATE TABLE operations.task (
    task_id     bigserial PRIMARY KEY,
    job_key     text,
    capability_key     text,
    script_id   bigint,
    trade_date  date NOT NULL,
    scope       jsonb,
    params      jsonb,
    state       text NOT NULL,          -- pending|running|succeeded|failed|cancelled|skipped
    progress    int NOT NULL DEFAULT 0,
    message     text,
    attempt     int NOT NULL DEFAULT 0,
    max_retry   int NOT NULL DEFAULT 2,
    cancel_requested boolean NOT NULL DEFAULT false,
    concurrency_key text,
    depends_on  bigint[],
    created_at  timestamptz NOT NULL DEFAULT now(),
    started_at  timestamptz,
    finished_at timestamptz,
    result_meta jsonb,
    error       text,
    UNIQUE (job_key, capability_key, trade_date, attempt)
);
CREATE INDEX ON operations.task (state, created_at);
```

**关键改进对比旧系统**

| 旧 | 新 |
|---|---|
| 两套队列并存（`core/task_queue.py` Tk 绑定且 web 零使用；`worker_*` 跨进程 HTTP 8766） | 一套，落 PG |
| 任务不持久化，重启全丢 | 落表，重启后 `running` 的任务重新入队 |
| 取消是假的 | `cancel_requested` 字段 → runner set Event → 脚本响应 → 终态 `cancelled` 不被覆盖 |
| `progress_cb` 只写内存，不推送 | 写 `operations.task.progress`，页面轮询即可看到 |
| 无重试 | `attempt` / `max_retry`，指数退避 |
| `MAX_CONCURRENT=2` 硬编码 | 配置项 + `concurrency_key` 细粒度串行 |
| 无 `skipped` 状态，上游失败下游照跑 | 上游失败 → 下游 `skipped` |

worker 拉任务用 `SELECT ... FOR UPDATE SKIP LOCKED`，多 worker 天然安全：

```sql
UPDATE operations.task SET state='running', started_at=now()
WHERE task_id = (
    SELECT task_id FROM operations.task
    WHERE state='pending'
      AND (depends_on IS NULL OR NOT EXISTS (
            SELECT 1 FROM operations.task d
            WHERE d.task_id = ANY(operations.task.depends_on)
              AND d.state <> 'succeeded'))
      AND (concurrency_key IS NULL OR NOT EXISTS (
            SELECT 1 FROM operations.task r
            WHERE r.concurrency_key = operations.task.concurrency_key
              AND r.state = 'running'))
    ORDER BY created_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
) RETURNING *;
```

## 调度器

`APScheduler` + PG JobStore（持久化），或自建 15s 轮询循环。两者都可，关键是：

- **交易日判定走 `reference_data.trade_calendar`**，不是 `weekday() < 5`。旧 `scheduler.py:229-242` 算了 `latest`/`today` 变量然后三个 return 全是 `weekday() < 5`，节假日照样触发。
- **不做"全局跳过但仍打日志"这种事**。旧 `scheduler.py:289-291` 让 `tdx_flow` 规则永远跳过却仍写日志，日志看起来在工作实际什么也没干。要么删掉规则，要么真跑。
- **规则来源单一**：全在 `config.job` 表。旧系统规则来自 `data_sync_config` 表 + 3 个 `mcp_config` key 的合并，且有 30s 缓存，难以推断实际生效值。

## 页面上怎么配

`/orchestrator` 页面三个 Tab：

**Tab 1 · 功能点** — 列表展示 `capability_key` / 名称 / 分类 / 依赖 / 已绑脚本数 / 最近成功时间。点进去看这个功能点绑了哪些脚本、各自权重，可拖拽调顺序、直接改权重、开关 enabled。归一化后的实际权重实时显示。

**Tab 2 · 脚本** — 扫描 `app/strategies/` 自动发现新文件并提示登记；显示 `checksum` 变更；`param_schema` 自动渲染成参数表单；"试跑"按钮可指定单个 `trade_date` + 小范围标的，结果只回显不落库。

**Tab 3 · 作业** — 触发方式配置、`scope` 选择、并发键、重试与超时；下方是任务列表（状态 badge、进度条、耗时、真实可用的取消按钮、失败原因、一键重跑）。

沿用 financeWeb 已验证的 `scoring_plans` 页面交互形态，但把"计划"拆成了"功能点 + 脚本 + 绑定"三层，这才是"匹配关系可自定义"要求的三层结构。

## 加工内容清单（首批实现）

基础因子（`calc_base_factors`）：MA5/10/20/30/60/120，BIAS5/10/20，CCI，ATR，MACD/Signal/Hist，量比，振幅，换手率，250 日高低点位置。字段清单沿用 `financeWeb/core/constants.py` 的 `FACTOR_FIELDS`。

评分（`calc_scores`），迁移旧逻辑但权重全部外置：

| 功能点 | 子项 | 旧硬编码权重（迁为配置默认值） |
|---|---|---|
| `stock_quality` (X) | 形态/趋势/位置/筹码/量能 | 0.25/0.25/0.20/0.20/0.10 |
| `sector_heat` | 涨幅/广度/动量/成交额 | 0.30/0.30/0.25/0.15 |
| `market_mood` | 平均涨跌幅×10 + (上涨占比−0.5)×100 | — |
| `env_resonance` (Y) | 板块热度/大盘情绪 | 0.65/0.35（**旧系统这里失效，见上文**） |
| `oper_score` | X/Y | 0.40/0.60 |

`market_mood` 旧实现用全市场个股统计而非指数，这个选择本身合理（能反映赚钱效应），保留，但在 `output_spec` 里注明口径。

四象限分类（Q1 买入 / Q2 持有 / Q3 试探 / Q4 回避）作为 `build_review` 的一部分。

其余可迁移的现成脚本：`score_10d_chg` / `score_10d_amp` / `score_20d_chg` / `score_20d_amp`（**必须先修 `get_recent_dates` 无视 `date_str` 的问题**）、`score_amp_trend`（21 天 → 20 个振幅点 → polyfit 外推）、`temp_score`（温度 = 位置分+量比分+趋势分+危险分，按流通市值插值阈值）、`calc_concept_heat` / `calc_group_heat`（旧版写 `data/scoring.db` 而该文件不存在，写入路径本就是失败的，改为写 `fct.*`）。

`_common_10d.py` 里的日涨幅/日振幅口径要注意：分母是**前收盘**而非开盘（`(h−l)/prev_c*100`）。这是个刻意选择，迁移时在 `output_spec` 里写清楚，不要"顺手改成教科书口径"导致历史数据不可比。
