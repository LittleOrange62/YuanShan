## 2. 边界：调度器只管"什么时候干什么"，只管这一件事

| | 调度器 scheduler | 执行器 runner | worker |
|---|---|---|---|
| 决定**该不该跑** | ✅ | ❌ | ❌ |
| 决定**怎么跑**（argv、白名单、超时） | ❌ | ✅ | ❌ |
| 真正起子进程、回收、写终态 | ❌ | ✅ | ✅（复用 runner） |
| 生命周期 | 常驻 | 被调用 | 常驻 |

调度器**不 import subprocess、不碰 vipdoc、不算因子**。它唯一输出的副作用是往 `operations.task` 插 `pending` 行。这条边界要卡死，理由见 §7.1：旧系统的调度器就是因为顺手自己做了别的事，才出现了"日志看着在工作、实际什么都没干"。

## 4. 三个职责分别怎么实现

### 4.1 看时间 —— 自建 tick 循环，cron 解析器也自己写

**决策：不用 APScheduler 的 Scheduler 本体，自己写 15 秒轮询。** 这与 `docs/01-架构总览.md`（"调度 | APScheduler（持久化 JobStore 落 PG）"）相反，是有意的偏离，理由三条：

1. **JobStore 与 `config.job` 是两个事实来源。** APScheduler 把下次触发时间存在自己的 `apscheduler_jobs` 表里，而作业规则在 `config.job`。积木管理页改一行 `cron_expr`，还得同步通知 APScheduler 重排 job；漏一次同步，页面上显示的 cron 和实际触发时刻就不一致——这正是本系统立项要消灭的那类"看着配好了其实没生效"。轮询循环每 tick 直接读 `config.job`，改完即刻生效，无缓存。
2. **需要"错过补偿"语义**（§7.2）。APScheduler 的 `missed_run_policy` 处理不了"按点击时刻算目标交易日"这种业务判定——`e1_fill_all.py` 开头用 30 行注释讲清楚的那三步（先同步日历 → 15:30 收盘线 → 取最后一个开市日）必须自己写。
3. **Windows 上没有 cron 的原生等价物**，APScheduler 常驻仍要靠一个 Python 进程守着自己，省不掉。

#### 原计划的"只借它的 CronTrigger 当解析器"也被实测否掉了

本文档 2026-09-20 初稿写的是"用 `apscheduler.triggers.cron.CronTrigger` 解析
`cron_expr`，零新增依赖"。2026-09-21 实现时实测推翻了：

```
CronTrigger.from_crontab('10 15 * * 1-5').get_next_fire_time(...)   → 触发在周二
CronTrigger.from_crontab('10 15 * * 0-4')                           → 触发在周一
CronTrigger.from_crontab('10 15 * * 7')                             → ValueError: 7 > 6
```

**APScheduler 3.x 的 `day_of_week` 是 0=周一…6=周日；标准 cron 是 0=周日、7=周日。**
`config.job` 里种的那批表达式（`sync_daily` 的 `10 15,16,17 * * 1-5`、
`sync_reference` 的 `0 8 * * 1-5`）是按标准 cron 写的，接上去的后果是
`sync_daily` **周二到周六**触发：周一整天不采、周六白采一趟，
而 `/jobs` 页面把 `1-5` 明明白白显示在「触发」列里，没有任何异常。

这类错误不会以报错的形式出现，只会以"数据少了三天"的形式出现，没人当场查得出来。
所以不能靠"在文档里提醒一句 0 是周一"绕过——下一个填表达式的人照样踩。
改成自己实现（`app/orchestrator/schedule.py` 的 `_CronSpec`，约 90 行），
语义按 Vixie cron：

* 星期 `0`/`7` 都是周日，`1-5` 是周一至周五，支持 `sun`–`sat` 名字与 `fri-mon` 回绕；
* dom 与 dow **都**受限时取并集（Vixie 的 OR 规则），不是交集；
* 表达式写错当场抛 `ValueError`，由调度器捕获后写成该作业的 skip 原因——
  绝不退化成"静默永不触发"。

每个分支都在 `tests/test_scheduler_decide.py` 里用真实日期钉住（37 条 cron 口径断言）。
APScheduler 现在**不再被任何代码引用**，只剩 `pyproject.toml` 的依赖声明和
`scripts/check_deps.py:10` 的名字。要不要清出去见 §11。

**时区**：cron 一律按 `Asia/Shanghai` 解释。所有取时间必须走 `tradeday.now_bj()`，禁止裸 `datetime.now()`——`pg_settings` 里四个角色都设了 `timezone=Asia/Shanghai`，但 Python 进程读的是系统时区，这两者在别的机器上会不一致。

### 4.2 记状态 —— 新增 `operations.schedule_state`，一个作业一行

"上次什么时候跑的、这次该不该跳过"必须有地方存，且**不能存在 `operations.task` 里**（那张表是执行历史，一次重跑多一行 attempt，问不出"上次成功是哪个交易日"）。

见 §5.1 的 DDL。要点：`last_fire_at` 防同槽重复触发，`last_success_date` 判"今天还要不要跑"，`next_fire_at` 是**算出来的**且要显示到页面上（§8）。

### 4.3 协调 —— 三层，每层挡不同的事故

| 层 | 手段 | 挡住什么 |
|---|---|---|
| ① 调度器自身单实例 | 专用连接上持 **session 级** `pg_try_advisory_lock(hashtext('ft_scheduler'))`，拿不到就退出 | 两个调度器同时入队 → 同一作业跑两遍 |
| ② 同槽去重 | `(job_key, trade_date, slot)` 部分唯一索引 | cron `10 15,16,17 * * 1-5` 一天三次，只该真跑一次 |
| ③ 作业互斥 | `concurrency_key` + `CLAIM_SQL` 的 `NOT EXISTS(... state='running')` | 两个作业同时写 `analytics.score` / 同时读 vipdoc |

**① 有个坑必须写明白**：`engine.advisory_lock()`（`app/db/engine.py`）用的是 `pg_try_advisory_lock` 的**事务级**变体 `pg_try_advisory_xact_lock`——事务一提交就释放。调度器不能拿它当单实例锁，因为 tick 循环的每次查询都是独立事务，锁会在两次 tick 之间松开。必须**另开一条长期连接**、用 session 级 `pg_try_advisory_lock`、进程退出时连接断开自动释放。进程被强杀也没关系，PG 断开连接即释放，不留死锁。

**③ 目前形同虚设**：`concurrency_key` 只在 `CLAIM_SQL` 里判，而路径 A（`run_job`）根本不查它——所以今天从页面上连点两次「同步ETF份额」，两个子进程会同时跑。虽然 ingest 是 `ON CONFLICT DO UPDATE` 幂等的（不会写坏数据），但白等一遍十几分钟。**§9 的 P1 里必须让 web 也走队列**，这是这个改造最实际的收益。

## 5. 数据模型增量

新增一个编号迁移脚本 `app/db/sql/07_scheduler.sql`（沿用 `scripts/init_db.py` 的 `APPLY_ORDER` + sha256 记入 `operations.schema_migration`，不引 Alembic）。全部 DDL 幂等。

### 5.1 `operations.schedule_state` — 调度器的记忆

```sql
CREATE TABLE IF NOT EXISTS operations.schedule_state (
    job_key          text PRIMARY KEY REFERENCES config.job(job_key) ON DELETE CASCADE,
    last_fire_at     timestamptz,              -- 上次真正入队的时刻（不是执行完成时刻）
    last_fire_slot   text,                     -- 触发槽标识，如 '2026-09-20T15:10'
    next_fire_at     timestamptz,              -- 算出来的下次触发，页面直接读这一列
    last_success_date date,                    -- 最近一次成功覆盖到的交易日
    last_result      text,                     -- succeeded|failed|skipped|error
    consecutive_fail int NOT NULL DEFAULT 0,   -- 熔断依据，见 §7.5
    missed_count     int  NOT NULL DEFAULT 0,  -- 因调度器停机跳过的槽数
    note             text,
    updated_at       timestamptz NOT NULL DEFAULT now()
);
```

### 5.2 `operations.task` 增列（不动现有列）

```sql
ALTER TABLE operations.task ADD COLUMN IF NOT EXISTS enqueued_by   text NOT NULL DEFAULT 'web';
                                  -- 'scheduler'|'web'|'cli'：区分自动跑和手点，排查必备
ALTER TABLE operations.task ADD COLUMN IF NOT EXISTS fire_slot     text;   -- 同槽去重用
ALTER TABLE operations.task ADD COLUMN IF NOT EXISTS next_retry_at timestamptz;
ALTER TABLE operations.task ADD COLUMN IF NOT EXISTS lease_expires_at timestamptz;

-- 同一作业同一交易日只允许有一条**成功**记录 —— 这是"双保险"（§6.5）成立的前提
CREATE UNIQUE INDEX IF NOT EXISTS ux_task_succeeded
    ON operations.task (job_key, trade_date)
    WHERE state = 'succeeded' AND job_key IS NOT NULL;
```

> ⚠ 这个唯一索引和现有的 `ux_task_job_cap_date_attempt`（`02_schema.sql:867`，含 attempt）**不是同一个约束**，两者并存：前者允许无限次重试（attempt 递增），后者保证成功只有一次。加索引前必须先查历史数据有无同日多条 succeeded：
> `SELECT job_key, trade_date, count(*) FROM operations.task WHERE state='succeeded' GROUP BY 1,2 HAVING count(*)>1;`
> 有的话先清理，否则 `CREATE UNIQUE INDEX` 直接失败、迁移卡住。

## 6. 触发决策（调度器的正文）

### 6.1 主循环

```
每 tick（15s，持 session 级单实例锁）：
  1. 读 config.job WHERE enabled AND trigger_kind<>'manual'      ← 每 tick 现读，无缓存
  2. 读 config.setting 的开关（scheduler_enabled / dry_run）      ← 关掉就空转
  3. target, why = tradeday.target_date()                        ← 今天该处理哪个交易日
     target is None → 记 state、本 tick 结束（日历坏到不能用）
  4. 对每个作业走 §6.2 判定链，任一环节不通过就**带着原因**记 schedule_state
  5. 通过 → enqueue 一行 operations.task(state='pending', enqueued_by='scheduler')
  6. 提交
```

关键点：**判定链的每一步不通过都要有可读的原因字符串**，落 `operations.schedule_state.note` 并显示在页面上（§8）。"没跑"而说不出为什么，等于旧系统的静默失效。

### 6.2 判定链（顺序不能换，换了会算错）

```
① enabled                              否 → skip: 作业已停用
② scheduler_enabled                    否 → skip: 调度器总开关未开
③ cron 槽是否到期（CronTrigger 算 next_fire_at 对比 now_bj()）
                                        否 → 等下个 tick
④ slot 未消费过（fire_slot ≠ last_fire_slot）   是 → skip: 本槽已触发
⑤ only_trade_day 且 今天 is_open        否 → skip: 非交易日
                                        ★ 必须在 ③ 之后：cron 表达式自己不带节假日知识
⑥ chain 型：after_job 当日已 succeeded  否 → 等（不占槽，下个 tick 再看）
⑦ on_ready 型：ready_on 全部 is_ready   否 → 等
⑧ has_blocking_error(target)            是 → skip: 质量阻断，见 §6.4
⑨ 今日已有 succeeded（task_exists_succeeded） 是 → skip: 幂等
⑩ concurrency_key 有 running            是 → 不阻塞入队，交给 CLAIM_SQL 排队
→ 入队
```

**为什么 ⑤ 在 ③ 后面**：旧 `scheduler.py:229-242` 的教训是算了 `latest`/`today` 变量，然后三个 return 全写 `weekday() < 5`，节假日照样触发。这里反过来——cron 表达式负责"几点"，`reference_data.trade_calendar` 负责"是不是交易日"，两问分开答，`sync_daily` 的 `10 15,16,17 * * 1-5` 里那个 `1-5` 只是粗筛，真判定靠 ⑤。

### 6.3 `on_ready`：轮询 `data_ready` 表，不用 LISTEN/NOTIFY

`docs/04` 写的是"PG LISTEN/NOTIFY 或 15s 轮询，两者都可"。**选轮询**，一条理由：NOTIFY 不持久——调度器停机的那一刻正好有数据落地，事件就永久丢了，而轮询读的是表里的既成事实。15 秒延迟对十几分钟一轮的采集毫无影响。

配套要求：**ingest 脚本必须在结束时调 `operations.repo.mark_ready(dataset_key, trade_date, row_count, batch_id)`**。这个函数已经在（`operations.py:88`），当前零调用——`scripts/ingest/c1…c15.py` 全部补一行。`dataset_key` 命名对齐 `config.dataset` 注册表，别自造。

### 6.4 质量门禁：让 `has_blocking_error` 从承诺变成事实

判定链 ⑧。语义：
- `config.quality_rule.blocking = true` 的规则未通过 → **阻断该交易日的 compute 类作业**（`kind IN ('compute','report')`），不阻断 ingest（数据该拿还得拿，不然永远补不上）。
- 阻断时 `operations.schedule_state.last_result='skipped'`、note 写明是哪条 `rule_key` 拦的，页面 §8 上要能一眼看到。
- 逃生口：`config.setting` 加 `quality_gate_override_date`，指定某日强行放行，用于"确认是规则本身写错了"的场合。**必须有 override**，否则一条误报的规则能让整条流水线停摆，人只能改代码——那比没有门禁更糟。

### 6.5 双保险：`on_ready` 主触发 + cron 兜底

`calc_scores` 这类作业同时配就绪触发和兜底 cron，靠 §5.2 的 `ux_task_succeeded` 保证一天只成功一次。这样"数据到了立刻算"和"事件/表状态出问题时当天仍算"两件事不冲突。

## 7. 失败模式清单

这一节是这份文档的主要价值。每一条都是**不做就会出事**的。

### 7.1 调度器死了，没人知道
最危险的失效形态：调度器进程没了，页面上一切正常，cron 列照旧显示 `10 15,16,17 * * 1-5`，看起来"在自动跑"。`runner.py:20-21` 的注释就是在警告这件事。
**处置**：调度器每 tick 刷 `operations.schedule_state.updated_at`；worker 同理写心跳。`/jobs` 顶部横幅：心跳超过 3 个 tick 未更新 → 红字「调度器已停止，数据不会自动更新」。**这条是上线的前置条件，不是后续优化**——没有它，自动化的最大风险从"跑错"变成"以为在跑其实没跑"，后者更难发现。

### 7.2 调度器停机期间错过了槽（停机 / 重启 / 断电）
`10 15,16,17` 三个槽，调度器 15:00 崩了，16:30 拉起 → 15:10 和 16:10 都过了。
**处置**：启动时先做 catch-up——对每个作业把 `[now - catchup_days, now]` 内**已到期且当日尚无 succeeded** 的槽重新走一遍判定链。窗口下界用 `tradeday.missing_days()` 的口径，且必须 `min(market_data.stock_daily)` 兜底，别让十年前的空洞把窗口撑开（`tradeday.py:67` 已经这么防了，照抄这个判据）。

### 7.3 任务跨进程重启变成僵尸
现存 bug 的调度器版本：worker 跑到一半被重启，`operations.task` 留下 `running`。现在靠 `reap_orphans()`（`runner.py:305`）用 `result_meta->>'owner_pid'` + `psutil.pid_exists` 收尸。
**这个机制对 worker 不能照搬**：worker 是常驻进程，重启后 pid 变了，旧 pid 消失会把**子进程还活着**的任务误判为失败；反之子进程和 worker 同生共死时 pid 检查又永远通过。
**处置**：改用 lease——worker 每 30 秒刷 `lease_expires_at = now() + interval '2 minutes'`；任何进程调 `requeue_stale_running()`（`operations.py:222`，已在，0 调用）把过期的重新入队（attempt+1），同时**先杀子进程再改状态**（否则僵尸子进程继续写 vipdoc 解析结果，和新起的那个并发写同一批分区）。worker 收到 SIGTERM 时要有 shutdown hook：停止 claim → 给在跑的子进程发 terminate → 等 grace → kill → 把任务标 failed，而不是让 lease 超时。

### 7.4 取消语义与文档承诺不符
`docs/04` 承诺"真取消"，`runner.cancel()`（:440）当前**只置 `cancel_requested` 标志、从不杀进程**。ingest 类作业点取消后，页面显示"已取消"而子进程仍在写库——这是假取消，正是旧系统 `/api/task/cancel:636` 被点名批评的那个毛病。
**处置**：worker 每次心跳顺带查 `cancel_requested()`，为真则 terminate 子进程 → grace 10s → kill → 终态写 `cancelled`。`finish_task`（`operations.py:180`）需要确认不覆盖已为 `cancelled` 的终态（`docs/04` 点过旧系统 `_finish_task:76` 会覆盖回去）。**ingest 作业可以立刻 kill**：所有落库走 `ON CONFLICT DO UPDATE` 且带 `source_batch_id`，半途中断最多是当天重跑一次，不会写坏。

### 7.5 稳定失败的作业每天烧资源
某个 cron 作业因数据源变更天天失败，`max_retry=2` → 每天 3 次 × 三小时超时，把 `concurrency_key='ingest'` 的队列占满，后面全堵。
**处置**：`consecutive_fail >= 3` 时自动把 `config.job.enabled` 置 false 并在页面标红待人工处理（**改配置要走 `operations.trg_config_history` 触发器留痕，可一键回滚**——这个触发器已经在，`04_constraints.sql`，自动挂在每张 `config.*` 表上）。不静默降级、不死循环重试。

### 7.6 目标交易日算错 → 空跑
`run_job` 的 `trade_date` 默认值是 `sec_repo.latest_trade_date()`（`runner.py:369`）——"库里已经有数据的那天"。调度器如果用这个默认值，追平就变成空操作：库里最新是 08-25，那永远只跑 08-25。`e1_fill_all.py` 的注释里记着 2026-08-27 实测踩过的同一个坑（日历停在 08-25 → 目标算成 08-25 → 判定永远"已最新"）。
**处置**：调度器**必须显式传** `tradeday.target_date()`，并给 `run_job` 加参数 `default_trade_date_source`（`'latest_in_db' | 'target'`），禁掉隐式默认。§9 的 P1 里做。

### 7.7 判定用的时间是本机时钟
调度器的所有触发判定依赖本机时钟。Windows 时钟漂移 / NTP 未同步 → 15:10 的槽在 15:09 或 15:40 触发。
**处置**：启动时打印 `now_bj()` 与 PG `now()` 的差值，超过 60 秒在 `/jobs` 上告警。用 PG 的时间当权威也可以，但每次判定多一次往返，先只做校验不做替换。

### 7.8 通达信 GUI 自动化不能无人值守
`tdx_predownload`（第一步，P0）需要能操作鼠标的交互式桌面：`win32.session_ok()` 拒绝 Session 0，`win32.input_desktop_ok()` 区分"能枚举窗口"和"能动鼠标"。**计划任务里跑必然失败。**
**处置**：这条作业**永远保持 `trigger_kind='manual'`，或者由调度器触发但预期它会以 `EXIT_HANDOFF=2` 结束**。失败时 `capture_stuck()` 已经会把窗口树/UIA dump/截图打包到 `var/stuck/<ts>_<step>/`。调度器要能识别退出码 2 = "交给人"，在页面上出显眼的"需要人工介入 + 指向那个目录"，而不是标成 failed 了事。这是设计上的正常路径，不是故障。

### 7.9 单 worker 串行 → 队列雪崩
`scheduler_max_parallel=1` 时，`fill_all` 的 timeout 是 14400 秒（4 小时）。它一跑，后面所有 `concurrency_key='ingest'` 的全排队。
**处置**：`fill_all` 和细粒度作业**不该同时被触发**——它本来就是"把这一串按顺序全跑一遍"。上线时给 `fill_all` 单独一个 `trigger_kind='manual'`（现状就是 manual，保持），并让调度器在检测到 `fill_all` 在跑时跳过所有 ingest 类触发（判定加一步，note 写"fill_all 在跑，本次跳过"）。

| 期 | 内容 | 完成后能验证什么 |
|---|---|---|

**开关默认关，随时可关**：`scheduler_enabled=false` 时调度器进程照常跑、照常发心跳，但只打日志不入队。这样自动化出问题时，回到今天的手动模式**不需要重启任何进程**。

**不许一步到 P4/P5。** 当前状态（人点一次 `fill_all`）虽然粗糙但**行为可预测、失败看得见**。自动化的失效模式是"静默不做"，正是 README 列的历史故障首位。

## 10. 测试

沿用项目现有风格：**钉口径，不追覆盖率**。参照 `tests/test_fill_all_failure.py` 的做法——用 `importlib` 把脚本模块注进 `sys.modules`，只测纯函数。

调度器的最大好处是**判定链可以是纯函数**：

```python
decide(job, sched_state, now, trade_day_info, ready_set, quality_blocked) -> (Fire | Skip, 原因)
```

不接 DB、不碰时间（`now` 传参）。必测用例：

| 用例 | 期望 |
|---|---|
| 节假日 15:10，`only_trade_day=true` | Skip 非交易日 |
| 节假日 `only_trade_day=false`（`fill_all`、`sync_ths_block`、`sync_snapshot`、`tdx_predownload` 都是） | Fire（种子注释明确要求：周末点它照样该干活） |
| 同 slot 二次 tick | Skip 本槽已触发 |
| `10 15,16,17` 三次槽、第一次已 succeeded | 后两次 Skip 幂等 |
| 15:00 崩、16:30 起 | catch-up 补 15:10 槽 |
| 质量 blocking 未通过 + `kind='compute'` | Skip，note 带 rule_key |
| 同上 + `kind='ingest'` | Fire（数据该拿还得拿） |
| 日历表过期 | 走 `target_date()` 的降级分支，不抛异常 |
| `cron_expr` 语法错 | Skip 并把异常写进 note，**不能让整个 tick 崩** |
| `after_job` 成环 | `registry.validate()` 已在保存时拦（:212-224），调度器侧再兜一层 |

`operations.task` 相关的集成测试按现有约定写（直连活库、没数据就 `pytest.skip`），但**判定链测试一个都不许碰数据库**——这是能不能在空库机器上验证这套逻辑的前提。

## 11. 明确不做

- **不做分布式**。PG 单实例在 127.0.0.1，所有采集脚本读的是本机 `D:\new_tdx64\vipdoc` 单份文件。多机调度要解决的是文件分发，不是调度算法。
- **不引入消息队列**（RabbitMQ/Redis）。`operations.task` + `FOR UPDATE SKIP LOCKED` 在这个量级（一天十几个作业）上绰绰有余。
- **不改 `e1_fill_all.py` 的内部逻辑**。P4 之前它照旧是"一键追平"的实现，调度器只是决定什么时候调它。
- **不做 per-capability 的细粒度并行调度**（P5 之后另议）。
- **不用 Windows 计划任务承载调度器**。它要 4 小时不关的交互桌面（§7.8 的 GUI 自动化）和 PG 连接池，做成计划任务的短进程会反复重建池；沿用 `scripts/web_ctl.py` 那套 start/stop/status 形态，加 `ft-scheduler` / `ft-worker` 两个子命令（顺便把 `pyproject.toml` 里那两个坏入口点补成真存在的模块）。

## 12. 需要你定的四件事

1. **P1 要不要一起把手工按钮改成走队列？** 不改，`concurrency_key` 继续形同虚设；改了，web 页面上点「立即同步」要等 worker 拉起（延迟 ≤1 个 tick，15 秒），手感变了。
2. **熔断后自动 `enabled=false` 能接受吗？**（§7.5）备选：只告警不停用，但那样队列会被反复填满。
3. **`tdx_predownload` 保持 manual 还是纳入自动？**（§7.8）它需要有人坐在这台机器前面。如果每天 15:05 你人在，可以自动；人不在就是每天一个 handoff 包。
4. **目标时间线**：现在全靠手点。定了自动之后，希望"收盘后自动跑完、晚上几点复盘页上是全的"？这个数字决定各作业 cron 怎么排（粗估：`tdxdl` 15:35 → `daily` 16:00 → 板块/ETF/两融等并行 16:30 → `indicators` 17:00 → `scores` 17:30 → `sectortrend`/`ignition` 18:00 → `quality` 18:30，串起来 3 小时上下）。
