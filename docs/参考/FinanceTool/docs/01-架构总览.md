# 架构总览

## 分层

```
┌─────────────────────────────────────────────────────────────┐
│  展示层 (块3)   Dash 页面 · 图表 · 筛选 · 导出               │
├─────────────────────────────────────────────────────────────┤
│  共享库层       ftdb（智能体 import 即用，与 Web 同一套仓储）  │
├─────────────────────────────────────────────────────────────┤
│  编排层 (块2)   就绪判定 · 策略注册表 · DAG · 任务执行器      │
├─────────────────────────────────────────────────────────────┤
│  加工层         策略脚本（用户可增删）· 因子 · 指标            │
├─────────────────────────────────────────────────────────────┤
│  接入层 (块1)   vipdoc 解析 · tqcenter 快照 · 外部 API        │
├─────────────────────────────────────────────────────────────┤
│  契约层 (块4)   字段单位注册表 · 校验规则 · 血缘               │
├─────────────────────────────────────────────────────────────┤
│  数据访问层     唯一 DB 出入口（repository，禁止裸连）         │
├─────────────────────────────────────────────────────────────┤
│  存储           PostgreSQL 17（行情+配置） · 文件（原始/导出） │
└─────────────────────────────────────────────────────────────┘
        底座横切：配置中心 · 密钥 · 日志 · 指标 · 交易日历
```

**唯一硬性架构约束**：任何代码——包括外部智能体的脚本——都不得裸连数据库文件、不得绕开单位口径写行情。落实方式不是"再封一层网关"，而是**把约束下沉进数据库**：CHECK 约束、单位一致性触发器、写审计触发器、四个角色的权限与超时。应用层的检查下一个脚本可以不调用，库层的约束绕不过去。Python 侧统一走 `ftdb` / `app.db.repo`，理由是省事，不是靠它兜底。

## 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 存储 | **PostgreSQL 17** | MVCC 解决实测到的锁问题；多智能体并发写是刚需 |
| 连接 | psycopg 3 + psycopg_pool | 官方驱动，`COPY` / 连接池 / 参数化查询齐全 |
| SQL 组织 | 手写 SQL 收在 `repo/`，不引 ORM | 行情是批量读写，ORM 挡在 `COPY`、`ON CONFLICT`、窗口函数前面 |
| 迁移 | 编号 SQL 文件 + `operations.schema_migration` 记 sha256 | 建库脚本本身幂等，再叠 Alembic 会出现两个 schema 事实来源 |
| Web | Dash 3.x + dash-bootstrap-components | 沿用 financeWeb，九页面逻辑可迁移 |
| WSGI | waitress | Windows 上验证过 |
| 智能体接入 | 直连 PG（`ftdb` 共享库），无 MCP/HTTP 封装 | 智能体在本机，多一层只是多一处会漂的契约。约束改由库层触发器与角色权限保证，见 `07-多智能体直连规范.md` |
| 调度 | APScheduler（持久化 JobStore 落 PG） | 现状是"1 个脚本有 cron"，等于零调度 |
| 数值 | numpy + pandas | 已有 |
| 校验 | pydantic v2 | 契约层的入参/出参校验 |

## 进程与端口

| 进程 | 端口 | 内容 | 守护 |
|---|---|---|---|
| `web` | 18420 | Dash 页面 | Windows 服务 / 计划任务 |
| `worker` | — | 任务执行器（拉 PG 队列，无端口） | 同上 |
| `scheduler` | — | APScheduler，JobStore 落 PG | 同上 |
| PostgreSQL | 5432 | 仅监听 127.0.0.1 + 内网段 | Windows 服务 |
| 通达信 tqcenter | 17709 | 外部，只读调用 | 不守护，探活后跳过 |

三个进程全部纳入守护，不再出现"只守护 web、MCP 和 Worker 裸奔"。

**安全默认值（与现状相反）**：认证默认开启；`api` 默认只监听 127.0.0.1，需要内网访问时显式配置网段白名单；不提供 `/api/exec` 这类任意命令执行接口，需要跑脚本走策略注册表。

## 关键设计决策

1. **一个解析器，一处实现** — `ingest/tdx_binary.py` 是全系统唯一的通达信二进制解析入口，带单元测试固定字节样本。当前 5 份重复实现直接淘汰。

2. **单位在类型里，不在注释里** — 字段名自带单位后缀（`amount_yuan`、`volume_shares`），并在 `quality/units.py` 注册。落库前校验，量级异常直接拒绝。

3. **写入幂等且可追溯** — 所有 upsert 走 `ON CONFLICT DO UPDATE`，每批写入登记血缘（源文件、源文件 mtime、批次号、行数）。

4. **策略是数据，不是代码分支** — 功能点与脚本的绑定关系存在 PG 表里，页面可编辑，不改代码。

5. **任务状态持久化** — 任务表落 PG，进程重启不丢；取消是协作式的，`cancel_event` 真的会被 set，且终态不被覆盖。

6. **智能体一等公民** — 智能体与 Web 用同一套仓储、同一批约束，只是入口不同（`import ftdb` vs Dash 回调）。写操作由库层触发器落 `operations.audit`：谁（`application_name`）、动了哪张表、什么操作、影响多少行。
