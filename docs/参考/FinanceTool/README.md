# FinanceTool — 股票复盘系统

## 这是什么

一套面向 A 股日常复盘的 B/S 系统：从通达信本地数据落库，按可配置的策略定时加工，最后在网页上呈现复盘视图。多个本机智能体通过 `ftdb` 共享库直连同一个 PostgreSQL 读写，不再各自裸连 DB 文件。

## 为什么重建

前身有两套系统，都还在跑但已经互不相通：

- `D:\financeWeb` — 全部应用代码（Dash + MCP + 26 个工具），约 21,000 行，服务已停约 5 天
- `D:\finance` — 数据（~40 GB）+ 361 个脚本 + 日志，多个智能体共享读写，仍在活动

两者从同一个 `D:\new_tdx64\vipdoc` 取数，各自实现了一套解析器，日线行数 9,531,333 vs 9,359,339（约 1.8% 分歧）。重建的目标不是加功能，是消灭这种分歧。

详细的历史系统盘点见 [docs/00-历史资产盘点.md](docs/00-历史资产盘点.md)。

## 架构分块

用户提出三大块，实际落地为 **1 个底座 + 4 大块**：

- **底座 · 平台层** — 统一数据访问层、调度并发协调、配置与密钥、日志与可观测
- **块 1 · 数据获取与同步** — vipdoc 二进制解析、tqcenter 快照、落库
- **块 2 · 定时任务与策略编排** — 数据就绪判定 → 触发加工；功能点↔脚本的映射关系完全可自定义
- **块 3 · 数据展示** — 复盘页面、图表、筛选、导出
- **块 4 · 数据质量与口径契约** — 单位注册表、校验规则、血缘追踪

底座为什么排在最前：前两套系统的故障全部集中在这一层——47 个脚本抢一个 SQLite 文件、调度器不认节假日、一键入口的子进程路径断裂、日志 213 MB 不轮转。先建底座，后面四块才有地方挂。

## 快速判断：这套系统解决什么

| 现状问题 | 本系统的解法 |
|---|---|
| `tq_minline_2026.db` 只读查询都 LOCKED | PostgreSQL MVCC，写不阻塞读 |
| 199 个脚本各自裸连 DB 文件 | `ftdb` 共享库 + 四个 PG 角色；校验与审计做在库层触发器里，绕不过去 |
| amount 单位元/千元混用（1000× 偏差） | 字段单位注册表 + 落库前强制校验 |
| 调度器不认节假日 | 交易日历表 + 数据就绪判定，而非 `weekday() < 5` |
| 功能点与脚本硬编码绑定 | 策略注册表，映射关系可在页面上配置 |
| 因子 Y 轴 65% 权重因少传参而失效 | 策略入参用契约声明 + 启动时校验 |
| 日志 213 MB 无轮转 | 按日轮转 + 保留策略 |
