1. **每档后面那个数是全场的**：`quadrant_options`（`value/label/count/meaning`）里 `count` 来自
   一条**不带象限条件、不带 limit** 的 `group by` 聚合 —— 实测 `买入 0｜持有 1151｜试探 0｜回避 4363｜没取到象限 12`，
   五档加起来 5,526 = 本榜当天全量。聚合成功时"这一档没出现在 group by 里"就是 **0 只**；
   只有整条聚合失败才交 `null`，界面显示 `—`（0 与没读到是两句话，`test_计数那条读不到时交null而不是0`）。
2. **「没取到象限」是一等选项**：`sc.quadrant is null`。榜上真有票当天在 `analytics.score` 里没有
   `oper_score` 行（这场 12 只）；不给这一档，勾完它们就"凭空消失"。
3. **回显读后端而不是读界面**：榜头那一行「象限筛选（在库里筛，先于取数上限）：持有、回避｜榜上这 150 行只来自这些档」

   （`filter.quadrants_rejected` + caveat `quadrant_bad_token`）—— 静默丢掉就成了一份"看着像筛过了"的榜，
   与 `jobs._valid` 对 `client_mode` 的处理同一口径。
4. **概念榜的分母跟着缩**：勾了象限后那一行会变成
   「上面那张倍量榜交出的 150 只（不是全市场）；这一批已经按上面选的四维象限筛过…」，
   否则那张表会被读成"与象限无关的全市场概念分布"。

「清除筛选」一次清掉两类（本地 `filters` 与 URL 里的 `quadrants`）—— 只清一半就是"屏上显示清了、其实还在筛"。

| **前4日涨幅**（10-15 新增） | `gain_first4` | **以前一天的收盘为基准，段内前四根（含启动日）的累计涨幅** = 第 4 根收盘 ÷ 首板日前一天收盘 − 1。与「区间涨幅」的区别：后者覆盖整段（段长可以是 5、6、7…），这一列只取前四根；段长正好 4 时两者相等。第三类母体 `board4_45` 就是这一列 > 45%（4 个 10% 满涨停本来就是 1.10⁴−1 = **46.41%**）。缺基价或第 4 根不存在 ⇒ NULL（不硬算、不按 0 算）|

| 倍量 / 准倍量 / 缩量 | `dbl_days` `near_dbl_days` `calm_days` | 倍量＝倍数 ≥ 2.0（门槛 2.0 是用户 2026-10-07 给的原话，**一天都凑不出也照实记 0**）；准倍量＝≥1.8 且 <2.0（单列免得被当成"没有"）；缩量＝≤0.5 |
| 复牌间隔 | `long_gap_days` | 上一根隔了 >10 个自然日的根数。这类倍数的分母是很久以前的量，读数偏大，**不是"今天突然放量"**；>0 时黄字 |
| 均值 / 中位 / 60 分位 / 80 分位 / 90 分位 / 最大 / 最小 | `ratio_avg` `ratio_median` `ratio_p60` `ratio_p80` `ratio_p90` `ratio_max` `ratio_min` | 都是**窗口内逐日倍数**（当日量 ÷ 上一根量）的统计。`bars_used < 10`（判据下限 `MIN_BARS`）时这八项按口径留空——六个样本的平均数与三十个并排排名没有意义，宁可空着。中位最抗极端值；`p80` 已接近 2.0 而 `dbl_days=0` 说明"量在憋着但没到门槛"；样本只 30 根时 `p90` 抖动比 `p80` 大，横比优先 `p80`；`ratio_max` 的分母是"上一根"而不是"近 20 日均量"，一根地量后接一根正常量就能出大数 |

## 6. 不许破的纪律

1. **判据只住一处**：倍量门槛（`MULT=2.0`、前 5 日均量不含当日）在 `app/compute/vol_double.py`；
   涨幅口径只住 `duanxian/day_returns.py`；象限轴语义只住 `QUADRANT_AXES`/`QUADRANT_MEANING`。
   页面**逐字透出**这些文字，不许在前端另写一套（两处各写一套早晚走偏，而读者看到的是同一个列名）。
2. **缺数是空，不是 0**：象限缺 ⇒ `—` 不当 0 分；涨幅缺 ⇒ `—` 不当 0%（平盘）；`bars_used<10` 的八个分布读数按口径留空。
3. **NaN/NaT 不许出门**：`fetch_df` 把 NULL 读成 float NaN（`is not None` 恒真），出口必须过 `_num/_int/_txt`，
   整包要能过 `json.dumps(allow_nan=False)`（10-10 这条在实跑里真炸过浏览器）。
4. **列名不许写"今日"**：这一屏锚在库里那一档，周末"今天"根本没有行情。
5. **三类母体不并榜**（`board4`／`board4_45`／`jump40`，其中 A′ 是 A 的子集）；跨板块比强度只读 `equiv_limit_ups`。
   新加一档时**写侧 `COHORTS` 与读侧 `STARTUP_COHORTS` 必须同一个名单**（分叉＝屏幕点得到一类而库里查不到），
   `tests/test_startup_volume.py::test_第三类母体在写侧与读侧是同一张名单` 钉住；门槛也只有一个真值
   （`GAIN_FIRST4_MIN`，SQL 里的数是它替换进去的）。
6. **上限要说出口，且两处都要说**：后端 `limit` 截断（黄字那一句，附带「全场实有几只」）与页面分页
   （`共 N 行 · 每页 60 行`）是**两件不同的事**，任何一处静默就等于把 1/6 说成全部。
   翻页后的行号必须用**整批序号** `gi`：选中态按行号存，用页内下标的话第 1 页的同一行会跟着亮（张冠李戴）。
   `qcTotal` 只在每档 count 都读到时才给，缺一档就不给合计 —— 半个合计会被读成全场。
7. **覆盖场数、上限值这类"会自己涨的数"不许写在代码注释里**：`_NOTE['coverage']` 与 `vr/app.py` docstring
   10-14 之前都还写着「19 场」，而库里已经是 208 场。屏幕要说真话，就得让数字从 `_coverage()` 现算出来随体交。
8. `picks()` 里那 8 条阈值（`min_dbl≥2`、`dev_med≤8`…，`app/compute/vol_double.py:272-282`）**不是本屏的筛子**，
   它只被 `d7_vol_double --verify` 用来打印"当前阈值下入选几只"。本屏默认 `min_count=0`，交的是**全市场按 `dbl_count` 排序的前 150 名**。

## 8. 跨 5 年复盘：启动前量能到底有没有规律（2026-10-16 那一轮，探查脚本＋结论）

**为什么原来只能看 12 个月**：这一块的逐日序列取自 `analytics.volume_ratio_daily`（vr-1），
而那张表当时**只有 2025-10-09 起 248 场** —— 不是日线不够（`stock_daily` 有 2021-08-02 起 1,260 场），
是**倍数底表只回算过近一年**。10-16 把它回补成全史：**6,435,774 行 / 1,260 场 / 2021-08-02 → 2026-10-16**
（+1.38 GB；回退＝`delete from analytics.volume_ratio_daily where trade_date < '2025-10-09'`），
再用同一份 sv-2 判据把 `analytics.startup_volume_profile` 回补到 **2021-11 起 7,380 条**
（board4 1,696 / board4_45 1,547 / jump40 4,137，其中完整 30 根窗 1,676 / 1,529 / 4,052，`--verify` 通过：无序列 0 条）。

**读这份结论前必须先接受的三条**（不写清楚就是骗人）：
1. **母体是事后筛的**：`launch_date` ＝那段连板的**第一天**，而 `len>=4` 这个条件要回头看才成立 ⇒
   启动日**当天及之后**的涨跌是"已知它会连板"的样本，任何从这里起的收益都带未来函数。
   所以这一屏只能回答「这批 4+ 板的票，启动前长什么样」，**不能**回答「今天买谁能涨」。
2. **两套口径分开报**（探查脚本里 `p_*` / `a_*`）：复盘口径（从启动日收盘起算）board4 5 场 **+32.22%**；
   能买到的口径（看得见信号之后那一早开盘进场）同一批 **−6.31%**、胜率 37%、进场后 5 场内最低中位 −13.69%。
   两个数都是真的，差的就是"前三板白送的那段"。
3. **进场当天一字板买不进**：board4 系 16%、board4_45 系 15%、jump40 只有 1% ⇒ 剔掉买不进的之后各档再差 1~2 个点。

**总账（2021-11 → 2026-10，能买到的口径，5 场中位超额 vs 对应分类指数）**：
board4 **−6.11%**（n=1,676）、board4_45 **−7.56%**（n=1,529）、jump40 **−5.14%**（n=4,052）；
分年每一年都是负的（board4：21 −0.54 / 22 −7.02 / 23 −6.25 / 24 −9.49 / 25 −5.62 / 26 −2.10）。

### 9.3 这一轮抓出来的两个真缺陷（都不报错，只有实测才会露）

**① 超额基准的起点搞错了一整版（fb-1 → fb-2）。** `ex*` 的分子从"进场当日开盘"起算，基准却拿**进场当日指数收盘**
当起点 ⇒ 基准的第一站被吞掉，`ex1` 恒等于 `r1`（那一列写着"超额"其实一个基准都没含），其余 `ex*` 统一少算一站。
修法不是就地改数：起点换成**进场当日该指数开盘**（`index_daily.open` 四个基准指数 1,260 场全有值，实测 0 缺）、
换号 `fb-2`、五年全量重灌（60,173 条、约 15 分钟、体检通过），旧 `fb-1` 批留在库里对账（删派生行的行要先问用户）。
并且把这一类缺陷变成**事后自证**：`verify()` 现在数"ex1 与 r1 相等"的行数，非 0 就把整批判成不通过（rc 3），
`tests/test_first_board_shape.py::test_超额的基准起点是进场当日指数开盘而不是收盘` 钉住 SQL 交 `open`、
`test_库里真的回填过五年首板_且基准不再是退化那一版` 在真库上要求这个计数为 0。

**② 第一档的区间念成了倒着的。** 读侧把区间写成 `cuts[g - 1] if g - 1 < len(cuts) else None`，而 `g` 是 0 基的档号 ——
第一档的 `g-1 = -1` 绕到了**最后一个**切点，`cuts=[1.0, 2.0]` 时屏幕上 Q1 念成「2～1（不含 2）」。
页面只是老实照拼后端交来的 `[lo, hi]`，所以这一句在接口 payload 里就能看到（不是渲染的锅）。
改成 `cuts[g - 1] if g >= 1 else None`，并加了一条真库端到端用例
`test_每一档的区间与切点一一对应_第一档不设下限`：逐档比 `range == [cuts[i-1] 或 None, cuts[i] 或 None]`、
左开那头的 `lo_obs` 必须严格大于下限、右闭那头的 `hi_obs` 不得越过上限、各档合计必须等于基线条数。

### 10.1 先记住三条口径（错了不报错，只会给一句听着合理的假话）

1. **窗口不含启动日当天**。读的是启动日**之前** N 个该票有效交易日（`win_to`＝T−1），因为启动日当天已经涨停，

3. **主键少了 `window_days`**：两张表都有 10/20/30 三档窗口控件，但主键里没有这一维 ⇒ 跑一次 `--window 20`
   把 30 场那批整行**盖掉**，界面切回 30 档只剩"这一档还没算"。解药＝`window_days` 进主键（43/44 号 DDL 与库里都改了、
   校验和重登记）＋写侧 `_PK`/`ON CONFLICT` 跟上（否则整批写库报 `InvalidColumnReference`）＋三档各回填一次；
   钉在 `tests/test_window_depth_pk.py`。**这是"可调参数界面"特有的新坑**：参数能改几档，表就得按那几档分行存。
4. **界面把 7 当 7%、接口要的是 0.07**：`vr/app.py` 那一行是 `jump_pct: float = Query(0.07, ge=0.03, le=0.15)`，
   而控件上的档位是百分数（5/7/9）。第一版把 `7` 原样发出去 ⇒ 每次点「重算一次」都被 **422** 挡回，
   那一屏从来没出过数。**更糟的是面板自己写着「接口尚未接上…现在是 HTTP 404」** —— 把 422 说成 404，
   排查方向就整个反了（会去找一条根本不存在的"没接线"）。解药三条：
   ① `jumpPctParam()` 做单位换算、`clampJumpPct()` 的上下夹**照抄接口那两条边界**（3~15%，不是原来随手写的 1~20），
   ② `ratioToPctText()` 回显成「突拉阈值 7.0%」（曾印成 0.1%），
   ③ 不可用那段话**不再替用户断言状态码**，只说"以那一行报错原文为准"。
   钉在 `frontend/test/spikeDays.test.ts`：那条新用例直接读 `vr/app.py` 的 `Query(默认, ge=, le=)` 来核对界面的夹范，
   后端改边界而界面没跟上就红。**这条是跨会话交付的接缝**：判据侧改过单位，展示侧没人通知，两边各自都"对"。
5. **两屏的"倍量"不是同一把尺，抄句子就把数说错了**：这一屏落地时把「倍量形态」第一块那句
   「量 ≥2× 前 5 场均量」原样抄进了口径句、列标题与三行表名（共 7 处），而这一块读的是 **vr-1（÷上一根日线量）**。
   后端 `spike_days_view.CALIBER` 一直是对的（「当日量÷前一根量」），错的全在展示侧。
   解药＝`lib/spikeDays.ts` 的 `COPY.proxy`／列 `title`／`jointRows` 行名与组件的 `note`、说明段统一改回
   「当日量 ÷ 这只票自己上一根日线的量」，并把这条**判据化**：
   `assert.doesNotMatch(lib, /前 ?5 ?日均量/)` ＋ `assert.match(COPY.proxy, /上一根日线量/)`，
   同时在 §10.1 第 4 条写清两把尺各自的定义。**教训：同一页里两个块都叫"倍量"时，措辞必须点名分母，
   不能只写"倍量"；抄别块的句子等于跨块借用判据。**

## 11. 2026-10-19 换尺：倍量次 → 量能加权分（＋新增一块「加权分进榜后的逐日涨跌幅」）

这一节往下是**现在的**事实；第 4 节里凡是把「倍量次」当主列、把分段差门槛写成 2 的句子，都只作历史口径。

⚠️ **同一天有两稿，第一稿当晚作废**（记下来是因为它是"判据被自己实现歪了最难自查"的一例）：
第一稿把加权分实现成「占比＝分值 ÷ Σ分值」，还带一个 `normalize`（`sum`/`top`）量纲开关，
主列上限因此只有 5.62、界面按占比说话。用户当晚纠正：
**「其实不存在系数这个参数，系数这个说法是错的。计算方式应该是：每个段出现的次数，乘以赋予的分值，
所有 次数×分值 单项相乘后累加，得分进行排名。」**
现在 `validate()` 会**主动拒绝**载荷里出现 `normalize`，`points()` 里没有任何除法。

### 11.1 主列换了什么

| 项 | 改前 | 改后（现在） |
|---|---|---|
| 主列 | 倍量次 `dbl_count`（日量比 ≥2.0 才 +1 的硬计数） | **加权分 `dbl_energy`**：量比每 0.1 一档（1.0→2.5 共 15 档）＋尾三档 2.5–3.5 / 3.5–5.0 / ≥5.0，共 18 档；**得分 = Σ 每档（这一档在窗口里出现的次数 × 这一档的分值）**，没有系数／占比／归一化 |
| 单位与上限 | 无量纲占比（满窗 5.62） | **分**：顶档一天记 1 分 ⇒ 满窗（40 场全顶档）数学上限 **40 分**（`energy.scale.max_score`）；实测 2026-10-19 全场最高 **11.61**、p50 **4.21**、p90 **6.51**、p99 **8.41** |
| 列名与位置 | 「倍量次」 | 「加权分」，仍在原位置（第 7 列），`sortKey="dbl_energy"` |
| 新增列 | — | **「当日名次」**（`sortKey="rank_in_day"`），规则读接口 `rank.rule` |
| 旧列 | 上屏 | **退役**：库里仍写、行里仍交回（`dbl_count_legacy`），只在悬停/档案里作对照，不排序、不筛、不排名 |
| 门槛参数 | `min_count`（整数 0~40） | `min_energy`（浮点 0~40），界面标签「最少加权分」，默认 0＝不筛 |
| 稳步提升 | 分段差 ≥2（次数） | 分段差 ≥**1.5 分**，阈值只住 `duanxian/quant.py::STEP_GAP_MIN`，界面读 `thresholds.step_gap_min`（现算：可比母体 5,514 只、不可比 22 只，**≥1.5 分 1,768 只**，与旧口径次数差 ≥2 的 1,695 只同量级） |
| 窗口 | 跨全部批次 | **只在全场同一指纹（`energy_fp`）里滑动**；对不上批的行交 `—` |

为什么换：本机实测近 25 场全市场 149,938 个票·日的日量比分布 —— <1.0 占 60.6%、1.0–1.5 占 28.6%、
1.5–2.0 占 6.4%、**2.0–2.5 只占 2.2%**、≥5 占 0.28%、p99=3.33。「≥2 才算一次」这把尺只截到最尾 3.5%。

默认分值（`app/compute/volume_energy.py::DEFAULT_SCORES`，一路可改）：
1.0–1.1 起 `0.05 0.08 0.12 0.18 0.25 0.35 0.45 0.55 0.68 0.80 0.88 0.93 0.96 0.98 0.99`，
**2.5–3.5＝1.00（顶档）、3.5–5.0＝0.90、≥5.0＝0.70**；<1.0 一分不给。
尾档回落的依据是公开口径一致把 5 倍以上叫剧烈/极端放量、高位极端放量偏见顶，但不给 0。

### 11.2 名次这件事做成了公用组件（用户点名「以后其他功能点也一并调用」）

- 规则（用户原话）：**得分相同 ⇒ 名次相同，后一个分数的名次按位置顺延**；
  最高分 3 只并列第 1 ⇒ 下一个分数是**第 4**（不是第 2）。没有得分的票**不参与排名、也不占号**（格子是 `—`）。
- 唯一实现 `duanxian/ranking.py`：`rank_sql()`（standard competition）、`dense_rank_sql()`（只给"第几档"那种语义）、
  `rank_in_memory()`、`tie_counts()`，文案 `RULE_NOTE` / `RULE_NOTE_SHORT` 也只在这里。
- 前端唯一实现 `frontend/src/lib/ranking.ts`：`rankText`（没数念 `—`，绝不补 0）、
  `rankTitle`（规则原文＋分母＋这一格的名次，规则由接口交、组件不抄写）、`trimNum`（显示层去尾零）。
- 榜上那一列**故意不用窗口函数**：读侧用相关子查询 `1 ＋ 同一场同一批里"分更高"的只数`
  （`_energy_rank_expr`）—— `rank() over ()` 在 `where` 之后算，象限一筛，"第 1 名"就变成"这一小堆里的第 1"。
  三种写法（SQL 窗口 / 相关子查询 / 内存）由 `tests/test_ranking_shared.py` 逐位比过，并写死用户那组期望
  `[10,10,10,9.9,9,9,8,None] → [1,1,1,4,5,5,7,None]`。
- **分母随体交出**（`rank.universe`）：实测 2026-10-19 `scored=5,514`、`rows_total=5,527`、`unscored=13`、
  `top_score=11.61`。同一个"第 40 名"在"全场 5,514 只有分"与"取前 120 名"里是两句话，所以两处分开念。
- 个股量化档案里那一块（`/stock-review` 的「倍量形态」）现在与倍量榜**同一条规则、同一个分母**
  （以前它用 `rank() ... , security_code` 自己破并列 ⇒ 同一个名字在两个屏上是两个数）。

### 11.4 配置在哪改、改完会发生什么

系统配置 → 「倍量加权分档（倍量榜那把尺子）」（`frontend/src/components/VolumeEnergyPanel.tsx`）：
作用域（`global` 全市场 / `market` 按交易所 SH·SZ·BJ 各一张，没单配的市场落回全局 ——
**不按板块配**，`security.board` 实测 3,972 只是空的）、18 档分值
（每格显示**分值（一天计几分）**、这一档一天最多贡献、满窗最多几分，没有占比那一格），
以及生效指纹、库里批次、实测分布、名次规则一行、后台重算现场。算式那行逐字读 `scale.formula`。

- 保存 `POST /api/config/volume-energy`：校验失败 422 并原样说原因（半份配置都不存，少一档等于偷偷把这档算成 0 分）；
  成功且指纹变了 ⇒ **后端自动起一次全量重算**（实测 104 / 110 / 107.5 秒各刷 1,153,318 行、211 场）。
- **保存了不等于已生效**：跑完之前倍量榜筛的还是旧批，那一侧会挂 `energy_batch_stale` 那句 caveat；
  卡片上 `job` 显示在跑/起止/结果。每日链 `d7_vol_double` 也会用**当前**档表重刷当天那一场并独立手算复核
  （`verify_energy`，实测「计数不一致 0 处、加权分不一致 0 处」），所以哪怕后台线程被打断，第二天收盘链也会把批追平。
- CLI（人要手动作时用）：`python -m app.compute.volume_energy --rebuild [--from --to]` / `--status`
  （退出码 0＝库里最新批就是生效配置）。**pytest 进程里硬挡这条后台线程**。

### 11.5 这一发接口为什么慢、10-26 怎么压下去的（两处、各带前后数字）

用户 10-25 点名「网页展示数据有点慢」之后逐条量到这一发（`.local/_track_probe.py` 把 `pg.fetch_df` 包一层计时）：
**同一进程内整发 13.1 秒**，六段里两段吃掉 11.7 秒。

| 那一段在做什么 | 改前 | 改法 | 改后 |
|---|---|---|---|
| 母体取「当日前 N 名」：每行现数「同一场同一批里分更高的只数」（`quant._energy_rank_expr` 那个相关子查询，5,519 行各数一遍） | 8,087 毫秒 | 窗口 `rank() over (order by dbl_energy desc nulls last)`，分组就是当日那一批 —— **只在 where 里除了分区键什么都没有时才等价**（探针 `.local/_et_rank_probe.py`：120 行名次逐位相同、边界并列那批也在） | **39.5 毫秒** |
| 每只票起算日到今天的逐日涨跌幅（`day_returns.series_by_code`） | 3,503 毫秒（扫到 2015..2026 **12 个年度分区**） | 日期上下界从 CTE 里挪成**字面参数**先单独取 `lo`，`stock_daily` 那一段再补一句显式上下界 ⇒ 分区剪到只剩一片（探针 2：行数 20,990、`hfq` 合计 359,324.0611 逐位不变） | 996 毫秒（含取 `lo` 那 44 毫秒） |
| 整发（进程内，同一条链路） | 13.10 秒 | 上面两处 ＋ 三段取数按「场次＋`energy_fp`＋名次线」进 `_agg`/`_agg_call` 的一小时缓存 | **2.48 秒** |
| 界面上这一发 | 冷 12.5 秒 / 第二发 11.8 秒 | 同上（缓存命中的那一发只剩出体与 gzip） | **冷 3.07 秒 / 热 0.69 秒** |

- ⚠️ 出体形状没动：同一份**未压缩 1.88 MB、压缩后 213,954 字节**（`_SelectiveGZip` 在 8910 上压）。
  量过、**没动**的那一条：把每行 `series` 收成共享日期轴能再省一半字节，但 0.69 秒里那部分已经在压缩之后了 —— 不是这次的瓶颈。
- 缓存键里带着 `energy_fp`（倍量档表的生效指纹）：**配置一改、指纹一换，键自己搬家**，
  旧键不可能把上一批的数顶给这一批；同一天同一批重算是同一个答案。所以这一块没有「旧值冒充新数」那一族风险，
  也因此**不进** `cached_aggregates` 那条 caveat（那条话是给"和今天无关的全库事实"用的）。
- ⚠️ 唯一的例外是 `_coverage('volume_double')` 那一发（最早/最新/场次数，按表名缓存一小时、键里不带场次）：
  刚回算过覆盖范围时它可能还是旧的一小时值，界面上「这张表最早一场是 …」那一行读的就是它。
- 「重取这一块」那个按钮（`EnergyTrackBoard.tsx`）自 10-26 起带 `refresh=1`（清的是 `energy_track_` 那几个键）。
  浏览器实测（bundle `index-Da0qFOom.js`）：首发的 URL 是 `?date=`，按下去之后的 URL 是 `?date=&refresh=1`，
  894 毫秒 vs 2,645 毫秒 —— 按钮与参数接在同一件事上，不是「亮着却交回同一份」（任务 #105 那一族）。
  这条由 `frontend/test/energyTrackBoard.test.ts` 钉住（端点签名、`refresh: bool = Query(False…)`、
  `clear_agg_cache('energy_track_')`、按钮那一行三处一起）。
- ⚠️ **另三处仍用相关子查询算名次**（倍量榜主查询 `volume_double`、`first_board_daily`、`momentum_follow`）：
