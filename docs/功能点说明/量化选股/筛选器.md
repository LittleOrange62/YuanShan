### 0.1 任务 #56 的结论：筛选项到底作用在哪（这条欠账已补，证据如下）

历史欠账原文见 `docs/页面展示工作指南/04-新增页面落地进度.md:398`（10-06/10-07 批，第 7 条）与
`frontend/src/pages/Screen.tsx:16-21`、`duanxian/screen_view.py:2-9` 的模块注释：
2026-10-06 之前只有 `GET /api/screen/rules` 端条件清单，执行引擎 `app/compute/screener.py` **没有任何 HTTP 入口调用**，
所以那一屏"长不出跑一次的按钮"。现在的链路（每一环都当场核过）：

1. **作用在 SQL 的 WHERE 上，不是前端行集**。页面把参数放进 query string（`Screen.tsx:225-228`）→
   `vr/app.py:951-952` 把除 `rule/universe/date/limit` 外的键原样收进 `given` → `screen_view.run` 按登记 schema 收类型
   （`_given` `screen_view.py:106-116`，没给的补登记默认）→ `screener.run([单条条件])`（`:147-148`）→
   `build()` 把模板渲染成 WHERE 片段并拼接：`where = ... join(frags)`（`screener.py:203`）、
   `WHERE d.trade_date = %(d)s AND {pool} AND ({where})`（`:212-213`）。
   值类参数一律 `%(cN_x)s` 绑定（`:140-141`），字面类（列名/比较符）只有命中 `enum` 白名单才做文本替换
   （`_coerce` `:76-82`、`:138-139`）。前端**没有**任何对 `rows` 的二次筛除 —— 拿回的行全部上表，唯一的前端重排是点列头排序。
2. **选了筛选条件之后有没有真的重新发请求？有，但只在点「跑一次」时**。点按钮 = `setSpec` 快照（`Screen.tsx:84-87`）→
   `{spec && <RunResult/>}`（`:199`）挂载 → `useProbe("/screen", …)` 发一次真 GET（`frontend/src/lib/probe.ts:98-111`）。
   条件卡里选哪条规则、换候选集/上限/日期、填参数本身都**不发请求**（纯 state）。
3. **同参数再点一次「跑一次」曾经什么都不会发生**（10-11 记下的真断链，**10-14 已修**，见 §6-1）：`useProbe` 的三个依赖是
   `[path, key, nonce, skip]`（`probe.ts:100/109`），`key = JSON.stringify(query)` 相同、`RunResult` 的 nonce 是自己关的且永远是 0
   ⇒ effect 不重跑，连 loading 都不进。现在的修法是给 `spec` 加一个 `seq`（每次点加一）并用它当 React `key`
   （`Screen.tsx:125/:286`）—— remount 之后组件自己的 nonce 从 0 开始、effect 照跑，请求真的又发一次。
   **另一条更新**：10-14 起条件是一个数组，`key` 里含 `conds=<JSON>` 整段，改任一条条件的任一参数都会变 key。

实测行差（§7 全表）：同一条 `limit_up` 自选池 `days=5`→53 行、`days=10`→102 行；`amp10_over` 全市场阈值 `9→5`
命中 94→200（触顶截断）—— 参数直接改 SQL 命中集，这是"作用在 WHERE"最硬的一条证据。

一句话定位：这是**"登记的条件 + 给的参数 → 库里实跑一次"**的选票台。条件不是页面临时拼的，命中不由界面重算，
界面只负责把登记表端出来、按 schema 生成控件、把结果原样摆出并说清分母与截断。

   （`screener.py:76-82`）。放宽这一道 = 库里能写任意 SQL。
3. **缺 required 报缺哪一项，不许猜默认跑一遍**（`screen_view.py:136-142`；测试 `test_screen_run.py:60-66`
   还钉了"缺参数时一条 SQL 都不该发出去"）。
4. **分母与截断必须随行交出**（`screen_view.py:16-19/:171-173`；`truncated = len(rows) >= lim` 的等号语义在
   `test_screen_run.py:90-94` 有钉）。自选池 1118 与全市场 5558 里"筛出 53"是两件事。
5. **模板原文不外显、自由 SQL 刻意不做**（`rules_view` caveat + `Screen.tsx:24-25`）；给只读成品项目开自由 SQL = 自己放大权限。
6. **缺数是空不是 0**：`cellText` null/''→`—`（`Screen.tsx:300-301`）；换手率缺股本留空不填 0（`06_comments.sql:81`）；
   操作分缺 score 行是 NULL 不是 0 分（SQL LEFT JOIN）。
7. **排序只是显示，不改行集与口径**；缺数永远在后（`useSort.ts:1-13`）。行序兜底 = 后端 `ORDER BY o.value DESC NULLS LAST,
   d.security_code`（`screener.py:214`），第三次点击必须能回到它。
8. **上限要说出口**：页面档位封顶 1000（读层夹，严于引擎的 2000，`screen_view.py:35-37` 注释给了理由），要全量去 CLI。
9. **不摆"保存方案"按钮**，除非存/取端点真开出来（`Screen.tsx:26-27` 的规矩；preset 表 0 行本轮复核属实）。
10. **`05_seed.sql:602` 那句话是本屏的宪章**：注册表里只放"点了真的动"的条件；点了不动的条目比明写"还没实现"更贵。
11. **均线一律复权，而且价与均线同底**（10-14 用户裁定）。`config.indicator` 的 ma5..ma250 与 bias5/10/20 用
    `close × IF(adjustment_factor > 0, 因子, 1)`；条件模板那一侧是发给 PostgreSQL 的，Postgres 没有 `IF()`，
    同一条规矩写成 `CASE WHEN d.adjustment_factor > 0 THEN … ELSE 1 END` —— **同一个语义两种写法，改必须两处一起改**。
    拿不复权现价去比复权均线，比不换底错得更隐蔽。依据：133/4,933 只年线上下判定翻转（§7.1）。
12. **密集/排列类条件必须要求组内均线齐全**：`HAVING count(*) = 5`（短五线）/ `= 4`（中长四线）/ 四条均线行都在（排列类）。
    **绝不把极差写成 `config.indicator` 的派生指标**：求值器的 `MAX/MIN` 是 `np.fmax/np.fmin`，**忽略 NaN** ——
    缺一条均线的票会被算成"四条线的极差"，极差假小、密集假通过，会被排到最前面（同一条纪律见 `ambush_setup.ma_spread_pct`：
    缺的那一根不按 0 参与）。这条形状由 `tests/test_screen_ma_combo.py` 直接读库里的模板钉住。
13. **读 `indicator_value` 的条件必须先过"那一场有没有因子行"这道闸**（§4.2）。不判就不能下结论：探测失败交 `None`
    （照跑并在 `caliber` 里说明没验过），**不许当成 `False`** 替库说"这一天没有因子"。
14. **条件数上限两处同一个数**（前端 `Screen.tsx:92` / 读层 `screen_view.py:176`，都是 6）。
    界面放开到 7 而后端退一句"最多 6 条"= 一次白跑的请求；`frontend/test/screenMultiCond.test.ts` 读两个文件比对。
15. **组合不是"跑两次单条"**：`conds` 拼的是同一条 SQL 里的多个 WHERE 片段（母体与 `universe_count` 不随条件数变），
    参数名前缀 `c{i}_` 保证"同一条条件带不同参数出现两次"不互相覆盖（`screener.py:104-112`）。
16. **模板里不许出现 `%` 与 `::`**：前者被 psycopg 当占位符起手，后者会被占位符正则 `:([a-z_]\w*)` 咬掉后半截
    （`screener.py:29-30` 的注释只说了"避免吃掉"，实测仍会漏 —— 所以新模板一律用 `* 100` 与 `CAST(x AS int)` 绕开）。
    这三条由 `tests/test_screen_ma_combo.py` 逐条读库验。
