用户 2026-11-04 点名：「推送任务，单独在『个股研究与回测』这个板块下建一个页面，用于汇总推送任务的，

## 一、这一屏管什么、不管什么

管四件事：**什么时候跑、发到哪些渠道、这一路还开不开**，再加上**那一天真发出去的原文**（11-10 新加的
「按日期回看推送正文」那一块）。上面三样并排给你看：配置说的 / 机器上真注册的（`Ready`、`Disabled`、
`未注册`、下次时间）/ 今天库里真发出几条。

**管正文的"回看"，不管正文的"怎么写"**：判据在各作业脚本里，措辞在 `app/intraday/templates.json`；
这一屏只读库里已经落下的那一份，不重算也不改一个字。
也不管"渠道机器人本身"与"本进程内的定时计划"（那是系统配置 ⑬ 与 ⑭ 两屏，本屏下方有指路链接）。

## 三、保存这一笔会发生什么（顺序固定，不可跳）

1. 校验：**一个键非法就整笔不写**（时点形状、间隔区间、渠道是否在册、`heat_times` 这类已作废的键）；
   错误原话经 `saveBroadcast` 的 `detail || reason` 上屏，不折成"保存失败"。
2. 写配置：作业配置 `jobs/config.json` 的 `intraday_broadcast`（41 个键，盖章 `_changed_at`/`_changed_by`）。
3. **动 Windows 任务计划程序**：开着的覆盖式注册，**关掉的那一路直接注销任务**
   （不留"每天空跑一次然后不出声"的任务）；每行按钮因此叫「保存并重注册」，不叫"保存"。

时点只有两格可改：`auction_times` 与 `push_times`。③④由 `push_times` 推导（④各自 +10 秒），
所以 ④ 那一行只有开关、没有时点格 —— 界面会不会出现"改了推送点忘了改热度"这种不一致，
就靠这一格结构堵掉。谁给输入框由后端那一格 `tasks[].times_field` 决定，前端不自拼 `${key}_times`。

## 四、数据与接口

- 端点：`GET /api/intraday/broadcast`（读数）、`POST` 同一路径（改 + 重注册，体 `{settings, reregister}`）、
  `GET /api/intraday/broadcast/bodies?day=YYYY-MM-DD`（按日期回看正文，见 §五）。
- 真源：`app/intraday/tasks.py`（一份 `SPEC` 在册表同时喂着 CLI、接口与任务 XML 生成）。
- 留痕：`analytics.intraday_broadcast`（几点发了什么、送达与否按**渠道业务码**判，不按 HTTP 200）；
  每行末尾那格「今天 N 针 · 发 N 条」是 `store.fold_ledger` 折出来的。
- 两处读数上的坑已在屏上处理：`Get-ScheduledTaskInfo` 的时间**秒位不可信**（本机实测秒==分），
  那两格只到分钟；从没跑过的任务回 `1999-11-30` 零值与 `LastTaskResult=0`，屏上落成「没跑过」，
  结果码与它同一个闸（`267011`＝还没跑过，不是成功）。

## 五、按日期回看推送正文（11-10 新增）

用户 11-10 点名：「5、9、10、11 这些分析的推送任务，都是先入库再推送或者推送的同时入库，
并且在系统页面"任务推送"中，可以选择日期查看推送具体内容。默认都显示最近一天的数据。」

**先核"是不是先入库"（真库现读，不打桩）**：四路的正文都在**发送之前**就写进
`analytics.intraday_broadcast.body`，之后 `what='sent'` 那一条只是回执 —— 两行同一个 `at_ts`
（作业把同一个 `now` 交给两次写），正文逐字相同。11-09 那一场实测：
⑤午间 12:10:02 846 字、⑦体系榜 14:40:32、⑨复盘 18:18:03 1269 字、⑩展望 19:00:15 1219 字，
每路都是「正文行 + 回执行」成对存在。**补的一处缺口**：⑤ 的降级分支（东财池子取不到，
播一句 `noon_fail_notice`）原先只写 `err` 不写 `body`，正文要等发完那条回执行才落下 ——
发送中途崩掉就一个字都留不下，屏上会把"群里收到过一条"说成"这天没发过"。现在那一行也带 `body`
（`ingest/jobs/push/t05_noon_review.py:271`，钉它的是
`tests/test_noon_review.py::test_池子取不到那一路也是先落正文再发`）。

| 项 | 事实 |
|---|---|
| 读哪张表 | 只有 `analytics.intraday_broadcast`（`body IS NOT NULL`），**一律不重算** —— 事后源站翻页、盘后补数都不会让屏上改口；`--resend` 补发读的是同一份 |
| 读哪几路 | `app/intraday/tasks.py::PUSH_KEYS`（由 `SPEC` 的 `mode != 'record'` 推出来，不是另写一份名单）⇒ **①⑥ 不列**：那两路只落库，它们留在 `body` 里的是池摘要／取数摘要，列进来同一份变化量会在①和③各出现一次 |
| 折法 | 同一路同一 `at_ts` 的正文行与 `sent` 行折成**一条**，正文取 `sent` 那份（真发出去的那一串）。`store.fold_bodies()` 是纯函数，测试直接喂假行 |
| 默认落点 | **最近一个有正文的日子**，不是"今天"：早上打开时今天那几路还没到点，默认今天会看起来像一条都没发过。「上一天／下一天」也只在真有正文的天之间跳（不按日历 ±1，否则一跳就跳到周末那片空白） |
| 三种送达说法 | `已送达 · 渠道`（看业务码判出的 `delivered`，不看 HTTP 200）／`没发成 · 渠道` + 失败原话／`只有正文，库里没有发送回执`。⑧ 微信镜像失败时写的是 `wx_warn` 而不是 `sent`，所以先看送达再看回执 —— 顺序反了会把一次真失败说成"只是没回执" |
| 读不出来 | 端点回 `readable=false` + 原话，屏上红字挂出来；**不兜成空列表**（那等于把观测层故障说成"那天没发东西"）。日期不成形状回 400 带原话，一次库都不打 |
| ⑤ 还有一份 | `analytics.noon_review`（家数／量能／情绪那些结构化格）与正文同一炉写的；回看屏给的是**发出去的正文**，两者不互相冒充 |
| ⑪ 的第一条 | `strong_mode` 11-10 才建好，库里还没有它的正文行 —— 今晚 19:19 那一炉发出去之后才有得回看（在那之前这一屏上 ⑪ 那一格本来就该是缺的，不是坏了） |

实现三处：读侧 `app/intraday/store.py`（`broadcast_bodies` / `broadcast_body_days` / `fold_bodies`）、
端点 `vr/app.py::intraday_broadcast_bodies`、屏 `frontend/src/components/BroadcastBodyViewer.tsx`
（挂在 `IntradayBroadcastPanel` 里，**借同一张配置表的 `no`/`label`**，所以行首那个圈号与路名不另抄一份）。
钉住它：`tests/test_broadcast_bodies.py`（20 条，含"真库最近一天每路每条都回看得出来"与
"这三路的正文与回执同一钟点且逐字相同"两条**不打桩**）与
`frontend/test/intradayBroadcast.test.ts`（新增 9 条：三种送达不混、跳日只跳有正文的天、
默认落点来自接口不是本机今天、读不出来不许装成没发过、正文走 `<pre>` 原样出不套 markdown）。
