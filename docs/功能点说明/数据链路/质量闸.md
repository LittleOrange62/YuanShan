> **新鲜度如何自证**（任务要点 1）：这张表**没有 `calculated_at` 列**，`operations.quality_result` 只有 `run_at`（建表 DDL `app/db/sql/02_schema.sql:903`）。所以"多新"靠三件事自证：① 判定日 `date`（读的是哪一场）、② `last_full_audit`（最近一次审全的日子）、③ 每张规则卡片里的 `run_at`（那条结论的落库时刻，`:113`）。本屏**没有 `CacheLine`/`age_seconds`**（`DataPanel.tsx:121`）——因为它读的是持久化行、不是缓存，但也不是"刚刚算的"，页面用 `run_at` 交代真实时刻。

### 2.2 三态判定：`verdictOf()`（`Quality.tsx:46-51`）—— 本页最要守的规矩

```
function verdictOf(r): Verdict
  if r.enabled === false → "disabled"（先判停用，否则被算进未审、看着像漏审）
  if r.passed === true   → "pass"
  if r.passed === false  → "fail"
  else（passed === null/undefined）→ "unaudited"
```

| Verdict | 界面文案 | 徽标配色（`:38-43`） | 三态来源与语义 |
|---|---|---|---|
| `pass` | 通过 | `bg-primary/12 text-primary`（主色/绿） | `quality_result.passed = true` 且有该场结果行 |
| `fail` | 未通过 | `bg-destructive/15 text-destructive`（红） | `passed = false` 且有该场结果行 |
| `unaudited` | 本场未审 | `bg-muted text-muted-foreground`（灰） | **该规则在这一场 `operations.quality_result` 里没有行** —— `quality.py:74` 显式 `rule["passed"] = None if got is None else got["passed"]` |
| `disabled` | 规则已停用 | `bg-muted/60 text-muted-foreground/70`（更浅灰） | `config.quality_rule.enabled = false` |

> **三态 `null`＝没探到，不等于 `false`**（项目纪律，任务要点 2）：`operations.quality_result.passed` 在库里是
> `boolean NOT NULL`（`02_schema.sql:908`），**每一行存下来的都是真 true/false**；页面里那条"未审"的 `null`
> 是**读层左连接造出来的**——规则登记了、这场却没有对应结果行，就折成 `passed=null`→「本场未审」灰。
> 把 `null` 折进"通过"，就会把"0/30 审过"报成"30/30 正常"，那正是质量闸唯一要防的假绿（`Quality.tsx:18-20` 注释原话）。
> **未审不许渲染成通过**；未审的规则卡片连"实测/应为"那一行都不渲染（`:109` 的 `v !== "unaudited"` 守卫）。

## 3. check / rule 全码表（30 条，含义 + 判据出处 + 失败怎么显示）

任务要点 2 要求逐类回答"检查项回答什么、判据住哪、失败严重级与界面着色"。下面这张表**当场按 payload 逐条列全**（实测 30 条，见数据现实）。
所有 `builtin` 类是**库层约束/触发器的存在性哨兵**：审计不重跑数据，而是查 `pg_constraint`/`pg_trigger` 里那个对象还在不在、
挂在几个分区上（`app/quality/audit.py::_run_builtin()` `:105-121`）——"约束被谁 DROP 了"就是"看板全绿但防线没了"（`audit.py:16-19`）。
所有 `sql_bool` 类的判据是 `check_body` 里那条**返回单个 boolean 的 SQL**（`:d` 是交易日占位符），
执行器 `_run_sql_bool()`（`:84-102`）跑它；**SQL 返回 NULL 也按未通过记**（`:96-101`，样本不足/除零不是"通过"）。
界面着色一律同 §2.2：`pass` 绿 / `fail` 红 / 未过且 `blocking` 额外挂「拦停」红标 / 停用浅灰。

> 判据文件速记：登记在 `app/db/sql/05_seed.sql:88-223`（原 24 条）；涨跌停三补在 `compute/sql/23_quality_rules_limit_prices.sql`；派生表三补在 `compute/sql/22_quality_rules_derived_tables.sql`。`scope` 值域 `row|table|cross_day|cross_table|score`（`03_registry.sql:58`），`check_kind` 值域 `sql_bool|builtin|expr`（`:61`；**本表无一条用 `expr`**，未知 kind 执行器按未过记 `audit.py:147-148`）。

## 6. 不许破的纪律

1. **三态 `null`＝没探到，不等于 `false`**：`verdictOf()`（`Quality.tsx:46-51`）把未审与停用与通过/未过分成四态、分开数分开色。
   库里 `passed` 是 `NOT NULL`（`02_schema.sql:908`），页面那条 `null` 是**左连接造出来的**（`quality.py:74`），代表"这场没这条结果行"。
   把它折进"通过"，就是把"0/N 审过"报成"N/N 正常"——**这一屏唯一要防的假绿**。未审的规则连"实测/应为"行都不许渲染（`:109` 守卫）。
2. **`enabled===false` 必须先判**（`:45-47`）：停用规则永远不会有结果；不先判停用，它会被算进"本场未审"，看着像漏审。
3. **本屏只读、不现算**：GET 不跑判据、不起子进程、不写库。质检由作业写、页面只读行（§0）。
   **别为"看着能点"给页面加一个偷偷 spawn 的按钮**；要加触发端点就走 `POST /api/quality/audit` 契约（`Quality.tsx:173-176`），且返回必须与 GET 同一份口径。
4. **未登记结果不混进分母**（`:139-141`、`quality.py:84`）：`unregistered_results`（如备份自检写的 `backup_daily`）单独列、不参与 `rules_total`，否则覆盖率虚高。
   非场次类作业 `trade_date` 为 NULL 是按日期一并带出的（`quality.py:66`、注释 `:12-13`），不是脏数据、不当"那几天没审计"。
5. **NULL 判据＝未过、不是过**：`sql_bool` 返回 NULL 被记未通过并说清原因（`audit.py:96-101`）；`builtin` 找不到约束/触发器记"不存在"（`:120,175-176`）。都不许静默算绿。
6. **只报本场、不累计历史**：结果表同一批可能被重复写，未去重前不许累成"共未通过 N 条"（`:168-171`）。
7. **判据只住库里/执行器，页面不自己写口径**：severity/scope/check_kind/阈值/描述全部原样透出 `config.quality_rule`；
   判据 SQL 只住 `check_body`（05_seed / compute/sql/22 / 23）与触发器（`04_constraints.sql`），页面既不重跑也不改词。
8. **preflight 与本页正交，不许合并**（`:162-167`）：一份判"够不够格进复盘"、一份判"进库后坏没坏"，两把尺子不能互翻。
9. **`audit` 这张表别当"已接上"**：见 §6.1。
10. **外观瑕疵别当数据错**：`actual/expected/threshold/sample` 走 `_plain()` 的 `str(dict)`，卡面显示 Python repr 串（单引号、`False`），
    是格式化缺失不是值错（§2.4 注）。

### 6.1 `operations.audit` —— 有表零写者（任务要点 3，如实登记）

- 表定义：`app/db/sql/02_schema.sql:872-885`（含 `occurred_at/actor/channel/action/target/params/rows_affected/ok/error`）；列注释 `06_comments.sql:563-573`；授权 `04_constraints.sql:271`。
- 注释宣称「由触发器写入，应用层绕不过去」（`06_comments.sql:563`）——但那个触发器函数 `operations.trg_audit_stmt()` 虽在 `04_constraints.sql:142-152` **定义了**，全库 grep 只找到它的 `CREATE OR REPLACE FUNCTION`，**找不到任何 `CREATE TRIGGER ... EXECUTE FUNCTION operations.trg_audit_stmt()`**（挂的是 `trg_config_history`，写的是 `config_history` 不是 `audit`）。应用层亦无 `INSERT INTO operations.audit`。**结论：`operations.audit` 有表、零写者。**
- 权威登记：`docs/系统配置工作指南/13-日志与运行台账.md` §五 `:80`——「`operations.audit` 有表零调用」（登记为任务 #91 未完部分）。
- **本屏（质量闸）不引用 `operations.audit`**：`Quality.tsx` 与 `duanxian/quality.py` 只读 `config.quality_rule` / `operations.quality_result`，与本表无关（grep 无 `operations.audit`）。因此本页**不涉及** audit；但凡引用它的地方，**必须写"有表没写者"，不许写成"审计已接上"**。
