## 2. 第一块「组热度表」（`Panel`，`:88-170`）

面板 `note` 原句（`:90`，逐字）：

> 行与列全部来自接口交出的字段，前端不重算任何分数。默认序是后端给的预测操作分从高到低。报「连不到后端」时先看服务在不在 —— 这一屏本身没坏（同一接口实测 200），取数层现在会自己补试两次（隔 2 秒、6 秒）再下结论，重启那几十秒里打开页面不会再一眼红。

那句「补试两次（隔 2 秒、6 秒）」的实体是 `lib/probe.ts:20`（`OFFLINE_RETRY_MS = [2_000, 6_000]`）与网络层失败分支 `:36-55`；
它是**有界**补试，超时不折算成"没有数据"（`describeState`，`lib/datastate.ts:36-53`）。

接口契约（`Contract`，`:91-99`；组件 `components/ui/DataPanel.tsx:59-83`）声明数据出处为
`config.watchlist_stock × analytics.score(oper_score) × market_data.stock_daily × analytics.indicator_value × market_data.dragon_tiger_detail`。
⚠️ `Contract` **只在取数不成（非 loading 且非 ready）时才渲染**（`DataPanel.tsx:52`）——正常出数时屏幕上看不到它，它是"取不到数那一晚"的验收单。

`slowHint`（`:89`，原句「这一屏要把每个组 × 20 场的加权分现场聚合出来，2026-10-07 实测 3.3~3.8 秒；先别当成卡死。」）
只在 loading 那一档出现（`DataPanel.tsx:49-51`）。⚠️ **3.3~3.8 秒这个数本轮实测偏小**：2026-10-11 两次墙钟 4.97s／4.50s，接口自报 `elapsed_ms` 4214／4009（§6）。
`vr/app.py:897` 那句 docstring「一次 ~2 秒，无缓存」同样过期；"无缓存"这一半是真的（两次 `elapsed_ms` 不同、`generated_at` 变，没有任何 `cache` 字段）。

## 2A. 近 N 场排名那一列（2026-10-26 加，列位在第 2 列：组名之后、预测操作分之前）

### 2A.1 这把尺是什么（一句话）

**每天**把「当日成交额加权操作分」在**这张表里的组**之间排一名，取窗口最后 `GROUP_RANK_DAYS`（=5）场，
给出一格：`最近那场的名次` + `净变化（进/退/持平）` + `逐场名次路径（早→晚，用 → 连）`。

三条不是注释而是会出错的点：

1. **名次按未舍入的原值排，不按屏上那两位小数**。`_SERIES_SQL` 因此多取一列 `w_raw`
   （`duanxian/watchlist.py:396`，`(h.sx / nullif(h.sw, 0))::float8`），Python 侧排完名**在返回前 pop 掉**
   （调用点 `:487`、丢弃 `:488-489`）—— 屏上与折线读的仍是那位小数的 `w_score`，
   全精度数不上线，免得多个"没人交代的水位"。
   实测（2026-10-26，基准场 2026-10-21、近 5 场、44 个组）：按两位小数会并成同一档而原值有先后的行
   **合计 8 行（每天最多 4 行）** —— 用舍入值排名就会把这 8 行念成"同分同名"，而它们不同分。
2. **那一天整组算不出加权分就不给名次**（组里没有一只票当天同时有分、有成交额）：路径里是 `·`、
   `rank_now` 是 null ⇒ 格子念 `—`。**不占号、更不是最后一名**（名次公用件那条纪律）。
   一名都排不出的组，路径交 null 而不是五个 `·` —— 一排点会被读成"场场垫底"。
3. **这一列与行序是两把尺**：行序（默认序）按 `pred_score`＝整个窗口的外推值，名次按**那一天**的加权分
   ⇒ 第一名不一定在第一行。这句话由后端 `calibers.rank` 原句上屏（悬停），页面不自写。

### 3.3 斜率类读数：`regr_slope` 的参数顺序（这一屏最贵的一条）

**X 轴是什么**：不是价格、不是自然日，是**场次号 `rn`**（1..20 的整数），
由 `_GROUP_SQL` 的 `sess` CTE 现造（`:200-205`：`select distinct trade_date from analytics.score where capability_key='oper_score' and trade_date <= date order by trade_date desc limit 20`，再 `row_number() over (order by trade_date)`）。
`hist` 里取的是 `min(u.rn)`（`:211`），即"这个组×这一场"落在窗口第几档。**因为窗口只圈有分的交易日，长假与停牌都不占位**，
所以等距 `x` 是这套斜率跨组可比的前提（`duanxian/watchlist.py:186-189` 写明了这条；测试 `tests/test_watchlist_group.py:105-107`）。

**Y 是什么**：那一场组内的**成交额加权操作分** `w_score = sx/sw`（`:225-230`），
`sx = Σ(value × amount_yuan)` 只累"有分且有成交额"的行、`sw = Σ(amount_yuan)` 同过滤（`:212-215`）。

**分子／分母**（PG `regr_slope(y, x)` 的定义，即最小二乘 `b`）：

```
b = Σ(xᵢ − x̄)(yᵢ − ȳ) ⁄ Σ(xᵢ − x̄)²        ← 分子是 x 离差×y 离差之积的和，分母只有 x 的离差平方和
trend_score = b × 10                        ← 读作"每 10 个交易日的加权分变化多少分"（`:233`）
pred_score  = intercept + b × (n + 1)       ← 外推到第 n+1 档（`:234-236`，n = trend_days）
```

调用点写的是 `regr_slope(w_score::float8, rn::float8)`（`:233`、`:235-236`）——**第一个参数是 y（分数），第二个是 x（场次号）**。

**参数顺序反了会怎样**（实测，2026-10-11 用 `wa2.json` 的 880 点独立做最小二乘）：
把两句写反成 `regr_slope(rn::float8, w_score::float8)` 拟合的是"场次号对分数的斜率"，其值 `= Σ(x−x̄)(y−ȳ) ⁄ Σ(y−ȳ)²`，**分母换成了分数的离差平方和**：

| 组 | 接口 `trend_score`（正确） | 反写的 `b×10` | 接口 `pred_score`（正确） | 反写的 `pred_score` |
|---|---|---|---|---|
| 信创网安 数据 | **+6.60** | +0.54 | **−7.80** | **+12.44** |
| 药CRO | +1.91 | +0.17 | −7.29 | +11.02 |
| PCB | **−3.95** | **−0.35** | **−12.54** | **+9.47** |

结论要分开说，别含糊：
1. `trend_score` 的**正负号不变**（两条回归的分子是同一个 `Σ(x−x̄)(y−ȳ)`，号由协方差决定），但**量纲被换掉、量级被压死**（±26.85 的真实范围被压成 ±0.5）⇒ 屏幕上"谁在起来"再也排不出层次。
2. **会反号的是 `pred_score`**（实测 −7.80 → +12.44、−12.54 → +9.47）：因为反写的截距与斜率一起换了一套量纲，`a + b(n+1)` 落回**场次号的均值附近（≈10.5）**。
   而 `pred_score` 正是这一屏的**默认排序键**与表下 caveat 的主角 ⇒ 整张表的头尾颠倒、并且把"水位在 −40 ~ −7"读成"水位在 +9 ~ +12"。
   当年 41 个组的预测分全都贴在 +10 附近，就是这个原因（`docs/页面展示工作指南/04-新增页面落地进度.md:157-160`、`tests/test_watchlist_group.py:5-9`）。
3. 这一条**按 SQL 原文钉死**，不许靠手改回来：`tests/test_watchlist_group.py:56-61` 同时断言正写 `regr_slope(w_score::float8, rn::float8)` 在场、反写 `regr_slope(rn::float8, w_score::float8)` 不在场。
4. `pred_score ≈ 窗口均值 + trend_score`（`calibers.pred_score` `:410-413` 与 `docs/…04:161-163`）不是巧合，是 `mean_x = (n+1)/2` 的代数化简 ⇒ 看见"今天 −23 分、预测 +3 分"不要以为算错。本场实测 `pred_score` 全为负（−39.5 ~ −7.3），
   这恰好是反写时"全落在 +10 附近"的对照组：**同一批票、同一份窗口，号都对不上就说明参数顺序翻了**。

## 7. 不许破的纪律

1. **判据只住一处**：所有聚合只住 `duanxian/watchlist.py` 的 `_GROUP_SQL`/`_SERIES_SQL`/`_MARKET_LEVEL_SQL`；
   指标本身的口径住 `config.indicator` 的表达式（`app/db/sql/05_seed.sql:262-281`）；`oper_score` 的合成住评分那一层（`app/db/sql/05_seed.sql:1364-1367`）。
   页面**只排版、不重算**（`:90` 那句是承诺，不是装饰）。目前唯一的前端再算，是 §2.1 那个 `ready` 计数与 §3.1 那条"top3 再排一次"，都不碰分值。
2. **库里没有组级结果表**（`caveats[0]`、`duanxian/watchlist.py:178-183`、`docs/…04:141-149`）：这一屏永远是"读个股列 + 现算聚合"，
   别因为"/volume-double 那种落一张 analytics 表"的做法就给它造一张组级表 —— 那会让"改了判据、历史行还挂着旧含义"这件事第一次发生在组这一层。
   名单快照表 `reference_data.watchlist_member_snapshot` 是给**板块趋势 scope=group** 攒实盘序列的（`16_sector_trend_signal.sql:11-14`），不是这一屏的结果表。
   ⚠️ **2026-10-26 加「近 N 场排名」那一列时这条纪律没有被绕过**：名次是把 `_SERIES_SQL` 本来就交出的
   20 场加权分**在读侧逐场排一遍**（`_daily_group_ranks()`），没有新表、没有新指标、没有新跑批。
   要给它落一张 `analytics.watchlist_group_daily` 得先推翻这条裁定，并想清楚"改判据后历史行含义"这件事。
3. **缺数是 `—`，不是 0**：趋势三列在 `having count(*) >= 10` 之外根本不出现（`:237`）；`up_ratio` 分母 0 给 `None`（`:372`）；
   `_plain()` 把 NaN 折成 `None` 而不是 0（`:48-50`）。**唯一的合法 0 是 `dt_times`**（`coalesce(...,0)` `:289`，语义是"真没上榜"）——别顺手把它也改成 `—`，也别把它读成"查不到"。
4. **`regr_slope(y, x)` 参数顺序不许翻**（§3.3），且不许把窗口从"有分的交易日"改成自然日；`top3` 判据是**斜率**不是当日分（测试 `tests/test_watchlist_group.py:94-102`）。
5. **bp 不许改回 %**（`calibers.chg10_bp` `:414-415`、`unit.chg10_bp` `"bp/日"`、测试 `tests/test_watchlist_group.py:118`）；
   两类母体式的"合成单一热度指数"也不许做（`:202-206`）。
6. **上限要说明白**：这一屏**没有 `limit` 截断**（行集是"全部有成员的组"，44 行），也没有前端 `.slice()` 渲染上限 ——
   所以"这是前 N 名不是全部"那句话在这一屏不该出现，出现了反而是假的。反过来，讲清另一件事更必要：
   **`_GROUP_SQL` 里 `day` CTE 算了 `eq_score_direct`（`:265`），但外层 `select` 没选它（`:283-289`）**，所以它是"算了没出门"的死列；
   `eq_score` 出门的那一份来自 `cur` CTE（窗口末场的等权分，`:228`、`:240`）。改这一列时别以为它们同源。
7. **单位随后端、页面不换算**（`lib/datastate.ts:124-136` 的规矩）：这一屏的 `%`／`bp` 后缀是 JSX 硬写的（`:133-144`），
   这是**已经存在的破口**（后端 `unit` 交了 12 条却没人读）。要修的方向是页面去读 `unit`，不是再补一套前端换算。

## 10. 搬家后的逐列实测（2026-10-14，浏览器 DOM 读数）

页面：`http://127.0.0.1:8910/grouped?v=1014seed`（加载的资产 `index-BgZqHm2Y.js`，与本轮构建产物一致）。

| 项 | 实测 |
|---|---|
| 位置与结构 | `div.space-y-4` 的**第一个子元素**就是这块：顺序＝`分组整体分析（组热度表）` → `各组的分数趋势` → `这一块的口径` → `这一块不做什么` → `分组`（那 48 张卡片）→ `自选明细` → `要分析哪一只` → `这只票的量化档案` → `该支票的趋势量化计算` → `自选股新高` → `本机名单`。也就是用户要的那句话：先看分组整体，再看组里的票 |
| 一份请求 | 页面加载后网络面板里 `/api/watchlist/group-analytics` **只有一发**；两次读到的 `elapsed_ms` = **4096 ms** 与 **5303 ms**（同一次进页内换排序不重发，因为排序是显示层）。屏上那句话写明「与最上方那张「分组整体分析」是同一次聚合（不是又发了一遍请求）」 |
| 行数与列数 | 表体 **44 行**（有成员的组）× **16 列**（组名 ＋ 15 个指标）；下面那叠卡片 **48 张**，其中 **44 张**默认就带组级 6 格，另外 4 张（隔夜持股法：／T+0／风向标／竞价>5%）写着「本组没有成员，接口不聚合空组」 |
| 逐列点击 | **16 列全点过**（点列头里的 `button`，不是点 `th`）。每一列都是同一台三档机：第一下 `aria-sort=descending` 且数值从大到小、第二下 `ascending` 从小到大、第三下回 `none` 且行序与后端榜序逐格一致。举几列的头尾：预测操作分 −5.45…−41.75；加权操作分 5.38…−29.34；趋势分数 8.8…−22.93；当日均涨幅 6.2…−4.96；组内10日均涨跌 57.3…−299.6（bp）；组内20日均涨跌 50.4…−94.6；上涨占比 100.0…9.1（%）；组内明日振幅 7.81…2.87；组内10日振幅 7.03…2.73；组内20日振幅 6.75…2.69；上榜次数 73…0；趋势天数 20（44 行全 20，本次无一行为空）；成员数 488…2；有分只数 488…2；组名（拼音）降序首格 `Token`、升序首格 `半导体材料` |
| 一次假红的教训 | 头两轮我用 30~60 ms 的采样间隔，"成员数""组内20日振幅"两列被判成**不单调**——实际是**点了以后还没重绘就读 DOM**，拿到的是上一列的行序。改成每次点击后等 200~600 ms 再读，16 列全部单调通过。⇒ 复验这一屏时**必须留够重绘时间**，否则会把正常的表判成坏表（这条与「点击实测要读真值」那条纪律不冲突，是要在点与读之间等一下） |
