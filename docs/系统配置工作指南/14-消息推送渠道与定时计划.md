# 14 · 消息推送：渠道、凭据、内容与定时计划（谁能发、发什么、几点发、发没发出去）

> 用户 2026-10-15 点名：「GitHub 上有没有集成了飞书、钉钉、微信、邮件等渠道的通知模块」并给了 Apprise，
> 口径随后收紧为：**「只做配置与手动测试，先不接自动事件；渠道只做邮件 / 企业微信群助手 / 钉钉群助手 /
> 飞书群助手，其他渠道与 SNMP 全不管；报警类型手动可以选择，可以选择内容也可以选择时间定时发送；
> 特别是每个策略里面筛选出来的内容，可以选择定时发送；自选股重点关注的，也根据个股情况定时发送
> （内容尽量全，也可手动多选）」**。
> 本文交这一块的**范围、真源位置、凭据纪律、可见性与边界**；开关在册判据仍以
> [05-调度宿主.md](05-调度宿主.md)、[12-定时任务全景.md](12-定时任务全景.md) 为准，
> 弄坏它来验证的配方并入 [07-故障恢复手册.md](07-故障恢复手册.md)。

## 一、范围（做什么 / 明明白白不做什么）

| 做 | 不做，且界面上不给那个框 |
|---|---|
| **四个渠道**：邮件（SMTP）、企业微信群助手、钉钉群助手、飞书群助手 | 短信、SYSLOG、**SNMP TRAP**、其它一切 apprise 支持的渠道 |
| 渠道的**增删改、启停、发一条测试消息** | 自动事件触发（链失败、连败到 N 次、告警规则）—— 本期**不接**，只留手动与定时 |
| **定时计划**：内容多选 + 时刻 + 频度（每日/每周几）+ 只在交易日 | 把正文写成 HTML/图片/卡片 —— 只发纯文本 |

`notifyconfig.validate_kind`对越界的 kind 说的是一句**归因正确**的话：
"短信/syslog/SNMP TRAP 本程没有这条通道，**不是填不了，而是本程没有它的执行体**"。
这句是刻意的：apprise 本身有 `syslog://`、`twilio://`，但 Windows 上它的 `syslog.py`
`import syslog` 直接失败，接了就是一个永远不会通的框。**没有的渠道要在写入面就拒掉**，
否则用户配完、测试、看到"已交付 0 个渠道"，那比不给这个框更难查。

依赖：`apprise>=2.0,<3`（`requirements.txt`，本机实测 2.0.1）。
⚠️ 许可证是 **BSD-2-Clause**，网上常说的"MIT"不准。判据一律住我们自己这边
（`notifyconfig.py` 做校验、`duanxian/notify.py` 组正文），apprise 只当最后的投递器 ——
这样将来换库或它改 URL 语法，页面与账本不动。

## 二、五层分工与唯一真源（缺一层就是"看得见关不掉"或"改得动没人读"）

| 层 | 位置 | 只管这一件事 |
|---|---|---|
| 配置 | `notifyconfig.py`（整份文件） | 渠道/计划的形状、校验、掩码、落盘原子写与留痕。**不含任何取数与发送** |
| 内容与发送 | `duanxian/notify.py` | **十七种内容块**（`_blk_*` 一族）怎么从**现成读层**拼成正文、`compose`、投递唯一入口 `deliver`（机器人自己 POST 走 `_post_json`、邮件走 `_apprise` + `_mail_via_apprise`）、去重与历史（`already_sent`/`mark_sent`/`log_history`）、`run_plan` |
| 宿主循环 | `server.py` 的 `_notify_scheduler` / `_start_notify_push` / `NOTIFY_SCAN_SEC`（第 12 条 `notify-push`），`_lifespan` 里 `_start_backup()` 之后一行的 `_start_notify_push()` | 每 60 秒问一次"到点了没有" |
| 端点 | `vr/app.py` 的 `_notify_payload` + 三个端点：`GET /api/notify`、`POST /api/notify`（一次只改一件）、`POST /api/notify/preview` | 校验全交 `notifyconfig`，这里**不重复一份**判据 |
| 面板 | `frontend/src/components/NotifyPanel.tsx` + 纯判据 `frontend/src/lib/notifyRules.ts`（能被 `node --test` 驱动）+ `lib/notify.ts`，挂在 `/system` 的 `<LoopSwitchboard />` 之后 | 渲染与交互；**后端那句人话原样显示，不在前端重抄一份** |

配置落点：`<data home>/notify/config.json`（默认 `~\.duanxian-agents\notify\config.json`），
发送历史 `<data home>/notify/history.jsonl`，去重表 `<data home>/notify/sent.json`。
`VIBE_NOTIFY_CONFIG` / `VIBE_NOTIFY_HISTORY` / `VIBE_NOTIFY_SENT` **只给测试注入用**，日常不要设。

⚠️ 循环自己**没有 `run_at`**（`_notify_scheduler` 的 docstring 记了理由）："几点发"是每条计划自己的字段，
给循环再配一个时点，就是页面上多一个改了也不生效的框 —— 与 `tdx_watch` 同一条理由。
因此 `duanxian/jobs.py::NOTIFY_PUSH_DEFAULTS` 故意只有 `{"enabled": True, "note": ""}`。

## 三、凭据纪律：只写不读

这一块是唯一一处**局域网白名单机器能往本进程写密钥**的地方，所以按下面五条钉死：

1. **读接口永远交掩码**。`notifyconfig.masked_channel`交 `url_masked` =
   `******` + 尾 4 位（`SECRET_KEEP = 4`：够认出是哪条，不够拿去用）。
   为什么不是"遮前缀"：`mailto://用户:密码@域/收件人` 与 `feishu://<32 位 token>` 的敏感段位置完全不同，
   逐段解析会漏。
2. **`.env` / 环境变量的名字优先**。渠道可以只填 `url_env`（如 `FEISHU_TOKEN_GROUP_A`），
   真串留在 `.env`（`notifyconfig.env_value`，环境变量优先于文件，与 `duanxian/pg.py` 同一约定）。
   指向不存在的变量**会当场说清**：`missing_reason` = "配置里写的是 XXX，但 .env 与环境变量里都没有这个变量" ——
   不说清就是"页面绿、发送空"。
3. **编辑时留空 = 不改这一条的凭据**（`validate_channel(..., allow_blank_secret=True)`，
   `notifyconfig.upsert_channel`）。掩码值回填真串那种事不允许发生，前端 URL 框是 `type="password"`
   且**不回填服务端任何凭据字段**（这条钉在 `frontend/test/notify.test.ts`）。
4. **历史与账本里没有 URL**。`log_history`只记渠道键、状态、字数；`jobs.record` 的 `detail`
   同理。诊断只报计数与键名。
5. **pytest 进程里硬挡真发**。两个出口各自硬挡：`duanxian.notify._post_json`（机器人）与 `_apprise`（邮件），
   判据是"这个口子还是不是默认那个"，见 `PYTEST_CURRENT_TEST` 直接抛
   —— 跑一次全量测试就给用户的工作群发一条消息，与 10-06 那次"pytest 在用户桌面启动通达信"同一类越界。
   要打桩就打这一个入口。

## 四、渠道：四种 URL 形状与校验会说的话

| kind | 中文名 | 真端点（**由我们按 token 拼**，不拿用户粘的地址直发） | 必填 | 界面上可以怎么填 |
|---|---|---|---|---|
| `mail` | 邮件（SMTP） | 交给 apprise | `host`、`to` | `mailto://用户:密码@smtp域名/收件人` |
| `wecom` | 企业微信群助手 | `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<key>` | `token` | `wecombot://<key>` 或粘贴整条地址。**没有加签**：密钥填了会被拒（不是忽略） |
| `dingtalk` | 钉钉群助手 | `https://oapi.dingtalk.com/robot/send?access_token=<token>` | `token`（密钥选填） | 同上；「加签」密钥填单独那一格（也可 `?secret=`） |
| `feishu` | 飞书群助手 | `https://open.feishu.cn/open-apis/bot/v2/hook/<token>` | `token`（密钥选填） | **直接粘贴群里复制的整条地址**，或 `feishu://<token>`；「签名校验」的密钥填**下面那一格** |

校验（`notifyconfig.validate_channel`）不是"看着像就行"，每条失败都是一句**能照着改**的话：
前缀不对（会印出实际收到的前缀）、只有前缀没有凭据（"发了也是空响"）、
邮件缺收件人（`@域名` 之后那一段）、`url_env` 不像变量名（要全大写字母/数字/下划线）、
URL 里还留着 `test` 占位串（除邮件外一律拒存 —— 防"我把示例 URL 存进来了"）。
渠道上限 12 条、计划上限 20 条（`MAX_CHANNELS`/`MAX_PLANS`，超了写入面拒并说明）。

### 10-17 补的两条：已配渠道要能点开看、能改；`url_env` 指向的地址也要查

用户原话：**「点开已配置的应该也能看到明细，但是要隐藏一部分，也可以进行编辑和保存啊！」**
原本渠道那一行只有「勾选 / 发一条测试 / 删除」三个动作 —— 配好的渠道**点不开、改不了**，
想换一句备注只能删了重填，而删重填要人手再抄一遍 token（那是最容易抄错的一格）。现在：

- **一份表单两个用途**：`ChannelForm`（新增与编辑共用，`channelDraft` / `channelPayload` 是纯函数、
  `frontend/test/notify.test.ts` 里有真用例）。回填只交屏幕上本来就有的东西 ——
  种类 / 键 / 名字 / `url_env` / `secret_env` / 备注；**`url` 与 `secret` 两格永远空着开**且是 password，
  空＝后端保旧值（`upsert_channel` 那条"留空不覆盖凭据"）。
  ⚠️ 把 `url_masked` 回填进输入框＝下次保存把 `******xxxx` 当凭据写回配置文件 —— 那是把掩码当真串存。
- **键（`key`）在编辑态只读**：后端按键定位那一条，改名等于新建一条，指着旧键的计划当场变成「渠道已删」。
- **明细（`ChannelDetails`）把该说的一次说完**：种类 / 键 / 名字 / 尾 4 位 / 凭据来自（内联或哪个变量）/
  加签有没有带 + 来源 / 启停 / 备注 / 现在能不能发（`invalid_reason`、`missing_reason` 原样）/ 配置文件路径。
  **隐藏的那一格就是真串**：地址里的 token 与加签密钥在任何读数里都不出现，连掩码都不给（密钥只有"有没有"）。
- 为此 `masked_channel` 多交一格 `secret_env`（**变量名不是凭据**，`sign_source` 本来就写着它）：
  不交出来，面板"编辑"时那一格是空的，而 `upsert_channel` 收到空串就把这条指回 `.env` 的引用清了 ——
  用户明明只想改一句备注。
- **`url_env` 现在也查它指向的地址**（`validate_channel` 里能解析出值时按同一套规则复跑一遍）：
  原先只查变量名形状，于是"种类选了飞书、而 `.env` 里那条还是钉钉地址"会被**静默收下**——
  面板标「可用」、计划算成 `sendable`，实发时被对面一句拒掉（10-17 用例 `test_改备注不许把指向env的引用清掉` 抓到）。
  变量在本机不存在时**不**跑这条（那已由 `missing_reason` 单独点名），免得把"没配 .env"说成"地址形状错"。

### 加签密钥这一格（10-16 补，之前"加不进去"就是缺它）

飞书自定义机器人的安全设置是三选一：**自定义关键词 / 签名校验（密钥）/ IP 白名单**。
之前的界面只有一格 URL，用户拿着「一条 webhook + 一串密钥」就没法填。现在：

- 多一个 `加密密钥（选填）` 的 password 框（`kind_choices.supports_sign` 决定给谁显示），
  也可以填变量名 `secret_env` 走 `.env`；
- **只写不读**：读数只交 `has_sign` / `sign_source` / `sign_warning`，密钥内容与掩码都不交；
  编辑时留空＝不改已存密钥；
- ⚠️ **两家 HMAC 取法相反**（这是本次最容易写错的一格，两家都各测了一条用例钉住）：

| 家 | 时间戳 | 算法 | 放在哪 |
|---|---|---|---|
| 飞书 | **秒**，转字符串 | `Base64(HmacSHA256(key="ts
secret", msg=""))` ← key 就是拼串 | **请求体** `timestamp` / `sign` |
| 钉钉 | **毫秒** | `Base64(HmacSHA256(key=secret, msg="ts
secret"))` | **URL 查询串** `&timestamp=&sign=` |
| 企微 | —— | 没有加签这一说（填了直接拒，不静默忽略） | —— |

### 每一档的参数格是一张描述符表（10-17 新增，`notifyconfig.SCENE_FIELDS`）

一条描述符 = 面板上的一个格子：`{key, label, type, unit, min, max, default, choices / choices_from,
empty_means, empty_error, bit_prefix, bit_suffix, note}`。`scene_catalog()` 把 `choices_from`
**就地解成候选清单**（共振源/规则/分组要查库，形态类型/象限标签/档位是判据表自带的标签、不查库），
连同条数的默认值与上限一起交给界面。于是：

- **加一档内容或加一格参数只动后端**：`SCENE_BUILDERS` 加执行体 ＋ 三张条数表各加一行
  ＋ `SCENE_KEYS`/`SCENE_HINTS`/`SCENE_FIELDS` 各加一条 ⇒ 界面自动多一个勾选项、一个条数框、若干参数格。
- **`validate_scenes` 只按描述符判**（原先是五段按档名写死的 if）。每种 `type` 各管一种形状：
  数字看 `min~max`、`select` 认静态候选、`multi` 收列表或逗号串（`as_objects` 那一格必须写成
  `{rule_key, params}`）、`codes` **只收列表**（收字符串会被执行体**逐字符**当六只票）、`bool` 只收勾与不勾、
  `text` 限长。
- ⚠️ **`empty_means` 与 `required` 是两件事**（10-16/10-17 各挨过一次）：
  "整项不填"＝用后端默认（合法）；"填了个空列表"＝勾了这一格却一个都没选（`empty_error` 当场拦）。
  把留空有含义的格子当必填拒掉，后端那条兜底就永远走不到；反过来 `screen.rules` 空着会发出空白正文，必须拦。
- **界面不许抄默认值 / 上限 / 单位 / 话术**：列表那一行的
  `自选股当日明细（分组 AI影视投流，涨幅≥1%，5 只）、市场概览（2 层）` 全部由描述符的
  `bit_prefix/bit_suffix` 拼出来（`%s` 由后端那句模板带值），`lib/notifyRules.ts` 里**一档 if 都没有**。
- 条数留空＝用后端默认值（不写进配置），填了才写 `scenes.<档>.limit`。
  表单的读回/写回在 `frontend/src/lib/notifyPlanForm.ts`（那边有"读回→写回必须一模一样"的真往返用例）。

三条形状上的纪律：

- **基准日不是"本机今天"**：`_session_date`取库里最近一个已收盘场次。休市日与凌晨按今天取
  会拿到库里根本没有的日子再报成"没有数据" —— 那是判据错，不是数据缺。
- **一块坏了不拖整条**：`compose`每块独立 `try`，坏的那块在正文里写成一行原因，其余照发。
  异常兜成空正文才是真事故（正文空 = 群里一条"今日复盘"啥也没有）。
- **缺失是 `—`，不是 0**：`_pct`取不到就是 `—`；持仓的 `quote_ok is False` 不参与汇总。
  过时的分项标注 `(旧)`。正文超上限会在正文里**声明截断**，不是默默切 —— 上限见下面那一节。
- **"筛完是 0 只"与"这一场没数据"是两句话**：`quant._empty_after_filter`（10-17 补）专门说前者。
  原先倍量次数≥12 筛空了也会被告知"这一场没有数据（未回填或当日非交易日）"，而同一分钟页面能列出 191 只 ——
  那是拿一句像样的假解释盖住一个真结果。推送与页面共用这一句，所以两边一起修好。
- **收窄只在对已读全的那一段做**：`watchlist.pct_min` 设了门槛时先把**整组**读全再筛
  （只读前 `limit` 行就筛，"筛完一只不剩"很可能只是"后面还没读到的才有 —— 本仓 10-13 记过"筛了个寂寞"），
  读不全时正文要写明"只对已读到的 N 只做筛"。`allocator` 因此**不给**温度门槛/排序（读层没有这个参数，
  本地排就等于对截断后的那段再排）。

### 正文上限是按渠道取的，而且管的是整条消息（10-17 补）

原先一个全局 `MAX_BODY_BYTES = 3500` 是**错的抽象**：

| 渠道 | 对方硬上限 | 我们用的 `BODY_LIMITS` |
|---|---|---|
| 企业微信群助手 | **text 消息 2048 字节**（超了 `errcode 45004 size too large`） | 1900（留余量：换行与表情都按字节算） |
| 飞书群助手 / 钉钉群助手 | 宽松得多 | 各 4000 |
| 邮件 | 没有这个量级的限制 | 20000 |

三条口径：

- 一条计划发**多个**渠道时取**这些渠道里最小的那个**（`body_limit`）—— 宁可短，不能发不出去；
- **上限管的是整条消息**：机器人收到的正文是「标题 + 换行 + 内容」拼起来的，只按内容切就会把标题那几十字节漏在外面
  （实测切到 1899、实发 1927，企微照样拒）。`compose` 现在先扣「标题+换行」再扣那句「已截断」自己的字节；
- 历史行里同时记 `bytes`（整条）/`body_limit`/`truncated` —— 手机上只收到半截时，这三格是唯一的解释。

候选项**全部现读**（`duanxian.notify.scene_catalog`）：共振源清单来自 `confluence_view.SOURCE_LABELS`、
筛选规则来自库里 `enabled` 的规则、自选分组来自 `watchlist.groups`。
写死一份常量清单的下场是"用户勾了个不存在的规则，apprise 照发一条空正文"。

### 10-16 补齐的两处"后端认、界面没接"（是用户点名那句才暴露出来的）

## 五·补 —— 10-16 改造：对面回 200 不等于送达（这是最要紧的一条）

用户界面上点「发一条测试」，当时看到的是「**1 个渠道已交付**」。真查下去是这样的：

| 事实 | 证据（本机现测） |
|---|---|
| apprise 2.0.1 的飞书插件**只看 HTTP 状态码** | `.venv/.../apprise/plugins/feishu.py` 的 `send()` 里只有 `if r.status_code != 200: return False`，否则直接 `INFO Sent Feishu notification.` 并 `return True` |
| 而飞书/钉钉/企微对**无效 token 也回 HTTP 200**，错误写在 JSON 回体里 | 假 token 实测：`POST https://open.feishu.cn/open-apis/bot/v2/hook/<假token>/` → `200`、85 字节；回体 `code=19001, param invalid: incoming webhook access token invalid` |
| 于是"没送达"被显示成"已交付" | 页面那格原话：`panel-check：1 个渠道已交付` |

**改法**（不 patch 第三方，改我们自己这一层）：

- 三个群机器人**自己 POST**（唯一出口 `duanxian.notify._post_json`），并**自己认回体**
  （`_verdict`：`code`/`errcode`/`StatusCode` 非 0 就是失败，并把对面的 `msg` 原样带出来）；
  只有**邮件**继续交给 apprise（SMTP 握手不该在这里重写），取模块的口子是 `_apprise()`。
- 顺带补上**超时** `SEND_TIMEOUT_SEC = 10`：原先一次调用没有超时，对面不回就把 60 秒心跳拖长
  （§十记过这条风险，现在这一格有主了）。
- 官方地址表 `BOT_URLS` 一份；钉钉带 `?secret=` 时按官方口径加签（时间戳 + HMAC-SHA256 + base64 + urlencode）。
- 整体 `ok` 的口径：**所有渠道都确认收到**才算成 —— 三个渠道里有一个没到，绝不能写成"已交付"。

改完后再点同一个假 token，界面上是：

```
panel-check：没发出去 —— 回体说没收到（code=19001，param invalid: incoming webhook access token invalid）
```

⚠️ 同一天还抓到一条形状问题：原先那个投递函数本体里写的是 `aprise.NotifyType`（`apprise` 少一个 p）。
它之所以活了一整天，是因为**所有用例都把整个发送函数打桩掉了**，那几行真代码一次都没被执行过
（`tests/test_notify_config.py::test_真发送路径要用假aprise模块跑一遍本体` 现在专门跑本体）。
打桩要打**取模块的口子**（`_apprise` / `_post_json`），不要打投递函数。

## 六、定时：判"到点"与判"发过"是两处，不许合并

`notifyconfig.due_minute`只判**时刻与星期**；"今天发过没有"由发送侧按
`计划 id + 日期` 去重（`already_sent` / `mark_sent`，`sent.json` 只留最近 60 天）。
分开是有意的：15:59 收盘链的教训就是"宿主自己判完了当天不再让人重发"。

| 字段 | 含义 | 判据 |
|---|---|---|
| `run_at` | `HH:MM`，`9:05` 会归一成 `09:05`（`notifyconfig._norm_time`） | 不归一就会让"面板显示 9:05、宿主按 09:05 判"这种偏差有机会出现 |
| `run_freq` | `daily` / `weekly` | 与 `duanxian/jobs.py` 同一口径 |
| `weekly_days` | `0~6` 逗号分隔（**0 = 周一**） | ⚠️ 写入面**比宿主更严**：宿主 `freq_allows` 是"判不了就放行"，`weekly` + 空周几在它那儿等于天天跑。所以 `notifyconfig.validate_freq` 直接拒，并在 `notifyRules.ts::scheduleText` 里把这句写给用户看（"没勾周几 ⇒ 实际会天天发"） |
| `trade_days_only` | 默认开 | `_trade_day`**判不了就照发** —— 日历缺一天不该让人一份日报都没有，与 `fundflow` 同一读法 |
| 去重 | 每天每计划一次 | **失败也记**（记的是"试过了、失败"），否则会在同一分钟重试成一串；重发的口子交给「立刻发一次」，不交给循环自己猜。⚠️ 这里的"一天"是**库里最近已收盘场次**（`_session_date`），不是本机日历日 —— 凌晨那条记的是"上一场"的账，实测 `sent.json` 里那格写作 `p1:2026-10-15` |

### 迟到窗口：15 分钟（10-15 补，专门堵"错过那一分钟"）

循环是**处理完再睡 60 秒**，所以一条网络慢的发送、或一次重启，就可能把 `09:05` 那个整分钟完全跳过。
原先 `due_minute` 只认"正好那一分钟"，于是那种跳过**什么都不会留下** —— 比"发失败"难查一个数量级。

- 现在认 `0 <= 现在 − 时刻 <= LATE_WINDOW_MIN（15）`。当天实测边界：`09:04 False / 09:05 True / 09:20 True / 09:21 False`。
- **窗口不是重试**（这条最重要）：去重照旧**失败也记**，所以窗口内第二、第三次心跳一律不再发。
  实测：`09:05` 那次 `fail` ⇒ `09:12` 的 `due_plans` 交**空列表**；要真重发只有「立刻发一次」（`force`）。
- 跨零点不回绕：时刻 `23:55` 而现在 `00:05` ⇒ 差值为负，不发（不会把昨天的档补到今天凌晨）。
- 过窗之后不静默：`slot_state` 把它读成 `missed` 那句（见 §八），由人决定要不要补。

## 七、三个手动动作（`POST /api/notify`，一次只改一件）

| 动作 | 语义 | 关键点 |
|---|---|---|
| **发一条测试**（`test_channel`） | 往**一条渠道**发一句固定测试文本 | 失败回 **502** 带渠道键与原因；不经计划、不进去重表 |
| **预览正文**（`POST /api/notify/preview`） | 不发送，只把将要发出去的那段字交出来（`duanxian.notify.preview`） | 光看勾是看不出对错的。同时交 `would_send_to`（可用渠道键）与 `blocked`（逐条不可用原因） |
| **立刻发一次**（`run_now`） | 走**与循环完全相同**的执行体 `run_plan(force=True)` | `force` 只绕过"今天发过了"这一道，**不绕过**渠道不可用、不绕过 `validate_plan` —— 没配好就是不许发，那正是要让人看见的失败 |

### 「保存」这一格：拦下来必须说话（10-17 用户点名「点保存计划，没反应」）

用户看到的现象是：填完点「保存计划」→ 屏幕上什么都没发生 → 判定"没生效、也没推送"。两条真因，都在界面这一侧：

⚠️ **10-19 用户第二次报同一句「点击了保存计划之后，没反应啊？？？」—— 上一轮只修了"缺项不说话"，漏了另外两条**：

1. **真提交那一发的回执在 1,200px 之外**。这一屏约 14 屏高：卡片顶（那句 `reason` 与错误原先只显示在这里）在 ~12,790px，
   而「保存计划」那颗按钮在 ~13,900px。点下去后端**确实保存成功了**，但成功之后表单收起、回执印在眼睛上面那片 ——
   用户那片区域一个字都没变，看起来就是"没反应"。改法是**回执跟着动作走**：
   `run(tag)` 记下这条消息属于哪一格（`plan|pe|now|pd` → 计划格里，其余 → 卡片顶），
   计划那一格的那行用 `scrollIntoView({block:"center"})` 把自己滚进视野（`NotifyPanel.tsx` 的 `noticeAt`）。
2. **渠道行那个「启用/停用」开关会把你正在填的计划表单整份抹掉**。`che:` 那次调用漏传了 `keepForm=true`
   （同族的 `pe:`/`toggle`/`now:`/`pd:` 都传了），于是手一抖勾一下渠道开关 ⇒ `setForm(null)` ⇒
   表单收起、草稿没了、也没说一句话。这一条是浏览器里**误点出来的**，不是读代码读出来的。

**10-19 实测记录**（bundle `assets/index-lf8RQH5O.js`，8910 已重启在前一次改动之后）：
新增计划 → 名字 `排查test-请删` → 勾「自选股当日明细」→ 勾「发送到 盯盘群」→ 点「保存计划」→
计划格里当场出现「**已保存（下一个心跳起按它判，不用重启） 保存不等于立刻发…**」并自动滚进视野，

钉它的是 `frontend/test/notify.test.ts` 新增那条用例（四句源码级断言：归位规则、卡片顶不许重复、格内必须有、要滚进视野，

1. **原本按钮是 `disabled={!form.name.trim()}`** —— 名字空着就灰掉，而灰掉的按钮点下去**一句话都不说**。

## 八、看得见：这一条循环的账记在哪

- `jobs/state.json` 的 `notify_push` 键：`_journal`每轮执行都记，**失败必须记成 not-ok**，
  否则"计划跑了但一个渠道都没通"在页面上只剩一片绿；归因文字只认 `reason` 键（系统配置的既有约定）。
  循环自己出异常也记（`_notify_scheduler` 里那条计划的内层 `except`），且记账坏在内部 `try` 里 —— 记账坏了不许带崩循环。
- `/api/jobs` 与「常驻循环与定时任务」卡：`vr/jobsboard.py::LOOP_JOBS` 第 12 行
  `("notify-push", "notify_push", "消息推送（每 60 秒扫一遍定时计划…）", "配好的定时推送不再发出去…")`。
  关掉之后那一格就写"配好的定时推送不再发出去"，徽标是「下一个心跳就生效，不用重启」。
- `/api/notify` 的 `last_run`（同一份 `state()` 构造处 `vr/app.py::_notify_payload`，读/改两次读数不分开写）
  与「最近发送记录」（`history`，最近 40 行，折叠在 `<details>` 里）。
- 面板每行右侧的 `planHealth` 有七档：**不合法 / 没选渠道 / 渠道已删 / 渠道都不可用 / 部分可用 / 就绪 / 空正文**。
  `sendable` 与 `invalid_reason` **不落库、每请求现算**（`notifyconfig.plan_view`）：渠道被删之后计划还留着那个键，
  存下来的字段就是"计划说发了、其实无处可发"的静默假成功。
- 每行下面那句 **`今天：…`** 是 `today_state` + `today_label`（八档：`off` / `bad` / `not_today` /
  `not_trade_day` / `sent` / `waiting` / `in_window` / `missed`）。判据与执行同住
  `notifyconfig.slot_state`（同一份 `slot_minutes`/`day_applies`/`LATE_WINDOW_MIN`），
  **面板只渲染那句、不自己重算时刻差** —— 两份口径迟早会说两句不同的话
  （钉在 `frontend/test/notify.test.ts`：`doesNotMatch` 那条禁止前端出现自己算延迟的写法）。
  `trade_day=None`（日历判不了）**不降级**成"今天不跑"，与发送侧"判不了照发"是同一个取舍。

## 九、生效时机（这一格不是一句话，是逐条的事实）

- **这条循环本身**每轮重读总开关（`_notify_scheduler` 每轮开头的 `_notify_enabled()`）⇒ 关掉它下一个心跳（≤60 秒）就停手，不必重启。
  所以它在 `LIVE_SWITCH_LOOPS` 里。⚠️ 别照 `tdx-watch` 的形状误判：`tdx-watch` 每轮读的是
  `client_mode` **子**开关而不是总开关，钉住这件事的是
  `tests/test_self_heal_inventory.py::_reads_master_switch`（只认总开关读法）。
- **但这一版面是本轮新写的代码** ⇒ 现在的 8910 进程里既没有 `notify-push` 线程、也没有 `/api/notify`。
  判"装上了没有"只看 `manage.py doctor` 的「常驻循环完整性」，别看 `state.json` 的时间戳。
  本轮实测（写这份文档时）：`GET /api/notify` = **404**、`/api/health` = 200、
  进程自报 10 条循环、体检转红并明写"磁盘上声明了 `notify-push` 而进程里跑的是旧代码 ⇒ 重启 8910 才装得上"。
  这一项**正确地**把"没重启"报成红，而不是假装生效。重启后要做的事在 §十一。

## 十、风险清单（自查表口径，逐条给"该亮起什么"）

| 风险 | 形状 | 现在会亮起什么 |
|---|---|---|
