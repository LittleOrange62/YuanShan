## 一、结论先说

本机的定时任务挂在**常驻 uvicorn 进程**里，不挂 Windows 计划任务。

进程里现在共有 **12 条常驻循环**（2026-10-06 起 7 条；10-07 补进第 8 条 `watchtower`；**10-08 补进第 9 条 `ths-cloud-sync`** ——
它一直在跑、一直往 `state.json` 记账，却既不在面板清单里也没有开关，是"梳理到底有多少定时任务"
时才发现的洞；**10-08 晚间再补第 10 条 `step-retry`** = 加工段失败那几步的夜间重试阶梯，用户点名要的；
**10-12 深夜补第 11 条 `pg-backup`** = 每日数据库备份，动作早就齐了、缺的只有调度，当天实测两份备份停在 148 小时前；

"几点发"住在每条计划里，判据与边界见 [14](14-消息推送渠道与定时计划.md)），

## 二、为什么是常驻进程，不是计划任务

三条实测理由，不是偏好：

1. **宿主本来就在跑**。网站要给人看，uvicorn 就得活着；再注册一个计划任务只是多一个"没人盯死活"的入口。
2. **旧那条计划任务的结局很难看**：`FinanceTool-DailyCloseSync` 实测在 2026-09-25 16:05 真跑过，写进库之后**结尾 `taskkill /F /IM TdxW.exe` 强杀通达信客户端**，退出码 1。计划任务里没有桌面会话、没人看见它干了什么 —— "非零退出 ≠ 什么都没发生"，这条已经吃过一次。
3. **注册与否由人点头**。用户 2026-10-08 点了一次头，本机现在有 **1 条** `YuanShan-KeepAlive8910`：AtLogon + 每 5 分钟，**只把 8910 拉起来、不跑任何数据**（health 不通但端口有人监听时它只写告警、绝不 kill，怕打断正在跑的 15:59 链）—— 判据与实测见 [12 §六](12-定时任务全景.md)。
   10-12 补了一层：任务的动作是 `scripts\keepalive_8910.vbs`（隐藏启动器），它再去跑 `scripts\keepalive_8910.ps1`。因为计划任务直接起 `powershell.exe` 时，**系统是先建控制台窗口、PowerShell 才来得及 `-WindowStyle Hidden`**，于是每 5 分钟闪一下黑窗。判活/判身份仍然看 pid + `StartTime`，与这层无关。
   ⚠️ `schtasks` 的输出是 UTF-16，用它判"0 个作业"会得假绿（见 [01](01-启停与端口.md)）；现在「外部计划任务」那项会把本项目注册的任务逐条列出来，不再只查外人。

代价要说清楚：**进程死了链就不跑**，而且机器休眠/关机也一样。所以 §六 把"今天到底跑没跑"变成页面上读得出来的状态，而不是靠人记得。

## 三、15:59 这条链的判据

代码在 `server.py` 的 `_daily_close_*`（循环体）与 `duanxian/jobs.py::CLOSE_CHAIN`（链的形状）。

**顺序是三段，缺一不可：**

1. **时点**：`run_at`（默认 `15:59`，见 §四），窗口给 3 小时（到 `18:59`）—— 进程晚起、机器休眠、段内失败都要在今天内补上。
2. **今天是不是大 A 交易日**：读 `reference_data.trade_calendar`（`duanxian/pg.py::trade_day_open()`，
   **三态**：`True` 开市 / `False` 明说不开 / `None` 判不了。宿主与 `/api/jobs`、`/api/jobs/chain`
   都调这一个函数，两边各查各的就会出现"页面说今天是交易日、宿主说不是"）。
   - **判不了（库没连、日历没覆盖这天）= 不动手，也绝不写成"非交易日"**。写成非交易日会让整条链安静地一天都不跑，而页面看着正常。
   - 不许用 `duanxian/util.is_weekend` 顶替：它只看周六日，节假日一律放行。
   - **但"日历里根本没有那一天"这一半是可以自己判的（2026-10-07 补）**：唯一的源
     （新浪 `tool_trade_date_hist_sina`）实测只登到 **2026-12-31**（8,797 行，与库里一模一样），
     2027 年的放假安排要等年底才发布，本机现在拿不到。所以没有那一行时：
     **周六/周日 → `False`**（交易所周末不开市与调休无关，这是可证的；不这么做，2027 年起的每个
     周末都会各记一笔"判不了"，噪声把真信号埋掉）；**周一至周五 → 仍然 `None`**（节假日就在工作日里，
     判不了就是判不了，绝不读成"是交易日"）。
   - 真要在日历没覆盖的那几天照跑，用**「只在交易日执行」这一档关掉**（`daily_close.trading_days_only=false`），
     而不是把"判不了"当成"是交易日"。关掉后段脚本自己仍按日历拒写（`fundflow` 那一类 rc 3），
     **非交易日只会多打一次网络请求，不会写出一场假数据**。
3. **数据全不全 → 跑**。两段按顺序放行：

| 段 | key | 执行体 | 超时 |
|---|---|---|---|
| 获取 | `daily_close` | `ingest.jobs.daily_close_sync` | 2400s |
| 加工 | `fill_all` | `ingest.jobs.e1_fill_all` | 5400s |

段1 **真跑成**（verdict=`run`）才起段2。加工跑在缺数的库上只会产出一堆"看着算完其实是空"的结果，比失败更难发现。

## 四、时点与开关是可配置项（三层，只有一份读法）

| 层 | 键 | 说明 |
|---|---|---|
| 作业配置 | `<作业>.run_at`（`HH:MM`） | **优先级最高**，页面/命令行都改这里：`python -X utf8 scripts/jobs.py set daily_close run_at=16:05` |
| 环境变量 | `DAILY_CLOSE_AT` / `WATCHLIST_SYNC_AT` / `FUNDFLOW_AT` | 作业配置没写时生效（双击启动的 `.cmd` 那条路没有页面） |
| 默认 | `duanxian/jobs.py::CLOSE_DEFAULTS` | `daily_close=15:59`、`watchlist=20:40`、`fundflow=20:50`；都没有时用这个 |

`fill_all`（加工段）**没有自己的时点**：它由段1 真跑成之后带动，只有 `enabled` 可关
（见 §三）。给它加 `run_at` 会造出"两个时刻各自开链"的双触发，那正是 §七 一把锁要防的事。

在册作业名（`scripts/jobs.py::_known()`）：`news`、`fundflow`、`watchlist`、`daily_close`、
`fill_all`、`coverage`、`tdx_watch`，外加一组参数 `completeness`（见 §四之三）。
不在册的采集 = 页面上看不见也改不动，和"没有宿主"是同一个坑的另一种形态。

- 读法只有一份：`duanxian/jobs.py::run_at()` → `(时刻, 这个值从哪来)`。宿主与 `/api/jobs` 都调它，**不许两边各读各的**，否则页面显示 15:59、实际按别的跑。
- **默认值也只许住一处**（`CLOSE_DEFAULTS`）：`server.py` 里再写一份 `"20:50"` 字面量，就是"页面改得动、代码不读"。`scripts/jobs.py::_defaults()` 也从这里取，测试 `tests/test_fundflow_c21.py` 钉这条。
- 非法值**出声并回落**，绝不静默采用：`"25:99" <= hhmm` 恒假 = "配了个值、链从此永不触发"，而页面看着像"今天还没到点"。这是最容易配错且最难发现的一类。
- 开关：`daily_close.enabled` / `fill_all.enabled`（关一个只跳那一段，见 §三的顺序），以及总闸 `VIBE_DAILY_CLOSE=0`（`0/false/off/no` 都算关）。**每轮都重读**，改完不重启就生效。
- ⚠️ `run_at` 里写的时刻只决定"什么时候开始判"，不决定"数据算哪天"—— 段脚本自己按 `trade_day_cutoff` 与真日历判目标日，别以为改 `run_at` 就能改口径。

## 四之二、提前拉起通达信（用户 2026-10-07 要的"自动执行时间点可配置"）

| 键 | 默认 | 含义 |
|---|---|---|
| `daily_close.launch_lead_min` | `0` | **链时刻前几分钟**把通达信拉起并登录（0 = 不提前，跟着链在那一次里拉起）。`0` 是合法值，`241` 以上拒（`ZERO_OK_KEYS` 给的上限 240） |
| `daily_close.trading_days_only` | `true` | 只在交易日执行。关掉 = 每天都发一次（见 §三第 2 条），**不是"每天都会有数"** |

为什么要这一档：客户端登录之后**自己还要同步 7~10 分钟数据**，`15:59` 才拉起的话，链里问 TQ
那一步（③b）正好撞上"它正在写 vipdoc"，而那正是历史上天天把链跑死的时刻。

三条实现规矩：

- **拉起时刻由后端算**（`vr/jobsboard.py::_hhmm_plus(slot, -lead)` → `launch_at`），页面只转述。
  让人自己从 15:59 减 10 分钟，跨小时/跨零点就会算错，而且没有任何地方会发现。
- **一天只发一次**（`server.py` 里 `launch_done_day` 记当天已发没发），且**不记进链状态**
  —— 它不是链的一段，记账了就会在页面上变成"今天链跑过了"。执行体是
  `ingest/jobs/daily_close_sync.py --launch-only`（`duanxian/jobs.py::run_tdx_launch_only`，
  900s 自限预算，抢 `daily_close` 那把锁，抢不到就什么都不做）。
- 改完**下一个心跳就生效，不用重启**（与 `run_at`/`enabled` 同一层，都每轮重读）。
  界面在「系统配置 → 收盘链 → 通达信自动拉起与执行日」，命令行
  `python -X utf8 scripts/jobs.py set daily_close launch_lead_min=10`。

## 四之三、条数完整性（判"这一场全不全"的两个偏离值，同一天要的另一格）

不是作业，是一组**参数**（没有 `enabled`，不自己跑，也不往 `state.json` 记账）：

| 键 | 默认 | 谁读它 |
|---|---|---|
| `completeness.deviation` | `30` 条 | 日线 / 板块 / 指数类 + vipdoc `.day` |
| `completeness.deviation_minute` | `200` 条 | 分钟类（`.lc1`/`.lc5`/PG 分钟线） |

判据与实测表在 [数据加工工作指南/05 坑 24](../数据加工工作指南/05-踩坑与经验清单.md)
与 `duanxian/completeness.py` 的模块文档；**默认值只住 `duanxian/jobs.py::COMPLETENESS_DEFAULTS`**，
判据、`/api/jobs/completeness`、`scripts/jobs.py set completeness …` 三处读同一份。
两个数各自"是默认还是有人在系统配置里填过"会一起交出来（`deviation_from`），
因为只报数字的话，下一次判错时会去查一个并不存在的改动。

`scripts/jobs.py enable|disable|run-now completeness` 一律**明确拒绝**（不是"默默写一个没人读的键"），
要看它此刻判出什么：`python -X utf8 -m duanxian.completeness --summary`。

## 四之二、开关被谁关了：留痕与那一格界面（09-28 下午补）

**这个开关是持久状态**：`<ASTOCK_DATA_HOME>\jobs\config.json` 里 `daily_close.enabled` / `fill_all.enabled`。默认 `true`，但**一旦被写成 `false` 就一直 `false`** —— 默认值救不回来，也不会自己恢复。原先能写它的只有 `scripts/jobs.py enable|disable|set`（接口和页面都改不动），而界面上留下的痕迹只有任务调度页一个小灰标签「已停用」—— 那措辞与"被谁误关"根本分不开。

09-28 上午就撞在这个缝上：一条"先停自动、到跟前自己点"的裁定被执行并写了 `note`，而另两次我读到 `enabled:false` 时**读不到任何理由**，就按"默认该开着"擅自打开了 —— 等于替别人推翻了别人的决定。教训写在这里：**看到"关着"先找理由与留痕，找不到就问，不要按自己的默认值改别人的状态。**

现在三层都在：

| 层 | 是什么 |
|---|---|
| `_changed_at` / `_changed_by` | 每次写入**自动盖章**：CLI 写 `cli:jobs.py disable`，接口写 `api:/api/jobs/chain@来源IP`。不依赖人记得写 |
| `note` | 人写的"为什么"（谁、停到什么时候）。已是登记键，`scripts/jobs.py set <名> note="…"` 不再报"未知配置项" |
| `/system`「每日收盘链（15:59）」卡 | 两段各自开关、时点与来源、**今天到底会不会跑**（开关 × 真交易日历 × 宿主循环，三个条件分开列）、最后一次改动、理由输入框。端点 `GET/POST /api/jobs/chain` |

`manage.py doctor` 的「收盘链自动开关」项按有没有人认领分三档：关 + 有 `note` → 只报状态不判红；关 + 只有留痕 → 报出来但不拦启动；**关 + 两者都没有 → 判红**（那才是真正的"没人知道自己把当天的采集关了"）。

## 五、退出码：两条链的同一个数字不是一回事

`CLOSE_CHAIN[key]["rc"]` 按段列表，**不许合并成 `rc in (0, 3)`**。

| 段 | rc | 原文语义 | verdict | 记成成功？ | 放行下一段？ | 今天还重试？ |
|---|---|---|---|---|---|---|
| `daily_close` | 0 | 成功，或"库里已经有了"按设计什么都没做 | `run` | 是 | 是 | — |
| | 1 | 骨干（个股日线入库 + 回验）没成 | `hold` | 否 | 否 | 是（≤3 次） |
| | 2 | 非交易日 / 未到收盘线，按设计跳过 | `stop` | 是 | **否** | 否 |
| | 3 | **数据没到位且自动手段用尽 —— 要人来** | `stop` | **否** | **否** | 否 |
| `fill_all` | 0 | 全部步骤成功 | `run` | 是 | 是（末段=收工） | — |
| | 1 | 骨干失败：日线没成 / 没拿到目标交易日 | `hold` | 否 | — | 是 |
| | 2 | vipdoc 没覆盖目标日又没开 `--allow-web`，**按设计停下** | `stop` | 否 | — | 否 |
| | 3 | **只有辅助源失败（两融/龙虎榜/资金流抖），骨干是好的** | `run` | 是 | — | — |
| 两段 | 124 | 宿主自己掐的超时 | `hold` | 否 | 否 | 是 |
| 两段 | 表里没有的非零 | 未知 | `hold` | 否 | 否 | 是 |

三个决定分开，是因为两句话不一样：**"今天别再试了" ≠ "这次算成了"**。
`daily_close` 的 3 和 `fill_all` 的 3 语义相反 —— 前者要人来、后者骨干是好的。合成一个判断，必然一边把真故障放过去、另一边把一次抖动当整链崩。

`stop` 与"重试耗尽"都会**挡住后面**：库里的数确实没到位。被挡住的段**不写运行记录** —— 契约 [03 §3](../页面展示工作指南/03-任务调度页契约.md) 要求没跑过的 `last_run_at` 是 null，编一个时刻出来会把"没干"显示成"干过了没成"，让人去查一个不存在的失败。页面上那句「未起（daily_close 今天停在 stop）」是 `/api/jobs` **现读现说**的（`vr/jobsboard.py::_recorded_job(after=…)`），不落状态文件。

## 七、三个入口共用一把锁

`daily_close` / `fill_all` 现在有三个入口：定时宿主、`POST /api/jobs/<key>/run`（页面「立即触发」）、`scripts/jobs.py run-now`。

- 互斥用 `duanxian/jobs.py::claim/release`（进程内）。**两个入口各起一个 `daily_close_sync`，点的是同一个通达信盘后下载窗口**，结果是两边都判"数据没到位"，日志看着像源坏了。
- 抢不到锁：宿主**本轮让路且不计数**（那不是失败）；HTTP 回 **409 + reason**（契约 §5.1）；命令行回退出码 4 并说明"另一个入口占着"，不排队假装已在跑。
- 执行体也只有一份：`jobs.exec_close_stage` / `run_close_stage`（后者抢锁、前者假定已持有，因为 HTTP 要先同步答 409）。
- ⚠️ **已知的洞**：`app/orchestrator/runner.py` 也登记了 `daily_close`（走队列那条路）。它**不认这把 claim 锁**。今天它不会被触发（FT 调度器 `enabled=false`、只发心跳不入队，见 §八），但**谁要是把那条入队链打开，桌面就会被并发点**。收口方式二选一：runner 那条也改成走 `run_close_stage`，或把 `config.job` 里这一行停掉。别默认它安全。
