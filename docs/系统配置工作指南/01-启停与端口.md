# 01 · YuanShan 启停与端口

## 启动链（别改，先看懂）

```
启动 YuanShan.cmd
  └─ .venv\Scripts\python.exe -X utf8 scripts\manage.py auto
       ├─ prerequisites()  Python≥3.10 / Node≥22
       ├─ doctor()         17 项体检（8 项是提示项，红叉画 `!`、不拦启动，见下文清单）
       │    └─ auto 专属：任一**硬项**红 → 先自动跑 setup()，跑完才 start()（提示项不算）
       └─ start()          占端口成功才继续
            └─ engine_guard.py 0 <父PID> -m uvicorn server:app --host <netconfig 给的绑定地址> --port 8910
                 └─ uvicorn 主进程 ── uvicorn 工作进程（真正 LISTEN 8910 的是它）
                      └─ 健康检查通过后：启动补备份（daily 过期才补，见 02 §五之二）
```

⚠️ **`auto` 和 `start` 不是一回事**（分派在 `main()` 里那行 `args.command == "auto" and not checks_ok(doctor(...))`，10-18 现读 `manage.py:1448`）：只有 `auto` 会在体检红时**自己去跑 `setup`**（联网、1~2 分钟），双击走的正是 `auto`；
`manage.py start` 遇红**直接抛「尚未就绪。请运行 scripts/setup」拒绝启动**（这句在 `start()` 里，10-18 现读 `manage.py:1369`）。所以「被拦住」只发生在手敲 `start` 或 `auto` 跑 setup 失败（断网/镜像挂）时。

Windows 上 `engine_guard.py` 建一个 **非可逃逸、KILL_ON_JOB_CLOSE 的 Job Object**，
取数子进程、Codex 引擎全部落在同一个 Job 里（`review_agent/windows_process.py`）。
`manage.py auto` 是**前台阻塞**的，窗口就是控制台，Ctrl+C 即优雅停止。

## 一键关闭

`关闭 YuanShan.cmd` → `scripts/stop.py`（纯标准库，Windows/POSIX 通用）。

**为什么不是 `taskkill` 端口占用者**：服务在 Job 里，直接杀 uvicorn 只拔掉树的中段。
正确顺序是先杀**启动器** —— guard 检测到父进程消失会自己 `TerminateJobObject` 收掉整棵树。
所以 stop.py 的顺序是：启动器 → 等优雅退出 → 守卫树 → 服务/取数子进程/AI 引擎 → 重新识别端口占用者。

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只列出将要关闭的进程，不动手（**双击前想先看一眼就用它**） |
| `--port N` | 默认取 `VIBE_PORT`，再默认 8910；即使当初用别的端口起，也会按项目路径认出进程 |
| `--wait S` | 优雅等待秒数，默认 8 |

三条刻意保守的行为：
- **只杀认得出的运行体**：镜像名白名单 `python.exe/node.exe/codex.exe` + 命令行特征；
  非本项目的端口占用者**一律留着**，只报 PID 让你自己确认。
- **不删 `backend.lock`**：那是字节范围锁，进程死了 OS 自动释放；手删会和活进程抢。
  stop.py 会去**试着加一次锁**来验证"没有僵尸后端"，并把结果打出来。
- **不碰自己的祖先链**：第一版没这道闸，把执行它的 shell 当成"启动器"杀了。

已实测：单轮识别并收掉 5 个进程（启动器×2、守卫×1、uvicorn 主+工作×2），端口与后端锁均释放，退出码 0。

## 端口有三个旋钮，双击路径上只有一个有用

| 入口 | 端口由谁决定 | 实测结论 |
|---|---|---|
| `启动 YuanShan.cmd` / `manage.py auto` / `manage.py start` | **只有 `--port`**（默认硬编码 8910，`parser.add_argument("--port", …, default=8910)`，10-18 现读 `manage.py:1428`），启动器把它作为 `--port` 参数显式传给 uvicorn（`:1383`） | 设 `VIBE_PORT` **没用**，服务仍在 8910 |
| `python server.py`（直跑，不走启动器） | `VIBE_PORT`，默认 8910（`port = int(os.environ.get("VIBE_PORT", "8910"))`，10-18 现读 `server.py:3888`，在 `__main__` 里） | 只在这种方式生效 |
| `scripts/stop.py` | `--port` > `VIBE_PORT` > 8910（`stop.py:194`） | **陷阱**：设了 `VIBE_PORT=8911` 而服务在 8910 时，进程树仍按项目路径认得出并收掉，但「端口是否已释放」的复检和端口占用者报告看的是 8911，等于白检 |

要换端口就统一用参数，别动环境变量：`scripts/manage.py start --port 8911`，关的时候 `stop.py --port 8911`。
（换端口 = 浏览器换 origin，`localStorage` 里那份自选/研究记录/AI 配置读不到新的。）

| 症状 | 怎么办 |
|---|---|
| `端口 8910 已被占用` | 双击 `关闭 YuanShan.cmd`；或 `start --port 8911`（注意：换端口 = 浏览器换 origin，`localStorage` 里那份自选/研究记录/AI 配置**读不到新的**） |
| `服务未能启动，请查看 .local\startup.log` | 看日志尾部；常见是上一次没退干净，先跑 stop.py |
| 页面 503 提示 `npm run build` | `frontend/dist` 缺失，需跑 setup |
| `✗ 安装与源码一致` | **指纹闸**，见下节 |
| 想看谁占着端口 | `netstat -ano -p tcp \| findstr :8910` |

## 确认服务活着：两个 health 端点，别混用

| 端点 | 返回 | 用途 |
|---|---|---|
| `GET /api/health` | `{"ok":true,"service":"yuanshan","version":"1.1.0"}` | 通用存活探针（进程在、路由通） |
| `GET /api/astock/health` | `{"service":…,"version":"1.1.0","launch_id":"<16hex>","ready":true}` | **看 `ready` 和 `launch_id`** —— `launch_id` 是启动器注入的环境变量（`env = {**os.environ, "ASTOCK_LAUNCH_ID": launch_id, …}`，10-18 现读 `manage.py:1377`；读回在 `server.py` 里搜 `ASTOCK_LAUNCH_ID`），直起 uvicorn 时它是空的，可据此判断服务是双击起的还是手工起的 |

⚠️ **curl 本机一定要带 `--noproxy '*'`**：这台机器设了 HTTP 代理，回环流量走代理会连不上或超时，误判成「服务挂了」。

```bash
curl -s --noproxy '*' -m 8 http://127.0.0.1:8910/api/astock/health
```

## 传输层这一档：gzip、缓存头、慢请求日志（2026-10-26 加）

首页提速实测（同一天）量出来的三件事：一次首页加载 26 发请求、**1.27 MB 未压缩 JSON**、
`/api/global/indices` 对端不通时 12.4 秒只回 11 字节而**空结果不缓存**（每个访客每一发重付一遍超时）。
所以在 8910 上加了一层与业务无关的传输层，三段都在 `server.py`（搜 `_SelectiveGZip`）：

| 这一段 | 做什么 | 验收怎么读 |
|---|---|---|
| `_SelectiveGZip` | `GZipMiddleware(minimum_size=1024)`，但**流式与文件类路径不压**（`_NO_GZIP_PREFIXES`：`/api/chat`、`/api/myreports/file/`、`/api/review-agent/chat-jobs/`）——压这三类会把增量推送与二进制成块堵在网关里 | `curl -H 'Accept-Encoding: gzip' -D -` 看 `content-encoding: gzip`；`/api/market/sector-cycle` 329,109 → 37,578 字节 |
| `_transport_headers_and_slow_log` | `/assets/*` 发 `cache-control: public, max-age=31536000, immutable`（文件名带内容哈希），其余非 `/assets` 一律 `no-cache`（HTML 与新接口不许被浏览器缓住）；同时给每一发计时 | `/assets/index-*.js` 读到 immutable，`GET /` 读到 `no-cache` |
| 慢请求台账 | **只**把 ≥500ms 的请求追加进 `.local/slow_requests.log`（时刻、路径、毫秒、状态码），不新开日志框架 | `tail .local/slow_requests.log` |

两条使用纪律：

1. **中间件的注册顺序＝请求进来的反序**：后 `add_middleware` 的在最外面。这一层的次序是
   `_origin_ip_guard` → `_vr_guard`（局域网白名单）→ `_transport_headers_and_slow_log` → `_SelectiveGZip` → 路由。
   把 gzip 放到白名单外面，就等于给未授权请求也压一遍。
2. **改了这一段必须重启 8910**（它是后端的 `.py`，不进前端指纹闸的覆盖范围，见下一节那张表）；
   验收要拿**改前记下的具体读数**去比（比如那 329,109 字节），`/api/health` 回 200 只证明端口有人在服务，不证明服务的是这一版。

`.local/slow_requests.log` 是**追加**写的，没有轮转 —— 它记的是"这一段时间哪些发慢"，
判据用它就够了；要清掉直接删文件（下次写自动重建）。


## 指纹闸：改了源码就会被拦住

`manage.py` 记一份 `.local/setup.json`（内容只有一个 sha256 指纹），启动前比对：

**指纹覆盖范围** = `requirements.txt` + `runtime/package.json` + `runtime/package-lock.json` + **`frontend/` 下所有文件**（排除 `node_modules`/`dist`/`.git`/`__pycache__`/`*.tsbuildinfo`/`*.pyc`/`*.pyo`）。

> `__pycache__` 与 `*.pyc` 是 2026-09-26 补进去的：`frontend/test/__pycache__/browser-acceptance.cpython-314.pyc` 曾被算进指纹，
> 于是**谁跑一次浏览器验收脚本，下次双击启动器就要白等 8~12 分钟的 setup**（`.pyc` 是再生成产物，不是构建输入）。
> 回归测试：`tests/test_launcher.py::test_source_changes_invalidate_install_but_generated_files_do_not`。

**不覆盖后端 `.py`。** 所以：

| 你改了 | 会被拦吗 |
|---|---|
| `duanxian/**`、`vr/**`、`server.py`、`review_agent/**`、`scripts/stop.py`、`tests/**` | ❌ 不会 |
| 任何 `frontend/src/**`、`requirements.txt`、`runtime/package*.json` | ✅ 会，要求重跑 `scripts/setup` |

**改完前端必须重跑 `scripts/setup`**（`def setup(root)`，10-18 现读 `manage.py:1150`，按顺序做：需要时建 `.venv` → `pip install -r requirements.txt` → 在 `runtime/` 和 `frontend/` 各跑一次 `npm ci` → `npm run build`，**需联网、约 1~2 分钟**）。
只 `cd frontend && npm run build` **不够** —— 那只会产出新 `dist`，`.local/setup.json` 里的指纹不会更新，`doctor` 的「安装与源码一致」照旧红。

⚠️ **指纹是 setup 的最后一步才落盘的**：它先要求除指纹外的**硬项**全绿（备份那条是提示项，不参与判定），再写 `setup.json`。
所以 **setup 中途任何一步失败（包括下面那个 `tsc` 假错）都不会刷新指纹** —— 表现就是"我明明跑了 setup，怎么还是红"。

**指纹闸不会告诉你是哪个文件变了**：`.local/setup.json` 里只存**一个** sha256（`def fingerprint(root)`，10-18 现读 `manage.py:78-91`，逐文件字节喂进同一个哈希器，不留清单）。
报红后只能自己按 mtime 找，例如：

```bash
cd /d/finance/YuanShan
ls -la --time-style=full-iso .local/setup.json                    # 指纹落盘时刻
find frontend -type f -not -path "*/node_modules/*" -not -path "*/dist/*" \
  -newer .local/setup.json                                          # 晚于指纹的文件 = 嫌疑人
```

**2026-09-24 现状**：`frontend/src/components/AgentAccess.tsx` 12:46 被改（`code：Yuanshan-AI` 接 new-api/openai-compat 那次），
`scripts/setup` 已在 **12:57** 跑过 → 指纹已刷新，`doctor` 硬项全绿，服务在 8910 健康。当日 00:57 那次红已经过去了。

临时绕过（不推荐长期用，指纹仍是红的）：直起 uvicorn。

```bash
cd /d/finance/YuanShan
PYTHONUTF8=1 .venv/Scripts/python.exe -X utf8 -m uvicorn server:app \
  --host 127.0.0.1 --port 8910 --no-access-log
```

（这样起的进程没有控制台窗口，但 `stop.py` 照样能按命令行特征认出并收掉。）

### `tsc -b` 的增量缓存会报假错（2026-09-24 实录）

`frontend/package.json` 的 build 是 **`tsc -b && vite build`**，且 tsconfig 开了
`noUnusedLocals` + `noUnusedParameters` —— **一个未使用的 import 就会打断整个构建**，`vite build` 根本不跑，`dist` 不更新。

但 `tsc -b` 是增量构建、读 `frontend/tsconfig.tsbuildinfo` 缓存，**会报已经修好的错**。当天第一次 setup 就死在：

```
src/components/AgentAccess.tsx(4,25): error TS6133: 'DEFAULT_ACCESS_PROVIDER' is declared but its value is never read.
```

实测该符号在第 19、103 行**确实在用**（**这两个是当天的快照**；10-18 现读它在 `AgentAccess.tsx` 的 4、19、128 行 —— 要看的是「确实在用」这件事，不是这两个数），文件 mtime 也早于构建时刻；**重跑一次 `npm run build` 直接过**。

> 处置纪律：遇到 TS6133 这类「明明在用却报未使用」的错，**先 `find frontend -name "*.tsbuildinfo" -delete` 再跑一次**，
> 两次都同样报才动代码。别看见红就改 import —— 那会改坏别人正在用的符号。

    **新循环在被服务装载之前就被点名，而不是等"零笔记账"跨一天再被读成故障**）；配对只住 `vr/jobsboard.py::LOOP_JOBS` 一处，**不许由线程名猜记账键**
    （`newswire` 记到 `news`、`watchlist-sync` 记到 `watchlist`）。见 [05 §四之四](05-调度宿主.md)。
  - ⚠️ **「安装与源码一致」必须永远是数组最后一项**：`setup()` 用 `checks[:-1]` 剔掉末项（那一刻指纹还没落盘），排在它后面的新项会被一起剔掉，进而把 setup 自己锁死。
  - ⚠️ **`doctor(phase=)` 有两个相位**：`start()`/`auto` 在**绑定端口之前**跑体检，走 `phase="startup"`，
    那一刻连不上 `/api/jobs` 是流程决定的，「常驻循环完整性」只报"**N 条循环待起**"（N 由在册清单现算，不写死）、不判红；
    手敲 `manage.py doctor` 走 `phase="steady"`，连不上就是**一条循环都没有**。合并成一份措辞会让每次启动都固定红一条。
  - 每一项"怎么弄坏它来验证"在 [07-故障恢复手册](07-故障恢复手册.md)，判据本身在 [06-自动执行机制自查表](06-自动执行机制自查表.md)。
  - 详见 [02-PostgreSQL与备份](02-PostgreSQL与备份.md) 与 [03-环境变量与作业配置](03-环境变量与作业配置.md)。
