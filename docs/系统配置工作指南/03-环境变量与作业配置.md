# 03 · 环境变量与作业配置

> 采集类常驻作业（快讯、每日资金流）的**键位、落点、时区**契约。
> 数据侧（`code：数据获取`）按本文接线；改键位必须先改本文。

## 一、环境变量：`ASTOCK_DATA_HOME` 有一个会静默分叉的坑

`duanxian/paths.py:data_path()` 的解析顺序只有一条：`os.environ["ASTOCK_DATA_HOME"]` → 否则 `~/.duanxian-agents`。要求**绝对路径**（相对路径直接 `ValueError`）。

⚠️ **它只影响从该终端启动的进程**（主 `README.md` 第 196 行原文："这些变量只影响从该终端启动的进程，需在每次启动前设置，或加入自己的启动脚本"）。而日常启动是**双击 `启动 YuanShan.cmd`**，那个 `.cmd` 里不设这个变量。

后果是**静默分叉**：人在终端里 `set ASTOCK_DATA_HOME=D:\data` 跑了一次 `collect_news.py`，第二天双击启动，采集线程写的是 `C:\Users\…\.duanxian-agents\news`。两边都在"成功"，没有一行报错，数据在两个根目录里各自长。

三条处置（都已实现或将实现，见 §四）：

1. **要用自定义数据根，就写进 `.cmd` 或自己的启动脚本**，不要只在终端里 `set`。
2. **所有诊断输出必须把生效的绝对路径打出来** —— `doctor` 的采集项、`jobs.py status`、`collect_news.py` 都印 `data home=<绝对路径>`。只报"已写入 102 行"而不报写到哪，等于没报。
3. 业务数据**一律走 `data_path()`**，不许在代码里硬编码 `~/.duanxian-agents`，也不许走 `.local/`（见 §二）。

其余变量（`VIBE_PG`、`VIBE_PORT`、`ASTOCK_AGENT_HOME`、`VR_REPORTS_DIR`）见 [01-启停与端口](01-启停与端口.md) 的端口三旋钮一节 —— 注意 `VIBE_PORT` **对双击路径无效**。

## 一之二、`.env` 的两套键名与 2026-09-25 的迁入（**没迁的就两个是故意的**）

`app/config.py` 读的是 **`FT_` 前缀**的键（历史包袱，不是依赖 —— 它在本项目里，只是名字沿用了旧项目）。`.env` 现在两套并存：

| 用途 | 键 | 说明 |
|---|---|---|
| YuanShan 自写的只读/写库通道 | `PG_HOST/PORT/DB/USER/PASSWORD`、`PG_ETL_USER/PASSWORD`、`VIBE_PG` | `pg.py` 走只读、写走 ETL |
| 吸收进来的采集/备份/TDX/在线源 | `FT_PG_HOST/PORT/DB`、`FT_DSN_{READER,APP,ETL,ADMIN}`、`FT_PG_SUPERPASS`、`FT_PG_BIN`、`FT_PG_DATA`、`FT_BACKUP_DIR`、`FT_TDX_{DIR,ACCOUNT,PASSWORD}`、`FT_{MIAOXIANG,ALPHAFEED,TUSHARE}_KEY/TOKEN`、`FT_LOG_KEEP_DAYS` | 2026-09-25 从旧项目迁入本项目 `.env` |

⚠️ **迁入的意义比"补几个键"大**：迁之前，吸收进来的采集、作业、备份、TDX 登录**全是哑的** —— 能 import、一调用就抛（实测 `dsn_parts('admin')` 报 `角色 'admin' 的 DSN 未配置`），而页面照常能读，因为页面走的是另一条自写的 `PG_*` 只读通道。**"接口通"和"作业能跑"是两件事**，这类缺口只会在全链路实跑时暴露，看代码看不出来。

**特意没迁的两个键，别"顺手补上"**：

- `FT_LOG_DIR` —— 补上会把日志**写回旧项目目录**，等于新系统往要删掉的地方拉一根血管。本项目日志落 `.local/`（诊断）与 `legacy/日志/`（归档）。
- `FT_LEGACY_DATA` —— 指向本机**已不存在**的目录，补上只会让某些路径解析成一条看似正常的死路。

"口令只有一份、旧项目被删就没了"这个风险已排除：键已进本项目 `.env`，删除旧项目不影响解析。仍要守的是**别把它打印出去**（见 `02` 里 `globals_*.sql` 那条同级纪律）—— `FT_TDX_PASSWORD`、四把 DSN、三个在线 token 现在是**本项目 `.env` 里唯一的明文份**。

## 二、`.local/` 不放业务资产（含缓存）

主 `README.md` 第 181 行把 `.local/` 定义成**「开发日志与运行诊断，默认不进入版本控制」**；第 196 行承诺的迁移/备份范围只有 `ASTOCK_DATA_HOME` 那棵树。

所以：**放在 `.local/` 下的东西，换机时没有任何一步会去搬它。** 这条是硬理由，不是风格偏好。

现存的偏离：`duanxian/qd_calc.py` 把计算缓存写在 `.local/qd_cache/`。自家惯例本来是 `data_path("cache/<名>")` —— `breadth`、`excursion`、`emotion_metrics`、`backtest` 全都这么放（`data_path("cache/breadth")` 等）。**缓存的既有惯例已经存在，用 `.local/` 是偏离它，不是两可的选择。** 应收口到 `data_path("cache/qd")`。

作业侧的落点因此定死：

| 内容 | 落点 | 谁能写 |
|---|---|---|
| 作业**配置** | `data_path("jobs/config.json")` | 用户 / `jobs.py set\|enable\|disable` |
| 作业**状态** | `data_path("jobs/state.json")` | 只有作业自己 |
| 快讯正文与游标 | `data_path("news/")`、`data_path("news/cursors.json")` | 快讯作业（已如此） |
| 日志与诊断 | `.local/` | 启动器 |

**配置与状态必须分文件。** 状态每轮被整体覆盖，和配置混写会在某次写状态时把用户手写的改动冲掉 —— 而用户唯一能 diff、能回滚的就是配置那份。

## 三、键位契约

顶层一个对象，**每个作业一个键**；值里**只写要改的项**，其余取代码里的 `DEFAULTS`（照 FinanceTool `config.setting['ignition.params']` 的成熟做法）。

```json
{
  "news":        { "interval_seconds": 30 },
  "fundflow":    { "run_at": "15:10" },
  "daily_close": { "enabled": true, "run_at": "15:59",
                   "launch_lead_min": 10, "trading_days_only": true },
  "fill_all":    { "enabled": true },
  "completeness": { "deviation": 30, "deviation_minute": 200 }
}
```

`daily_close` / `fill_all` 是 2026-09-28 接进来的**收盘链两段**（获取段 + 加工段），
判据顺序、退出码读法、互斥与"重启到底生效没有"都在 [05-调度宿主.md](05-调度宿主.md)。
键位这边只有三条本地事实：

- `daily_close.run_at` 是**整条链的起点**，`fill_all` 没有 `run_at` —— 它跟在前一段后面，前一段真跑成才起。给它配时点等于配一个没人读的键。
- **关一个只跳那一段**：关掉获取段，加工段照跑（`e1_fill_all` 自己带 `tdxdl`/`daily` 两步补齐）。把"人关了一个"读成"整条链都别动"是替操作员做决定。
- 时点有**三层**（作业配置 > `DAILY_CLOSE_AT` > 默认 15:59），读法只有一份：`duanxian/jobs.py::run_at()` 返回 `(时刻, 这个值从哪来)`，第二个值必须一起上页面。宿主和 `/api/jobs` 都调它；**别再补一层 env 读取**，两处各读各的就会出现"显示 15:59、实际按别的跑"。

knob 的语义写死在这里：

| 键 | 类型 / 默认 | 含义 |
|---|---|---|
| `enabled` | bool / `true` | 关掉 = 线程还在但空转，**不删作业、不改代码**。默认开：快讯过了那个点就永久没有，默认关等于默认丢数据 |
| `interval_seconds` | int / 各作业自带 | **仅轮询型**用（快讯 30s）。每日型设了也忽略，但 `jobs.py status` 要显示"此键对该作业无效"，不要静默 |
| `run_at` | `"HH:MM"` / 无 | **每日型**用。**是上海时区的 HH:MM，不是本机时区** |
| `backfill_minutes` | int / 各作业自带 | **迟到补跑窗口**：过点后多久之内仍会补跑（进程晚起、上一轮失败都靠它）。对应 `newswire.BACKFILL_MINUTES`，也对应盘中快照那个 6 分钟窗口 |
| `launch_lead_min` | int / `0`（**0 合法**，上限 240） | `daily_close` 专有：**链时刻前几分钟**把通达信拉起并登录。为什么留这一档与三条实现规矩见 [05 §四之二](05-调度宿主.md) |
| `trading_days_only` | bool / `true` | `daily_close` 专有。关掉 = 每天都发一次，**不是"每天都会有数"**（段脚本自己按日历拒写）。留这一档是因为日历源实测只登到 2026-12-31 |
| `deviation` / `deviation_minute` | int / `30` / `200`（**0 合法**） | 不在某个作业名下，而是顶层 `"completeness"` 这一组**参数**（判"这一场全不全"允许比前一天少几条）。见 [05 §四之三](05-调度宿主.md) 与 数据加工 05 坑 24 |
| `sync_mode` | `full` / `append`（**字符串键只认这两个值**） | `watchlist` 专有：`full`=以同花顺本机 `stockblock.ini` 为准（ini 里没了的组/成员这里也删）；`append`=只加不删（库里会留着同花顺已经不要的票）。默认 `full`，含义与代价见 [05 §四之四](05-调度宿主.md) |
| `note` | str / 空 | 人写的理由（谁、为什么停一天）。与自动盖章的 `_changed_at` / `_changed_by` 互补 |

⚠️ **字符串键的取值只列在 `duanxian/jobs.py::ENUM_KEYS` 一处**（现在只有 `sync_mode`）：
以前字符串键一律放行，那等于"页面上能填任何字、代码读到什么算什么"—— `sync_mode=fulll`
会静默按全量跑，而人以为开的是增量。
⚠️ **允许取 0 的键只列在 `duanxian/jobs.py::ZERO_OK_KEYS` 一处**（`deviation`、`deviation_minute`、
`launch_lead_min`）。别的新键若照"正整数"统一判，用户最想试的那一档（0 = 完全不打折 / 不提前）
反而填不进去；反过来 `tdx_watch.sync_reap_after_min` **不许**进这张表 —— 它设成 0 是"刚起就收进程"，
会把正在下的那批打断。

⚠️ 收盘链的补跑窗口**不在 `config.json` 里**：它是宿主常量（15:59 起 3 小时，段内失败重试上限 3 次，`server.py` 的 `_plus_minutes(slot, 180)` / `DAILY_CLOSE_MAX_TRIES`）。写成 knob 会让人以为"窗口能调大"，而真正的约束是**今天之内**——过了 18:59 就不再试，缺的就是永久缺。要调它得改代码并同步 05。

三条不可谈判的规则：

1. **时区写死上海。** `server.py` 的盘中调度已经为这事写过警告：机器在别的时区时用本机时间会"整天抓不到任何一个时点，而界面上看不出异样"。**不提供 `tz` 配置项** —— 提供就是把一个已知的静默故障模式摆回菜单上。
2. **非法值要出声并回退默认，不许静默。** `interval_seconds: "三十"`、`run_at: "25:99"`、负数、未知作业名 —— 一律在日志和 `jobs.py status` 里点名"该值无效，按默认 X 跑"。旧项目的教训就是静默吞（当年 `c11_fundflow.py` 的 `except: continue` 直接把表写成 0 行）。现役 `ingest/jobs/c11_fundflow.py` 的 except 分支已带 `exc` 出声，**这条规则针对的正是回潮**。
3. **只有成功才推进游标/记成功。** 与 `newswire` 模块头的纪律 3、盘中调度的"只有成功才标完成"同源。配置改坏不能造成数据缺失。

然后保存之后后续按照这个计算值来筛选」＋「以后更新之后都需要**回算覆盖**，要有这样的一个回算机制」。
卡片实现 `frontend/src/components/VolumeEnergyPanel.tsx`，算与存全部只住 `app/compute/volume_energy.py` 一处，
判据与实测数见《数据加工工作指南/10-每个数怎么算》§4.1 之二与《功能点说明/量化选股/倍量形态》§11。

| 项 | 事实 |
|---|---|
| 存哪 | `config.setting`，键 `volume_double.energy_profile`，value `{"scope": "global"/"market", "global": {档名: 分值}, "by_market": {市场号: {档名: 分值}}}`，`category='quant'` |
| 没存过 | 用代码里的 `DEFAULT_SCORES`；`profile()` 会把来源一起交出（`profile_source` 写「默认（已存的配置不合法：…）」而不是静默兜一份看着合理的数） |
| 校验 | 只住 `validate()` 一处：**少一档就拒收**（少一档等于偷偷把这档算成 0 分）、档名不认得就拒、全 0 分拒（每场得分恒 0，排名无从谈起）、**载荷里出现 `normalize` 直接拒**（第一稿那层已取消） |
| 键的维度 | 作用域按 `reference_data.security.market`（SH/SZ/BJ，其余落 `OTHER` 那份兜底）。**不按 `board`**：那列实测 3,972 只是空的，按板块配会让这批票静默落回全局而界面像配过了 |
| 生效方式 | `fingerprint()` 是"这批数按哪份口径算的"的哈希（摊平档表一起进）。**保存本身不改库里任何一行**，只交 `needs_rebuild` |
| 保存后 | `POST /api/config/volume-energy` 的调用方（`vr/app.py`）看到指纹变了就 `start_rebuild_async()` ⇒ 后台一条集合式 SQL 全量重算 `analytics.volume_double.dbl_energy/energy_fp`（实测 104 / 110 / 107.5 秒各刷 1,153,318 行、211 场） |
| ⚠️ 保存 ≠ 已生效 | 重算跑完之前倍量榜筛的仍是**旧批**，那一侧挂 `energy_batch_stale` caveat，卡片上 `job` 显示在跑/起止/结果/失败原因；每日链 `d7_vol_double` 当晚也会用当前档表重刷并独立手算复核 |
| 接口 | `GET/POST /api/config/volume-energy`（GET 交 `profile`/`scale`/`status`/`bands`/`default_scores`/`rank_rule`/`top_n_default`/`page_size`/`job`） |
| 手动兜底 | `python -m app.compute.volume_energy --rebuild [--from --to]` / `--status`（退出码 0＝库里最新批就是生效配置）。`start_rebuild_async` 在 `PYTEST_CURRENT_TEST` 里**硬挡**，测试不会起真线程 |

三条别改回去的语义：① **一档分值变了只影响落在这一档的那些天** —— 这正是取消「÷Σ」的理由，
那一层会把全表每一档一起牵动（改一格≠改一格，用户读不出区别）；
② **窗口只在同一指纹里滑**（`_step_gap_source()` 里那句 `energy_fp = %s`），跨批做差等于拿旧尺减新尺，
对不上批的票交 `—` 不交 0；③ 新榜「加权分进榜后的逐日涨跌幅」的母体是**当日得分前 N 名**（同分并列整批进来），
不是分数门槛 —— 换成门槛就会出现"填 6 筛出 0 只"那种看着像坏掉、其实是口径对不上的读数。

## 四、启停与可见性

**不动 `manage.py` 的子命令表。** 它是前台阻塞的启动器（`setup/doctor/start/auto` 四个固定值），把"改个作业开关"塞进去意味着每次调开关都要跑一遍启动器 —— 而常驻进程本来就是作业的宿主，**开关是文件，改完即生效**（每轮重读，这是 FinanceTool `watchman` 唯一学对的地方：它每次 tick 重读 `config.setting`，所以改完不用重启）。

⚠️ **"改完即生效"只对一部分循环成立，别把它当全体**（10-18 现读 `vr/jobsboard.py:99-110`）：在册 12 条里 **8 条每轮重读开关**（`LIVE_SWITCH_LOOPS`：intraday、newswire、daily-close、ths-cloud-sync、watchtower、step-retry、pg-backup、notify-push），另外 **4 条只在启动时读一次**（`DEAD_UNTIL_RESTART_LOOPS` ＝ 不在 `LIVE_SWITCH_LOOPS` 里的那些：watchlist-sync、fundflow-sina、coverage-precompute、tdx-watch）—— 面板上把它们的开关关掉，**当前进程照跑到重启 8910 为止**。面板把这件事当场说清（`live_switch` 那一格交的就是这两个集合），别在文档里留一句"改完即生效"糊过去。

入口是 **`scripts/jobs.py`**：

```bash
python -X utf8 scripts/jobs.py status                 # 含生效的 data home 绝对路径
python -X utf8 scripts/jobs.py enable  fundflow
python -X utf8 scripts/jobs.py disable news
python -X utf8 scripts/jobs.py set     fundflow run_at=15:10 interval_seconds=
python -X utf8 scripts/jobs.py run-now fundflow       # 立刻跑一轮，不等窗口
python -X utf8 scripts/jobs.py set     daily_close launch_lead_min=10     # 收盘前 10 分钟拉起通达信
python -X utf8 scripts/jobs.py set     completeness deviation=30           # 判"全不全"允许少几条
```

`completeness` 在 `status` 里印的是 **`[参数]`** 而不是 `[开]/[关]`：它没有 `enabled`、不自己跑、
也不往 `state.json` 记账。对它敲 `enable/disable/run-now` 会**直接拒绝并说明为什么**（写出一个
没人读的键 = 页面上多一个假开关）；要看它此刻判出什么用 `python -X utf8 -m duanxian.completeness --summary`。

`doctor` 加**「采集作业」项**：报每个作业的 `enabled` / 最近一次成功时刻 / 连续失败次数。**两个硬规定**：

- 它排在**「安装与源码一致」之前**。`setup()` 用 `checks[:-1]` 剔掉最后一项（那一刻指纹还没落盘），排在指纹后面的新项会被一起剔掉，而 `setup()` 的 `all(...)` 一假就抛错、永不写 `setup.json` —— 等于把 setup 自己锁死。已用测试钉住。
- 它是 **advisory**（红叉画 `!`，不拦启动）。采集没跑不是启动的前提，拦启动只会逼人绕开启动器直起 uvicorn。
