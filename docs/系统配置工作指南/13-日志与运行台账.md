# 13 · 日志与运行台账：分几层、各层在哪、怎么看

> 用户 2026-10-10 问的就是这三句：**日志全不全 / 有没有分层展示 / 文件放在哪里**。
> 这一篇既是答案，也是新增那一层之后该守的规矩。
> 不管"某个作业跑不跑"（那在 [12-定时任务全景](12-定时任务全景.md)），也不管业务口径（[数据加工](../数据加工工作指南/README.md)）。

## 一、四层，各管一件事

| 层 | 存在哪 | 回答什么 | 谁能看见 | 会不会丢 |
|---|---|---|---|---|
| **L1 结论台账**（每个作业最近一次 + 最近 12 笔流水） | `~\.duanxian-agents\jobs\state.json` | 跑没跑成、什么时候、连败几次、为什么 | `/jobs`、`/system` 的循环开关盘 | 覆盖式，只留 12 笔（`jobs.RUNS_KEEP`） |
| **L2 加工段逐步台账** | 同目录 `last_chain_steps.json`（重试阶梯在 `step_retry_plan.json`） | 41 步里哪一步没成、第几轮、单步补跑过没有（verdict 那句 10-15 晚起还会写「分钟线入库已就地补跑（链尾）」——那是下载晚到时链上自己补的 c16 入库，见《数据加工工作指南/05》第 34 条） | `/system`「加工段逐步结果与单步补跑」 | 每场覆盖；`--only` 走合并不覆盖 |
| **L3 数据库记账** | `operations.ingest_batch`（批次/行数/状态）、`.task`、`.schedule_state`、`.schedule_log`（唯一有 30 天清理的）、`.quality_result` | 某次采集到底写了几行、成没成 | `/datasource`（`vr/sysboard.py`）、`/quality`（`duanxian/quality.py`）、`/jobs`（`vr/jobsboard.py` 读 `.schedule_state`） | 在库里，跟着表走 |
| **L4 原始文本日志** | `YuanShan\.local\uvicorn.out.log`（进程 stdout：链与循环的 print）＋ `uvicorn.err.log`（uvicorn 自己） | **过程**：异常栈、"这一步正在跑"、被 except 吞掉的东西 | 10-10 起：`/system`「原始文本日志（尾部）」，接口 `GET /api/system/log` | 以前每次重启被 `-RedirectStandardOutput` **覆盖**；现在启动前先归档 |

L1 那 12 笔流水在**存储里是旧→新**（`jobs.py` 追加、满了丢最旧的，后端测试钉着这个顺序），
但 `/jobs` 上「最近运行记录」那一格**显示时倒过来（新在前）**并写明"新在前"（10-11 实测：
照存储顺序渲染时，最新那一下落在列表最底下，读者要拉到尾才知道"刚才那次怎么样了"）。

另有两类**产物侧证据**（不是日志，但常被拿来当日志用）：`~\.duanxian-agents\news\news-YYYY-MM-DD.jsonl`（快讯按天追加，日均 1.4 MB，**无删除逻辑**）、
`completeness\`、`coverage\`、`tdx\gui_trail.json`（唯一自带 200 条上限的）、`YuanShan\var\stuck\<时间戳>\`（卡住的现场，只增不删）。

## 二、反面教材：为什么 L4 必须有界面（2026-10-10）

通达信看护那条假绿：`/api/jobs` 的 `host_loops` 里写着 `tdx-watch` 在跑、作业状态"正常·连败 0"，
但 `state.json` 的 `tdx_watch.last_run_at` 已经 **18 小时没动**。真相只在 L4：

```
⚠️ 通达信探测循环异常（继续跑）：AttributeError: 'str' object has no attribute 'isoformat'
```

每两分钟一行。根因是看护里那道"该不该在"的闸把 `china_today()`（契约是字符串 `'YYYY-MM-DD'`）
当成 date 调了 `.isoformat()`，而抛点排在**记账、收同步进程、收空壳、下载阶梯之前** ⇒ 四件事一起停摆；
`except` 只 print 一行，所以 L1/L2/L3 全都表现为"没动静"。测试当时 8 条全绿 —— 因为
时钟桩也打成了 `dt.date`（桩和被测代码一起错，见 [[stubs-must-match-real-contract]]）。

**这一层没有界面时，这类故障只能靠人恰好在终端里看见。** 现在有两条路：
`/system` 那一格，或 `curl "http://127.0.0.1:8910/api/system/log?name=uvicorn.out&lines=200"`。

## 三、`GET /api/system/log` 的三条规矩

判据与读取只住 `vr/logtail.py`，端点在 `vr/app.py`，页面 `frontend/src/components/LogTailPanel.tsx`。

1. **白名单，绝不接受路径**。这台机器按用户 09-28 的指示开了局域网访问，所以
   `name` 必须命中 `logtail.LOGS` 的键（现在只有 `uvicorn.out` / `uvicorn.err`），
   路径由后端拼；翻旧日志的 `run` 必须命中"当场 `archives()` 列出来的那几份"。
   两者都是**查表**，不是拼字符串 —— 拒绝时连 `lines` 都不带出去。
2. **只倒读尾巴**（20~800 行，一次最多 512 KB）。不许为看几十行把整份读进内存，
   也不许在页面上做"翻页看全文"—— 那会变成一台远程文件浏览器。
3. **读数要能自证**：`path / size / mtime / mtime_age_seconds / skipped_bytes / returned / asked`
   一起交。`skipped_bytes > 0` 就说明这是尾巴不是全部；`mtime_age_seconds` 是
   "日志停在 14:37"（块缓冲那次的坑，见 [05-调度宿主](05-调度宿主.md)）唯一的可见方式。

**零字节 ≠ 没这一层**：文件在但 0 字节时写"这个进程还没打过东西"，不写"没有日志"。

4. **NUL 空洞要抹掉并留话**。归档那份实测有洞：55,776 字节的第 72~634 字节全是 `0x00`
   —— PowerShell 的 `-RedirectStandardOutput` 不是顺序追加，进程退出时文件里就是留了空档。
   原样送进界面是屏幕上 563 个看不见的字符，读起来像"日志坏了"，其实是读取器没处理。
   现在解码后把 `\x00` 抹掉、交 `nul_bytes_stripped` 并在 `note` 里明说抹了多少。
   洞总在两条记录之间（上一条自带换行），所以抹掉不会把两条并成一条 —— 回归
   `tests/test_logtail.py::test_归档里的_NUL_空洞要抹掉并留话` 钉着这条。

## 四、启动时归档（`scripts/restart_8910.ps1`）

`Start-Process -RedirectStandardOutput` 是**覆盖**不是追加，所以脚本在启动前把上一份
`uvicorn.out.log` / `uvicorn.err.log` 改名成 `uvicorn.out.<末次写入时刻>.log` 归档，
只留最近 14 份。实测（10-10 23:52 那次重启）：55,776 字节的上一份保留成
`uvicorn.out.20261010-235122.log`，接口用 `&run=20261010-235122` 能读出它，
新的一份从 0 开始长。

⚠️ 为什么不用"追加"：两个进程（旧没退干净 + 新的起来）同时写一个文件会互相截断，
归档再重启是幂等的，而"谁在写这一行"也更好断（文件名带启动时刻）。

## 五、还缺的三层（登记为任务 #91 未完部分，别当成已完备）

| 缺什么 | 现状 | 后果 |
|---|---|---|
| L1 的**长历史** | 只有 12 笔流水，按天汇总（"这周红过几次"）没有 | 周报型问题仍答不上来；只能靠 L4 翻归档 |
| **轮转与清理** | 只有 `operations.schedule_log`（prune 30 天）与备份目录 `rotate()` 真接上；`app/config.py` 里 `LOG_DIR=logs/`、`LOG_KEEP_DAYS=30` 是**孤儿配置**（`logs/` 空目录，无人写） | `news\*.jsonl` 一年约 +500 MB；`var\stuck\` 每失败一目录（现 36 个）；`.local\`、`var\` 里堆着会话留下的临时日志（实测 20 MB / 38 MB） |
| **加工段的库内记账** | 采集侧与 FT 调度侧写 `operations.*`；d1~d7 计算段、qd 轨、复盘链**不写**，`operations.audit` 有表零调用 | "这场加工到底跑没跑"只在 L2 那个文件里；库内查不到，跨会话/跨进程时最弱 |

补哪一层按"出问题最难发现的那条"排，不按工作量排。
