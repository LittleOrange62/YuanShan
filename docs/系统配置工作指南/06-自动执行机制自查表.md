## 七条判据（每条必须**实测**回答，不许凭读代码给结论）

1. **异常有没有出声并留下可查记录？**
   要求：捕获后 (a) 打日志带原因，(b) **往 `duanxian/jobs.py::record()` 记一次**（归因文字只认
   `reason` 键），(c) 页面上看得见。只 print = 没做（stdout 进文件是块缓冲，等于没说）。
   *怎么验*：把依赖人为弄坏一次（拔网 / 改错 DSN / 让子作业返回非零），看 `/api/jobs` 与
   `manage.py doctor` 有没有长出对应那一格的红/黄。
2. **重试有没有节奏、上限和"到点才试"？**
   反例（已修）：hold 每 60 秒敲一次、上限 3 次 ⇒ 两分钟烧完，而通达信文件 17:2x 才落盘 ⇒
   **"晚到"被读成"没有"**。现规矩：节奏表只住一处（`DAILY_CLOSE_RETRY_MIN = (0,25,60,100,150)`），
   宿主与页面都调同一份函数（`close_attempt_due` / `close_next_attempt_min`）。
   每条自动机制都要有自己的那张表，或在文档里写明"为什么不需要"。
3. **有没有超时？** 凡起子进程/联网/等界面的地方都要有硬上限，**并且上限要说清是谁给的**。
   ⚠️ 只杀直接子进程会留孤儿孙进程：`subprocess.run(timeout=)` 到点 `kill()` 的是它自己起的那个，
   被它再起的 `c1/c3/c16/p0/run_agent` 还在跑。要么按**进程树**收（`taskkill /PID <pid> /T /F`，
   **绝不按映像名杀** —— 那会连用户的通达信一起杀掉），要么给子作业自己一份超时。
4. **幂等 / 回补做没做？** 判据必须是**库里有没有那一天**，不是"我上次跑成功了没"。
   重复运行的代价必须是零，否则没人敢让计划任务天天跑。
   同时反过来也要成立：**库里没有 ≠ 别去拿**（`c10` 把"日期齐但派生列空着"错当成缺数，
   就是这条没拆开：`dates`＝要不要取数，`touched`＝要回算哪几天）。
5. **"成功"是按数据判的，还是按退出码判的？** 只看 rc==0 就算成的，全部要复核一遍。
   已知可疑（**未逐条验证，归各会话自查**）：`app/orchestrator/runner.py` 里 rc→succeeded 那一处。
6. **有没有并发/互斥保护？** 三入口一把锁（`jobs.claim`），但它是**进程内的集合** ——
   `app/orchestrator` 那条 worker 是另一个进程，**不认这把锁**，而它的 `RUNNERS` 里也登记了
   `daily_close`。谁要真启用那条入队链，同一时刻就会有两个进程去点同一个通达信窗口。
   结论必须写死：要么它也走 `run_close_stage`，要么把 `config.job` 里那行停掉。
7. **卡住/中途死了能不能被外部看见？** 至少要能回答"现在在跑什么、跑到哪、多久没动了"。
   `run_agent` 的 `var/stuck/` 现场包、`p0` 的 `STALL_LIMIT`、`readiness` 的覆盖门都算，
   但要**指出是谁在什么时候读它** —— 没人读的现场包等于没留。

## 通达信三条硬要求（用户点名，归 数据获取；验收标准写死在这里）

1. **进程要有监控，而且监控必须真的在跑。**
   `watchman.py` 现在是零引用。要求：常驻进程里起一条**只探测（probe，不动界面）**的看护，
   把结果同时交给 ① `jobs/state.json`（键名建议 `tdx_watch`）② `/api/jobs` 的 `host_loops`
   ③ `/system` 的一格（"通达信：在跑/不在/登录框弹出/同步中/最近探测时间"）。
   **自愈 `heal()` 仍必须默认关**（它会抢前台发真实键鼠），打开要用户点头 ——
   但"探测"是只读枚举窗口，可以默认开。
2. **下载完成必须关窗，且关完要验。** `s8_finish.close_dialog()` 现在写完 `WM_CLOSE`/系统菜单/
   点按钮之后只是记一句"对话框仍在"。要求：关→`IsWindow` 复验→没关就升级下一手段→最后仍没关
   要**出声**（记一次 not-ok），不许静默。`cleanup()` 吞异常是设计（不能盖掉真失败原因），
   但吞掉之后必须留一句可读的记录。
3. **下载到一半没成功要自动重试。** 现状：`p0_tdx_predownload` 有 `--attempts 2`（reset + 重来），
   但"重试"的触发只在它自己那一层。要求把这三件事分清并在文档里写死：
   ① 怎么判定"中途死了"（`TPyth*` 还在但覆盖数连续 N 轮不涨 / 窗口消失而 `.day` 尾部没前进 / 超时）；
   ② 每种判定各自的重试动作（等 / 重开对话框 / 重启客户端 / 交给人）与**上限**；
   ③ 重试仍不成时，整条链要退化成"晚到等到"而不是"要人来"（对齐总协调侧的退出码 4）。

### 补：下载阶梯（用户 2026-10-06 19:1x 原话，`server.py::_download_ladder_round`）

> 「大概下载了 10 分钟之后你就应该去检测对应的数据是否全了，全了就关闭进程。如果不全，就再等
> 10 分钟，再检测如果数据全了就关闭，如果不全，就关闭重新试一次（我指的是通达信相关的全重启一下）」

| 档 | 时刻 | 判据 | 动作 |
|---|---|---|---|
| 0 | 第一次看到 `TPyth*` 在跑 | 只记"起算点" | 不动（10 分钟后再说） |
| 1 | +10 分钟 | `_vipdoc_download_complete`：**日期到位（日线/指数/1 分/5 分）+ 整目录条数 ≥ 前一天的条数 − 偏离值**（`duanxian/completeness.py`，偏离值默认 30、分钟类 200，系统配置改得动） | 全 → `kill_tree` 收 `TPyth*`（`force=True`，不再等年龄阈值）；不全 → 排第二档 |
| 2 | +20 分钟 | 同上 | 全 → 收进程；**不全 → `_restart_tdx_for_retry`：`reset` 关掉全部进程 → `run_agent s1/s2/s3` 重新起+登录+清弹窗**，下一轮自己会重新判 |

三道不许越的线：**① 有收盘链在跑（`jobs.stage_busy()`）就整段不接管**（p0 自己有 `STALL_LIMIT` 与 `--attempts`，两双手会抢一个客户端）；**② 只收 `TPyth*`，绝不动 `TdxW.exe`**（TQ 那条腿要主客户端登录着）；**③ `tdx_watch.auto_restart=false` 就只做"查 + 关进程"，不碰键盘**。
"全不全"**不看窗口文字、不看 mtime、不看退出码** —— 09-23 那次分钟线只进了北交所 351 只（日期齐、量级差 27 倍），所以**条数**是硬判据。回归在 `tests/test_auto_execution_hardening.py`（含"半截冒充全量必须判不全"）+ `tests/test_completeness.py`。

### 判据换血：从"抽样比例"到"动态条数"（用户 2026-10-06 20:5x 原话）

> 要设置个硬性规则……因为会有新股上市，后面只会更多——最好是能动态变化，每次记录总条数，
> 近一个交易日的条数是必须大于等于前第 2 个交易日的

落点是新模块 **`duanxian/completeness.py`**（判据只有这一份实现，三处调用它：
常驻阶梯 `_vipdoc_download_complete`、收盘链 ③a 的 `step_complete`、覆盖体检 `_entity_day_check`）：

| 条 | 实现 | 实测依据 |
|---|---|---|
| 数整目录，不抽样 | `vipdoc_counts()`：`.day`/`.lc1`/`.lc5` 各数"尾部记录日期已到那天"的文件个数，8 线程 | 2026-09-30：`.day` 9,490 / 目录共 9,564（sh 4,813 / sz 4,327 / bj 350）；冷跑 ~49 秒、热跑 ~2.8 秒，三种口径一起数完 6.3 秒 |
| 每判一次登记一次 | `<ASTOCK_DATA_HOME>\completeness\session_counts.json`，**只登记判为全的那些场** | 半截那天进了池子 = 第二天跟它比双双通过，规则自己废 |
| 基线 = 前一天（T-1） | `baseline()`：过绝对下线的场次里取**最新**一场，并交出"实际隔了几场" | 2026-10-06 曾取次新一场（怕前一天是坏的）；10-07 用户改回 T-1 —— "半截那天"靠**只登记判为全的场**挡住，不靠跳过一场 |
| 没有历史时按绝对下线 | `KINDS[kind]["floor"]`，并在结论里写清"这是按量级判的" | 各口径 floor 都取实测量级的 ~95%（日线 5,000 / 分钟 8,500 / 指数 150 / 板块 1,000） |
| 允许的回退按**条数**给 | `deviation` 30 条（日线/板块/指数类）、`deviation_minute` 200 条（分钟类），**默认值只住 `duanxian/jobs.py::COMPLETENESS_DEFAULTS`** | 10-07 逐日实测：`.day` 相邻两场最大回退 −11 条、`.lc1/.lc5` −107 条、PG 分钟线只数 −143 条（停牌/退市那天就是没有那些文件）。百分比容差已被否：按"前一天数量 ± 偏离条数"判，且分钟类若也压成 30 会天天误报 |

**偏离值是对"必须大于等于"的一处打折**（退市、停牌那些票那天就是没有条数，用户 2026-10-07：
"我之前说的方法没考虑退市、停牌的……偏离值在 30 以内就算全了"）。要完全不打折就在
「系统配置 → 收盘链 → 条数完整性」把偏离值改成 **0**（合法值），代价是上面那几种正常日子
每天都会判不全、每天都去重启通达信重下一遍。反过来把它调到不小于基线（比如日线类填 6,000），
这道门就等于没有 —— `judge()` 会在结论里当场写"这个口径**等于不再判不全**"，不会静默放行。
两个数也可以命令行改：`python -X utf8 scripts/jobs.py set completeness deviation=30`。
命令行能直接问判据：`python -m duanxian.completeness --summary | --seed | --vipdoc`。
PG 侧的头几天基线由 `--seed` 从库里补登记（不然要等两天才有基线）。

用户点名要的功能（保持运行 / 需要时才运行 + 定时任务不要弹窗）做完之后，**看护循环替我跑了一早上**，

连带补的两处：

- **假警报**：07:48 那条「需要人工点一次退出」在 08:09 程序做完之后仍挂在待人工清单上
  （`pending()` 的默认纪律"`done` 不抹掉前面那条没做成的"本身是对的）。加了**显式**例外
  `add(..., supersedes=True)`：只抹同 `(day, step, target)` 的旧交人工记录，账本原始记录一条不少。
  顺带把 `close_client` 补进 `MANUAL` —— 此前那句一直是"这一步没有登记手动做法"，
  而这一步恰恰要点准「退出」（按成「取消」就是不关）。
- **默认值的诚实性**：《12-定时任务全景》把 `auto_restart` 登记成"默认关"，现查
  `TDX_WATCH_DEFAULTS:535` 是 `True` —— 已更正。读数口径错一次，下一个人就会按错的口径做决定。
- **第四个洞是 doctor 自己抄的那份判据**（同一天晚些时候，跑 `manage.py doctor` 才撞见）：
  页面（`gui_trail.pending()`）说 **0 条要人补**，体检那一项却说 **3 条没做成，要人补**——
  `scripts/manage.py::tdx_gui_trail()` 里另写了一遍"读 json 数 `status != 'done'`"，
  那份抄本既不认同日同步骤去重，也不认这次新加的 `supersedes`。
  **同一件事两个读数比没有读数更坏**：体检是人在命令行上看的那一眼，它会指挥人去补一件已经做完的事。
  现在这一项只调 `gui_trail.pending()/items()`，判据只住一份；`duanxian` 真 import 不动时
  按"未判"出声（既不说要人补，也不说没有），**不许回退成一份自己写的数法**——
  这一条也是为什么函数里要显式把 ROOT 补进 `sys.path`（`doctor` 单跑时 `sys.path[0]` 是 `scripts/`，
  只有 `start()` 那一步才插过 ROOT）。钉在
  `tests/test_self_heal_inventory.py::test_doctor的待人工读数就是gui_trail那份`。
