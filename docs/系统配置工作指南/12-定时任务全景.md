# 08 · 定时任务全景（谁在什么时候真的跑、开关在哪、看不见的那几条）

> 用户 2026-10-07 问：「是不是有一大堆的定时任务，这块内容在系统配置里吗？是不是叫做调度器？
> 梳理一下这个维度的任务情况。」**这本指南那一句问题的答案**，判据仍以
> [05-调度宿主.md](05-调度宿主.md) 与 [06-自动执行机制自查表.md](06-自动执行机制自查表.md) 为准。

## 一、一句话总量

**12 条常驻循环（本进程 uvicorn 里的线程）+ 1 条 15:59 收盘链（内含 52 步：获取 10 步 + 加工段 42 步）+ 1 条 Windows 计划任务。**

（**10-15 补进第 12 条 `notify-push`**：消息推送的定时计划表，每 60 秒扫一遍"到点没有"。
它是用户点名 Apprise 之后建的那一块，渠道/凭据/内容/定时四件事的判据都不在本进程，
见 [14-消息推送渠道与定时计划.md](14-消息推送渠道与定时计划.md)。**这一条自己没有 `run_at`**
—— "几点发"住在每条计划里，给循环再配一个时点就是页面上多一个改了也不生效的框。）

（**10-12 深夜补进第 11 条 `pg-backup`**：每天 18:40 背一次库。`app/ops/backup.py` 的
dump → 恢复验证 → 轮转 → 写质量规则**早就写全了**，缺的只有"每天有人去敲一次"——
当天实测 daily 与 weekly 两份都停在 **148 小时前**，doctor 只能红着念同一句话，没人也没程序去补。
库里是这台机器唯一的真资产：日线/分钟线重灌按小时计，而**已经采过的那些场补不回来**。）

（10-08 晚间补进第 10 条 `step-retry`：加工段**失败那几步**的夜间重试阶梯，用户点名要的"21 点不行就 22 点、再不行隔日 1 点 / 2 点多 / 4 点多，都不行就算了等下一次收盘顺手补"。
先前这句写的是 9 条 —— 数一数就红，所以逐条清单与 `LOOP_JOBS` 必须一起改。）

⚠️ 那条计划任务是 **`YuanShan-KeepAlive8910`**（用户 2026-10-08 点头注册）：它**只把 8910 拉起来，
不跑任何数据作业**——判"要不要拉起"只看 health 与端口监听，绝不打断正在跑的链（判据见 §六）。
所以"数据只在常驻进程里跑"这个结论没变，变的是"本机 `YuanShan-*` 零条"这句不再成立。

旧项目那 36 条 `config.job` 登记**不在本机运行**（`ft-scheduler` 进程心跳停在 2026-09-25、
`enabled=false / dry_run=true / fired=0`），它们只在「任务调度」页上以"不可用 + 原因"的形态出现。

## 三、这一轮梳理挖出来的三个洞（都已补，各钉了一条测试）

1. **第 8 条 `watchtower` 根本不在任何清单里**：它每 3 秒发一次外部请求、一直在记账，
   但既不在 `LOOP_JOBS`、也不在 `CLOSE_DEFAULTS` ⇒ **看不见也关不掉**。
   判据只查"在册清单 ∩ 进程自报"，而它两边都不在册 —— 所以它永远不会被报成缺。
   现在它进了两处清单，宿主真读 `_loop_enabled(...)`。
2. **面板上的开关有三条是假的**（`intraday` / `watchtower` / `news`）：`set_switch` 会写
   `enabled=false` 进 `jobs/config.json`，可宿主那边只看环境变量总闸（`VIBE_NEWS` 等），
   于是"页面上关了、线程照跑"。这正是 09-28 那套"两份读法一份留痕"的老形状，
   现在三条都走 `server.py::_loop_enabled(env_var, name, defaults)` 这**一份**读法。
3. **`/api/jobs/loops` 交齐了字段却没有一个前端消费者**（`grep loops frontend/src` 零命中）：
   接口 10-06 就写完了，界面上仍然只有收盘链那两段能关。
   ⇒ 新增 `frontend/src/components/LoopSwitchboard.tsx`，挂在 `/system`（导航名「系统配置」）。
   ⚠️ 路由名会骗人：`/settings` 是「AI 探索」，`/system` 才是「系统配置」。

## 四、"在系统配置里吗？是不是叫调度器？"——两个都回答

- **在系统配置里**：`/system` 新增一张「常驻循环与定时任务」卡，十二条逐条给
  开关 / 节奏 / 最近跑过 / 最近成功 / 连败 / 留痕 / 关掉会失去什么，
  并明写"没记录"和"活着但零笔记账"是两件事。**任务调度页 `/jobs` 继续只管历史读数**
  （最后成功、落库日期、锁、手动触发），两处不重复一套开关。
- **不该叫"调度器"**：这个词在本机同时指五件东西，对照表在
  [05 §4b](05-调度宿主.md)。任务调度页顶部那张卡原来标题就是「调度器」，
  10-07 已改成事实句「本进程宿主的循环读数」。

## 五、加一条循环要动哪几处（缺一处就是"看得见关不掉"或"改得动没人读"）

| 步 | 位置 | 少了会怎样 |
|---|---|---|
| 1 | `duanxian/jobs.py::CLOSE_DEFAULTS` 加一键（默认值**只住这里**） | 面板 `switchable=false`，只能命令行；`scripts/jobs.py` 改不动它 |
| 2 | `vr/jobsboard.py::LOOP_JOBS` 加一行 `(线程名, 记账键, 中文名, 关掉的代价)`；节奏不是"到点"的再加 `LOOP_CADENCE` | 体检与面板看不见 ⇒ 永久漏报 |
| 3 | 宿主线程名必须与第 2 步的线程名**逐字一致**，且每轮走 `_loop_enabled(env_var, key, defaults)` | 开关是假的（页面上关了、线程照跑） |

## 六、`YuanShan-KeepAlive8910`（2026-10-08 起本机唯一那条计划任务）

| 项 | 事实 |
|---|---|
| 注册处 | 任务名 `YuanShan-KeepAlive8910`，触发 **AtLogon + 每 5 分钟**，动作 `scripts\keepalive_8910.vbs` → 里面再起 `scripts\keepalive_8910.ps1` |
| 为什么多一层 `.vbs`（2026-10-12） | 任务原来直接以 `powershell.exe ... -WindowStyle Hidden -File keepalive_8910.ps1` 为动作，**每 5 分钟在屏幕上闪一下黑窗**。原因不在参数：`powershell.exe` 是控制台程序，计划任务起它时**系统先创建控制台窗口**，`-WindowStyle Hidden` 要等 PowerShell 自己跑起来才生效，晚了。`wscript.exe` 是 GUI 子系统宿主（根本不建控制台），`Run(cmd, 0, true)` 让子进程**从创建起就是隐藏的**。第三个参数 `true`（等子进程结束）不许改成 `false`：那是让 `MultipleInstancesPolicy=IgnoreNew` 和 `ExecutionTimeLimit PT4M` 继续生效的唯一办法，放开就会让两轮看护叠在一起、各起一个服务 |
| 它做什么 | 只判"8910 还活着没有"，死了就把服务拉起来。**不跑任何数据作业**，也不碰采集/加工/收盘链 |
| 判据（三条，顺序不许调） | ① `health` 通 ⇒ 什么都不做；② 不通**且端口无监听** ⇒ 拉起；③ 不通**但端口有人监听** ⇒ **只写告警、绝不 kill** |
| 为什么第 ③ 条这么硬 | 端口有人听而 health 不通 = 进程卡在半起/正在干活的形状。此时杀进程会把**15:59 正在跑的收盘链连带杀掉**，而那一段的数当天不采就永久少一天。宁可不动，让人来看 |
| 日志 | `.local\keepalive.log`（每次判定一行） |
| 怎么自己看 | `manage.py doctor` 的「外部计划任务」项现在会把**本项目注册的任务**逐条列出来（名字=状态），不再只查外人 |
