# 07 · 故障恢复手册：怎么**弄坏它**来验证

> 2026-10-06 立。配套 [06-自动执行机制自查表](06-自动执行机制自查表.md)：那页给**判据**，这页给
> **把判据跑一遍的具体动作**。
>
> 为什么要单独一本：本项目已经立过规矩 —— **判据要能执行，不能只"看代码确认存在"**。
> 09-28/29/30 三天连着的事故形态不是代码写错，是"写着有、其实没接"和"在跑、其实一步没执行"，
> 而这两种都**只有弄坏一次才看得出来**。光读代码谁都能读出一句"这里有异常处理"。

## 用法与红线

- **每条实验都标了「实测」**：✅＝今天真跑过、下面贴的是原样输出；⬜＝写法给出来了但今天没跑，
  并且**写清为什么没跑**。没跑过的判据不算验证过，别把它抄成"已验证"。
- 全程在临时目录里造文件。**不动 `.env`、不动库、不注册计划任务、不碰通达信窗口**
  （口令不许上屏：实验 1 用的是环境变量占位串，不是真口令）。
- 体检项一律**按名字**引用，别按序号 —— 序号随加项漂移，01 页就自己错过一次。
- 跑之前先记住两件事：① 判"改码生效没有"只看 `/api/jobs` 的 `scheduler.host_loops`；
  ② 全量测试要在**前后各夹一次 mtime**，窗口内有 `.py` 落盘整份作废（见 §八）。

## 一、库连不上 → 必须说「读不到库」，不许说「缺数」 ✅ 实测

| 弄坏什么 | `PG_PASSWORD` 环境变量（临时占位串，不改 `.env`） |
|---|---|
| 命令 | `cd D:\finance\YuanShan && PG_PASSWORD=zhangchang-bucu PG_USER=ft_reader .venv\Scripts\python.exe -X utf8 scripts\manage.py doctor` |
| 该亮起 | 「当日数据到位」变 `!`，且措辞必须是**读不到库**，不是"缺 2026-09-30" |

2026-10-06 18:07 实测原文：

```
! 当日数据到位：读不到库（`select 1` 就失败）—— 这**不等于缺数**：先确认 PostgreSQL 服务在跑、
  凭据没改错（.env 的 PG_*），再看《故障恢复手册》「库连不上」那一节
✓ 采集作业：最近成功 news:文件侧 2026-10-06 18:07:57（1 分钟前…）、daily_close:2026-09-30 16:00:15、
  fill_all:2026-09-30 17:01:26、fundflow:2026-09-30 20:50:55、tdx_watch:2026-10-06 17:58:02、
  watchlist:2026-10-05 20:40:31
```

**这条是今天改出来的**：第一版把"读不到库"渲染成了"缺数"，会让人去补一个根本不缺的交易日。
现在 `data_freshness` 先跑 `select 1` 当探针（`probe_ok`），探针失败就只报连通性、不报缺数。

恢复：去掉那两个环境变量即可（本次实验没落盘任何东西）。

## 二、服务没在跑 / 一条循环都没起 → 要说清"今天不会有东西自己跑" ✅ 实测

| 弄坏什么 | 不弄坏服务，只把体检指向一个没人听的端口（等价于服务没起） |
|---|---|
| 命令 | `.venv\Scripts\python.exe -X utf8 scripts\manage.py doctor --port 60999` |
| 该亮起 | 「常驻循环完整性」`!`，且必须把**后果**说出来，不是只说"读不到" |

实测原文：

```
! 常驻循环完整性：服务没在跑或读不到（URLError: <urlopen error [WinError 10061]…>）
  ⇒ 一条常驻循环都没有 ⇒ 15:59 的收盘链、20:40 的自选同步今天都不会自己跑
```

⚠️ 反过来有一条**必须不亮**：`manage.py start` 的体检跑在**绑定端口之前**，
那一刻连不上是正常流程，不是故障。所以 `doctor(port, phase="startup")` 这一档
只报"7 条循环待起"，不判红 —— 第一版没分相位，每次启动都红一次。

## 三、改完码没重启 →「进程里跑的是旧代码」 ✅ 实测（今天真出现过）

这是全项目最阴的一类：**服务活着、页面绿、`state.json` 时间在走，但跑的是编译进内存的旧清单**。

10-06 17:5x 的现场：磁盘上 `vr/jobsboard.py::HOST_LOOPS` 已经声明 7 条（含 `tdx-watch`），
而当时跑着的服务报"活着 6 条、缺 0 条" —— 它拿**自己那份旧清单**比，所以永远"不缺"。
现在 `loop_inventory` 是**磁盘清单 ∩ 进程自报**，磁盘有、进程不认 ⇒ 判红并直接说「重启 8910 才装得上」。

重启后（同一台机器、同一命令）：

```
✓ 常驻循环完整性：7 条常驻循环都在（pid 30140）：intraday、newswire、watchlist-sync、
  fundflow-sina、coverage-precompute、daily-close、tdx-watch
```

恢复动作就是重启，**验证动作也只能是重启后再跑这一项**。别看 `state.json` 的时间戳 ——
那是"有没有人写"，不是"装的是哪份代码"。

## 四、声明清单本身被弄坏 → 「判不了」是红，不是"没清单所以不用起" ✅ 实测

| 命令 | 在临时目录造一个 `vr/jobsboard.py`，把 `HOST_LOOPS` 改名，调 `manage.loop_inventory(temp_root, 60999)` |
|---|---|
| 实测原文 | `(False, '判不了该起哪些循环：vr/jobsboard.py 里找不到 HOST_LOOPS 这个元组（清单被改名了？） —— 判不了不等于「循环都在」')` |

为什么值得单独一条：`watchman.py` 那次事故的本质就是"没人声明它该跑"。
如果清单读不出来就返回"无缺口"，那这条体检项会在最需要它的时候闭嘴。

## 五、采集作业：「从未成功」与「成功过但今天没跑」必须分开 ✅ 实测

09-28 那场的形状：20:40 的自选同步**从未成功过（连败 91）**，而页面上照常显示 41 个组（旧存量），
体检的旧写法只看"最后一次成功是什么时候"，于是那一档是**绿的**。根因（`added_at` 的
not-null/default 绑成裸 NULL、序列 `config.watchlist_group_group_id_seq` 没授给 `ft_etl`）
已由数据获取侧修掉，迁移在 `app/db/sql/22_watchlist_sequence_grant.sql`。

| 命令 | 在临时 `ASTOCK_DATA_HOME` 造 `jobs/state.json`（照 09-28 那份形状），调 `manage.collector_status("2026-09-30")` |
|---|---|
| 该亮起 | 三档各有各的话，且红的那两条都带归因 |

实测原文（`ok=False`）：

```
最近成功 brand_new:从未运行（刚接入，还没跑过第一场）、fundflow:2026-09-28 20:50:00、
watchlist:从未成功/连败91（data home=…）；**要人看的**：
fundflow 最近成功停在 2026-09-28，而应到 2026-09-30 —— 这一场要么没跑要么没跑成；
watchlist 从未成功过（跑过 2026-10-05 20:40:00，连败 91；最近一次归因：null value in column added_at violates not-null constraint）
```

四档判据（`scripts/manage.py::collector_status`）：

| 状态 | 判据 | 颜色 |
|---|---|---|
| 从未运行 | 没有 `last_run_at` 也没有连败 | 提示，不判红（判红等于造一条天天红的项） |
| **从未成功** | 跑过 / 连败 N>0，`last_ok_at` 为 null | **红**，把 N 与最近一次归因点出来 |
| **成功过但应到那场没成** | `last_ok_at[:10] < expected_session` 且开关为开 | **红** |
| 停用 | `config.json` 里 `enabled=false` | 不判红（那是「收盘链自动开关」那一档的事，见 §六） |

`expected_session` **不是**这项自己算的：它复用同一次 `data_freshness` 探针里的"最近一个已收盘交易日"。
长假期间它本来就是旧日期，所以不会误报 —— 10-06 实测：应到 2026-09-30，库里 09-30 齐，绿。

页面侧同源：`vr/jobsboard.py::_recorded_job` 原来把"没成功记录"一律写成「从未运行」，
现在分「正常 / 从未成功（跑过 X，连败 N）/ 未起（上游今天停在 hold）」三档。

## 六、开关被关：没署名 vs 署名 ✅ 实测

09-28 用户问"为什么被关了三次"时立下的规矩：**关必须是一个署名的动作**。

| 命令 | 临时 `ASTOCK_DATA_HOME/jobs/config.json` 写 `{"daily_close": {"enabled": false}}`，调 `manage.close_chain_switches()` |
|---|---|
| 没署名 | `(False, '…停用但**没人说明是谁关的、为什么**：daily_close…')` ⇒ **红** |
| 写了 `note` | `(True, '…停用且已署名：daily_close（用户 2026-09-28 裁定：先停自动，等 p0 自限预算落地）…')` ⇒ 绿，只报状态 |

真出事时的读法（顺序别倒）：`GET /api/jobs/chain` → `jobs/config.json` 的
`_changed_by`/`_changed_at`（每次写都自动盖章）→ `note`。三步之内一定有人或没人，"没人"就是这条红项存在的理由。

## 七、作业路径指向不存在的位置（`c10` 那一类）✅ 实测（单元级）

**为什么单独一条**：09-29 整条加工链没跑，根因是 `c10_catchup` 用**参考仓库**的路径
`scripts/ops/p0_tdx_predownload.py` 起子作业，每步 `can't open file`、退出码 2，
长得跟"下载没成功"一模一样，而当时体检的「外部路径引用」是**绿的** —— 它只盯绝对路径的盘符。

现在 `external_path_refs` 多叫了一个 `missing_job_targets(root, rel, lines)`（`manage.py:237`）：

| 抓什么 | 怎么抓 |
|---|---|
| `ingest.jobs.X` 这种模块名注册表引用指向不存在的模块 | 只要出现注册表写法就查，10-06 实测全仓 68 处、0 命中 |
| 起子作业的**相对脚本路径**（`scripts/<子目录>/x.py`） | 只在"起进程"的上下文里查（同段里有 `subprocess`/`Popen`/`run_now` 之类），避免把注释、文档里的路径当故障 |
| 不误报 | 只有当**那一行或它上面两行**出现 `subprocess`/`Popen`/`check_output`/`check_call`/`sys.executable`/`run_script`/`cmd=` 之一时才判（`SPAWN_CTX_RE`）—— 否则 `Path("code/signal_engine.py")` 这种带 `.exists()` 守卫的探测会被判成故障（实测过：全仓扫命中 2 处，全是无害的） |

复现（安全，不动仓库）：在临时目录写一个 `ingest/jobs/c99_x.py`，内容是
`subprocess.run([sys.executable, "scripts/ops/p0_tdx_predownload.py"])`，
调 `manage.missing_job_targets(temp_root, "ingest/jobs/c99_x.py", lines)` ⇒ 报出那条路径不存在。

⚠️ 这条只能证明"引用指向了不存在的东西"，**不能**证明"作业跑成功了"。后者要看 §五 与库里的日期。

## 八、子作业返回非零 / 中途死掉（退出码那条链）⬜ 端到端今天没跑

**没跑，并且说明为什么**：现在这台机器上 10-01~10-07 休市，真跑一次 `daily_close` 会走
`p0_tdx_predownload` 那条**要点通达信窗口**的路径 —— 起客户端碰用户的桌面是红线
（10-06 就实测越界过一次：把执行体从 `subprocess.run` 换成 `Popen` 之后，宿主测试里假的 `run`
不再被调用，pytest 真的起了下载链、在用户桌面上把 `TdxW.exe` 启动了）。

所以起真链的入口收成**一个具名洞** `duanxian/jobs.py::_spawn_stage`，它第一行查
`PYTEST_CURRENT_TEST` 直接返回 127 并说明为什么 —— **测试只许打这个洞，不许打 `subprocess.*`**。
今天做到的是**单元级实测**：交回假 rc 验证四种处置：

| rc | verdict | 现象（测试钉住的行为） |
|---|---|---|
| 0 | run | 记一次 ok，放行下游 |
| 3 | stop | 今天不再试，下游**不写 `last_run_at`**（没跑过就说是没跑过） |
| 4 | hold | 晚到等到：按 `DAILY_CLOSE_RETRY_MIN=(0,25,60,100,150)` 到点才再试，不算失败 |
| 其它非零 | stop + 出声 | `jobs.py::record` 记一条带 `reason` 的 not-ok，页面与 doctor 都看得见 |

端到端的自然验证点：**下一个交易日 2026-10-08 15:59**。到点后来查这三处 ——
`GET /api/jobs/chain`（不是 `/api/jobs` 的 `scheduler.chain`，那里没有这一节）、
`jobs/state.json` 的 `daily_close.last_detail.reason`、
以及体检「采集作业」里 `daily_close` 那格的日期。

## 九、备份：三种坏法 ✅ 实测

| 弄坏什么 | 命令/做法 | 该亮起 |
|---|---|---|
| 备份目录移走 | `VIBE_BACKUP_DIR=<不存在>` 跑 `manage.py doctor` | 「数据库备份」`!`：`备份目录不存在：…（可设 VIBE_BACKUP_DIR）`。**判不了不等于备份新** |
| 有一份正在写 | 最新 dump 的 mtime 在 20 分钟内 | 不跑 `pg_restore` 验它、也不叠第二份（10-06 18:07 原文：`weekly＝0 小时前（20 分钟内还被写过…这一刻不跑 pg_restore，免得半截文件被读成坏文件）`） |
| 锁文件遗留 | 造一份 1 小时前的 `.local/backup_on_start.daily.lock` | 过期锁**被重新拿起**、照常补跑（第一版 `O_EXCL` 不清旧锁 = 一次崩溃把通道永久焊死，而它看起来还在工作） |
| **第二块盘写不进去**（10-18 新） | `FT_BACKUP_MIRROR_DIR=<不可写的深层路径>` 跑一次 `python -m app.ops.backup daily`（kind 是**位置参数**，没有 `--kind`） | 这一轮**记失败**，措辞点名是哪一半坏的：`跨盘副本没落地：<原因> → 这一轮只有一份档，在 D:\…`。加这一档的来由：`C:\finance_backup\TataPG\daily` 里还是 09-25 那两份，而 09-24 之后**没有任何代码在写它**（`grep -rn finance_backup --include=*.py` 零命中）—— "有一份在另一块盘上"这句话悄悄过期了三周，体检只看 D 盘那棵树，看不见这件事 |
| 周末把 daily 判成过期（10-18 修） | 周六/周日跑 `manage.py doctor` | **不该红**：那两晚按排程背的是全库 `weekly`，daily 根本不该有。原来是一条裸的「daily≤36h 文件年龄」，于是周日 22:40 必然报 `daily＝52 小时前`（10-18 实测到的假红）。现在按 `backup_last_daily_due()` 的日历判（与 `app/ops/backup.kind_for()` 同一套：1 号 monthly、周六周日 weekly、其余 daily），措辞里直接给出"应到哪天"。代价写在函数 docstring 里：昨天漏背要到今天那一档跑完才报得出来，宁晚一天也不要天天误报 |

「不注册计划任务也能每天备份」那条替代方案（启动即补 + 为什么 weekly 不挂启动路径）写在
[02-PostgreSQL与备份](02-PostgreSQL与备份.md) §五之二。

## 十一、"写死的读数"这一类：跑着的东西被报成没接 ✅ 实测（10-06 复核）

前面十条都在抓"没跑的被说成跑了"。还有一类方向相反，同样致命：**在跑的被页面说成没接**。
`fundflow` 那一行原先是手写的 `available=false` + "YuanShan 内还没有资金流采集的执行体" +
"`fund_flow_rank` 现空表" —— 而 `c21_fundflow_sina` 早就接进了常驻循环（`fundflow-sina`），
2026-09-30 20:50 还在成功记账，表里两天各约 5,570 行。

怎么查（对任何一格读数都适用，10-06 实测这套动作能抓出来）：

| 步骤 | 命令 | 看到什么算有问题 |
|---|---|---|
| 1. 找出页面里的**字面量读数** | `grep -n "available\": False\|还没有\|空表" vr/jobsboard.py` | 任何一句"业务判断"是字符串常量而不是从 state/库读的。**命中要分诊**（⚠️ 这里原本抄的是 `:331` / `:678` 两个行号 —— 中段一插代码就全漂，10-18 实测那两行已经是别的语句，改成按内容认）：带 FT/`config.job` 注释那一支的 `available=False` 是**真的**（那些旧登记在本进程确实没有执行体），阶梯模块导入失败、读数异常那两支也是真的；只有"某条循环还没跑过所以 `available=false`"那种**把没记账说成没执行体**的才是旧假话。判据只有一条：这句话旁边有没有 `state.json` / 库里的读数撑着 |
| 2. 拿 `state.json` 对照 | `python -X utf8 scripts/jobs.py status` | 页面说没执行体，而那一格有 `last_ok_at` ⇒ 页面在编 |
| 3. 拿库对照 | `select max(trade_date), count(*) from market_data.fund_flow_rank` | 页面说空表而库里有数 ⇒ 同上 |
| 4. 看代码路径 | 那一行是不是 `_recorded_job(...)`/`_file_job(...)` 这类**现读现说**的构造 | 手写 dict 就是嫌疑对象 |

10-06 复核结果：`scripts/jobs.py status` 现在报 `fundflow 最近成功 2026-09-30 20:50:55`、
`coverage 18:54:01`、`tdx_watch 19:08:37`（并在 19:16:50 记了一次真实失败，原话见下）；
`vr/jobsboard.py` 里那条手写的 `fundflow` 假读数已经换成 `_recorded_job` 现读现说。

**为什么 `tdx_watch` 那条失败是好消息**（19:16:50 原话）：

> 通达信没在跑 —— vipdoc 不会再刷新，收盘链的 ③b（TQ 直取）也要它登录着才有数；自愈没接，需要人到电脑前开一次

这就是 06 页"通达信三条硬要求"第 1 条要的读数：只探测、出声、留下可查记录，
**探测期间没有任何进程被起、没有任何窗口被关闭**。用户如果不想让网站进程一直看着桌面，
现在能在 `/system`「常驻循环」那一格里关掉它（见下面 §十二）。

## 十四、面板上关掉一条循环，怎么知道它真停了 ✅ 判据 / ⬜ 端到端未跑

**先看这一格，别看 `enabled`**：`/system`「常驻循环与定时任务」每行有个徽标 ——
`关掉即时生效` 或 `要重启才停得下来`。10-08 逐条读循环体：9 条里只有 5 条每轮重读开关
（`intraday`、`newswire`、`daily-close`、`watchtower`、`ths-cloud-sync`），
另外 4 条（`watchlist-sync`、`fundflow-sina`、`coverage-precompute`、`tdx-watch`）的
`_*_enabled()` 只出现在 `_start_*` 里 ⇒ **关掉后当前进程照跑到重启为止**。

| 怎么验 | 判据 |
|---|---|
| 关掉一条"即时生效"的循环 | `POST /api/jobs/loops {"key":"news","enabled":false}` → 30 秒内 `state.json` 的 `news.last_run_at` 不再前进 |
| 关掉一条"要重启"的循环 | 同一动作后 `last_run_at` **继续前进**（18:20 那条 coverage 就是这样）⇒ 这不是坏，是没重启；重启后才会停 |
| 声明与源码到底一致不一致 | `pytest tests/test_self_heal_inventory.py -k 即时生效` 两条源码级判据（说要即时的，循环体里必须有 `*enabled(`/`settings(`；说不要即时的，必须没有） |
| 频度选错 | `run_freq=weekly` 而 `weekly_days` 空 ⇒ 面板那行出现「每周但没勾周几 ⇒ 现在实际是天天跑」；宿主侧仍照跑（配置写坏了不该让循环静默停产） |

⬜ **端到端那条"关掉后照跑"今天没有在真进程里演**：要演就得关掉 `coverage`/`watchlist` 之类
再等一个心跳，而这台机器上另有会话正在按心跳读这些读数。已做的是**判据本身**（徽标 + 源码级测试 +
`switch_effect` 逐行读数）。真验证点：下一次重启 8910 之后，关掉 `tdx_watch`，
看 `state.json` 的 `tdx_watch.last_run_at` 是否停 —— 停了才说明"每轮重读"那条改动真的补上了。

⚠️ 本节 10-08 那句"9 条里只有 5 条每轮重读"两个数都已过期（在册现为 **12 条**、每轮重读 **8 条**，
且当初少数了 `pg-backup`）。逐条名单与行号以 [12 §七](12-定时任务全景.md) 为准，
真正说了算的是 `vr/jobsboard.py::LIVE_SWITCH_LOOPS` / `DEAD_UNTIL_RESTART_LOOPS` 那两份集合。

## 十五、消息推送：四种坏法（10-15 现跑，配置指向临时目录、**全程没有真发一条**）

细则与判据在 [14-消息推送渠道与定时计划.md](14-消息推送渠道与定时计划.md)，本节只管"弄坏它该亮起什么"。
复现方式：把 `VIBE_NOTIFY_CONFIG`/`VIBE_NOTIFY_HISTORY`/`VIBE_NOTIFY_SENT` 指到临时目录再调
`notifyconfig` / `duanxian.notify`（**别不设就跑**，那会写进真的 `<data home>/notify/config.json`）。

| 弄坏什么 | 该亮起什么 | 今天原样输出 |
|---|---|---|
| 渠道 URL 前缀写成另一类（把飞书填成 `dingtalk://`） | 保存当场 400，句子带**实际收到的前缀** | `g1（飞书群助手）的 URL 前缀不对：应以 feishu:// 开头，收到 'dingtalk'` |
| 选了"每周"却一个周几都没勾 | 写入面直接拒，并把"不勾会怎样"说出口（**比宿主严**） | `选了每周就必须勾至少一个周几 —— 不勾的话按「判不了就放行」会天天发，与你的选择相反` |
| 时刻写成 `9:5` | 拒收而不是归一后偷偷存（`_norm_time` 只在合法形状上归一） | `p1: 时刻要写成 HH:MM（24 小时制），收到 '9:5'` |
| `url_env` 指向一个 `.env` 里根本没有的变量 | 渠道 `has_secret=false` + 一句指名道姓的缺因，掩码格是**空串**不是 `******` | `配置里写的是 FEISHU_TOKEN_NOT_SET_ANYWHERE，但 .env 与环境变量里都没有这个变量` |
| 真凭据会不会被读出来 | 交出去的只有 `******` + 尾 4 位；把整份掩码结果序列化后查原 token 是否在里面 | `url_masked: ******bbbb` ／ `这一格有没有真 token： False` |
| 渠道删掉、计划还留着那个键 | `sendable=false`、该行 `channels` 里 `exists=false`；**注意 `invalid_reason` 是 `None`**（配置本身合法，坏在引用）—— 所以判"发得出去吗"必须现算，不能存字段 | `sendable: False \| channels: [{'key': 'g1', ..., 'exists': False, 'usable': False}] \| invalid_reason: None` |
| 到点执行时一个渠道都不可用 | **不会**拿空 URL 去调 apprise：`send_to` 直接 `ok=false` + `"没有可用渠道，未发送"`，逐条缺因进 `skipped`，失败照样 `record` 进 `notify_push` 与历史 | 预览那格同形状：`would_send_to: ['g3'] \| blocked: ['g1：配置里没有这条渠道（可能被删了）']` |
| 在 pytest 进程里真发 | 两个出口各自硬挡（机器人 `_post_json`、邮件 `_apprise`），抛 `RuntimeError` 并被 `deliver` 收成一句逐渠道 `detail`（不会带崩测试，也不许有一条真出门） | `pytest 进程里不许真发消息 —— 请 monkeypatch duanxian.notify._post_json` |
| **对面回 200 但没送达**（10-16 改造的核心） | 三个机器人都自己 POST 并读 JSON 回体：`code`/`errcode` 非 0 就判失败，并把对面的 `msg` 原样带出来 | 假 token 实测：`panel-check：没发出去 —— 回体说没收到（code=19001，param invalid: incoming webhook access token invalid）`（改造前这一格显示的是「1 个渠道已交付」） |
| 一次发送挂住把心跳拖长 | `_post_json` 自带 `SEND_TIMEOUT_SEC = 10` | 用例 `test_发送有超时不许把心跳挂住` 直接核对传进 `urlopen` 的 `timeout` |

### 补：迟到窗口那两格（10-15 当晚加的，同一套探针现跑）

| 弄坏什么 | 该亮起什么 | 今天原样输出 |
|---|---|---|
| 让宿主"错过那一分钟"（模拟：慢发送/重启把 `09:05` 整分钟吃掉） | 到点后 **15 分钟内**仍算这一档该发（`notifyconfig.LATE_WINDOW_MIN`）；过窗就**不再补** | `09:04 -> False ／ 09:05 -> True ／ 09:20 -> True ／ 09:21 -> False` |
| 错过了却没人说得清 | 每条计划交 `today_state` + 一句人话（八档：`off`/`bad`/`not_today`/`not_trade_day`/`sent`/`waiting`/`in_window`/`missed`），判据与执行同住 `slot_state`，**面板只渲染不改写** | `[waiting] 还没到点（09:05，还有 5 分钟）` ／ `[in_window] 到点了、还没发（5 分钟前那一档）⇒ 下一轮心跳就补` ／ `[missed] 错过：09:05 那一档已过补发窗口（25 分钟前）而今天没发过 —— 要补用「立刻发一次」，宿主不会自己追` ／ `[sent] 09:05 那一档今天已经发过` |
| 把"窗口"顺手当成"自动重试" | **不是重试**：发失败也当天记一笔，窗口内下一分钟不再发；只有「立刻发一次」能绕过 | `9:05 那次：fail \| pytest 进程里不许真发消息…` → `9:12（仍在窗口内）due_plans -> []` → `立刻发一次（force） -> fail`；`sent.json` 那一格是 `{"p1:2026-10-15": {"at": "2026-10-16 10:29:17", "ok": false}}` |

## 十六、界面动作挂着 `need_human`：哪件真要人做、怎么做完让它闭账（10-18）

每一次"程序动了你的桌面"都记在 `duanxian/gui_trail.py` 那本账上（状态四档 `done/skipped/failed/need_human`），
页面上「系统配置 → 待人工清单」读的就是它。三条规矩与 10-18 修掉的两个谎：

1. **手动做法只住一处**：`gui_trail.MANUAL[step]`。10-18 之前 `reap_plugin_shell` 没有这个键，
   于是屏幕上念的是兜底那句「这一步没有登记手动做法，见 07」—— 而那恰恰是最需要教人点哪一格的步骤
   （桌上杵着一个黑色 cmd 窗口，谁都怕那是还在跑的东西）。现在补了键，**本节不复述内容**，
   要看做法直接在页面上点那一步的「怎么做」，或读 `duanxian/gui_trail.py` 里那条串。
2. **`need_human` 不会因为后来成功就自己消失**（这是有意的：人做没做程序不知道）。
   要闭账只有两条路：后来的 `done` 带 `supersedes=True`（＝这件事程序自己做完了），或人在清单里勾掉。
3. 10-18 实测到的两个谎，都已修：
   - **收空壳那一步的"复核"用的是杀之前的快照**。`server.py` 调 `shells.reap(probe=lambda: found)` 时，
     `after` 默认等于 `probe`（`app/tdx_client/shells.py:74`），于是"重探"返回的还是杀之前那一份进程表，
     被杀的 pid **必然**出现在 `left` 里 → 每晚记一条「这几个发了关闭请求但还在（pid ×××）：需要人工看一眼」。
     实测 pid 3896 早已不在（`Get-CimInstance Win32_Process -Filter "ProcessId=3896"` 空），账还挂着。
     修＝调用点显式传 `after=shells.find_plugin_shells`（收完真重探，接受多一次 PowerShell 的成本）。
   - **"这一轮没有壳"那一档不写台账**，所以那条 fail/连败没有东西能覆盖它：`_reap_plugin_shells()`
     在 `not found` 时直接 `return None`。修＝**只在有旧账要平的时候**补记一笔 `ok` 并交一条
     `done + supersedes=True`（两分钟一轮的空白轮不写，免得把台账刷成「没有壳」）。
4. 「我发了关闭请求」不等于「已关闭」—— 这一族判据（关窗、杀进程、收壳）**必须重探真实对象**，
   拿动作前的快照复核等于没复核。同族已修的先例是 `close_pids` 假成功（见 [05-踩坑与经验清单](05-踩坑与经验清单.md)）。

# 全量四条状态（含已经做完的）用 items()

| 说好了自动跑却没跑 | 「收盘链自动开关」（谁关的、有没有署名） | `GET /api/jobs/chain` 的两段 `enabled`/`next_attempt_at`/`today_will_run` |
| 改了码像没生效 | 「常驻循环完整性」（磁盘清单 vs 进程自报） | `scheduler.host_loops` 的清单，**别看 state.json 时间戳** |
| 子作业像失败却又说不出 | `jobs/state.json` 里该作业的 `last_error` + `reason` | 体检「外部路径引用」（路径指向不存在的位置，rc 长得像业务失败） |
| 局域网对面连不上 | `/api/net` 的 `denials`（对面实际以哪个 IP 进来） | 是不是没重启换绑定；防火墙有没有放行 8910 |
| 明明在面板上关了，它还跑 | 那一行的徽标是不是「要重启才停得下来」（§十四） | `state.json` 里这格的 `last_run_at` 还在不在前进 |
| 服务自己起来了，怀疑有东西在后台动手 | 体检「外部计划任务」现在连**本项目自己**注册的一起列（§十三） | `.local\keepalive.log` 那几行判定 |
| 说好几点推给群的消息没来 | `/api/notify` 那条计划的 **`today_label`**（`waiting`/`in_window`/`sent`/`missed`/`not_today`/`not_trade_day`/`bad`）—— 先分清"还没到 / 正在补 / 错过了 / 今天不该跑" | 再分渠道：`sendable` 与逐渠道 `blocked`（渠道被删、密钥变量不见了是两类不同的坏）；`notify/history.jsonl` 有没有那一档的行 —— **过窗而没行 = 压根没执行**（10-15 起 15 分钟内仍会补，见 14 §六） |
| 页面显示"就绪"却什么都没收到 | 是不是拿存下来的字段判的 —— `sendable` 与 `invalid_reason` 必须每请求现算（§十五第 6 行） | `<data home>/notify/sent.json`：失败也记，所以"今天不再自动重发"是设计，重发用「立刻发一次」 |
