# 03 · 任务调度页契约（`/jobs` + `GET /api/jobs`）

> 用户原话：**"还要有『任务调度大全』这样的管理页面。"** 参照物是 FinanceTool 的 `/jobs`（18420、只绑本机、有"立即触发"按钮）。
> 采集类作业的后端与前端**都在 YuanShan 内**（2026-09-24 终态裁定：没有"另一边"，只有搬没搬完）；本页形状以本文为准 —— **改字段先改本文，再改代码**。
> 前置纪律：[01-数据口径展示规范](01-数据口径展示规范.md) 全部适用，本文只写调度特有的部分。

## 0. 为什么这页必须存在（不是"再做一个 dashboard"）

FinanceTool 那次事故是这页存在的唯一理由：**`ops.schedule_state.note` 13 个作业全写着"调度器总开关未打开"，页面上看不出来，跑了三天才发现一条都没落库。**

所以这页的本职不是"显示一堆作业"，而是回答一句话：**今天的数据到位了吗？没到位的话卡在哪一环？** 任何让这个问题变得不明显的设计都是失败的设计。

三条贯穿全文的判据：

1. **判据只认数据日期**，不认"上次跑过"、不认墙钟时间、不认状态栏颜色。
2. **"没跑"、"跑了没写"、"写坏了"、"取不到"是四件不同的事**，页面上必须长得不一样。
3. **红不能成为噪声**。如果每个长假都报"从未运行"，用户就会开始忽略红色 —— 那比没有红更糟。

## 1. 位置与入口（本会话定的，理由写死防止被改回去）

- 路由 **`/jobs`**，标题「任务调度」，放在**侧栏底部运维区**、与「接入 AI」并列（`Layout.tsx` 底部那一格）。
- **不进七个一级模块**（`lib/workspace/modules.ts` 的 `MODULES`）：`test/modules.test.ts` 断言一级模块标题序列恰好是那 7 个；调度是运维入口，不是工作流阶段，混进去既破测试又误导用户。
- **不进 `lib/workspace/features.ts` 的 `FEATURES`**：`test/workspace.test.ts` 断言该列表**等值**于固定 14 项。加首页卡片需要先改那条断言，别偷偷加。
- 允许（且需要）在 `router.tsx` 加路由：`workspace.test.ts` 对路由是**包含**断言，加一条不破。

## 2. 顶层形状

```jsonc
{
  "generated_at": "2026-09-24T23:40:00+08:00",   // 必填。页面据此显示"本快照 X 秒前"
  "scheduler": {
    "enabled": false,            // 总开关。false 时**一切 never_ran 都重新解释为"未调度"**
    "dry_run": true,             // true 时成功也要标"试跑（已回滚）"，不许显示"成功"
    "host": "ft-scheduler",      // 宿主进程是谁：ft-scheduler | yuanshan-uvicorn | windows-task
    "pid": 28600,                // 拿不到就 null，不许填 0
    "started_at": null,
    "heartbeat_at": null,        // 最近一次心跳；与 generated_at 之差 = 调度器多久没说话
    "note": "调度器总开关未打开"   // 原样显示，不美化
  },
  "scheduler_available": true,   // false = 读不到调度器状态（与"调度器关着"是两件事）
  "scheduler_reason": null,      // available=false 时必填
  "jobs": [ /* §3 */ ],
  "jobs_available": true,        // false 时 jobs 可为空，但必须带 reason
  "jobs_reason": null,
  "truncated": false             // 作业过多被截断时必须 true，并交出 total
}
```

`jobs_available=false` 时页面显示"读不到作业清单 + 原因"，**不许**渲染成"当前没有作业"。

## 2.1 顶层 `scheduler` 的适用边界（2026-09-25 补，后端已按此实现）

**`scheduler{}` 只描述本进程宿主（`host:"yuanshan-uvicorn"`）**，不是全局真值。理由：`jobsView.ts` 第 6 级用 `scheduler.enabled===false` 会把**所有**作业判成「未调度」，而这一页同时装着两类东西 —— 本进程真在跑的（快讯、盘中快照、备份）与只登记在 FinanceTool `config.job` 的（实测 36 条）。用全局开关解释后者，就会出现"本进程作业在跑却显示未调度"。

因此：**非本进程的作业一律 `available=false` + `reason`**，由 §4 第 2 级接住（第 2 级在第 6 级之前，且此时不显示 state，正好避免两套口径）。它们仍带 `origin:"financetool"` + `runner:"ft-scheduler"`，页面上要能看出"这不是我们的作业，是被吸收进来的登记"。

FinanceTool 调度器的真相**从它自己的心跳表读**（`operations.scheduler_heartbeat`），别再写"从未跑过"——2026-09-25 实测：`role=scheduler` 心跳每 ~3 秒推进、`meta.enabled=false`、`dry_run=true`、`fired=0`、`jobs=16`。**进程活着，只是每个 tick 只发心跳不入队**；这两句话对用户的动作完全不同。

## 3. 单个作业的字段（★ = 必填；☆ = 强烈建议，缺了界面会降级）

| 字段 | 类型 | 说明与 NULL 语义 |
|---|---|---|
| ☆ `origin` | `yuanshan-ingest\|yuanshan-compute\|financetool` | 2026-09-25 新增：这项**归谁跑**。决定 state 该由哪个开关解释 |
| ☆ `runner` | `yuanshan-uvicorn\|ft-scheduler\|none` | 2026-09-25 新增：执行体所在进程。`none` = 本地计算尚未覆盖该项 |
| ☆ `basis` | str | 2026-09-25 新增：这些数**从哪算出来的**。例：快讯的 `last_run_at` 现在取自"文件侧证据（news/ 最新产物 mtime）"，因为采集循环还没写 `jobs/state.json` —— 有依据就必须写依据，不许看着像 state.json 出来的 |
| ★ `key` | str | 稳定标识，按钮与日志都用它 |
| ★ `name` | str | 人读的名字（"快讯采集"） |
| ★ `entry` | str | **只当说明文字**，前端不渲染成命令、后端不得据它执行 |
| ★ `state` | str | 见 §4 的取值全集 |
| ★ `enabled` | bool | 作业自身开关（与总开关分两层） |
| ★ `available` / `reason` | bool / str\|null | `available=false` 时 `reason` **必填**（01 §1） |
| ★ `schedule_kind` | `interval\|cron\|trade_day_after_close\|event\|manual` | 机器可解的调度种类 |
| ☆ `schedule_spec` | str | `"30s"` / cron 表达式。人读串 `schedule` 可选保留 |
| ★ `trade_day_aware` | bool | **非交易日不跑算不算正常**。没有它每个长假都满屏假红 |
| ★ `last_run_at` | str\|null | 墙钟时刻。**没有跑过就是 null，不许填 epoch/空串** |
| ★ `last_ok_at` | str\|null | 与 `last_run_at` 分开：跑过但没成功，前者有值后者 null |
| ★ `consecutive_failures` | int\|null | null=未知；0=没有连续失败（**不等于跑成功过**） |
| ★ `last_data_date` | str\|null | **本次落库覆盖到的交易日**（FT 的「上次交易日」列）|
| ★ `expected_data_date` | str\|null | 按交易日历该到哪天。拿不到就 null，界面不自己算 |
| ☆ `days_behind` | int\|null | 两者之差（交易日数）。null 表示算不出，**不是 0** |
| ★ `next_due_at` | str\|null | 下次应在何时跑。30 秒轮询"卡死"与"刚跑完"全靠它区分 |
| ☆ `overdue_seconds` | int\|null | 服务端算好的逾期量，避免前端各拿各的钟 |
| ★ `last_error` / `last_error_at` | str\|null | 末次错误原文（不截断、不美化） |
| ☆ `run_history[]` | `{started_at, finished_at, outcome, rows_written, error}` | `outcome` ∈ `ok\|error\|no_data\|rolled_back\|skipped`。**没有它，`never_ran` 与"跑了但 0 行"在页面上永远分不开** |
| ★ `counters` | obj | 见下 |
| ★ `counters.scope` | `per_run\|cumulative` | 不给窗口的计数是没法读的 |
| ☆ `counters.since` | str\|null | cumulative 时给起点（时间或游标） |
| ☆ `counters.total_seen` | int\|null | 让 `written+already_had+dropped` 有可核对的分母 |
| ★ `counters.unit` | `"条"\|"行"` | 数值保持数值类型，**前端不做二次格式化**（01 §3） |
| ☆ `cursor` | obj | 各源游标原样交出 |
| ☆ `cursor_meaning` | str | 一句话解释游标是什么，否则页面只能打印一串裸数字 |
| ★ `source_health[]` | `{source, ok, last_err, last_ok_at, consecutive_failures}` | 部分源挂不能把整个作业显示成绿 |
| ★ `sink_health` | `{writable, last_err, targets[]}` | **下游**。`qd.news_item` 当初 0 行的成因在 sink 不在 source；`targets` 就是 FT 的「落到哪些表」列 |
| ☆ `lock_state` | `idle\|held\|contended\|stuck` | TQ 是单连接串行锁，**锁卡住=最典型的"看起来都在排队"** |
| ☆ `lock_held_by` / `lock_waited_ms` | str / int | stuck 时必须能说出谁占着 |
| ★ `run_preview` | obj | 见 §5，按钮的安全依据 |
| ☆ `basis` | str | 统计/结果出自哪里（如 `qd 基准表` / `本地重算缓存`） |

## 4. `state` 判定顺序（前后端共用同一份，禁止各自解释）

自上而下第一个成立的即是结论。前端**只按这个顺序出标签**，不再自己判一次。

1. `jobs_available=false` → 「作业清单不可读」+ `jobs_reason`
2. 该作业 `available=false` → 「不可用」+ `reason`（此时**不显示** state，避免 state 与 reason 各说一套）
3. `scheduler_available=false` → 「调度器状态未知」
4. `lock_state=stuck` → 「锁被占住」（最高优先级的真故障）
5. `enabled=false` → 「已停用」（作业自己关的）
6. `scheduler.enabled=false` → 「未调度 —— 总开关未打开」
7. `last_run_at=null && next_due_at=null` → 「从未运行」← **fundflow 的刚需，样式最重**
8. `consecutive_failures>0` → 「连续失败 N 次」
9. `trade_day_aware && last_data_date < expected_data_date` → 「数据落后 N 个交易日」（红）
10. `state=running` → 「运行中」；其余按后端 `state` 直出

两条不许：
- **不许把 `days_behind=null` 显示成"不落后"**，要显示「数据日期未知」；
- **不许用颜色代替文字**（色盲 + 截图丢失语义），每个结论都要有中文标签。

## 5. 手动触发（`POST /api/jobs/<key>/run`）

1. **互斥**：同作业已在跑 → **409 + `reason`**，页面显示"该作业正在运行，本次未触发"。快讯有游标，并发跑会双写。
2. **异步**：立即返回 `{run_id, status:"queued"}`；前端轮 `GET /api/jobs/<key>/runs/<run_id>`（或复用 `run_history`）。同步等会让页面看起来卡死。
3. **`run_preview` 必须在 `GET /api/jobs` 里就带着**，二次确认弹窗要写清：
   `outbound_hosts[]`（这次会向哪些域名出网）、`writes`（写哪个文件/哪张表）、`touches_db`、`est_seconds`。
   纪律 4 的原文是"**别让人误点成刷新缓存**"——光靠一句警告挡不住人，只有"会出网 + 会写这里"看得见才挡得住。
4. 按钮不得出现在 `enabled=false` 或 409 之外的禁用原因不明的作业上；禁用必须有 `reason`。

## 6. 界面纪律（页面侧硬约束）

- 顶部**调度器横条**先于一切作业卡渲染；`scheduler.enabled=false` 时整页罩一层提示，并按 §4 重新解释每个 `never_ran`。
- **`never_ran` 用最重的样式**（整卡描边 + 大标签），因为它对应"当天不采就永久没有"这类不可回补损失。
- 空值一律 `—`；`0` 只在真是 0 时出现。`written/already_had/dropped` **不合成"重复率"百分比**（没有那个字段就不发明）。
- `dry_run=true` 的成功显示「试跑（已回滚）」—— 沿用 FT 的判断：`dry_run` 是真执行 + 强制回滚，跳过写库的代码路径不是同一条。
- 配色必须走 `lib/colors.ts`；调度语义与涨跌无关，用 `primary/muted` 系，不得直写 `success/danger`。
- 外链/原文按钮一律 `target="_blank" rel="noopener noreferrer"`。

## 6. 「调度器」这个词只有一个页面配叫它，而那个页面不是任务调度页（2026-10-07 补）

用户 2026-10-07 问：「是不是有一大堆的定时任务，这块内容在系统配置里吗？是不是叫做调度器？」
—— 这个问题问得准，因为本机 **`调度器` 三个字同时被用在五件不同的东西上**（逐条对照见
[系统配置/05 §4b](../系统配置工作指南/05-调度宿主.md)）。从展示侧固定三条：

1. **"有哪几条循环、各自什么时候跑、开关在哪"这张卡的归属是 `/system`（系统配置）**，
   组件 `frontend/src/components/LoopSwitchboard.tsx`，读 `GET /api/jobs/loops`。
   `/jobs`（任务调度页）继续做它本来做的事：**每个作业的历史读数**（最后成功、落库日期、锁、
   手动触发），不再重复一遍开关 —— 两处各一套开关就是 09-28"被关三次"的形状。
2. `/jobs` 顶部那张卡的标题**不叫"调度器"**，写的是"本进程宿主的循环"之类的事实句；
   旧项目那 36 条 `config.job` 登记一律 `available=false + reason`，页面上必须看得出
   "这是被吸收进来的登记，不是本进程在跑的"（§2.1 那条不变）。
3. 常驻循环的条数**由 `vr/jobsboard.py::LOOP_JOBS` 决定，界面不许写死**。
   10-07 从 7 条变 8 条（补进 `watchtower`）时，写死 7 的断言一次红了三处；
   现在 `test_jobsboard.py` 判的是 `len(loops) == len(LOOP_JOBS)`，加一条只改注册表。

⚠️ 展示侧仍然不回答"这条循环到底在不在"—— 那只看 `/api/jobs` 的 `scheduler.host_loops`
（进程自报），别拿 `state.json` 的时间戳推。这一条与《系统配置/06》判据①是同一件事。
