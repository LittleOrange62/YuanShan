## 1. 要回答的两个问题（分开，别合成一个数就完事）

1. **趋势形成度**：这个板块的涨幅/热度，是"有点斜率但随时会翻"，还是"短中长同向、广度跟得上、量能配合"？
2. **低吸候选**：如果是左侧交易，**刚转那一瞬**在哪 —— 位置低、趋势刚由负翻正、且没被资金追到高位。

合成一个分数就看不出是哪一项在起作用，所以界面**分项全列 + 最后一列才给档位**。

## 2. 判据草案（这就是要写进界面"逻辑"那块的内容）

记号：`H_t`=热度、`S_w`=窗口 `w` 的最小二乘斜率（分/天，库里现成）、`P_t`=板块收盘、
`R_t`=当日热度排名、`U_t=up_count/member_count`=广度、`V_t`=量能比（5 日均量比）。

**参数默认（都进 `config.setting['sector_trend_signal.params']`，界面顶部要能看见当前值）**
`W_SHORT=5`、`W_MID=11`、`W_LONG=21`、`MIN_POINTS=0.7×W`、`POSITION_LOW=0.35`、`TURN_LOOKBACK=3`、`BREADTH_MIN=0.55`

**分项（每项 0~100，缺数据交 NULL 不给 0）**

| 分项 | 公式 | 为什么这么切 |
|---|---|---|
| `dir_agree` 方向一致 | 三窗口斜率同号 → `3×`，两同号 → `1×`，否则 0；再按 `\|S\|` 是否超过该板块自身斜率分布的 60 分位加成 | 单窗口斜率一根插针就能翻；短中长同向才是"成形状"，这是趋势是否成立的第一判据 |
| `persist` 持续性 | 窗口内 `H` 逐日抬升的天数占比（`up_days/W`），或 `S_mid` 连续为正的场次 | 斜率说方向，持续性说这个方向保持了多久 —— 左侧要的是刚起步，不是第 20 天 |
| `breadth` 广度 | `U_t` 与 `U` 的 5 日均值，`<BREADTH_MIN` 直接判"普涨没起来" | 板块涨幅能被 3 只权重股拉起来；广度不跟上，趋势是虚的（本库已有 `up_count/down_count/member_count`） |
| `volume_ok` 量能 | `V_t` ∈ [1.0, 3.0] 给满分，>3.0 **反而降分** | 温和放量是资金进场，3 倍以上是一次性情绪，趋势持续性最差 |
| `position` 位置 | `pos = (P_t − min_{W_LONG}) / (max_{W_LONG} − min_{W_LONG})`；`heat_pctile` 作为热度维度的同类分位 | **低吸的核心就是位置**：同一套方向判据，pos 0.9 是追高、pos 0.2 才是低吸 |
| `rank_momentum` 排名动量 | `R_{t−k} − R_t`（k=5），排名在往前挤才给分 | 板块之间是零和的：它不涨排名不代表资金进来了 |

**档位 `regime`（互斥、按顺序判，先命中先定）**
1. `insufficient` 点不足：任一窗口 `point_count < MIN_POINTS` → **不给档位**，界面显示「数据不足」，不猜。
2. `downtrend` 退潮：`S_mid < 0` 且 `dir_agree` 为负向一致。
3. `turn_up_seed` **刚转（低吸主看这一档）**：`S_short > 0` 且 `S_short` 在 `TURN_LOOKBACK` 天内由 ≤0 翻正，且 `position ≤ POSITION_LOW`，且 `breadth ≥ BREADTH_MIN`。
4. `forming` 趋势形成中：`dir_agree` 三窗口同正 且 `position ≤ 0.6`。
5. `established` 已确立：`dir_agree` 三窗口同正 且 `position > 0.6`。
6. `overheated` 过热：`position ≥ 0.85` 且 `heat_pctile ≥ 0.9`（或 `V_t > 3`）。

**`dip_score` 低吸分（0~100，只在 `turn_up_seed`/`forming` 下有意义）**
`dip_score = 0.35·刚转新鲜度 + 0.25·(1−position) + 0.20·breadth + 0.10·volume_ok + 0.10·rank_momentum`
权重必须上界面显示，且**明写这是可商量的先验、不是市场规律**；调权重要能改 `config.setting`，不许硬编码在页面里。

## 3. 落库表（⚠️ 归属待定，见 §5）

```sql
-- 名称按现有习惯放在 analytics；如果裁定归 ys schema，我只改前缀不改逻辑
create table if not exists analytics.sector_trend_signal (
  sector_code   text        not null,
  trade_date    date        not null,
  window_set    text        not null,      -- '5/11/21'：参数集指纹，换窗口就是另一批结论
  dir_agree     numeric(8,3),
  persist       numeric(8,3),
  breadth       numeric(8,3),
  volume_ok     numeric(8,3),
  position      numeric(8,3),
  rank_momentum numeric(8,3),
  dip_score     numeric(8,3),
  regime        text        not null,      -- insufficient/downtrend/turn_up_seed/forming/established/overheated
  reasons       jsonb       not null,      -- 每个分项的原始输入值，界面上"为什么是这个档"就念它
  missing_terms smallint    not null default 0,
  universe      int,                       -- 当日母体板块数：不交分母，前 N 名没有意义
  spec_version  text        not null,
  calculated_at timestamptz not null,
  primary key (sector_code, trade_date, window_set, spec_version)
);
```

要点：
- **`reasons` 存原始输入而不是只存分数** —— 界面要能回答"凭什么叫它刚转"，事后重算的理由必须与当时一致。
- **`spec_version` 进主键**：判据一改（阈值、权重、窗口）就是新一批行，旧行不覆盖，否则回看历史信号会被今天的参数悄悄改写。
- 全量回算 692×1244 ≈ 86 万行/参数集，按现有 `app/compute/` 的批处理风格做，别放接口请求路径里算。

## 4. 三个坑，现在不说清楚就会变成假信号

1. ⚠️ **自选板块的历史趋势是未来函数**。`config.watchlist_stock` 只有当前成员，
   没有每日快照 → 拿今天的成员去回算 6 月的组涨幅，等于"用未来知道的名单做过去的决定"。
   两条路选一：**(a) 从今天起每日快照成员**（组趋势要攒够窗口才有，21 日趋势要 21 个交易日之后才有）；
   **(b) 回算但显式标注"以今日成员回算，不可用于回测/胜率统计"**。我倾向 (a)+(b) 同时做，界面上分开显示"实盘序列"与"回算序列"。
   注意 `reference_data.sector_member` 有 `in_date/out_date`（真时点），**通达信板块没这个问题，自选板块有**。
2. **母体口径要钉死**：`sector_type` 里 概念/行业/风格/指数/自定义/地区 混在一起，
   而"昨日涨停 / 突涨"这类是**行为统计板块不是题材板块** —— 参与排名会把"资金在往哪走"读成"谁涨了"。
   建议母体默认 = 概念 + 行业（+ 风格可选），其余单独一档列出、不进排名分母，界面把 `universe` 交出来。
3. **`window_days=1` 不是斜率**（它是日趋势分值，`point_count=2`），别和 21 日斜率放进同一个"强度"比较里；
   点数不足的行一律 `insufficient`，不补 0（这条 `analytics.sector_trend` 的注释里已经写了，沿用）。

### 实测抓出的两处判据错误（都是"看着能用、其实误导"那一类）

1. **`sts-1`：把横截面名次当"自身热度分位"用进过热判据。**
   `heat_pctile` 取了「当日热度在全体板块里的名次 / 母体」，于是 **369 行被判 `overheated` 的板块，热度全在当日中位数以下** ——
   最冷的板块被读成过热。修法是改回"自身长窗口分位"（与 `analytics.ignition.detail._q_heat` 同口径），
   横截面名次只进 `reasons.heat_rank` + `universe`，不进档位。
2. **`sts-1`：`dir_agree` 得分含强度分，档位从得分反推方向。**
   三窗斜率 `[+2.10, -13.06, +0.65]`（中线明显向下）拿到 60 分，被判 `forming`（"三窗口同向"）。
   修法：`_dir_agree` 另外返回 `同向数`，档位在 `pos_n == 3` 这种硬条件上判，**不许从得分反推**。

两条都把判据版本升到 **`sts-2`**：`spec_version` 在主键里，所以 `sts-1` 的 15,559 行原样留着，
`GET /api/quant/sector-trend?spec=sts-1` 仍可读 —— **这就是版本进主键的意义：历史上哪天被算成"刚转"，不会被今天的修正改写**。
`dip_score` 口径同步更正：权重本身就是百分数，不再除以在场权重（除完变成 0~1，读起来像"几乎没有低吸价值"）；
缺项按 0 计入，同时交出 `reasons.dip_score_ceiling` 说明这一行的上限只有多少。

## 7. 界面侧的三条口径（09-26 与计算侧对齐后）

1. **`overheated` 念出来必须带名次**：它是"在自己 21 日区间的顶部"，不是"今天全场最热"。
   档位表里过热行旁边直接印 `当日 479/561`，悬停写明口径；`reasons.heat_rank` 只作事实陈列。
2. **母体由后端说**：`/api/quant/sector-trend` 交出 `universe{sectors, active_total, note}` ——
   `sectors` 是当日有热度行的板块（某场 561 = 行业 293 + 概念 268），`active_total` 是 active 的概念+行业（1,907）。
   两个数差 3 倍以上，不交出 `note`，"前 N 名"就会被读成在 1,907 个里选。
   后端没交时界面退回**标注为人工实测**的那句，不伪装成接口结论。
3. **7 档不是 6 档**：`no_shape`（点数够但没形状）与 `insufficient`（数据不足）是两件事，界面各给独立标签与颜色。

**取生效判据版本**：读 `config.setting['sector_trend_signal.params'].spec_version`，**不要用 `max(spec_version)`** ——
字符串比较下 `sts-1 < sts-10 < sts-2`，出现两位数版本号就会把旧版当最新端出去。

**快照不是按钮**：`app/compute/sector_trend_signal` 每次真跑先把当日自选名单幂等存进
`reference_data.watchlist_member_snapshot` 再算（漏一天就少一天，事后补的只是"今日名单"=未来函数）；
这条执行路挂在 `ingest/jobs/e1_fill_all.py` 的 `signal` 步（非骨干；10-18 现读是第 37 步、整链 41 步，序号会随加步漂，引步名不引序号）。
`ys.watchlist_member_snapshot`（**10-18 现查仍 0 行**）是历史双写残留，**界面不读它**；删不删等《数据获取》确认 `duanxian/watchlist_sync.py` 的指向后再定。
## 9. 快照表的来源问题（09-26 实测，界面已把判据做进去）

`reference_data.watchlist_member_snapshot` 本节写下时只有 5 天（09-02(1,095) · 09-14(1,114) · 09-16(1,221) · 09-22(1,259) · 09-26(1,283)）；**10-18 现查 18 个不同交易日、2026-09-02 → 2026-10-16** —— 因为快照改成了"每次真跑先幂等存一遍"（上面那条纪律），链跑一天就长一天。
**它们不能当实盘序列**，判据是单调性检查（`/api/quant/sector-trend` 的 `groups.live_trustworthy`，界面直接念）：

- 每一天都是**今日成员集的真子集**，且人数逐日单调不减（`它有今日没有的 = 0`）；
- `config.watchlist_stock` 只有 `added_at`，**没有任何"移除"记录** —— 按 `added_at` 反推历史必然只增不减；
- 这与总协调量到的漂移方向一致（09-14→09-16 +110/−0，三周只加不删）。

所以这五天是 **rebuilt 换了件 live 的衣服**。界面做法：天数照实念，但**红字标"不能当实盘序列用"**，
并把逐日人数摊开让人自己看单调性；`ready` 因此为 false（不是"还没攒够"，是"攒的这些不算"）。
真·实盘只能从下一个交易日起由收盘链在交易日存（非交易日整链 return 2 已经挡住周六那种情况）。
我自己 09-26 那次 `--snapshot-only` 存的一行曾被我误删一次（判它是周六脏数据），已按原样重存 —— 它反而是这五天里唯一"当场抓"的一天。

## 10. 界面侧的排序纪律（总协调 Q5）

**两张榜、两个方向**：档位表按 `dip_score` 降序（谁最像刚转），低吸榜按 `position` 升序（谁还在最低位），
两者都由后端 `sort=dip|seed` 决定，**界面不许自己 reorder** —— 排序本身就是一种判据。
