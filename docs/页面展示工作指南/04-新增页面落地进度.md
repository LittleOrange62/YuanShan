## 踩到的一次假绿（值得写进纪律）

`/quality` 首版按我写的契约壳渲染，实测 `/api/quality` 早就 200，但真返回是：

```
rules_audited = 0, rules_total = 24, rules_blocking = 12,
rules[].passed = null（全部 24 条）, failed = [], last_full_audit = 2026-09-23
```

按"未通过列表为空"渲染，页面会显示「本批没有未通过项」—— 而事实是**本场一条都没审**。
质量闸唯一要防的就是这种"看着正常"。已改成四态分开数、分开筛：

- 通过 / **未通过** / **本场未审** / 已停用（`enabled=false` 先判停用，否则它会被算进"未审"，看着像漏审）
- 覆盖率不满时顶部标警，并把 `last_full_audit` 与接口 `caveat` 原文一起端出来
- `unregistered_results`（如 `backup_daily`）单列，**不参与 24 条的分母**
- 不把历史结果累计成"共未通过 N 条"：结果表存在同一批被重复写入的情况，未去重前相加会凭空放大

## 本轮接真接口时踩到的两个字段坑（写下来免得下一个人再踩）

1. **`/api/quality` 的 `rules[].passed` 是 null**，含义是"本场没审过这条"，不是"通过"。按"未通过列表为空"渲染 = 假绿。
2. **`/api/screen/rules` 的 `presets` 是条数（`0`）不是数组** —— 我第一版按数组写，界面直接印出「用户预置 undefined 条」。
   同接口 `param_schema` 是 **Python dict 的 repr 字符串**（单引号），不是 JSON：前端只原样展示，不 `JSON.parse`。

## 慢接口与缓存的两条页面纪律（09-25 由总协调实测引出）

1. **超时不能白屏。** `probe()` 加了 `SLOW_TIMEOUT_MS = 45_000` 与 `AbortController`：掐断后走 `error` 分支，
   话术是"等待超过 45 秒未返回，已中断 —— 这是后端跑得慢，不是没有数据，点『重新取数』可重试"，
   面板下面的字段契约仍在（用户能判断该重试还是该报后端）。无限转圈与"后端坏了"在屏幕上长得一样。
2. **缓存必须带年龄。** 实测 `/api/coverage` 的 `cache{source,saved_at,age_seconds,is_stale,fresh_within_seconds}`、
   `/api/system/doctor` 的 `age_seconds=8790 / ttl=600 / refreshing=true`、`/api/quant/sector-heat` 的 `freshness{stats_mode,cache_ttl_seconds,cached_or_absent}`。
   只印 `generated_at` 等于把 2.4 小时前的结果摆成刚刚算的 —— 所以统一走 `DataPanel.CacheLine` 与 `datastate.ageText()`，
   并且**超过新鲜窗口要标黄、`refreshing=true` 要明说"下面显示的是上一份"**。
   踩过的坑：我第一版按猜的 `cached: boolean` 写，真实字段是 `cache{}` 对象 —— 结果那句"本轮为缓存结果"**永远不会出现**（假安心）。
3. `cached_or_absent` 这类"哪些键命中了缓存"的结构，后端没解释语义之前**原样 JSON 贴出并声明不替它解释**，不翻译成"新鲜/陈旧"。

## 09-27 · 自选组分析换成"组"这一层的读数（用户点名）

用户原话：「并不需要展示 涨跌未取到的数量，也不需要平均成本。也不需要显示同花顺导入这一列，
因为自选股都是同花顺导入的，你这个显示就是多此一举。你好好学习一下 financetool 的内容，
它里面有多自选股有详细的分析啊，比如说趋势、得分、近X天的平均涨跌幅变化，组内个股振幅……
这些数据应在数据加工的时候都计算入库了，你直接取就行。（如果没有就让数据加工去学习过来）」

**先记一句事实核对的结论**：这些数**库里没有组级表存着**（`information_schema` 全查过，
只有 `config.watchlist_group`/`watchlist_stock` 两张配置表）。存的是组内**个股**的
`analytics.score(capability_key='oper_score')`、`analytics.indicator_value`
（`chg10_avg`/`chg20_avg`/`amp10_avg`/`amp20_avg`/`amp_pred`，77 场）、
`market_data.stock_daily`（`amount_yuan` 当权重、`pct_change` 算当日）、
`market_data.dragon_tiger_detail`（06-01 起 80 场，够算上榜）。
那份参考实现**也是**在展示查询里现场聚合（`docs/参考/FinanceTool/docs/系统说明书.md`
的"自选组的分数、趋势与振幅"一节写得很明白），所以这里不是"绕过了本该入库的东西"，
是同一做法。聚合发生在后端一处（`duanxian/watchlist.py:group_analytics`），前端零重算。

列序照那份参考：**组 → 预测操作分（默认序）→ 加权 / 平均 / 趋势分数 → 当日均涨幅 /
10·20 日均涨跌(bp) / 上涨占比 → 明日·10 日·20 日振幅 → 上榜次数 → 趋势天数 / 成员数 / 有分只数**。
最后三列是元信息，用来判断前面那些数可不可信，压在最后。

四条口径，都是实测出来的、不是抄来的：

1. **`regr_slope` 的参数顺序是 `(y, x)`。** 第一版写成 `regr_slope(rn, w_score)`，
   拟合的是"场次号对分数的斜率"，于是 41 个组的预测操作分**全都落在 +10 附近**
   （那是场次号的均值），趋势分数被压成 ±0.5。手算复核（`python` 端独立做最小二乘）
   才发现。钉在 `tests/test_watchlist_group.py::test_regression_is_fitted_on_score_given_session_index_not_the_reverse`。
2. **预测操作分 ≈ 窗口均值 + 趋势分数**（`a + b(n+1)`，`mean_x=(n+1)/2` 代数化简）。
   这条写在 `calibers.pred_score` 里 —— 不然读者看见"今天 −23 分、预测 +3 分"会以为算错了。
   本场实测值域 −27.7 ~ +3.1，且这串数由接口现算，不是文档里写死的。
3. **`oper_score` 是全市场相对分**，全市场等权均值自己就会摆：窗口 20 场里从 −36.6 摆到 +21.9
   （摆幅 58.5 分，这条由 `_MARKET_LEVEL_SQL` 当场查出来填进 caveat，不写死常数）。
   所以趋势分数里混着"今天全市场的水位"，**横着比组可以，跨月纵着比要小心**。
4. **加权分分母只统计有分的行**；不足 10 场的组趋势三列 NULL 不补 0（本场 41 组全部够 20 场）。

页面另外三件事：撤掉的三列在「本页不做什么」里写明撤了什么、去哪看（成本与备注逐票在 `/grouped`）；
`10/20 日均涨跌`抬头写 **bp** 不写 %；折线默认只画**斜率最好的 3 条**（问的是"谁在起来"不是"谁最强"），
其余 38 条收进图例点开，缺数那天**断线不连**。16 个列头全部可排序，`aria-sort` 在 `th` 上。

实测（`http://127.0.0.1:8910/watchlist-analytics`）：41 行 × 16 列真数、41 个图例、

### 10-07 深夜补 · 标题定名与整组汇总（后端加了 `summary` 之后）

**标题改成「启动前量能分布」**（用户定名）。标题里不把"启动前一定放量"这种待验证直觉写成结论，也不反过来否定放量。测试钉住：`startupVolume.test.ts::标题不预设"放量启动"，也不反过来宣称放量没用`。

**整组汇总只读后端 `summary`，界面一次都不自己按行归并。** 这不是风格问题：榜固定 `limit=200`，jump40 近 12 个月母体 627 行只交出前 200 行，页面 `reduce` 一遍行得到的是"前 200 行的均值"却顶着"整组读数"说话 —— 那是假汇总。判读层 `groupReading()` 只吃 `summary.med_of_median` / `mean_dbl_days` / `n` 加 `window_days`，三种翻向分开：

- 中位数 < 1 → 说「「启动前普遍放量」这个直觉在本机这批票上不成立」，同句挡反向结论（也别读成「放量没用」）；
- 中位数 > 1 → 只说这批票启动前量在放大，不推未来；
- 任一为空或整批没 `summary` → 明说"后端没算出来，这一屏不猜"，**不退回按行凑一个**。

## 10-26 晚 · 首页滚动提速：撤重复的那层毛玻璃 ＋ 两节滚近才画（bundle `index-C0-tiDq4.js`）

用户原话：「首页这个页面滚动起来很卡…是否可以滚动设计，界面功能点从上到下陆续加载和显示，或者你有没有什么办法优化」。

**先量的三条**（这三条决定了改什么、不改什么，尤其决定了**不该**上 `content-visibility`）：
① 每次跳 2000px 后强制读几何 = **0.1 毫秒** ⇒ 布局/样式不是瓶颈；
② 打开首页的主线程长任务 = **521 毫秒**（356＋79＋86），DOM 5,196 个节点，页高 18,147px；
③ 21 个 `.glass` **全带** `blur(14px)`，其中 **15 个套在另一个 `.glass` 里面**（「盘面数据」那张 14,115px 的卡里叠了 8 张）。
所以这条线《首页.md》§7 里"blur 验过没用"那句只适用于**点击**，嵌套 blur 在**滚动**侧是每帧重复取快照，而视觉上看不出第二遍。

**做的三条**（全在前端，8910 不用重启）：`.glass .glass` 不再自己糊（21 → **6** 个带 blur 的面）；
`Layout.tsx` 在 `<main>` 上挂一个 `{passive:true}` 的 scroll 监听，只往 `<html>` 写 `data-vscroll`（**不走 React state**：
一帧 setState 等于每帧重协调整棵树，比它治的病更重），停手 160 毫秒删属性 ⇒ 静止时质感原样；
新共用件 `components/ui/LazySection.tsx` 把「异动提醒」（4,154px／1,018 节点）与「首板分析」（2,645px／1,014 节点）

**三条设计取舍写进组件头上**（比"加个 IntersectionObserver"容易做错的地方）：只延后不卸载；
**不预留高度**（预留要靠猜，猜错会在读者眼皮底下挪行位置 ⇒ 宁可让滚动条滚到下面才长齐）；
